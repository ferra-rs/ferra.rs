retry_exhausted

Retries Exhausted

503 Service Unavailable

Returned when a write was aborted by the database on each of its three attempts, with SQLSTATE 40001 (serialization failure) or 40P01 (deadlock): two requests wrote the same rows at the same time, and the loser lost every time it was run again. Ferra runs the whole write again, up to three attempts with a short random wait before each retry; this is the answer past the third. That write was not applied, so it is safe to send it again, after the Retry-After: 1 second the response carries. The detail is one fixed text for every cause: it speaks for the write that was given up, and names no SQLSTATE, table or constraint. A generated route makes one write per request, so nothing of the request was written. In a route of your own, an earlier write stands: the detail speaks for the write that was given up, not for the request. A handler that committed a write through Resource<M> before it keeps that write, so do not retry a non-idempotent request blindly; read the resource first, or send an idempotency key. When the server sets a request time budget and it leaves no room for another attempt, the answer is timeout instead. A conflict that no retry can fix (conflict, 409) and a refusal your own hook chose are not retried. New in v0.14.0.

Example RFC 7807 body

{
  "type":   "https://ferra.rs/errors/retry_exhausted",
  "title":  "Retries Exhausted",
  "status": 503,
  "detail": "this write conflicted with concurrent writes on every attempt and was not applied; retry it"
}
