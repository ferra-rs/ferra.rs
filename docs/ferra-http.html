Ferra.rs — User Guide

ferra-http — the Axum CRUD handler layer

The HTTP layer: what Foundry mounts for a model, the wire contracts of the routes (RFC 7807 errors, flat and HAL representations, pagination, Prefer:), and the default layer stack. An application reaches it through the ferra facade and does not declare ferra-http; what is public is the list of stability.md, and the signatures are the snapshot api/ferra-http.txt. The response envelopes (ItemResponse, CollectionResponse), the link builders and PaginationParams are not public in 0.9: a route of your own answers with a struct of its own (Custom Handlers).

This page is the authoritative user-guide for ferra-http. A reader with only this page plus standard Rust knowledge produces a compiling Foundry::new(conn).etag_key(key)?.mount::<Film>().build() call site on the first attempt — no ADR, no constitution, and no framework source is required.

Dependencies and URLs

The examples on this page assume the dependencies of Getting started:

[dependencies]
ferra   = { git = "https://github.com/ferra-rs/ferra", tag = "v0.15.0" }
sea-orm = { version = "2.0", default-features = false, features = ["macros", "runtime-tokio-rustls", "sqlx-postgres"] }
tokio   = { version = "1", features = ["macros", "rt-multi-thread"] }
axum    = "0.8"
serde   = { version = "1", features = ["derive"] }

A model’s URL segment ({resource} below) is its table name: table_name = "films" is served at /films. To serve a table under another name, put #[ferra(resource = "movies")] on the model. A model’s table is its own to create (a migration, or Schema::create_table_from_entity in development): Ferra never creates one.

Zero-to-API in five lines

use ferra::Foundry;
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod film {
    use super::*;
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "films")]
    #[ferra(auth = "none")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub title: String,
    }
    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}
    impl ActiveModelBehavior for ActiveModel {}
}
use film::Model as Film;
async fn demo(database_url: String) -> Result<(), Box<dyn std::error::Error>> {
let conn = sea_orm::Database::connect(&database_url).await?;
let app = Foundry::new(conn).etag_key(std::env::var("ETAG_KEY")?)?.mount::<Film>().build();
let listener = tokio::net::TcpListener::bind("0.0.0.0:3000").await?;
axum::serve(listener, app.into_make_service_with_connect_info::<std::net::SocketAddr>()).await?;
Ok(())
}
fn main() {}

Film here is declared #[ferra(auth = "none")]. A model that needs an identity (auth = "bearer", or #[authorize] rules other than Anyone) must be mounted on a chain with .with_auth::<YourClaims>(jwt) — see ferra-auth.md. Foundry is the only way to mount a model: it is what applies the model’s authorization rules. There is no lower-level router constructor.

You get GET /films, GET /films/{id}, POST /films, PUT /films/{id} and DELETE /films/{id}, a Location header on creation, and an application/problem+json body on every error. The primary key may be single or composite. Serve with into_make_service_with_connect_info: the rate limiter keys on the peer address.

See examples/hello-ferra/ for the full worked example with PostgreSQL container + Rust-coded migrations.

Every write above, restore and the actions included, runs in a transaction the framework owns, and answers 503 retry_exhausted (with Retry-After: 1) when the database aborts it on each of its three attempts; nothing is written. See Transient conflicts are retried.

The path names the row on update and delete; a key in the body is refused (422). PATCH is served on the bare path and under every projection prefix, with the update rule of that route as PUT; it takes application/merge-patch+json alone (any other Content-Type, application/json included, is a 415 naming that type). The rule is checked before the body is read. See Projections and routing § Writes for what a write body may contain.

A declared action (#[ferra(action(..))]) is one more route, on the bare path alone: its own rule, its own handler, the write of a PUT. A collection action (collection) is POST /{resource}/{name}: it runs the handler on up to 100 listed rows in one transaction, all or nothing, and answers 204; on a model with a String key it shadows the row whose key is its name (GET, PUT, PATCH and DELETE of that path answer 405). Its rows are in Declared actions.

Public reads, protected writes

A model that must be readable without a token but writable only with one says so per operation, and the chain names the claims type. A field is sortable (?sort=-price_cents) or filterable (?filter[name]=…) only if it says so with #[field(sortable)] / #[field(filterable)] (Pagination). The table is shop_products and the URL is /products: #[ferra(resource = "products")] sets the URL segment; without it, the segment is the table name (/shop_products):

use ferra::{ClaimCheck, FerraIdentity, FerraModel, Foundry, HmacAlgorithm, JwtConfig};
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};

mod product {
    use super::*;

    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "shop_products")]
    #[ferra(auth = "bearer", resource = "products")]
    #[authorize(
        list = Anyone,
        get = Anyone,
        create = Authenticated,
        update = Authenticated,
        delete = Authenticated
    )]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        #[field(filterable)]
        pub name: String,
        #[field(sortable)]
        pub price_cents: i64,
    }

    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}

    impl ActiveModelBehavior for ActiveModel {}
}

#[derive(Clone, Debug, Deserialize)]
struct Claims {
    sub: String,
}

impl FerraIdentity for Claims {
    fn id(&self) -> &str {
        &self.sub
    }
    fn has_role(&self, _role: &str) -> bool {
        false
    }
}

fn demo(conn: sea_orm::DatabaseConnection) -> Result<(), Box<dyn std::error::Error>> {
let jwt = JwtConfig::single_secret(
    "key-1",                                        // `kid`: every token must carry it
    std::env::var("JWT_SECRET")?,                   // the HMAC secret, from the environment
    HmacAlgorithm::Hs256,
    ClaimCheck::expect("https://auth.example.com/"), // `iss` the token must carry
    ClaimCheck::expect("products-api"),              // `aud` the token must carry
)?;
let app = Foundry::new(conn)
    .etag_key(std::env::var("ETAG_KEY")?)?
    .with_auth::<Claims>(jwt)
    .mount::<product::Model>()
    .build();
let _ = app;
Ok(())
}
fn main() {}

(Authentication and Authorization has the rest of the JWT configuration.)

A model that carries one or more #[ferra(projection(...))] declarations also mounts a parallel set of routes under each named projection’s URL prefix (e.g. /detail/films/{id}). The wire shape on those routes is the projection’s own: a response is serialized from its read struct, and a body is parsed into its write struct. See Projections and routing for the full URL contract, naming convention, and the path_prefix override.

{

Internals never leak. The detail field on a 500 is always the literal string "internal server error"; the cause (a sea_orm::DbErr, a failed hook) is kept in the error’s source() chain for your logs and never reaches the HTTP body. The Axum "Failed to deserialize … into the target type: " prefix and any axum::extract::rejection:: substring are stripped at the extractor boundary; only human-readable messages reach errors[*].message.

Worked body for a 429 from the rate-limit mapper:

{
  "type":   "https://ferra.rs/errors/rate_limited",
  "title":  "Too Many Requests",
  "status": 429,
  "detail": "rate limit exceeded; retry after 3 seconds"
}

The response also carries the Retry-After header (integer seconds, at least 1). A refill shorter than a second is answered as Retry-After: 1, never 0, which would invite an immediate retry that is refused again. If the component ever emitted no Retry-After header, detail would degrade to the literal string "rate limit exceeded" and the header would be absent from the response; the default rule always emits it. The rate-limit mapper mounts only alongside the framework’s default rate-limit component — consumer-provided rate-limiters produce their own error shape (see ADR-0015 for rationale).

Response representations

A successful response comes in two shapes, and the client chooses with Accept: flat (application/json) is the row, or the collection envelope, as plain JSON; HAL (application/hal+json) is the same body plus _links, so an AI agent can navigate the API without prior URL knowledge. Both go through the same query and the same read projection: they show the same rows, the same total and the same keys.

Before 0.11.0 the HAL body was served as application/json. A client that sends Accept: application/json now gets the flat body: it no longer has _links. A client that sends no Accept still gets HAL, with the Content-Type application/hal+json.

Flat bodies

{ "id": 1, "title": "Rust en pratique", "director": "Alice", "year": 2025 }

A page list is {"items": [...], "total": 25, "page": 2, "per_page": 10}; a cursor list is {"items": [...], "per_page": 10, "next_cursor": "<token>"}, and next_cursor is null on the last page (the key is always there). Pass next_cursor back as ?cursor= with the same filter[...] and sort.

HAL single-item body

Model fields are flattened at the top level via #[serde(flatten)]. A Film { id: 1, title: "Rust en pratique", director: "Alice", year: Some(2025) } serializes as:

{
  "id": 1,
  "title": "Rust en pratique",
  "director": "Alice",
  "year": 2025,
  "_links": {
    "self":       { "href": "https://api.example.com/films/1" },
    "collection": { "href": "https://api.example.com/films" }
  }
}

HAL paginated collection body

{
  "items": [ /* array of items, each with its own _links */ ],
  "total": 25,
  "page": 2,
  "per_page": 10,
  "_links": {
    "self":  { "href": "https://api.example.com/films?page=2&per_page=10" },
    "next":  { "href": "https://api.example.com/films?page=3&per_page=10" },
    "prev":  { "href": "https://api.example.com/films?page=1&per_page=10" },
    "first": { "href": "https://api.example.com/films?page=1&per_page=10" },
    "last":  { "href": "https://api.example.com/films?page=3&per_page=10" }
  }
}

An item’s _links.self is present only if the caller may GET that row, and _links.collection only if the caller may list the collection: a caller who may list but not read a row gets the row without self, so following a link as the same caller always answers 2xx (0.13.0). Under a projection prefix every link carries it: a page served at /admin/films links to /admin/films?page=…, and its items to /admin/films/{id}. A served row has no restore link (a served row is live).

On boundary pages, next or prev serialize as JSON null (never omitted). On total == 0, last_page == 1 and first == last == self.

Every link repeats the request’s filter[...] and sort (percent-encoded), so following next stays on the same list. A cursor list in HAL also carries next_cursor, the cursor of _links.next.

Links in a route of your own

The link builders are not public in 0.9.0: they know neither the base path, the version prefix nor the configured origin that Foundry applies. A route of your own that returns a resource with links writes the _links object itself — see custom-handlers.md.

Pagination

0.7.5 Enameling — collection-read parameters widened. The new filter[<field>], sort, and cursor parameters layer on top of page / per_page without changing the existing extractor surface — see pagination.md for the consumer-facing guide (the load-bearing surface for filtering, sorting, and cursor pagination). The handler dispatches on the model’s #[ferra(pagination = …)] posture; the page-mode parameters below continue to work unchanged.

The page-mode parameters are read by the generated routes; the extractor is internal since 0.9.0. A missing page is 1 (and 0 is read as 1), a missing per_page is 20, and per_page is clamped to 1–100, silently: no Warning header (RFC 9111 §5.5 obsoletes it; the body says what applied).

  • Default: page=1, per_page=20.
  • Cap: per_page ≤ 100 (hard limit). Values below 1 or above 100 are clamped, with no Warning header (RFC 9111 §5.5 obsoletes it; before 0.12.0 the response carried Warning: 214).
  • The response body’s per_page field reports the clamped value, so a client detects a clamp by comparing it with what it asked.
  • A page or per_page that is not a non-negative integer (page=abc) is a 400 with the code invalid_parameter; it is not read as the default.

Links and Location

Hypermedia links (_links, HAL-inspired) and the Location header are relative by default: /films/42, or /api/films/42 under a FerraLayer base_path. Resolve them against the URL you called, as an HTTP client does for Location. The request’s Host, X-Forwarded-Host and X-Forwarded-Proto headers are never read: a client cannot make the API emit links to another origin.

Location on a 201 is the self link of the new row (the same href a HAL read gives it), under a projection prefix as on the bare path. It is present only if self is: a caller who may create but not GET the row gets 201 Created with no body and no Location, with or without Prefer: return=minimal, so no id, stamp or author reaches a caller who may not read them (0.13.0).

To emit absolute links, configure the public origin once:

use ferra::Foundry;
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod film {
    use super::*;
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "films")]
    #[ferra(auth = "none")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub title: String,
    }
    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}
    impl ActiveModelBehavior for ActiveModel {}
}
use film::Model as Film;
fn demo(conn: sea_orm::DatabaseConnection) -> Result<(), Box<dyn std::error::Error>> {
let app = Foundry::new(conn)
    .etag_key(std::env::var("ETAG_KEY")?)?
    .with_base_url("https://api.example.com")? // Result<_, BaseUrlError>
    .mount::<Film>()
    .build();
// Location: https://api.example.com/films/42
let _ = app;
Ok(())
}
fn main() {}

The value must be an http or https origin — scheme, host and optional port; a trailing / is dropped — with no path, query, fragment, userinfo (https://user:password@host) or whitespace; otherwise BaseUrlError::NotHttp, NoHost or NotAnOrigin. A path prefix is not part of the origin: declare it with FerraLayer::base_path (for instance behind a proxy that serves the API under /api).

On a versioned chain (.api_version("v1")), links carry the version prefix the routes are served under, relative or absolute: /v1/films/42, or https://api.example.com/v1/films/42 with an origin. The order is origin, then base_path, then the version prefix.

Resource<M> — a model’s rows from a route of your own

A route of your own reaches a model’s rows through Resource<M>, an axum extractor. Foundry::mount_and_handle::<M>() mounts the model and issues a ResourceHandle<M> (Foundry); the handle goes in the router state — .with_state(handle), or a field of an application state that derives axum::extract::FromRef — and the handler takes Resource<M>.

use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod film {
    use super::*;
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "films")]
    #[ferra(auth = "none")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub title: String,
    }
    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}
    impl ActiveModelBehavior for ActiveModel {}
}
use film::Model as Film;
use axum::{Json, Router, extract::Path, routing::get};
use ferra::model::FerraViews;
use ferra::{FerraError, Foundry, Resource};

async fn one(films: Resource<Film>, Path(id): Path<i32>)
    -> Result<Json<<Film as FerraViews>::Read>, FerraError>
{
    Ok(Json(films.get(id).await?))
}

fn demo(conn: sea_orm::DatabaseConnection) {
let (foundry, films) = Foundry::new(conn).etag_key("a-development-key-of-at-least-32-bytes").expect("a key of at least 32 bytes").mount_and_handle::<Film>();
let app: Router = foundry
    .build()
    .merge(Router::new().route("/films/{id}/mine", get(one)).with_state(films));
let _ = app;
}
fn main() {}

Who the caller is, and the order of refusals

The caller is bound when Resource<M> is extracted: the identity the JWT layer verified, if the request went through it; else the bearer token of the Authorization header, verified with the chain’s own JWT configuration; else nobody.

  1. A token that is present and invalid — an Authorization header that is not a well-formed Bearer credential included — is refused at extraction with the 401 the JWT layer gives, before any database statement.
  2. On a chain without .with_auth() no token is read, and the caller is anonymous: a rule that needs an identity answers 401.
  3. Your route’s own extractors (FerraPath, FerraJson) run before you call a method, so a malformed path or body can be answered 400 before the access answers 401 or 403. What the access then refuses — 401, 403, 404, 422 — is what the generated route refuses, because it is the same code: another caller’s row under IsOwner is a 404, indistinguishable from a missing row.

What it hands back

get, list and create return the model’s read view, <M as FerraViews>::Read: the {Model}ReadProjection struct #[derive(FerraModel)] generates (or the projection promoted with default = true). A #[ferra(write_only)] or #[ferra(skip)] field is not a member of that type, so a route that serializes it cannot leak it. update takes <M as FerraViews>::Patch, the generated {Model}Patch: one Option<T> per field of the write projection, None meaning “leave the column” (and Option<Option<T>> for a nullable column, Some(None) writing null). Only the set columns reach the UPDATE; a write-only column is writable and never read back.

create and update return the row they wrote with the field read rules applied, but without the can(Get) check of the model’s #[ferra(authority)] that the generated routes make before they send a body (a caller who may write a row but not read it gets no body from the route). A handler of yours must not echo that value to a caller who may not read the row: check with get first, or send nothing. The same holds for the rows tx.resource::<N>() returns inside a hook. Their computed fields are computed only for a caller who may Get the row (see Computed fields); for one who may not, the field stays at its default and the view is meaningless.

Limits, by design:

  • The access serves the bare route’s projections. Selecting a named projection comes with per-projection authorization, later.
  • restore is not offered.
  • A write through Resource<M> evaluates no If-Match or If-None-Match in 0.14.0, and a route of your own cannot compute the entity tag of the row; see Preconditions on a write.
  • The read view carries the model’s Rust field names; #[ferra(rename_all = "camelCase")] is applied by the generated routes when they serialize, not by the struct. A route of your own answers with a struct of its own.
  • A filter you put in a CollectionQuery or a CursorQuery is held to the route’s safelist: only #[field(filterable)] fields, by their Rust names, with a value of the field’s type. Under IsOwner the list holds the caller’s rows whatever filter you pass.

A handler that extracts Resource<M> from a state that carries no handle for M does not compile; see FRG-152 in the diagnostics.

Rate-limit observability event. Each time the rate-limit mapper rewrites a 429, it emits a single structured tracing::warn! event so an operator tailing logs can see rate-limit rejections without reading the framework source:

  • Target: ferra_http::rate_limit — namespaced so an operator can isolate it via EnvFilter (RUST_LOG=ferra_http::rate_limit=warn).
  • Message: rate limit exceeded.
  • Severity: WARN.
  • Fields (deliberately minimal):
    • http.method — the request HTTP method (e.g. "POST"). Always present.
    • http.target — the request path, never the query string (e.g. "/films" for POST /films?page=2; ADR-0076). Always present.
    • http.retry_after_seconds — integer seconds parsed from the inbound Retry-After header. Present only when the header parses as a non-negative integer; genuinely absent otherwise (not recorded as 0).

Request and response body content never appear in this event — only the three fields listed above. The schema is pinned minimal so the framework’s dedicated observability phase at 0.12.0 Sheen can absorb it into span-based telemetry (adding trace_id, span_id, and peer-IP once the trusted-proxy story lands) without breaking a consumer’s existing EnvFilter or custom tracing::Layer.

Wire up a subscriber in your host binary’s main to surface these events:

#![allow(unused)]
fn main() {
tracing_subscriber::fmt()
    .with_env_filter("ferra_http::rate_limit=warn")
    .init();
}

Layer placement (FR-006). The rate-limit mapper mounts as the outer layer of the mutation sub-router only, wrapping tower_governor::GovernorLayer from the outside (the last .layer() call on that sub-router). Consumer-added middleware appended to Foundry::…build() wraps the mapper from further outside — see §“Layer ordering — how .layer() composes” below for the full diagram.

Overriding the defaults. CORS with the cookie

When the JwtConfig has with_cookie(name, origins) (ferra-auth.md § Cookie), each model’s CORS layer is built from that origin list instead of the deny-all default: a listed origin gets its exact Access-Control-Allow-Origin and Access-Control-Allow-Credentials: true, any other origin gets no Access-Control-Allow-* header, and a preflight needs no credential. The same list is the CSRF guard of a write the cookie authenticates. CORS wraps the authentication layer, so what that layer answers (the 401 of an expired cookie, the 400 of two credentials, the 403 of the CSRF guard) carries the CORS headers too: a listed app can read it and tell that its session expired.

Do not set FerraLayer::cors(...) with the cookie. build() panics: “a custom CORS layer cannot be combined with the cookie credential: remove FerraLayer::cors; the origins given to JwtConfig::with_cookie drive CORS”. Two policies would leave one silently ignored, and a custom layer with allow_credentials(true) answers every origin. A chain without the cookie keeps FerraLayer::cors as it was.

What the cookie CORS layer exposes (0.14.0). A browser script reads only the response headers a CORS answer exposes, so the layer lists ETag and Location in Access-Control-Expose-Headers for a listed origin: the app reads the tag of a row to send it back in If-Match, and the URL of a created row. It allows If-Match and If-None-Match among the request headers of a preflight, next to Content-Type, Accept and Prefer. A foreign origin gets no Access-Control-Expose-Headers, as it gets no Access-Control-Allow-* (tower-http adds the exposed headers to every answer whatever the origin; Ferra strips them from the answers it does not allow).

Your own FerraLayer::cors(...) (a chain without the cookie) does its own exposure: Ferra adds nothing to it. List the origins, the request headers a write may carry and the response headers the app reads, and never use CorsLayer::permissive(), which allows every origin and every header:

#![allow(unused)]
fn main() {
use ferra::FerraLayer;
use tower_http::cors::{AllowHeaders, AllowMethods, AllowOrigin, CorsLayer};
use axum::http::{
    Method,
    header::{ACCEPT, CONTENT_TYPE, ETAG, IF_MATCH, IF_NONE_MATCH, LOCATION},
};

let cors = CorsLayer::new()
    .allow_origin(AllowOrigin::list(["https://app.example.com".parse().unwrap()]))
    .allow_methods(AllowMethods::list([
        Method::GET,
        Method::POST,
        Method::PUT,
        Method::PATCH,
        Method::DELETE,
    ]))
    .allow_headers(AllowHeaders::list([
        CONTENT_TYPE,
        ACCEPT,
        IF_MATCH,
        IF_NONE_MATCH,
    ]))
    .expose_headers([ETAG, LOCATION]);
let layer = FerraLayer::new().cors(cors).build();
let _ = layer;
}

Layer ordering — how .layer() composes

Tower’s .layer() wraps the current router as the inner service, so the last .layer() call becomes the outermost layer. A .layer(MyCustomLayer::new()) appended to Foundry::…build() therefore wraps every Ferra-provided layer from the outside.

Side-by-side: the conceptual stack (top = outermost, bottom = innermost) and the literal .layer() call sequence in Foundry::…build() (top = first call, bottom = last call). Arrows map the inversion:

CONCEPTUAL stack (request top→bottom):        LITERAL call sequence (first→last in source):

 outer → cache defaults (Cache-Control, Vary)   (chain level, outside everything below)
         request budget
         CorsLayer                              .layer(DefaultBodyLimit::disable())   ← first call (innermost)
         JWT / API key authentication
         body_limit_mapper                      .layer(TraceLayer::new_for_http())
         RequestBodyLimitLayer(1 MiB)           .layer(RequestBodyLimitLayer::new(1 MiB))
         TraceLayer                             .layer(middleware::from_fn(body_limit_mapper))
         DefaultBodyLimit::disable              .layer(CorsLayer::new())              ← last call (outermost)
         (on mutation sub-router:)             
           rate_limit_mapper                    [on mutation sub-router:]
           GovernorLayer                          .layer(GovernorLayer { ... })       ← first call on mutations
 inner → handlers                                .layer(middleware::from_fn(rate_limit_mapper))  ← last (outer)

Reading it: on the generated routes the order, outermost first, is cache defaults, request budget, CORS, JWT (and API key) authentication, body limit, trace, then the rate limiter on mutations. A request enters at the cache defaults (outermost), traverses down to the handler, and the response retraces the stack back out. In the source, the call order is inverted — the first .layer() call is the innermost layer on the merged router, and the last .layer() call is the outermost.

Mutation sub-router subtlety. GovernorLayer (rate-limit) and rate_limit_mapper (the 429 RFC 7807 wrapper) mount on the mutation sub-router only — never on the merged router and never on read routes. rate_limit_mapper is the last .layer() call on that sub-router, so it wraps GovernorLayer from the outside and sees the 429s that layer produces. Placing a custom observability layer is a decision about which sub-router you wrap — consumers who want to observe only mutations attach to a sub-router; consumers who want to observe everything attach to the merged router returned by Foundry::…build().

Worked consumer example. A consumer appending two custom layers on top of the framework stack:

use ferra::Foundry;
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod film {
    use super::*;
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "films")]
    #[ferra(auth = "none")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub title: String,
    }
    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}
    impl ActiveModelBehavior for ActiveModel {}
}
use film::Model as Film;
use axum::{extract::Request, middleware::{from_fn, Next}, response::Response};
async fn observe(request: Request, next: Next) -> Response { next.run(request).await }
async fn shed_load(request: Request, next: Next) -> Response { next.run(request).await }
fn demo(conn: sea_orm::DatabaseConnection) {
let app = Foundry::new(conn).etag_key("a-development-key-of-at-least-32-bytes").expect("a key of at least 32 bytes").mount::<Film>().build()
    .layer(from_fn(observe))      // outer: sees requests before the framework
    .layer(from_fn(shed_load));   // appended AFTER → now the TRUE outermost
let _ = app;
}
fn main() {}

On incoming requests: shed_load runs first, then observe, then the framework stack (CORS → body_limit_mapper → RequestBodyLimitLayer → TraceLayer → DefaultBodyLimit::disable → handlers; with the mutation-only branch adding rate_limit_mapper → GovernorLayer before mutation handlers). On the way back out, responses traverse the stack in reverse.

See also §“RFC 7807 error taxonomy” for the 429 wire body the rate_limit_mapper produces.

Caching

Every response a Foundry router gives, errors included, carries Cache-Control: no-store and a Vary that names Accept, Authorization and Cookie (and the configured API key header when API keys are configured). This covers the generated routes, your .route(...) routes, /docs, a 404 or 405 before any route, the 503 of the request budget, the 413, the 429 and a CORS preflight answer. A shared cache (CDN, API gateway, proxy) therefore stores nothing and cannot replay an authenticated answer to another caller (RFC 9111 §3.5 protects Authorization only, and a 200 or 404 is cacheable with no header at all, §4.2.2).

  • Cache-Control is inserted only when the response has none: a route that sets its own Cache-Control, whatever its directives, keeps it.
  • Vary is merged, never replaced: the names the route already sent stay, the missing ones among the three are added, case-insensitively. A Vary: * is left as it is. A route that opts into caching still carries Vary: Authorization, Cookie: the entries are keyed on them (over-keying is safe).

A public route that may be cached. Declare it with .route(...) and give its MethodRouter a layer that sets Cache-Control; the default only inserts when the header is absent, so this route alone keeps its directive:

#![allow(unused)]
fn main() {
use axum::{http::{HeaderValue, header}, response::Response, routing::get};
use ferra::Foundry;

fn configure(conn: sea_orm::DatabaseConnection) {
    let cacheable = get(|| async { "a public page" }).layer(
        axum::middleware::map_response(|mut response: Response| async move {
            response.headers_mut().insert(
                header::CACHE_CONTROL,
                HeaderValue::from_static("public, max-age=60"),
            );
            response
        }),
    );
    let _router = Foundry::new(conn).route("/public", cacheable).build();
}
}

tower_http::set_header::SetResponseHeaderLayer::overriding does the same; it needs the set-header feature of tower-http, which Ferra does not enable, so your application declares it. A generated model route has no such knob before 1.0.

Warning. Do not add a layer that overwrites Cache-Control to the Router that build() returns: it wraps Ferra’s default and replaces no-store on every route, authenticated ones included. Ferra cannot see it and does not refuse it. FoundryBuilder::layer takes a FerraLayer, which cannot set Cache-Control: its knobs are CORS, body limit, rate limit, trace and base path, and trace_layer takes a TraceLayer, which does not set response headers. Only a layer added to the Router after build() can override no-store.

Responses that depend on the caller

A response whose content depends on who asks carries no-store and the full Vary above. Tests prove it on each such surface: a field only some roles read, a list scoped to the caller’s own rows, a list narrowed by an authority and GET /me. No generated response carries public or s-maxage, whatever the model, the operation or the identity.

What the guarantee does not cover is yours: the responses of your .route(...) handlers, which keep any Cache-Control they set, and a layer you add after build(). A public or s-maxage there lets a shared cache replay a caller’s answer to another (OWASP API8, security misconfiguration).

Entity tags are not cache validators here

Every response that serves one row carries a strong ETag (see Entity tags and preconditions), and a row response is still no-store: a GET with If-None-Match is not answered 304 Not Modified, whatever the tag. The tag serves writes, not caches.

Entity tags and preconditions

A caller that reads a row and later rewrites it needs a way to say “only if nobody changed it meanwhile”. The ETag response header is the read half of it: an opaque version of one row, issued by the server and given back by the client.

The tag

GET /films/1 HTTP/1.1

HTTP/1.1 200 OK
ETag: "k3Qm0u8bW1xHn7c9sFqYtA2R5eJvZ_dLw4iUoPgXaBE"
  • Opaque and strong. The value is a quoted base64url text, never W/. Compare it as a whole and send it back as it came; do not parse it, it has no structure a client may rely on and its length may change.
  • One tag per row. The same row gives the same tag on every projection URL (/films/1, /summary/films/1, a version prefix) and on GET /me; the tag changes when the stored row changes. The key of a composite-key row is part of it, so two rows never share a tag.
  • Where it is sent. On every response that serves one row: GET of an item (every projection, /me), 201 Created (with Location), PUT, PATCH, POST /{resource}/{id}/restore, and the 204 of a write under Prefer: return=minimal. The DELETE of a soft-delete model answers its 204 with the tag of the row as deleted, so that a restore has a current tag to send.
  • Where it is not. On a collection or any row inside one, on the DELETE of a model without soft delete (the row is gone), and on any refusal (401, 403, 404, 422, …).
  • It follows Location. A response that withholds the body and Location from a caller who may write a row but not GET it (a 201 with no body, the 204 of a write-only authority, the DELETE of a row the caller may not read) withholds the tag too: a tag is a statement about a row the caller may read.
  • Never cached, never a 304. A GET carrying If-None-Match is not answered 304 Not Modified: row responses are no-store (see Caching) and the tag serves writes.

What the tag reveals, and does not

The tag is keyed by the server’s entity-tag key, which also covers rotation, restores and the other operational cases. Without the key nobody can compute a tag, test a guess about a field they may not read, nor tell that two rows were written in the same transaction.

The residual signal. Any stored change of the row changes its tag, hidden fields included. A caller who cannot read a field therefore learns that something changed when its tag moves, one bit per observation, never the value. This is accepted: it is the price of one tag per row whatever the projection.

Preconditions on a write

PUT, PATCH, DELETE, POST /{resource}/{id}/restore and a declared row action (POST /{resource}/{id}/{name}, Declared actions) accept If-Match and If-None-Match. A client that read a row and sends its tag back says “only if nobody changed it meanwhile”:

PUT /films/1 HTTP/1.1
If-Match: "k3Qm0u8bW1xHn7c9sFqYtA2R5eJvZ_dLw4iUoPgXaBE"
Content-Type: application/json

{"title": "Aliens"}

HTTP/1.1 412 Precondition Failed
Content-Type: application/problem+json
  • If-Match is optional. A write without it goes through as it always did: there is no 428 Precondition Required, and no setting that asks for one. A create (POST /{resource}) ignores both headers.
  • The tag must be current. If-Match passes when * is sent or when one of the listed tags is the row’s current tag. The comparison is strong: a W/ tag never matches. Ferra only issues strong tags, but an intermediary can weaken them; send the tag as the server issued it.
  • If-None-Match is the reverse. The write is refused when * is sent, or when a listed tag is the row’s current tag. Here the comparison is weak, as RFC 9110 §13.1.2 defines it: the W/ prefix is ignored and the opaque-tag decides, so If-None-Match: W/"<current>" is refused too. It is evaluated after If-Match.
  • Lists. Several header lines are one list (RFC 9110 §5.3), so a row’s tag may sit on any of them. A list holds at most 32 entries. A value that is no list of entity-tags (a missing quote, a bare word), an empty list, * beside a tag, or a list of 33 tags is a 412 for both headers: it is never ignored, and never read as “no match”, so a mangled If-None-Match cannot let a write through.
  • If-Unmodified-Since is ignored. The tag is the only validator a write reads; a date has a one-second resolution and a row can change twice within it.
  • The decision is the locked row’s. It is taken inside the write’s transaction, after the row is locked, so two writers that hold the same tag cannot both win: the second one gets the 412, its write is not applied, and the first writer’s change stays. A 412 is also decided before the early return of an empty patch: {} with a stale If-Match, or with If-None-Match: *, is a 412, not a no-op 200.
  • The order. A precondition never tells a caller anything about a row they may not see: the row is looked up first, and a row that is absent, soft-deleted or hidden from the caller is a 404 whatever the headers, * included. For a row the caller may write, the 412 comes after the 415 and before everything the body can provoke (400, 422 unknown_field, the 403 of a field rule, the 422 on values): a stale If-Match with a forbidden field in the body is a 412, with a wrong Content-Type a 415. The full order is in What a patch is refused with.
  • The 412 says nothing. Its detail is one fixed text. It does not repeat the header, does not carry the current tag, and the response has no ETag. The client GETs the row again, redoes its change on what it reads, and writes with the new tag.
  • restore compares against the row’s tag. The DELETE of a soft-delete model answers the tag of the row as deleted, and that is the tag restore expects: the tag from before the delete is stale and gets a 412, and If-Match: * passes.
DELETE /films/1 HTTP/1.1
If-Match: "<tag read before>"

HTTP/1.1 204 No Content
ETag: "<tag of the row as deleted>"

POST /films/1/restore HTTP/1.1
If-Match: "<tag of the row as deleted>"

Known limitation: a route of your own. A write route you write by hand on Resource<M> evaluates no precondition in 0.14.0, and returns no tag. An If-Match sent to such a route is ignored and its write is unconditional; the response you build carries no ETag. If clients of that write need to avoid lost updates, route them through the generated PUT or PATCH. A typed precondition on Resource<M> can be added later without breaking the API.

PUT and RFC 9110 §9.3.4: a deliberate deviation

RFC 9110 §9.3.4 forbids a validator on a successful PUT response unless the stored representation is byte-identical to the content the client sent, so that the client knows whether the copy it sent is the result. Ferra’s PUT never stores the content as received (an absent optional field is cleared, the stamps and the key are the server’s), so the letter of §9.3.4 forbids the tag, and Ferra sends it anyway: the tag of a successful PUT names the stored row, never the sent content. The 200 response carries that row, and it is the row to keep. A client must not cache its PUT body under that tag; a client that chose Prefer: return=minimal holds no representation of the stored row at all, and caches nothing under the tag. This is what OData 4.01 §11.4.3 requires and the Azure REST API Guidelines prescribe (ADR-0077 § Consequences).

Transient conflicts are retried

Two writes that touch the same rows can make PostgreSQL abort one of them: SQLSTATE 40P01 (deadlock detected) at any isolation level, and 40001 (serialization failure) when the server’s default isolation is REPEATABLE READ or SERIALIZABLE (at COMMIT too under SERIALIZABLE). The request is valid, so since 0.14.0 Ferra runs the write again instead of answering a 500. A write of a model with a system grant (ADR-0073) runs at READ COMMITTED; the others at the server’s level.

  • What is rerun. The whole operation, decided again on the new state of the database, hooks included (Hooks can run more than once).
  • Only two codes. 40001 and 40P01, a failure at COMMIT included. Nothing else is: a failed precondition stays the 412 of the first attempt, a unique violation (23505) stays a 409, and an error a hook chose stays what it chose.
  • Only an operation that owns its transaction. The generated routes and the writes of Resource<M>. A tx.resource call inside a hook borrows the transaction of the write: its abort goes up to the loop of the write, which reruns everything.
  • The constants. 3 attempts (one plus two retries). Before retry k the wait is uniform in [0, min(100 ms, 10 ms × 2^(k−1))]: at most 10 ms before the first retry and 20 ms before the second, so at most 30 ms are added. These are constants of the crate, not settings.
  • Exhaustion. A write aborted on all three attempts answers 503 https://ferra.rs/errors/retry_exhausted with Retry-After: 1 (whole seconds). That write was not applied, so the client may retry it; the detail is one fixed text that speaks for that write and names no SQLSTATE, table or constraint. An aborted attempt logs one line with its number and its SQLSTATE, never a value.
  • The request budget. With .request_budget(..) the deadline bounds every attempt as it bounds the first: no attempt starts once it has passed, no wait ends past it, and a COMMIT the database refused with 40001 or 40P01 committed nothing, so it is not a started commit. Each of these answers 503 timeout, without Retry-After, with nothing written. Without a budget only the three attempts bound the work.
  • A route of your own. Only the operation is rerun. In a handler that calls Resource::update, the code around the call (your extractors, what you did before it, what you do after it) runs once, however many attempts the write takes; two calls are two operations, each with its own attempts. Keep the effect of a handler after the call, or in after_commit (see Hooks can run more than once). A write that was given up after an earlier Resource<M> write of the same handler answers retry_exhausted while that earlier write stands: the detail speaks for the write that failed, not for the request; do not retry a non-idempotent request blindly (RFC 9110 § 9.2.2).
  • The cost. A request under conflict does up to three times its work.

Write bodies reject unknown fields

Both write paths now refuse a request body carrying a field the model does not declare, with HTTP 422 and an application/problem+json body naming every offending field.

Since 0.8.0 (a break from 0.7). Through 0.7.x the two paths disagreed: projection-routed writes were already strict, while bare-path (POST /films, PUT /films/{id}) writes silently dropped unknown fields and returned 201 / 200. The same model therefore enforced two different postures depending on which URL a consumer addressed. That divergence is closed; the bare path is now strict too.

Why strict. The model’s field set is the safelist. A typed model surface that silently discards consumer-supplied fields is the silent-tolerance shape adjacent to mass assignment — a client sends {"role": "admin"}, receives 200, and has no signal that the field went nowhere. The industry is genuinely split here (Stripe and OWASP allowlisting on one side, Postel’s-law tolerant-reader on the other); Ferra picks strict as a deliberate security-over-convenience arbitration, not as a claim of consensus.

Migrating. Request bodies must match the model’s declared field set.

  • Remove fields your model does not declare. If a client was sending them and relying on the drop, that reliance was silent and is now visible — which is the point.
  • A field you want accepted must exist on the model, or on the projection’s write = [...] set for a projection-routed write.
  • Every offending field is reported in one response; the framework does not stop at the first.
  • Since 0.9.0 the bare path reads the model’s default write projection, which leaves out the primary key, the owner, read-only, skipped and computed fields, and the behavior columns: a body carrying any of them is a 422 too (see Projections and routing § Writes).

The OpenAPI document says so. It carries additionalProperties: false on every write-body schema, so generated clients and API-discovering agents see the same strictness the server enforces.

Partial updates with PATCH

PUT replaces a row; PATCH changes the fields it names and leaves the others as they are. The body is a JSON merge patch (RFC 7396): a JSON object, sent as application/merge-patch+json.

PATCH /films/1 HTTP/1.1
Content-Type: application/merge-patch+json

{"title": "Aliens", "year": null}

HTTP/1.1 200 OK
ETag: "k3Qm0u8bW1xHn7c9sFqYtA2R5eJvZ_dLw4iUoPgXaBE"

See The routes a model gets for where PATCH is served.

What a patch means

In the patchEffect
a key with a valuethe field is set to it, under the rules PUT applies to that value
a key with nulla nullable field is cleared; a field that cannot be null is the 422 required
a key that is absentthe field is untouched, whatever it is
{}nothing is written; the answer is the row (a stale precondition is a 412)

PUT is a replacement and answers the same body differently: it writes every write field, so an optional field without a read or write rule that the body leaves out becomes NULL, a field with such a rule is kept, and a #[field(required)] field that is missing is the 422 required. A client that wants to change one field sends a PATCH; one that sends a PUT sends the whole row.

  • Only the fields the patch sets are judged. Each value gets what PUT gives it (its type, the #[field(...)] rules, the write rule of the field, the JSON bounds), so a PATCH never stores a value a PUT refuses. A field the patch does not set is neither typed, nor judged, nor named in an error: a row stored before a rule was tightened, or before a JSON bound was lowered, can still be patched elsewhere, and the stored value stays as it was, byte for byte.
  • A JSON field is merged. When the stored value and the patch value are both objects, the patch is merged into the stored one member by member, and a null member removes its key. Stored {"a": 1, "b": 2} patched with {"a": 3} is {"a": 3, "b": 2}; patched with {"a": 3, "b": null} it is {"a": 3}. Any other patch value (an array, a scalar, null) replaces the field or clears it, and an object patched onto a stored value that is not an object is merged into {}. The max_bytes and max_depth bounds apply to the merged document.
  • The key and the owner are not patchable. A patch that names the primary key, the owner column or any key outside the write set is a 422 unknown_field, nothing written, as for PUT; so is a key the caller may not read, so that the answer does not tell a field that exists from one that does not.

What a patch is refused with

AnswerWhen
415 unsupported_media_typethe Content-Type is not application/merge-patch+json, application/json included; the detail names the type to send
400 validation, code invalid_jsonthe body is not a JSON object, a key is repeated in it at any depth (a JSON field included: a key is repeated at line L column C), or a value is of the wrong type for a field the caller may read
404 not_foundthe row does not exist, is soft-deleted, or is one the caller may not see: the same answer, byte for byte. It comes before the 415, 400 and 422 of the body when a rule, an authority, an owner field or a precondition header reads the row; see the order below
403 forbiddena key the caller may read but not write (a write rule of the field)
422 validation_failedunknown_field (above); required for a null on a field that cannot be null; a #[field(...)] rule of a value the patch sets (min_length, max, pattern…); json_too_large or json_too_deep for the merged document; reference_not_found for a re-parenting to a parent the caller may not use

Every errors[] entry names its field and its code (Validation codes). A refused PATCH writes nothing, computes no field and runs no hook.

The refusals come in the order every row write follows (PUT, PATCH, DELETE, restore): 401, 403 for a rule that reads no row, 404, 403 for the row-dependent part of the rule, 415, 412 (the If-Match and If-None-Match preconditions, see Entity tags and preconditions), 413, 400 (the body is decoded once: a repeated key, a wrong type on a key the caller may read), 422 unknown_field, 403 for a field write rule, then 422 on the values, and last the 400 of a required key the body omits. A caller who is not allowed to touch a row therefore learns nothing from the body it sent, and a key the caller may not read is never judged by the 400: it is an unknown key. An unknown key next to a wrong-typed value on a readable key is the 400. A PATCH types the keys it sets after the merge, on the locked row: where nothing reads the row before the body (no rule, authority, owner field or precondition header does), its unknown and unwritable keys are still judged first, before the 404, so there an unknown key beside a wrong-typed value is the 422.

That order holds whenever something reads the row before the body is judged: a rule of the model, a projection, an authority or an owner field, or an If-Match or If-None-Match header; for a model nothing reads the row of, see Update-vs-create symmetry.

Prefer and the ETag

PATCH honours Prefer as PUT does (below): return=minimal answers 204 No Content with no body and Preference-Applied: return=minimal; return=representation, or no Prefer at all, answers 200 OK with the projected row. The 200 and the 204 of a PATCH carry the ETag of the stored row, which is not the tag the row had before the write (a caller who may not GET the row gets a 204 with no body and no tag, as for PUT).

Content negotiation — RFC 7240 Prefer: header

Every mutation endpoint (POST, PUT, PATCH, DELETE) recognises the RFC 7240 Prefer: request header and branches the response shape accordingly. Consumers that do not send the header observe the default shape.

Recognised tokens

A caller who may PUT, PATCH or restore a row but not GET it gets 204 No Content with no body whatever it asked, as a create gets its 201 with no body (0.13.0): the write is done, nothing of the row leaves. Preference-Applied: return=minimal is echoed only when return=minimal was asked, never return=representation. A hand-written route on Resource::update serves what it chooses.

The parser is case-insensitive, whitespace-tolerant, and silently drops unrecognised tokens and ;-delimited parameters per RFC 7240 §2 (“recipients SHOULD ignore preferences they do not understand”):

Prefer: Return=Minimal, respond-async; wait=10

…parses as return=minimal + respond-async (the ; wait=10 parameter is dropped).

Preference-Applied: response header

Per RFC 7240 §3, the framework echoes honoured preferences via the Preference-Applied: response header. The header is absent when no preference was honoured — including the no-header case (table row 1) and the unrecognised-token case.

Interaction with the 422 validation path

When a mutation request fails declarative validation (the application/problem+json 422 path), the Prefer: header is recognised but does not change the response. The 422 body is mandated by the framework’s closed-namespace contract; Preference-Applied: is not emitted on the 422 path (no preference was honoured that changed observable behaviour).

Worked example

# Default — full body returned.
curl -i -X POST https://api.example.com/films \
  -H 'Content-Type: application/json' \
  -d '{"title": "Inception", "director": "Christopher Nolan", "year": 2010}'

# HTTP/1.1 201 Created
# Content-Type: application/json
# Location: /films/42
# { "id": 42, "title": "Inception", ... }

# `return=minimal` — body omitted, Location preserved.
curl -i -X POST https://api.example.com/films \
  -H 'Content-Type: application/json' \
  -H 'Prefer: return=minimal' \
  -d '{"title": "Inception", "director": "Christopher Nolan", "year": 2010}'

# HTTP/1.1 204 No Content
# Location: /films/43
# Preference-Applied: return=minimal

Batch-processing consumers gain bandwidth and JSON-parse savings on every mutation.

The ferra facade

[dependencies] ferra = { git = "…", tag = "…" } is the entry point (the facade package is ferra; nothing is published on crates.io). Resource, FerraError, FerraJson, FerraPath and Foundry are named from this single dependency, alongside the #[derive(FerraModel)] macro (use ferra::{FerraModel, Foundry};; use ferra::prelude::*; opens them all, for an application that declares no sea-orm of its own). The exact list of what ferra exports is stability.md.

Consumers do not depend on ferra-core, ferra-db, ferra-forge, or ferra-http directly. A compile-fail fixture pins ferra::Statement, ferra::execute_unprepared and ferra::raw_sql as unreachable: the root of the facade has no raw-SQL entry point. ferra::sea_orm is Sea-ORM itself; what Ferra guarantees is about the routes it generates.

Worked end-to-end example

use ferra::{FerraModel, Foundry};
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};

mod film {
    use super::*;

    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "films")]
    #[ferra(auth = "none")] // deliberately public: this example has no JWT
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        #[sea_orm(unique)]
        pub title: String,
        pub director: String,
        pub year: Option<i32>,
    }

    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}

    impl ActiveModelBehavior for ActiveModel {}
}

pub use film::Model as Film;

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let database_url = std::env::var("DATABASE_URL")?;
    let conn = sea_orm::Database::connect(&database_url).await?;
    let app = Foundry::new(conn).etag_key(std::env::var("ETAG_KEY")?)?.mount::<Film>().build();
    let listener = tokio::net::TcpListener::bind("0.0.0.0:3000").await?;
    axum::serve(listener, app.into_make_service_with_connect_info::<std::net::SocketAddr>()).await?;
    Ok(())
}

Troubleshooting

413 vs 400 on oversized bodies

A request whose body exceeds the 1 MiB default cap is rejected either with 413 Payload Too Large or with 400 Bad Request, depending on a single precondition: whether the request declares a Content-Length header.

RequestResponse codetype URIResponsible mapper
Body > 1 MiB with Content-Length declared413https://ferra.rs/errors/payload_too_largebody_limit_mapper (FR-033a)
Body > 1 MiB without Content-Length (streaming / chunked)400https://ferra.rs/errors/validation (single errors[0].code = "invalid_json")FerraJson<T>::from_request surfacing as FerraError::Validation

When Content-Length is present, RequestBodyLimitLayer short-circuits at the layer level before the stream is consumed — hence the early 413. When the header is absent, the stream is consumed up to the cap, the read fails, and the JSON extractor rejects the request as a parse error (still machine-readable, still RFC 7807, still parseable via the same generic type-dispatch path you use for the other validation failures).

Both outcomes are semantically correct — the oversized input is rejected either way. The divergence is intentional; a regression test pins the 400 fallback, so any change to it is visible. If you can set Content-Length on your client, do — your clients then see a single, predictable 413.

Other diagnostics

  • 413 with application/problem+json body — request body exceeds 1 MiB. Split the request or raise the limit via FerraLayer::body_limit(...) (Foundry).
  • 429 with Retry-After — peer IP hit the mutation rate limit (2 per second, burst 5 by default). Back off for the number of seconds in Retry-After.
  • problem+json with type: ".../validation" and errors[0].code = "invalid_path_param" — the path segment after /{resource}/ is not a valid primary key for M (e.g. GET /films/abc when Film.id: i32). The built-in path extractor rejects before the handler runs.
  • 500 with detail: "internal server error" — the DB surfaced an error the framework does not map. Inspect logs / tracing for the Debug form of FerraError::Internal; the HTTP body intentionally says nothing more.
  • CORS preflight fails — CorsLayer::new() denies all cross-origin by default. Open it with FerraLayer::cors(...) (Foundry § Transport-layer overrides).
