Ferra.rs — User Guide

Stability policy

What a Ferra release guarantees: the API frozen in v0.18.0 is the API of v1.0.0, and this page says what holds from 1.0 and what each release before it allowed. What changed release by release is in the changelog and the migration pages.

How Ferra is released

  • One version for the whole workspace, one git tag per release: v0.9.0, v0.9.1, v0.10.0. Nothing is published on crates.io.

  • An application depends on a tag, and on the facade only:

    ferra = { git = "https://github.com/ferra-rs/ferra", tag = "v0.18.0" }

  • A tag is never moved. CHANGELOG.md has one section per tag.

What the contract is

The contract is what the ferra crate exports, and nothing else:

  • the FerraModel derive and its attributes (#[ferra(...)], #[field(...)], #[authorize(...)], #[behavior(...)]), with the FRG- code of each refusal, and #[ferra(action(...))] with ActionBody, the derive and trait that type an action’s body;
  • Foundry, FoundryBuilder and their options;
  • JwtConfig and its types; the FerraIdentity trait; testing::bearer;
  • Id, DateTime, Date, Time;
  • SortDirection, exactly Asc and Desc. It is closed on purpose: a third variant would break a match, so it is a major change after 1.0;
  • the error types, and the problem+json documents they render — status, type URI, title;
  • ferra::hooks: FerraHooks, Saving, Saved, Committed, HookTx (with HookTx::system), TxResource, SystemAccess, and HookError, what an application’s hook or action handler returns to refuse a write;
  • for a route of your own: Resource, ResourceHandle, CollectionQuery, CursorQuery, Page, CursorPage, FerraPath, FerraJson, FerraAuthLayer, the two middlewares, CurrentUser;
  • the description of a model, to read: meta, model. Operation is a #[non_exhaustive] enum with the variant Action(name) since 0.14.0, so an authority matches it explicitly (see below); ModelMeta::actions lists a model’s actions, and OperationMeta and ModelMeta::operations are removed (only the derive used them);
  • the Cargo features observability and test-support;
  • the HTTP behavior of the generated routes: paths, methods, statuses, the shape of bodies and of the OpenAPI document.

The exact list, name by name, is the file api/ferra.txt of the repository; the signatures are in the other files of that folder.

Not in the contract, whatever its visibility:

  • the implementation crates taken directly (ferra-core, ferra-db, ferra-forge, ferra-http, ferra-openapi): depend on ferra;
  • everything #[doc(hidden)] — the __private modules, the constructors of the meta types, ferra::ferra_core, ferra::ferra_http, FerraDraft, NoHooks, Hooked, ComputedFields, NoActions, Actioned, FerraActions, ApplyDraft, FerraHooksDeclared, FerraSystemOnly, FerraNotBlameable, FerraSystemGrant, HookRunner and ActionRunner, the write transaction WriteTx of ferra-db and its entry points (begin, commit, lock_row, lock_rows, insert_row, update_row, delete_row, soft_delete_row, restore_row, row_at, lock_parent_shared). It exists for the derive’s generated code and for Ferra’s own crates, and changes without notice;
  • the code the derive generates: read it with cargo expand, do not call it;
  • the text of a log event, of a detail member, of a compiler diagnostic beyond its FRG- code;
  • the inside of a cursor: it is an opaque string, hand it back as it came.

The repository is not in the contract

Since 0.10.0 the repository (PgRepository, FerraRepository, DatabaseTransaction, FerraDbError) and FerraState are not exported: a route of your own reaches a model’s rows through Resource<M>, which applies the model’s rules. See migrating-to-0.10.md.

What a version number meant before 1.0

Ferra 0.x followed Semantic Versioning as Cargo reads it for 0.x.

From → toMay it break the contract?What you do
v0.9.0 → v0.9.1 (patch)No. Fixes and additions only.Change the tag.
v0.9.x → v0.10.0 (minor)Yes, each break listed in CHANGELOG.md under “Changed — breaking”, with what to do.Read the changelog, change the tag, follow the compiler.
v0.x → v1.0.0Yes, for the last time without a major bump.Same.

Two exceptions, both written in the changelog when they happen:

  • A security fix may change behavior in a patch release — a request that was wrongly served is refused. Refusing more is never held back for a minor.
  • Becoming more permissive is not a break. A 400 that becomes a 200 (a filter on a date field, a descending cursor walk), a new optional attribute, a new variant of a #[non_exhaustive] enum (Operation::Action: an authority whose can ends in _ => true allows it, so end the match with _ => false and name Action(_), see migrating-to-0.14.md), a new method on Resource, a new field on a meta type, a new member in a response object: all are additions (a client ignores members it does not know).

A removed attribute keeps a migration diagnostic for at least one minor version: the compiler says what to write instead (as FRG-105, FRG-106 and FRG-335 do for what 0.9.0 removed).

What 1.0 guarantees

From v1.0.0 the contract above is frozen under Semantic Versioning as Cargo reads it for 1.x:

From → toMay it break the contract?What you do
v1.0.0 → v1.0.1 (patch)No. Fixes only, with exceptions (i) and (iv) below.Change the tag.
v1.0.x → v1.1.0 (minor)No. Additions, and changes of the “Changed (not breaking)” class below, with exceptions (ii) and (iii).Change the tag.
v1.x → v2.0.0 (major)Yes, each break listed in CHANGELOG.md under “Changed — breaking”, with what to do.Read the changelog, change the tag, follow the compiler.

The exceptions, each written in the changelog when it happens:

  • (i) A security fix comes in a patch, and may refuse what was wrongly accepted: a request that was served answers a refusal status, or a model that compiled is refused by the derive.
  • (ii) Becoming more permissive is an addition, in a minor: a refusal that becomes a success (a 400 that becomes a 200), a new optional attribute, a new variant of a #[non_exhaustive] enum.
  • (iii) The minimum supported Rust version may rise in a minor, never in a patch (Rust version).
  • (iv) A patch of a crate Ferra pins exactly comes in a Ferra patch: if your application names the same crate, it follows that version (Third-party crates in the contract).

What the changelog heading says is the class of a change, and the class decides the version number:

ClassAfter 1.0Example
Changed — breakingA major.A public signature moves: DocsAuthVerifier is built from a closure over &http::request::Parts, where it took &axum::extract::Request (0.18.0). A public item is removed: DateTime::from_duration (0.18.0). A generated route answers another status: the wait for a pool connection is a 503 where it was a 500 (0.17.0). An FRG- code changes: an #[authorize] that does not parse is FRG-023, it was FRG-103 (0.18.0). A change of status is breaking. The status of a generated route’s answer is in the contract (above), so a route that answers another status, type or title is “Changed — breaking”, whatever the two statuses are, but for exceptions (i) and (ii): a security fix in a patch, which may change a status toward the refusal, and a refusal that becomes a success, in a minor. A 500 that becomes a 503 is therefore breaking, although both tell the client the operation failed: the pool’s wait (0.17.0) is listed under “Changed — breaking”. The 0.14.0 section classed retry_exhausted, a 500 that became a 503 after three aborted attempts, as not breaking; that line stays as history, and from 0.18.0 this is the rule.

A derive that refuses more is a break. A model that compiles today and is refused by a later derive is “Changed — breaking”, a major, but for exception (i): a security fix may refuse it in a patch. FRG-147 and the refusals of model_attrs(..) mistakes are such breaks, made before 1.0 (0.18.0).

The OpenAPI document alone. A change of the document that leaves every answer as it was is “Changed”, not breaking, when it brings the document closer to what is served. A change of what is served follows the rule on statuses above. A status a route still serves is never removed from the document, and a change that takes the document away from what is served is a defect, fixed as such.

Traits you implement

ApiKeyStore, FerraAuthority, FerraListAuthority and FerraIdentity are traits an application implements, and none is sealed. After 1.0 a method added to one of them has a default body, and the default refuses or changes nothing: an implementation written for 1.0 keeps compiling, and a default can narrow what it accepts, never widen it. A refusing default is fail closed: an implementation that does not answer the new method may see the new check refused, and is never granted more. A default method added to a trait you implement (FerraHooks, FerraComputed, …) arrives in a minor release; its default changes nothing and refuses nothing that passed before.

Metrics and spans

With the observability feature, Ferra records five metrics. With or without it, each request has a request span and its phase spans (the names and labels are in observability.md). The compatibility rule: from 0.18.0, a metric’s name, unit and label set are frozen (a new label is a new metric); a new value of a closed label is an addition; span attributes are add-only; Ferra’s names are the dotted OpenTelemetry names and translating them is the exporter’s job, with both Prometheus spellings shown: http_server_request_duration_seconds with OpenTelemetry exporters by default and with metrics-exporter-prometheus under with_recommended_naming(true), http_server_request_duration otherwise; and the metrics major is in the table of third-party crates in the contract, below.

Third-party crates in the contract

Types of other crates appear in Ferra’s signatures, and two crates are re-exported whole. A major version change of one of them (a minor of a 0.x crate) is a break of Ferra, listed in the changelog: from 1.0, a Ferra major, since a type of that crate in a Ferra signature changes with it. Before 1.0 it came in a minor.

What ferra::sea_orm and ferra::garde contain is theirs, under their own version numbers: Ferra’s snapshots do not cover it, and no tool can see inside a re-export. Four things stand in for that:

  • Six of them are exact requirements. garde, utoipa-scalar, jiff, tower-http, base64 and secrecy are declared =x.y.z in Ferra’s manifests. If your application also names one of them, it must name the same version (or a requirement that version satisfies): another patch fails to resolve. A patch of one of them, for an advisory for instance, reaches you in a Ferra patch release, exception (iv): align your requirement with it.
  • Sea-ORM is a public dependency of Ferra. A new major version of Sea-ORM (or a new minor of garde or of jiff, 0.x crates) is a breaking change of Ferra: a Ferra major from 1.0 on, and the changelog says so. A new jiff minor reaches as_inner alone.
  • Your sea-orm follows Ferra’s major. The documented way to use Sea-ORM is to declare sea-orm yourself, at the major version the release you use was built with. Each release’s changelog names it and gives the line to change in your Cargo.toml. A different major is two copies of the crate; #[derive(FerraModel)] refuses it with FRG-400, and cargo tree -d -i sea-orm shows it. Declaring no sea-orm and writing ferra::sea_orm::… is supported as well.
  • Ferra’s CI pins it. A check fails when Ferra’s lockfile holds two copies of sea-orm, garde or metrics, or another version than the one documented here; changing the pin is a decision made in one change with this page and the changelog. A new metrics minor (0.x) is a breaking change of Ferra too: a recorder built on another copy would receive none of Ferra’s metrics.

Sea-ORM in Ferra’s signatures

Ferra’s own signatures name a Sea-ORM type in four places only:

  1. the ferra::sea_orm re-export and the prelude’s glob of its entity prelude;
  2. the constructors that take the application’s connection, Foundry::new(DatabaseConnection) and api_key::PgApiKeyStore::new(DatabaseConnection), and the DatabaseConnection re-export;
  3. the trait bounds that make a model a Sea-ORM entity (Mountable’s, the builder’s, Resource’s, HookTx::resource’s, TxResource’s and SystemAccess’s where clauses: ModelTrait, EntityTrait, ActiveModelTrait, ActiveModelBehavior, FromQueryResult, IntoActiveModel, IntoValueTuple, PrimaryKeyTrait), and PkValue<M>, the key type the entity declares;
  4. the trait impls that make a Ferra value type (Id, Date, DateTime, Time) a Sea-ORM column (feature sea-orm of ferra-core).

The rule for later lots: no other Ferra-owned signature names a Sea-ORM type. That covers hooks, authority, actions, computed fields, the request context and resource access: they take and return Ferra’s types (FerraError, Resource<M>). Your own code reaches Sea-ORM through your own DatabaseConnection, outside Ferra’s contract.

Ferra’s CI fails on any other public signature that names a Sea-ORM, sea_query or sqlx type.

Rust version

  • The minimum supported Rust version is 1.94, checked in CI. Raising it is allowed in a minor release, never in a patch, and is listed in the changelog (exception (iii) above).
  • The repository pins the toolchain it is developed with (rust-toolchain.toml); an application is free to use a newer one.
  • Ferra builds natively on Linux, macOS and Windows. Its CI runs on Linux at each push to main, the whole test suite with a database; on Windows and macOS a workflow started by hand builds it and runs the tests that need no database.

What is planned, and will not break you

Each of these is an addition under the rules above: an external authenticator next to .with_auth (RS256/JWKS, sessions); a response envelope for custom routes.

How the contract is kept

Ferra’s CI fails a change that moves the contract without saying so: the public API of each crate is recorded as text in the repository’s api/ folder and any difference fails until the record is updated with the change; each crate is compared with the previous tag for a break the version number does not allow; the Sea-ORM and HTTP types are kept to the places this page names; and one test names the contract item by item, so removing one breaks the build.
