Ferra.rs — User Guide

Stability policy

What a Ferra release guarantees, what may change between 0.9 and 1.0, and how to upgrade. It applies from v0.9.0.

How Ferra is released

  • One version for the whole workspace, one git tag per release: v0.9.0, v0.9.1, v0.10.0. Nothing is published on crates.io.

  • An application depends on a tag, and on the facade only:

    ferra = { git = "https://github.com/ferra-rs/ferra", tag = "v0.17.0" }

  • A tag is never moved. CHANGELOG.md has one section per tag.

What the contract is

The contract is what the ferra crate exports, and nothing else:

  • the FerraModel derive and its attributes (#[ferra(...)], #[field(...)], #[authorize(...)], #[behavior(...)]), with the FRG- code of each refusal, and #[ferra(action(...))] with ActionBody, the derive and trait that type an action’s body;
  • Foundry, FoundryBuilder and their options;
  • JwtConfig and its types; the FerraIdentity trait; testing::bearer;
  • Id, DateTime, Date, Time;
  • the error types, and the problem+json documents they render — status, type URI, title;
  • ferra::hooks: FerraHooks, Saving, Saved, Committed, HookTx (with HookTx::system), TxResource, SystemAccess, and HookError, what an application’s hook or action handler returns to refuse a write;
  • for a route of your own: Resource, ResourceHandle, CollectionQuery, CursorQuery, Page, CursorPage, FerraPath, FerraJson, FerraAuthLayer, the two middlewares, CurrentUser;
  • the description of a model, to read: meta, model. Operation is a #[non_exhaustive] enum with the variant Action(name) since 0.14.0, so an authority matches it explicitly (see below); ModelMeta::actions lists a model’s actions, and OperationMeta and ModelMeta::operations are removed (only the derive used them);
  • the Cargo features observability and test-support;
  • the HTTP behavior of the generated routes: paths, methods, statuses, the shape of bodies and of the OpenAPI document.

The exact list, name by name, is api/ferra.txt; the signatures are in the other files of api/.

Not in the contract, whatever its visibility:

  • the implementation crates taken directly (ferra-core, ferra-db, ferra-forge, ferra-http, ferra-openapi): depend on ferra;
  • everything #[doc(hidden)] — the __private modules, the constructors of the meta types, ferra::ferra_core, ferra::ferra_http, FerraDraft, NoHooks, Hooked, ComputedFields, NoActions, Actioned, FerraActions, ApplyDraft, FerraHooksDeclared, FerraSystemOnly, FerraNotBlameable, FerraSystemGrant, HookRunner and ActionRunner, the write transaction WriteTx of ferra-db and its entry points (begin, commit, lock_row, lock_rows, insert_row, update_row, delete_row, soft_delete_row, restore_row, row_at, lock_parent_shared). It exists for the derive’s generated code and for Ferra’s own crates, and changes without notice;
  • the code the derive generates: read it with cargo expand, do not call it;
  • the text of a log event, of a detail member, of a compiler diagnostic beyond its FRG- code;
  • the inside of a cursor: it is an opaque string, hand it back as it came.

The repository is not in the contract

Since 0.10.0 the repository (PgRepository, FerraRepository, DatabaseTransaction, FerraDbError) and FerraState are not exported: a route of your own reaches a model’s rows through Resource<M>, which applies the model’s rules. See migrating-to-0.10.md.

What a version number means

Ferra is 0.x: it follows Semantic Versioning as Cargo reads it for 0.x.

From → toMay it break the contract?What you do
v0.9.0 → v0.9.1 (patch)No. Fixes and additions only.Change the tag.
v0.9.x → v0.10.0 (minor)Yes, each break listed in CHANGELOG.md under “Changed — breaking”, with what to do.Read the changelog, change the tag, follow the compiler.
v0.x → v1.0.0Yes, for the last time without a major bump.Same.

Two exceptions, both written in the changelog when they happen:

  • A security fix may change behavior in a patch release — a request that was wrongly served is refused. Refusing more is never held back for a minor.
  • Becoming more permissive is not a break. A 400 that becomes a 200 (a filter on a date field, a descending cursor walk), a new optional attribute, a new variant of a #[non_exhaustive] enum (Operation::Action: an authority whose can ends in _ => true allows it, so end the match with _ => false and name Action(_), see migrating-to-0.14.md), a new method on Resource, a new field on a meta type, a new member in a response object: all are additions (a client ignores members it does not know).

A removed attribute keeps a migration diagnostic for at least one minor version: the compiler says what to write instead (as FRG-105, FRG-106 and FRG-335 do for what 0.9.0 removed).

Metrics and spans

With the observability feature, Ferra records five metrics. With or without it, each request has a request span and its phase spans (the names and labels are in observability.md). The compatibility rule: from 0.18.0, a metric’s name, unit and label set are frozen (a new label is a new metric); a new value of a closed label is an addition; span attributes are add-only; Ferra’s names are the dotted OpenTelemetry names and translating them is the exporter’s job, with both Prometheus spellings shown: http_server_request_duration_seconds with OpenTelemetry exporters by default and with metrics-exporter-prometheus under with_recommended_naming(true), http_server_request_duration otherwise; and the metrics major is in the table of third-party crates in the contract, below.

Third-party crates in the contract

Types of other crates appear in Ferra’s signatures, and two crates are re-exported whole. A major version change of one of them is a break of Ferra, made in a minor release and listed in the changelog.

What ferra::sea_orm and ferra::garde contain is theirs, under their own version numbers: Ferra’s snapshots do not cover it, and no tool can see inside a re-export. Four things stand in for that:

  • Five of them are exact requirements. garde, utoipa-scalar, jiff, tower-http and base64 are declared =x.y.z in Ferra’s manifests. If your application also names one of them, it must name the same version (or a requirement that version satisfies): another patch fails to resolve. A patch of one of them, for an advisory for instance, reaches you in a Ferra patch release.
  • Sea-ORM is a public dependency of Ferra. A new major version of Sea-ORM (or a new minor of garde, a 0.x crate) is a breaking change of Ferra: it ships in a minor release, and the changelog says so.
  • Your sea-orm follows Ferra’s major. The documented way to use Sea-ORM is to declare sea-orm yourself, at the major version the release you use was built with. Each release’s changelog names it and gives the line to change in your Cargo.toml. A different major is two copies of the crate; #[derive(FerraModel)] refuses it with FRG-400, and cargo tree -d -i sea-orm shows it. Declaring no sea-orm and writing ferra::sea_orm::… is supported as well.
  • A gate pins it. reexport_pin fails CI when the lockfile holds two copies of sea-orm, garde or metrics, or another version than the one documented here; changing the pin is a decision made in one change with this page and the changelog. A new metrics minor (0.x) is a breaking change of Ferra too: a recorder built on another copy would receive none of Ferra’s metrics.

Sea-ORM in Ferra’s signatures

Ferra’s own signatures name a Sea-ORM type in four places only:

  1. the ferra::sea_orm re-export and the prelude’s glob of its entity prelude;
  2. the constructors that take the application’s connection, Foundry::new(DatabaseConnection) and api_key::PgApiKeyStore::new(DatabaseConnection), and the DatabaseConnection re-export;
  3. the trait bounds that make a model a Sea-ORM entity (Mountable’s, the builder’s, Resource’s, HookTx::resource’s and SystemAccess’s where clauses: ModelTrait, EntityTrait, ActiveModelTrait, ActiveModelBehavior, FromQueryResult, IntoActiveModel, IntoValueTuple, PrimaryKeyTrait), and PkValue<M>, the key type the entity declares;
  4. the trait impls that make a Ferra value type (Id, Date, DateTime, Time) a Sea-ORM column (feature sea-orm of ferra-core).

The rule for later lots: no other Ferra-owned signature names a Sea-ORM type. That covers hooks, authority, actions, computed fields, the request context and resource access: they take and return Ferra’s types (FerraError, Resource<M>). Your own code reaches Sea-ORM through your own DatabaseConnection, outside Ferra’s contract.

The gate sea_orm_surface reads api/*.txt and fails on any other line that names sea_orm::. The internal items of ferra-db (PgRepository, FerraRepository, FerraDbError, WriteGuard) are not in the facade; the gate lists them apart.

Rust version

  • The minimum supported Rust version is 1.94, checked in CI. Raising it is allowed in a minor release, never in a patch, and is listed in the changelog.
  • The repository pins the toolchain it is developed with (rust-toolchain.toml); an application is free to use a newer one.
  • Ferra builds and tests natively on Linux, macOS and Windows. What is proven: a real trial on Windows 11 on 2026-09-30, before lot L4, built the workspace, ran both test suites and check_compile_error_spans there. The checklist L4.28 runs it again on the final state of the lot, with a default clone; until it has passed, the claim rests on that first trial.

What is planned, and will not break you

Each of these is an addition under the rules above: an external authenticator next to .with_auth (RS256/JWKS, sessions); a response envelope for custom routes.

How the contract is kept

Four gates block CI (CONTRIBUTING.md has the commands):

  • public_api_snapshot — the public API of each crate is a text file under api/. Any difference fails until the snapshot is regenerated and committed with the change, which makes every change of the contract visible in review.
  • semver_checks — cargo-semver-checks compares each crate with the previous tag: a break without the minor version bump that allows it fails.
  • sea_orm_surface — fails when a line of api/ names sea_orm:: outside the places listed in “Sea-ORM in Ferra’s signatures”.
  • reexport_pin — ferra::sea_orm and ferra::garde are the crates themselves, and neither of the two gates above can see inside a re-export: this one fails when Cargo.lock holds two copies of either, or a version other than the documented one (Sea-ORM 2.x, garde 0.23.x). It pins metrics (0.24.x) the same way, the facade Ferra records its metrics through.

And one test names the contract item by item (crates/ferra/tests/contract_surface.rs), so that removing one breaks the build on the stable toolchain too.
