Ferra.rs — User Guide

Relations

A model with owner(from = ..) is the child of another model: its rows live under a parent’s owner. This page states what Ferra guarantees when a parent and its children are written at the same time. It grows with the release.

Declaring relations

A model written with #[sea_orm::model] (Sea-ORM’s dense form) may declare its relations inline, as HasMany<..>, HasOne<..> or BelongsTo<..> fields. The macro expands the struct twice: Model keeps the scalar fields, a second struct ModelEx keeps all of them. #[derive(FerraModel)] runs on both. On Model it reads the columns as ever, so a relation field is never a column or a wire field, and never a projection field of its own, with one exception: a BelongsTo named in a projection’s read list is embedded (Embedding). On ModelEx it emits one typed marker per relation (name, kind, foreign key, both models), which Foundry reads at .mount.

use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod client {
    use super::*;

    #[sea_orm::model]
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "clients")]
    #[ferra(auth = "none")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub name: String,
        #[sea_orm(has_many)]
        pub contexts: HasMany<super::context::Entity>,
    }

    impl ActiveModelBehavior for ActiveModel {}
}

mod context {
    use super::*;

    #[sea_orm::model]
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "contexts")]
    #[ferra(auth = "none")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub client_id: i32,
        #[sea_orm(belongs_to, from = "client_id", to = "id")]
        pub client: BelongsTo<super::client::Entity>,
    }

    impl ActiveModelBehavior for ActiveModel {}
}
fn main() {}

A relation field is only valid in this form. On a struct that is not an expansion of #[sea_orm::model], such as a hand-written Model with an enum Relation, it is refused (FRG-125, see ferra-forge-diagnostics.md). The split form stays valid for a model without relation fields.

The three kinds. The kind comes from the attribute, not from the field’s type:

  • BelongsTo: the field carries #[sea_orm(belongs_to, from = "..", to = "..")]. Its foreign key is the column from names. A nullable key is written HasOne<..> in Sea-ORM 2.0, and is still a BelongsTo here.
  • HasMany: the rows of another model that point back at this one.
  • HasOne: the same, for at most one row.

The back key. The foreign key of a HasMany or a HasOne is the one BelongsTo its target has back to this model. Ferra does not guess it. When both models are mounted on the same Foundry, build() (and try_build()) refuses a target with none, or with two or more, naming both models and the relations:

`films.reviews` is a `HasMany` to `reviews`, but `reviews` has two `BelongsTo` back to `films` (film, other_film); keep exactly one, or do not mount both

Keep one BelongsTo, or mount only one of the two models: a pair with a single side mounted is not checked.

The target must be a Ferra model. A relation whose target does not derive FerraModel fails to compile at .mount, with FRG-136: “<Target> is not a Ferra model that Foundry can serve, yet a relation points at it”.

Sub-collections

A HasMany or HasOne whose target is mounted on the same Foundry serves its rows under the parent (0.16.0). With films having reviews: HasMany<review::Entity> and both models mounted:

GET  /films/{id}/reviews
POST /films/{id}/reviews

There is nothing to switch on and no method to call: the two .mount and the relation field are the declaration, as for restore and the row actions. The routes appear in the OpenAPI document (listFilmReviews, createFilmReview: list or create, the parent’s name, the relation’s name) and are listed, with the parent’s path parameters, next to the routes of the child. A pair with a single side mounted serves nothing. A parent with a composite key has no sub-collection: a foreign key is one column.

A sub-collection is the child’s own path with one more term. POST /films/1/reviews allows nothing that POST /reviews with film_id = 1 does not, and GET /films/1/reviews lists what GET /reviews?filter[film_id]=1 lists:

  • It runs the child’s own list and create, with the child’s own rules, projections, field rules, hooks, soft-delete state, pagination mode, count and cursors. The parent’s term is added to the child’s authority, so a client’s filter[film_id]=2 cannot widen it: it narrows to nothing.
  • It goes through the child’s layers: its mount_with_layer, rate limit, body limit, CORS, JWT and cookie guard. Its rate-limit bucket is its own, as that of each route family of a model is. The JWT layer follows the stricter of the two policies, because the parent is judged on this route: a public child under a parent that needs an identity still reads the caller’s token. So do the child’s own routes, because they judge the parent too (the key, the parent link, a POST naming the parent): under .with_auth(), a model reads a credential (the Authorization header, the cookie, an API key) when a model one of its relations targets needs an identity, so a valid token is seen and a broken one is a 401. Such a model read no token before, and a request that carries the cookie may now meet the CSRF guard. A request with no token still reaches the child’s Anyone rules, with the key and the link hidden.
  • The representation is the child’s default one. A named projection’s prefix does not get sub-collections (/summary/films/1/reviews is not served).
  • The parent’s key comes from the URL and wins over the body’s film_id. The created review is canonical at /reviews/{id} (Location, self); the links of a page of the sub-collection (next, prev) stay on the sub-collection.

What the parent adds. Only refusals, in this order:

  1. The parent, judged exactly as GET /films/{id} judges it for this caller. A parent that is absent, soft-deleted or unreadable answers the 404 of an absent parent, byte for byte, and so does a key that is no key of the parent (/films/not-a-key/reviews: the 400 of GET /films/not-a-key would tell a caller that the key’s format is wrong, where no row would tell it anything).
  2. For POST, the parent’s update right: a parent the caller can read and may not update answers 403, before the child’s body is looked at.
  3. The child’s own refusals, in their own order. A parent the caller can read with a child list rule that refuses the caller answers the child’s 403 on GET. For an owner(from) child the create judges the parent again under its FOR SHARE lock; a parent that lost the right in between is that path’s 422 reference_not_found, which only a race can reach.

For a plain BelongsTo child (no owner(from)) Ferra takes no lock on the parent: its update right is read without one, like any plain BelongsTo (The aggregate protocol). The database still has a say: a Ferra write of film 1 holds it FOR UPDATE, and the INSERT of a POST /films/1/tags takes FOR KEY SHARE on film 1 through the foreign-key constraint, so it waits for that write to commit. A hold that does not conflict with FOR KEY SHARE (FOR NO KEY UPDATE, the mode of an UPDATE that leaves the key alone) does not make it wait.

A soft-deleted parent. Its children stay served on their own path (ADR-0059 limitation); a POST /reviews naming it is the 422 reference_not_found; a POST under it (/films/{id}/reviews) is the absent parent’s 404.

A relation that shares its name with a route. A HasMany or HasOne named like a row action, or restore, of its own model would take the path of that route: build() refuses it, naming the model and both names (BuildError::RelationNameCollision). Rename the relation or the action.

To serve none of them, write the parent in the split form (it declares no relation) or do not mount the child. There is no per-relation opt-out yet.

The aggregate protocol

A parent’s check (a film is published only when it has a live review, a studio’s rows are counted) is valid only if no child can be written behind its back. Ferra enforces that with locks, on by default, with nothing to switch on.

  • FR-001. Every write of a child (PUT, PATCH, delete, restore and row action, through the generated routes, Resource<M> and tx.resource alike) takes FOR SHARE on its direct parent, then locks its own row FOR UPDATE, whether or not the foreign key changes. The parent lock judges no rule and no authority, and it locks a soft-deleted parent too. A row the caller cannot see answers its 404 before any lock, so it never locks its parent. Creating a child keeps its parent check (FOR SHARE, judged under the parent’s update rule).
  • FR-002. Every write or action of a parent holds the parent’s row FOR UPDATE. A child write waits for it, and it waits for the child writes in flight. The children a parent writes from its hook or action are locked FOR UPDATE when they are written.
  • FR-004. Every write opens at READ COMMITTED (see Transactions).
  • FR-005. The lock order is total: the parent, then the row. Along a chain each level’s write is its own transaction, so the root is locked first.
  • FR-006. A plain BelongsTo (no owner(from)) locks nothing.
  • FR-007. Residual deadlocks go to the bounded retries of Transient conflicts are retried, and end at the 503 retry_exhausted. Ferra does not promise the absence of deadlocks: two child writes whose hooks write each other’s siblings can still cross.

A foreign key that changes between the read of the row and its lock (only a raw statement can do that) makes the attempt transient: it is rolled back and retried, and ends at the 503 retry_exhausted if the key keeps moving.

An empty collection under publish. A parent whose action reads “no review yet” holds the parent FOR UPDATE; a concurrent POST /reviews for that film waits for the parent’s lock, so the review cannot appear between the check and the commit.

A three-level chain. For studio, film and review, a review write locks its film only, and a film write locks its studio only. The ancestors are locked root first because each level’s write is its own transaction.

A collection action over several parents. A model with owner(from = ..) reads the keys of its rows without a lock, then locks the distinct parents FOR SHARE in one statement in key order, then the rows FOR UPDATE in key order, and checks that each row still has the key it was read with. A row the caller cannot see is the batch’s 404 before any parent is locked; a parent that no longer exists is that 404 too.

A plain BelongsTo locks nothing. Reading the target is enough: a PATCH of a tag whose film is held FOR UPDATE does not wait.

A raw INSERT, UPDATE or DELETE is outside the protocol. A raw INSERT into the child table waits on the parent’s FOR UPDATE when the table carries the foreign-key constraint (its check takes FOR KEY SHARE). A raw UPDATE or DELETE of an existing child does not wait: only the writes Ferra makes take the parent lock.

The protocol needs the database foreign-key constraint. It locks the parent row the key names; without a FOREIGN KEY on the child table nothing stops a parent from being deleted under its children. A child whose parent row is gone answers 404 to every write (PUT, PATCH, delete, restore and row action): there is no row to lock.

Hooks and the parent

A child’s hook runs with its parent held FOR SHARE. Its tx.resource may read the parent, create a sibling and write a row of another parent, but an update or a delete of the held parent is refused: 500 internal, one error! with both resource names and no key, and the write commits nothing even when the hook swallows the error (details). Write the parent from its own action, which holds it FOR UPDATE.

Across aggregates, write from the root’s action: a child’s hook that writes a grandparent can cross another write’s locks, and ends at the 503 retry_exhausted rather than waiting forever.

A database trigger that writes the parent on a child’s insert deadlocks the same way, and Ferra cannot see it: keep a counter on the parent in the parent’s action, or compute it on read.

Moving a child

The foreign key of a model with owner(from = ..) is set when the row is created and never changes (0.16.0, FR-010):

  • A PUT or a PATCH that names it is the 422 unknown_field of any key outside the write set, whatever value it names and whatever the caller may read, with nothing written. The key is not in the PUT and PATCH request schemas of the OpenAPI document, and it stays in the POST one.
  • A PUT that leaves it out keeps the row under its parent: the stored value fills in before the body is decoded.
  • A row action or a hook that changes it is a bug of yours: the action answers 500 internal, and a hook’s tx.resource().update naming it is refused with the same 422, and the hook that returns it rolls the whole write back; a hook that swallows it commits nothing either.

To move a child, delete it and create it again.

A delete then a create is not a move. The new row has a new identity: references to the old one (links, other tables, a client’s cached id), its history and its created_at do not follow it. A move protocol is post-1.0.

Links and foreign keys

A row never reveals a parent its caller cannot read. For each BelongsTo, the foreign key and the link to the parent follow the parent’s readability (0.16.0, FR-030):

ParentNon-nullable keyNullable key
readablethe value, and a linkthe value, and a link
none (NULL)null, no link
unreadableabsent, no linkabsent, no link
 
"_links": {
  "self": {"href": "/reviews/5"},
  "collection": {"href": "/reviews"},
  "film": {"href": "/films/1"}
}
  • The link is named after the relation and is the parent’s bare item path (no projection prefix), under the same origin and version prefix as self. HAL only. It is present if and only if the caller may GET that parent, so following it never answers a refusal.
  • The link to a sub-collection is named after the HasMany or HasOne relation and is the bare {item}/{relation} ("reviews": {"href": "/films/1/reviews"}), under the same origin and version prefix as self and whatever projection prefix served the row. It is present if and only if the sub-collection is served (the child is mounted on the same Foundry) and the caller may list the child, by the child’s own list rule and projection rule, so following it never answers a refusal. A HasOne is linked as a sub-collection too, never to the item. HAL only.
  • Readable is exactly what GET {parent item} judges: the get rule, the authority’s filter and can, the owner condition and soft delete. One statement per BelongsTo per page decides it for all the rows (key IN (...)), whatever the page size. It fails closed: an authority that fails or panics hides every key and link of the page and is logged, and a parent that is not mounted on the Foundry is hidden for everyone, with no statement.
  • Every response that serializes the row follows it: item, list, cursor page, /me, the write responses, each projection prefix, Resource<M> and a hook’s tx.resource. In FerraViews::Read the key is an Option.
  • Never required. The OpenAPI read schema leaves the key out of required and says it is absent when the caller may not read it; the Hal schema lists the parent and sub-collection links as optional.
  • A PUT does not need the key when the caller cannot read the parent: the stored value is kept.
  • Accepted residual: on a nullable key, “absent” against “null” tells a caller that the row has a parent it cannot read (one bit). A non-nullable key has none.

Embedding

A projection’s read list may name a BelongsTo relation (0.16.0, FR-040). The response then carries the parent’s row, under the relation’s name, next to the link to it. The row is served in the parent’s projection of the same name: the summary of a review embeds the summary of its film.

use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod film {
    use super::*;

    #[sea_orm::model]
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "films")]
    #[ferra(auth = "none")]
    // The target's `summary` carries its own `path_prefix`: see below.
    #[ferra(projection(name = "summary", path_prefix = "/film-summary", read = [id, title]))]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub title: String,
        #[sea_orm(has_many)]
        pub reviews: HasMany<super::review::Entity>,
    }

    impl ActiveModelBehavior for ActiveModel {}
}

mod review {
    use super::*;

    #[sea_orm::model]
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "reviews")]
    #[ferra(auth = "none")]
    #[ferra(projection(name = "summary", read = [id, body, film]))]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub film_id: i32,
        pub body: String,
        #[sea_orm(belongs_to, from = "film_id", to = "id")]
        pub film: BelongsTo<super::film::Entity>,
    }

    impl ActiveModelBehavior for ActiveModel {}
}
fn main() {}

GET /summary/reviews/5 answers (HAL; the plain JSON representation has the same members, without _links):

{
  "id": 5,
  "body": "Worth the trip.",
  "film": {"id": 1, "title": "Heat"},
  "_links": {
    "self": {"href": "/summary/reviews/5"},
    "collection": {"href": "/summary/reviews"},
    "film": {"href": "/films/1"}
  }
}
  • Exactly what the parent’s projection answers. The embedded row is what GET /film-summary/films/1 answers that caller, member for member: the projection’s own rule, the field read rules of each row (a field the caller may not read is no member, whatever the other embedded rows show), the computed fields (the hook runs once per computed field for the rows of the page), and the wire names. It is judged per row, so a page may hold an embedded row with a field and another without.
  • Not readable, nothing. A parent the caller may not read, or that is soft-deleted, gives no embed, no link and no key, as in Links and foreign keys. A parent the caller may read but whose projection of that name refuses them (its authorize rule), or a parent with no projection of that name, gives the link alone: the GET of that projection is a 404 for them, and the embed does not say more. No embed without the link: a parent whose bare route refuses the caller (a promoted projection with a stricter rule, say) is not embedded, even when the projection of that name would answer them.
  • One statement. The statement that decides the link (key IN (...), one per BelongsTo per page) returns the parent rows, and the embed serializes those: the number of statements does not depend on the number of rows, nor on the embed. The total, the page numbers and the cursor of a page are those of the same page without the embed.
  • A computed field that fails is a 500 on the whole response. If a computed field of the embedded target fails, the child’s response is the 500 internal of a failing hook, and no part of it is served: the embed is not dropped silently. The log line names the target’s model and the operation get.
  • The tag does not follow the parent. The ETag of the response is the child row’s: the embedded parent can change under the same tag. See The tag.
  • Depth 1. The embedded row carries no _links, no embed of its own and no foreign key of its own: its parents are not read again, so their keys are not served. Follow the film link for the whole row.
  • Every response that serializes the row embeds: item, list, cursor page, /me and the write responses of a projection route (the bare route too, when a promoted projection names the relation). Resource<M> and a hook’s tx.resource never embed: they return the typed read view, which has no member for a parent’s row.
  • Two projections of one name. The summary of reviews and the summary of films would both default to the URL prefix /summary/, and Foundry::build() refuses two projections on one prefix (FRG-310, see projections-and-routing.md). So the target’s projection carries its own path_prefix (/film-summary above), or the embedding one does. There is no syntax to embed a projection of another name.
  • No cycle. If the summary of films embedded a BelongsTo back to reviews and the summary of reviews embedded films, Foundry::build() (and try_build()) refuses the chain with BuildError::EmbedCycle: Embedding cycle: `reviews.summary → films.summary → reviews.summary`; remove one embed from a `read` list. The path is made of resource names, which are the table names unless resource = says otherwise, and starts at the first node the check meets again. Only an embed that is served counts: a relation whose target is not mounted (no key and no link either) or has no projection of that name (the link alone) closes no loop.
  • Only a BelongsTo. A HasMany or a HasOne named in a read list does not compile: it stays the link to its sub-collection, bounded by the pagination of the child.
  • OpenAPI. The projection’s read schema gets the relation as an optional member, a reference to the read schema of the parent’s projection of that name, when the parent is mounted on the same Foundry. The required list does not hold it.

Writing a foreign key

A create, a PUT or a PATCH that sets the key of a plain BelongsTo (no owner(from)) reads the target before it writes (0.16.0, FR-032). The read is the one that decides whether the caller may see the parent: the target’s get rule, its authority, its owner condition and soft delete, judged in the write’s own transaction. It takes no lock, so a plain BelongsTo still waits for nothing.

  • One refusal. A target that is absent, soft-deleted, out of the caller’s reach, or not mounted on the Foundry is the same 422 reference_not_found with field the key, whichever it is. The bytes are those of the parent check of an owner(from) child, and the same for the route, Resource<M> and a hook’s tx.resource. A caller cannot tell a film that does not exist from one it may not read, and nothing is written.
  • A table the API does not serve. A target that is not mounted on the Foundry is refused for every value, one that exists as much as one that does not: nobody can read it through this API, so none of its rows may be pointed at, and an answer that told the two apart would tell which ids exist. Two ways to write such a key:
    • mount the target model: its get rule then says who may point at it, and the key and the link are served;
    • set the key in before_save from another value the body carries, reading the reference through tx.resource (it reaches an unmounted model under its own rules).
  • A key a hook writes is the application’s responsibility: Ferra reads the targets of the keys the body names, before before_save runs, and does not judge what a hook then puts in the draft. The constraint still answers the 422 for an absent target. What an action writes (its changed) is the same: the application’s code and its responsibility, not judged by this read.
  • Several keys. When a body names several refused keys, the 422 names the first in declaration order, whatever the others are.
  • null and silence. null clears the key and reads nothing. A PATCH or a PUT that does not name the key reads nothing and keeps the stored value, even when the parent became unreadable.
  • An owner(from) key keeps its own check (lock_for_child): it is not read twice, and a PATCH naming it is still the 422 unknown_field first.
  • One statement per key named, none for a write that names no key.
  • Before 0.16.0 a target the caller could not read was accepted (201), and an absent one was a 500 (SQLSTATE 23503): the two answers told a caller which ids exist. See Migrating.

Deleting a parent

Whether a parent that still has children can be deleted is the schema’s choice, made in the foreign-key constraint of the child’s table (0.16.0, FR-033). Ferra asks the database and answers what it says.

  • ON DELETE RESTRICT (or the default, NO ACTION): the database refuses the DELETE. Ferra answers the 409 conflict with its fixed detail, nothing is deleted, and the statement is run once (a foreign-key violation is not a transient failure, so it is not retried). The OpenAPI document declares the 409 on the DELETE of every model that a BelongsTo targets. The server log holds the constraint’s name (INFO, target ferra_http::conflict), never the key value that Postgres prints in its detail line.
  • ON DELETE CASCADE: the database deletes the children itself. Ferra does not see them: their before_delete and after_delete hooks do not run, their rules and their soft delete are not applied. Use it only for rows nothing else has an opinion on.
  • A write the database refuses for a foreign key (the target was removed between Ferra’s read and its write) is the 422 reference_not_found of Writing a foreign key, on the key the constraint names, with the same bytes as a target that was absent at the read.
  • Accepted residual. Under RESTRICT a caller who may delete the parent learns, from the 409, that some row references it, including a child that caller cannot read: one bit per parent. When that matters, make the children owner-scoped (owner(from = ...) on the child, so the parent’s owner owns every child) or let the schema CASCADE.
  • A soft delete is an UPDATE: no constraint refuses it, and the children stay as they are.
