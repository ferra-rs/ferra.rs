Ferra.rs — User Guide

Getting started with Ferra

Ferra is a Rust framework for building HTTP APIs from a single Sea-ORM entity and one derive, #[derive(FerraModel)]. The entity gives you a CRUD router, an OpenAPI 3.2 document, a Scalar documentation page, hypermedia responses and typed RFC 7807 errors, all derived at compile time, with every route behind an authorization check that refuses by default.

This page takes you from cargo new to a running, protected, documented API. Every step below is run, as written, against a real database, by the cold_start check of the Ferra repository: if a step on this page is wrong, that check fails. Five minutes is the target, most of it spent compiling.

Create the project

cargo new my-api
cd my-api

Ferra is not published on crates.io: an application depends on a tag of the Ferra Git repository. Replace the Cargo.toml that cargo new wrote with:

[package]
name    = "my-api"
version = "0.1.0"
edition = "2024"

[dependencies]
ferra   = { git = "https://github.com/ferra-rs/ferra", tag = "v0.15.0" }
sea-orm = { version = "2.0", default-features = false, features = ["macros", "runtime-tokio-rustls", "sqlx-postgres"] }
tokio   = { version = "1", features = ["macros", "rt-multi-thread"] }
axum    = "0.8"
serde   = { version = "1", features = ["derive"] }

[dev-dependencies]
ferra = { git = "https://github.com/ferra-rs/ferra", tag = "v0.15.0", features = ["test-support"] }

ferra is the only Ferra crate you declare: ferra-core, ferra-db, ferra-forge, ferra-http and ferra-openapi are reached through it, and the repository’s own examples are held to that by the dep_gate check. The repository is private until the first release: your Git credentials must give Cargo access to it, for example with net.git-fetch-with-cli = true in .cargo/config.toml.

sea-orm is the one dependency you also declare yourself, with the same major version as Ferra (each release of Ferra names the major in its CHANGELOG.md). A different major is a second copy of the crate, and #[derive(FerraModel)] refuses it with FRG-400. cargo tree -d -i sea-orm prints nothing when there is a single copy. The facade also re-exports Sea-ORM whole, so an application may declare none and write ferra::sea_orm::…; Architecture shows that form.

The test-support feature, in [dev-dependencies] only, gives the example below the helper that signs a token; it is not in your application.

The model, and the server

A Ferra model is a Sea-ORM entity with the FerraModel derive next to DeriveEntityModel, and a posture: #[ferra(auth = "bearer")] says every operation requires a valid bearer token. A model with no posture does not compile (FRG-100): Ferra never decides for you between a public and a protected API.

Put this in src/main.rs:

use ferra::{ClaimCheck, FerraIdentity, FerraModel, Foundry, HmacAlgorithm, JwtConfig};
use sea_orm::entity::prelude::*;
use sea_orm::{ConnectionTrait, Schema};
use serde::{Deserialize, Serialize};

mod film {
    use super::*;

    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "films")]
    #[ferra(auth = "bearer")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        #[sea_orm(unique)]
        #[field(filterable, sortable)]
        pub title: String,
        pub director: String,
        pub year: Option<i32>,
    }

    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}

    impl ActiveModelBehavior for ActiveModel {}
}

// What the token says about its bearer. Ferra needs two things of it:
// a stable id and a role test.
#[derive(Clone, Debug, Deserialize)]
struct Claims {
    sub: String,
    #[serde(default)]
    roles: Vec<String>,
}

impl FerraIdentity for Claims {
    fn id(&self) -> &str {
        &self.sub
    }
    fn has_role(&self, role: &str) -> bool {
        self.roles.iter().any(|r| r == role)
    }
}

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let conn = sea_orm::Database::connect(std::env::var("DATABASE_URL")?).await?;

    // Development only: create the table when it is missing. A real
    // application owns its schema with `sea-orm-migration`.
    let table = Schema::new(conn.get_database_backend())
        .create_table_from_entity(film::Entity)
        .if_not_exists()
        .to_owned();
    conn.execute(&table).await?;

    // The secret comes from the environment, never from the source: at least
    // 32 bytes for HS256. A token must name this issuer and this audience.
    let jwt = JwtConfig::single_secret(
        "key-1",
        std::env::var("JWT_SECRET")?,
        HmacAlgorithm::Hs256,
        ClaimCheck::expect("https://auth.example.com/"),
        ClaimCheck::expect("my-api"),
    )?;

    // The key that signs the entity tags: at least 32 bytes, the same on every
    // replica, and never the JWT secret.
    let app = Foundry::new(conn)
        .etag_key(std::env::var("ETAG_KEY")?)?
        .with_auth::<Claims>(jwt)
        .mount::<film::Model>()
        // Public in development: /docs needs no token (see `with_docs_protected` in ferra-openapi.md).
        .with_docs()
        .build();

    let listener = tokio::net::TcpListener::bind("0.0.0.0:3000").await?;
    eprintln!("listening on 0.0.0.0:3000");
    // Serve with the peer address: the rate limiter keys on it, and the bare
    // router would answer every write with a 500.
    axum::serve(
        listener,
        app.into_make_service_with_connect_info::<std::net::SocketAddr>(),
    )
    .await?;
    Ok(())
}

What you get:

URLBehaviour
GET /filmsPaginated list (HAL _links, or flat JSON on Accept: application/json).
GET /films/{id}One film and its self-link.
POST /filmsCreate: validates, answers 201 Created. The server chooses id.
PUT /films/{id}Update the row named by the path.
PATCH /films/{id}Change the fields the body names (JSON merge patch); the others stay.
DELETE /films/{id}Delete.
GET /docs/openapi.jsonThe generated OpenAPI 3.2 document.
GET /docsThe Scalar page rendered from it.

The URL segment (films) is the model’s table name. To serve a table under another name, say so: #[ferra(resource = "movies")] on the model.

Errors come back as RFC 7807 application/problem+json, with a type from the closed namespace https://ferra.rs/errors/<name>.

A token to call it with

Ferra validates tokens; it does not issue them (your identity provider does). For development, sign one yourself with the helper of the test-support feature. Put this in examples/token.rs:

use ferra::HmacAlgorithm;
use ferra::testing::bearer;
use serde::Serialize;

#[derive(Serialize)]
struct Claims {
    sub: String,
    iss: &'static str,
    aud: &'static str,
    exp: u64,
}

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let now = std::time::SystemTime::now().duration_since(std::time::UNIX_EPOCH)?;
    let claims = Claims {
        sub: "alice".to_owned(),
        iss: "https://auth.example.com/",
        aud: "my-api",
        exp: now.as_secs() + 3600,
    };
    let secret = std::env::var("JWT_SECRET")?;
    // Prints `Bearer eyJ…`, valid for an hour.
    println!("{}", bearer("key-1", &secret, HmacAlgorithm::Hs256, &claims)?);
    Ok(())
}

Run it

You need PostgreSQL reachable at DATABASE_URL. The fastest local setup uses Podman or Docker:

podman run --rm -d --name pg \
  -e POSTGRES_USER=ferra -e POSTGRES_PASSWORD=ferra \
  -e POSTGRES_DB=my_api \
  -p 5432:5432 \
  postgres:17

export DATABASE_URL=postgres://ferra:ferra@127.0.0.1:5432/my_api
export JWT_SECRET=a-development-secret-of-at-least-32-bytes
export ETAG_KEY=another-development-key-of-at-least-32-bytes

Start the server (the first build is the long part of the five minutes):

cargo run

You should see listening on 0.0.0.0:3000; open http://localhost:3000/docs in a browser. In another terminal, from the same directory, ask for a token and call the API. A request with no token is refused, before anything about it is read:

curl -s -i http://localhost:3000/films                                        # expect: 401

export TOKEN=$(cargo run -q --example token)

curl -s -i -H "Authorization: $TOKEN" http://localhost:3000/films             # expect: 200
curl -s -X POST -H "Authorization: $TOKEN" -H "Content-Type: application/json" -d '{"title":"Alien","director":"Ridley Scott","year":1979}' http://localhost:3000/films   # expect: 201 contains "Alien"
curl -s -H "Authorization: $TOKEN" http://localhost:3000/films/1              # expect: 200 contains "Ridley Scott"
curl -s -X PUT -H "Authorization: $TOKEN" -H "Content-Type: application/json" -d '{"title":"Alien","director":"Ridley Scott","year":1980}' http://localhost:3000/films/1   # expect: 200 contains "1980"
curl -s -X DELETE -H "Authorization: $TOKEN" http://localhost:3000/films/1    # expect: 204
curl -s -i -H "Authorization: $TOKEN" http://localhost:3000/films/1           # expect: 404
curl -s http://localhost:3000/docs/openapi.json                               # expect: 200 contains "openapi"

The # expect: … comments say the status each line answers; the check that runs this page reads them.

MSRV and toolchain

Ferra’s MSRV is Rust 1.94 (edition 2024, resolver v3), set by the sea-orm dependency, which declares rust-version = "1.94.0" itself. Any stable Rust at or above 1.94 works in your project; the pinned toolchain of the Ferra repository (rust-toolchain.toml) does not propagate to you. Building on an older one fails inside sea-orm, not in Ferra.
