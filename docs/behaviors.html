Ferra.rs — User Guide

Behaviors

The 0.7.0 Pre-tempering deliverable. A #[derive(FerraModel)] struct can enrol cross-cutting behaviors that the framework injects in lockstep across the entire stack — fields, SQL, default projections, hypermedia links, and OpenAPI emission — from a single container-level attribute.

This page is the authoritative user-guide for the behaviors surface. A reader with only this page plus standard Rust knowledge produces a working #[behavior(...)] declaration on the first attempt — no ADR and no framework source is required.

Mental model

A behavior is a cohesive cohort of cross-cutting modifications the framework applies to a model: the fields it carries, the SQL the framework emits, the projections the framework derives, the hypermedia links the framework attaches, and the OpenAPI operations the framework documents — all at once, from one attribute line.

The three behaviors that ship at this release:

NameEffect
soft_deleteUses a nullable deleted_at column of your table (any name, see below). Every framework-generated SELECT filters rows whose stamp is non-null. The standard DELETE rewrites to an UPDATE deleted_at = NOW(). A new POST /{resource}/{id}/restore action sets the stamp back to NULL. The column is in no response.
timestampableUses created_at and updated_at columns of your table (any names, see below). Both are in every read response; every framework-generated UPDATE and restore sets updated_at in its own statement. A value for either in a create/update body is a 422.
blameableUses created_by and updated_by TEXT columns of your table (any names, see below): the subject of the caller who wrote the row. Only callers that pass the behavior’s read rule see them (authenticated callers by default). A value for either in a create/update body is a 422.

A model that declares zero #[behavior(...)] attributes has the plain CRUD surface. Adding a behavior is strictly additive to the model’s surface — the existing routes, the existing projections, and the existing OpenAPI emission all continue to exist; the behavior layers new structure on top.

The attribute

#[behavior(name1, name2, ...)]
#[behavior(timestampable(created = "inserted_at", updated = "modified_at"), soft_delete(column = "removed_at"))]
  • Container-level — applied to the struct declaration, not to individual fields.
  • Closed vocabulary at this release: soft_delete, timestampable, blameable. An unknown name is a compile-time error.
  • Stackable — the attribute can appear multiple times on the same struct; the framework dedupes by set-union. A repeat must name the same columns: a behavior declared twice with different columns is FRG-327.
  • Order-irrelevant — #[behavior(soft_delete, timestampable)] and #[behavior(timestampable, soft_delete)] produce byte-identical ModelMeta.
  • Column names (0.11.0) — each name takes an optional argument list that names the columns of your table. timestampable(created = "..", updated = "..") and soft_delete(column = ".."), and blameable(created_by = "..", updated_by = "..", read = <rule>) (read takes a rule, not a string; see ## #[behavior(blameable)]); an argument left out keeps its default, and the bare form keeps created_at, updated_at, deleted_at, created_by and updated_by. Each name is a Rust identifier (letters, digits and _, not a keyword), which is also the SQL column name, quoted; a column whose name is not one cannot be named here. A behavior declared twice with different columns is an error too. An unknown key, an empty or non-identifier name, or two behavior columns with one name is FRG-327; a field of the struct with the same name, or the same #[sea_orm(column_name)], is FRG-323. The behaviors work on tables that already exist: the columns are not fields of the struct, and the table keeps its own names.
#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
#[derive(
    Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize,
)]
#[ferra(auth = "none")]
#[sea_orm(table_name = "films")]
#[behavior(
    timestampable(created = "inserted_at", updated = "modified_at"),
    soft_delete(column = "removed_at")
)]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
}
}

#[behavior(soft_delete)]

Worked example

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
// Sea-ORM entity scaffolding (the `Relation` enum + `ActiveModelBehavior`
// impl) is required alongside every `DeriveEntityModel` — see
// `examples/hello-ferra/src/main.rs` for the canonical shape. The
// fence below shows the framework-facing surface; hidden setup keeps
// the visible example focused on `#[behavior(...)]`.
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
#[derive(
    Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize,
)]
#[ferra(auth = "none")]
#[sea_orm(table_name = "films")]
#[behavior(soft_delete)]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
}
}

The framework’s ModelMeta for Film carries:

  • A behaviors slice containing BehaviorKind::soft_delete("deleted_at"); ModelMeta::soft_delete_column() reads the name.
  • An automatically injected deleted_at: Option<ferra::DateTime> field at the end of the user’s field list, flagged skip, so no read projection and no read schema lists it and no write projection takes it. It is a column the database keeps: the model has no such field, so no response carries it, for any caller.
  • No entry for restore: Ferra serves POST /{resource}/{id}/restore from its one list of served operations (CRUD, then restore when the model soft-deletes and is not system_only), the same list the links and the OpenAPI document read. ModelMeta has no operations field since 0.14.0.

The migration

The column shape is hand-written into your sea-orm-migration migration file at 0.7.0 (no migration scaffolder ships with Ferra; the column shape below is what M::meta().behaviors declares):

ALTER TABLE films ADD COLUMN deleted_at TIMESTAMPTZ NULL;

That is the entire migration surface — the framework’s runtime SQL composes the predicate (WHERE deleted_at IS NULL) and the rewrites (DELETE → UPDATE deleted_at = NOW()) on top of this single column.

What changes on the wire

  • DELETE /films/{id} on a live row → 204 No Content, no physical delete; the row’s deleted_at is set to NOW().
  • DELETE /films/{id} on an already-soft-deleted row → 404 Not Found (the framework’s SELECT predicate filters the row out before the handler reaches it).
  • GET /films/{id} on a soft-deleted row → 404 Not Found.
  • PUT /films/{id} on a soft-deleted row → 404 Not Found; nothing is written. Revive the row with restore first.
  • PATCH /films/{id} on a soft-deleted row → 404 Not Found, byte for byte the answer for an absent row, also under If-Match and If-None-Match.
  • GET /films → soft-deleted rows are absent from the collection.
  • deleted_at does not appear in any response — not on a live row, not on the row restore returns — nor in any read schema of the OpenAPI document.

The deletion column is guarded twice

The column is kept out of every response by two guards that fail independently (0.13.0):

  1. At compile time, FRG-357: a projection whose read = [...] names the deletion column does not compile, and neither does a model with a field whose JSON name under rename_all is the column’s. Earlier releases compiled the first case and silently left the column out.
  2. At run time: before a response object is returned, ferra-core refuses one that holds a key equal to the deletion column’s SQL name (a 500 internal with no row data, never the value). It reads only ModelMeta::soft_delete_column, not the generated read structs.

Restoring a row

POST /films/{id}/restore
  • On a soft-deleted row → 200 OK with the row, as GET returns it. The deleted_at is set back to NULL.
  • On a row that never existed → 404 Not Found.
  • On a row that is already live (deleted_at IS NULL) → 404 Not Found (idempotent — re-restoring a live row is a no-op as far as the client is concerned).
  • The route honours Prefer: return=minimal per the framework’s standard preference header rules: with the header → 204 No Content, Preference-Applied: return=minimal, empty body.

A served row is live, so it carries no _links.restore (0.13.0): a link is present only if following it answers 2xx, and POST …/restore on a live row answers 404. restore stays in the OpenAPI document.

The restore action mounts under the standard Tower stack — CORS deny / body cap / mutation rate-limit / tracing — exactly like the standard CRUD mutation routes. It composes with per-projection URL prefixes by simple concatenation:

POST /admin/films/{id}/restore   ← when the model has an `admin` projection

Restore passes the same authorization checkpoint as every other route, with the model’s restore rule: update + delete (both must pass) when #[authorize] does not name restore. Under an IsOwner rule the checkpoint reads the soft-deleted row to compare its owner; someone else’s row answers 404, and an anonymous caller 401. On a #[ferra(authority)] model the authority judges the soft-deleted row too, and an answer of no is the same 404 (see ferra-auth.md § Programmatic authority).

No _links.restore

A row a response serves is live, so its HAL _links hold self and collection only (and self only when the caller may GET the row). Before 0.13.0 every live row carried a _links.restore.href that answered 404; a client that read it must call POST /{resource}/{id}/restore itself, on a row it knows was deleted.

Other named operations

restore is the only operation Ferra names itself. A business verb on a row — POST /films/{id}/publish, say — is a declared action: #[ferra(action(name = "publish", ..))] serves it with its own rule, your handler, the write of a PUT, and its _links and OpenAPI operation; see actions.md.

#[operation(path = "...", method = "...")] is a compile error since 0.9.0 (FRG-335): it produced a HAL link and an OpenAPI entry, but no route and no authorization rule. Declare an action instead. A route that is not a row’s verb is a handler you write and add to the router Foundry::build() returns; see custom-handlers.md. Such a route is outside Ferra’s authorization policy: protect it yourself.

error: FRG-335: `#[operation(...)]` declares a route Ferra does not mount
         help: remove the attribute and add the route yourself with `.route(...)` or `.merge(...)` on the value `Foundry::build()` returns — see docs/user-guide/custom-handlers.md

The codes that described the attribute’s grammar — FRG-330 (missing key), FRG-331 (unknown key), FRG-332 (/ in path), FRG-333 (unsupported method) and FRG-334 (duplicate name) — are retired: no build can produce them any more, and the numbers are never reused.

No physical delete on a soft-delete model

Every DELETE route of a soft-delete model — the bare path and every projection prefix — sets deleted_at; none issues a physical DELETE. To purge rows for good (retention, legal erasure), run your own SQL against the database, outside the API.

Edge case — identifier collision with a soft-deleted row

A POST /films that supplies an id matching an existing soft-deleted row returns the framework’s standard 409 conflict response:

{
  "type": "https://ferra.rs/errors/conflict",
  "title": "Conflict",
  "status": 409,
  "detail": "..."
}

This is the standard duplicate-key shape unchanged — the soft-deleted row continues to occupy the UNIQUE (id) index, and an INSERT colliding on it is a primary-key collision regardless of stamp state. The framework’s behaviour matches the database’s natural semantics.

If your application needs identifier reuse across hard-deleted-and-restored cycles, apply a partial unique index in the same migration:

-- Allow re-use of soft-deleted identifiers:
CREATE UNIQUE INDEX films_id_live_only ON films (id) WHERE deleted_at IS NULL;
ALTER TABLE films DROP CONSTRAINT films_pkey;
ALTER TABLE films ADD CONSTRAINT films_pkey PRIMARY KEY (id) DEFERRABLE INITIALLY IMMEDIATE;

The partial-unique-index pattern is an opt-in schema customisation; the framework does not emit it automatically.

#[behavior(timestampable)]

Worked example

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
#[derive(
    Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize,
)]
#[ferra(auth = "none")]
#[sea_orm(table_name = "films")]
#[behavior(timestampable)]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
}
}

The framework injects created_at: ferra::DateTime and updated_at: ferra::DateTime at the end of the field list, both flagged read_only: true (absent from the default-write) and listed by the default read projection. They are columns the database keeps: the model has no such field, so the repository returns them next to the row and the response adds them (see below). BehaviorKind::Timestampable { created, updated } carries the names; ModelMeta::timestamp_columns() reads them.

The migration

ALTER TABLE films ADD COLUMN created_at TIMESTAMPTZ NOT NULL DEFAULT NOW();
ALTER TABLE films ADD COLUMN updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW();

NOT NULL DEFAULT NOW() ensures that pre-existing rows in the table receive a value at migration time and that an INSERT fills both with one instant. The framework’s UPDATE and restore set updated_at = NOW() themselves.

What changes on the wire

(Bodies below are for a caller who may GET the row. One who may write it but not read it gets 201 with no body on a create and 204 with no body on an update or a restore, see migrating-to-0.13.md.)

  • POST /films → 201 with created_at and updated_at in the body, equal, read from the INSERT … RETURNING that wrote them.
  • PUT /films/{id} → updated_at advances in the UPDATE … RETURNING itself, one statement, and the response carries the new value; created_at is unchanged.
  • POST /films/{id}/restore → same, in the restore statement.
  • GET /films/{id} and GET /films → both fields on every item, under the column names, after rename_all if the model has one.
  • A projection lists a stamp like any field: a named read projection with read = [id, title] answers neither key, and one with read = [id, title, updated_at] answers only that one. The stamps follow the projection’s field list; they are not a _links-style addition.
  • The request body cannot set them: a body carrying created_at or updated_at (or the configured names) is a 422 unknown_field, and the stored values are unchanged.

The 422 follows from the read_only: true flag: the default-write projection excludes both fields and the write projections refuse a key they do not list. The persisted value is always the database’s NOW().

A Resource<M> route reads the same: the Read shape of the model has created_at and updated_at as Option<DateTime> fields, filled by Resource<M>; From<Model> alone leaves them None, since the model does not carry the columns, and a stamp that is None is absent from the serialized shape: the key is left out, not null (0.13.0).

#[behavior(blameable)]

timestampable says when; blameable (0.13.0) says who. It stamps the subject of the caller who wrote the row: the string your FerraIdentity::id() returns for the identity Ferra validated on the request (conventionally the JWT sub, see ferra-auth.md), never a value from the body. The operations below need an identity: create, update and, on a soft-delete model, delete and restore (the rules Authenticated, IsAdmin, HasRole(...) of ferra-auth.md § Authorization rules; Anyone is refused at compile time).

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
#[derive(
    Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize,
)]
#[ferra(auth = "bearer")]
#[sea_orm(table_name = "films")]
#[behavior(blameable)] // or blameable(created_by = "author", updated_by = "editor", read = HasRole("auditor"))
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
}
}

The framework injects created_by and updated_by at the end of the field list. The names are configurable like the other behaviors: with #[behavior(blameable(created_by = "author", updated_by = "editor"))] the columns are author and editor, and the migration below uses those names. They are columns the database keeps: the model has no such field, they are read-only and in no write projection.

The migration

Existing rows have no author. The migration below gives them the placeholder 'migration' (choose your own); an audit that reads created_by will see that value as the author of every row that existed before, so decide what it should say.

ALTER TABLE films ADD COLUMN created_by TEXT NOT NULL DEFAULT 'migration';
ALTER TABLE films ADD COLUMN updated_by TEXT NOT NULL DEFAULT 'migration';
ALTER TABLE films ALTER COLUMN created_by DROP DEFAULT;
ALTER TABLE films ALTER COLUMN updated_by DROP DEFAULT;
ALTER TABLE films ADD CONSTRAINT films_author_not_empty CHECK (created_by <> '' AND updated_by <> '');

Both columns are TEXT NOT NULL: a subject is whatever FerraIdentity::id() returns (a JWT sub, the subject an API key was issued for), stored verbatim. The CHECK is a second line of defence: Ferra already refuses to write an empty subject.

What is written, and when

  • created_by on the insert; updated_by on the insert, an update, a soft delete and a restore (the writes that set updated_at on a timestampable model). Both are written in the statement that writes the row, as bound parameters; the model need not be timestampable.
  • updated_by is last-writer attribution: it says who made the latest change, not the history of the row.
  • The subject is the id() of the validated identity of the request, or of the caller a Resource<M> is bound to. A body never chooses it: a body carrying created_by or updated_by (or the configured names) is a 422 unknown_field, and the stored values are unchanged.
  • A write with no subject, or an empty one, is refused: 500 internal, one error!, nothing written. The compile-time rule (FRG-121, below) is the normal guard against a missing caller; this 500 is defence in depth for an identity whose id() is empty. The application must give a verified, stable, non-empty id() (the OIDC sub). A physical delete (a blameable model without soft delete) writes no author, so it needs no subject.
  • A JWT sub = "svc-1" and an API key subject svc-1 stamp the same author: one column serves every credential kind. Keep API key subjects in a namespace of their own (for example svc:).

Who writes: FRG-121

An operation that writes the author must need an identity. create and update, and on a soft-delete model delete and restore, whose rule lets an anonymous caller through is a compile error: there would be no author to stamp. #[ferra(auth = "none")] is Anyone for every operation, so a blameable model cannot take it.

Who reads: blameable(read = <rule>)

The subject can be personal data (an email as sub), so by default only an authenticated caller sees the columns (read = Authenticated). read = Anyone shows them to every caller, an anonymous one included (do not copy it onto a model whose subjects are personal data); a role rule (read = HasRole("auditor")) shows them to that role. The rule is decided once per request, never per row, so IsOwner is refused (FRG-119). A caller who fails it gets the row without the keys: they are absent, not null, from the item, the list and Resource<M> reads. In OpenAPI they are optional read-only strings described “absent when the caller may not read it”. They are not filterable or sortable.

Combined behaviors

#[behavior(soft_delete, timestampable)] enrols both. The framework injects all three fields and the restore action. The composition behaves as the union of the two individual behaviors:

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
#[derive(
    Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize,
)]
#[ferra(auth = "none")]
#[sea_orm(table_name = "films")]
#[behavior(soft_delete, timestampable)]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
}
}

Composition rules:

  • DELETE /films/{id} rewrites to UPDATE films SET deleted_at = NOW(), updated_at = NOW() WHERE id = $1 AND deleted_at IS NULL. Soft-delete refreshes updated_at because the soft-delete is logically a write.
  • POST /films/{id}/restore emits UPDATE films SET deleted_at = NULL, updated_at = NOW() WHERE id = $1 AND deleted_at IS NOT NULL. Restore refreshes updated_at; created_at stays at the original creation time.
  • The order of names is irrelevant — #[behavior(timestampable, soft_delete)] produces the same ModelMeta as #[behavior(soft_delete, timestampable)].

The combined migration:

ALTER TABLE films ADD COLUMN deleted_at TIMESTAMPTZ NULL;
ALTER TABLE films ADD COLUMN created_at TIMESTAMPTZ NOT NULL DEFAULT NOW();
ALTER TABLE films ADD COLUMN updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW();

Hooks

Application code that runs inside a write. A model declares #[ferra(hooks)] and writes impl FerraHooks for Model; Ferra calls the hooks after it has authorized the request, inside the write’s transaction. The key and the impl go together: one without the other is FRG-129, and a key inside hooks(...) is FRG-132.

Every hook has a default that does nothing, so the impl names only the ones it uses:

HookRunsReceives
before_savebefore a create, an update or a restore writesSaving: the operation, the locked row for an update or a restore, and the pending values
after_saveafter the write, still in the transactionSaved: the row as written
before_deletebefore a delete&Self: the locked row
after_deleteafter the delete, still in the transaction&Self: the row that was locked, as it was before the delete
after_commitafter the commit, before the responseCommitted: the operation and its row

Every hook also receives the &RequestContext. The four transactional hooks get a &mut HookTx too (the rows of other models, the system grant); after_commit gets none. Here are the five signatures, with a body that does nothing; Self is the hooked model:

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "accounts")]
#[ferra(auth = "bearer", hooks)]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub name: String,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
use ferra::hooks::{Committed, FerraHooks, HookError, HookTx, Saved, Saving};
use ferra::request_context::RequestContext;

/// Stand-in for your queue client.
async fn enqueue(event: &str, id: i32) -> Result<(), HookError> {
    let _ = (event, id);
    Ok(())
}

impl FerraHooks for Model {
    async fn before_save(
        _w: Saving<'_, Self>,
        _ctx: &RequestContext,
        _tx: &mut HookTx<'_, Self>,
    ) -> Result<(), HookError> {
        Ok(())
    }

    async fn after_save(
        _w: Saved<'_, Self>,
        _ctx: &RequestContext,
        _tx: &mut HookTx<'_, Self>,
    ) -> Result<(), HookError> {
        Ok(())
    }

    async fn before_delete(
        _row: &Self,
        _ctx: &RequestContext,
        _tx: &mut HookTx<'_, Self>,
    ) -> Result<(), HookError> {
        Ok(())
    }

    async fn after_delete(
        _row: &Self,
        _ctx: &RequestContext,
        _tx: &mut HookTx<'_, Self>,
    ) -> Result<(), HookError> {
        Ok(())
    }

    // No `HookTx`: the transaction is over.
    async fn after_commit(
        event: Committed<'_, Self>,
        _ctx: &RequestContext,
    ) -> Result<(), HookError> {
        match event {
            Committed::Created(row) => enqueue("account.created", row.id).await,
            Committed::Deleted(row) => enqueue("account.deleted", row.id).await,
            // `Updated` and `Restored` hold the row as written.
            _ => Ok(()),
        }
    }
}
}

Saving, Saved and Committed are enums of ferra::hooks, #[non_exhaustive]: a match on one ends with a _ arm. Each variant says which operation it is.

EnumVariants
Saving<'_, Self>Create { values }, Update { before, values } (a PUT, a patch or an action), Restore { before, values }; before is the locked row, values the pending values (below). w.values() reaches values in all three, w.before() is None for a create.
Saved<'_, Self>Create(&row), Update(&row), Restore(&row): the row as written.
Committed<'_, Self>Created(&row), Updated(&row) (a PUT, a patch or an action), Restored(&row): the row as written. Deleted(&row): the row that was locked, as it was before the delete.

Order and rollback

A create, an update or a patch (Resource::update) runs in this order, in one transaction (an action’s handler runs between steps 1 and 2: Hooks of a declared action):

  1. Ferra’s own checks: the rule, the field rules, the owner scope, the authority, the body and its validation, the lock of the row (an update) and the parent check (owner(from)). A request refused here runs no hook.
  2. before_save, which may rewrite the pending values.
  3. The draft’s Some fields are put on the row, and the statement runs.
  4. The authority’s post-check, when the model has an authority.
  5. after_save, then the commit, then after_commit.

A delete runs the same checks and the lock of the row, then before_delete, the statement (a soft delete or a physical one), after_delete, the commit and after_commit. A restore runs its checks and the lock of the soft-deleted row, then before_save (Saving::Restore, whose draft starts empty: the hook may fill it), the statement, after_save (Saved::Restore), the commit and after_commit.

An Err or a panic from a hook rolls the whole write back, whatever the hook already wrote. The answer is the HookError’s. A HookError is built with one of four constructors of ferra::hooks::HookError (Hook errors has the examples):

ConstructorAnswer
HookError::failed(msg)500 with the generic body; msg (impl Into<String>) is logged, never sent. A panic in a hook is the same.
HookError::conflict(detail)409, detail (impl Into<String>) as given
HookError::unprocessable(field, code, message)422, one error on field (a &'static str) with code (a ferra::ValidationCode) and message (impl Into<String>)
HookError::unavailable(detail)503, detail (impl Into<String>) as given

after_commit answers these differently, because its write stands: see After commit. A hook reads the whole row, hidden columns included, and Ferra gives it no way into the response: the text of a HookError is yours, so put no value in it that the caller may not read. A refusal after the statement (the authority’s 403 on the row as written, a unique violation) also rolls back: before_save ran, after_save does not, and nothing it wrote survives. An empty patch writes nothing and runs no hook. A write made directly through FerraRepository (*_in_tx, insert_active) bypasses the hooks: it is raw access, outside the contract.

A hook cannot write its own row

An update (a PUT, a patch, Resource::update, and a declared action) writes only the row it locked: its UPDATE is conditioned on that row’s version and, on a soft-delete model, on its deletion column. A before_save hook that updated, soft-deleted or deleted that row through tx.resource has changed the version (or removed the row), so the write finds no row: the answer is the generic 500, one error! names the model and the operation, and nothing is written, the hook’s write included. It is never the 404 of the repository. Since 0.14.0:

a before_save hook that wrote its own row through tx.resource now fails with 500: set the value on the draft instead

The draft is the hook’s way to change the row being written (the pending values); a write to another model’s row through tx.resource is unaffected (ADR-0072, amended 2026-10-15).

A child’s hook cannot write the parent it holds

A write of a model with owner(from = ..) holds its parent row FOR SHARE for the length of the transaction (the aggregate protocol). A hook of that child that updates or deletes the same parent through tx.resource would ask for FOR UPDATE on a row it shares, which deadlocks against any other child of that parent in flight. Since 0.16.0 Ferra refuses it before any statement:

  • the call returns FerraError::Internal, and the write is answered 500 internal, with one error! that names the child’s resource, the parent’s resource, the operation and the fix, and never a key value;
  • the refusal poisons the write: a hook that swallows the error and returns Ok still commits nothing, and a rollback to a savepoint does not clear it. A refused write is not transient, so it is never retried;
  • a read of the parent, a sibling create and a write of a row this write does not hold are not touched, and neither is a row the write holds FOR UPDATE (a parent’s own action writing its children through tx.resource).

Write the parent from its own action, where it is locked FOR UPDATE first. A hook that writes a grandparent, or a row under another parent, writes a row the write does not hold: Ferra allows it, and it can deadlock against that row’s own protocol. The bounded retries end it at the 503 retry_exhausted; write across aggregates from the root’s action.

Hooks can run more than once

When the database aborts a write with 40001 or 40P01, Ferra runs the write again from its start, up to three attempts (Transient conflicts are retried). The four transactional hooks (before_save, after_save, before_delete, after_delete) run once per attempt, each on the state of the row that attempt locked. A HookError built from a FerraError that carries one of those codes (a tx.resource or tx.system call you propagated with ?) starts a new attempt too; any other HookError ends the write with its own answer. After the third abort the answer is a 503 retry_exhausted and that write was not applied.

So a transactional hook must be re-runnable:

  • No external I/O before the commit. A message, an HTTP call or a file written from before_save, after_save, before_delete or after_delete goes out once per attempt, and for a write that is then rolled back. Do the work on the database through tx, which the abort rolls back, and nothing else.
  • Effects go to after_commit. It runs once, for the attempt that committed, never for an aborted one.
  • Keep no state between attempts. A counter, a flag or a cache that a hook changes in the application is changed once per attempt.

Hooks of a declared action

A declared action (actions.md) writes as an update does: its handler returns the new state of the locked row, and the hooks of the model see that write as an update. before_save gets Saving::Update, after_save gets Saved::Update and after_commit gets Committed::Updated; Committed keeps its four variants above, an action is not a fifth. The handler is under the same rules as a hook: an Err rolls the write back, a panic is a 500 with the generic body (panic = "abort" defeats the catch, as for a hook), and the error! of a failed names the resource and the action and carries no value.

A handler and its hooks may run again on a retried attempt (Hooks can run more than once): do no external I/O in the handler before the commit, and send effects from after_commit.

After commit

after_commit runs once per committed create, update, patch, delete and restore, after the commit and before the response, outside the transaction. It receives a Committed (which operation it was, and the row: see the variants) and the request context, and no HookTx: it has no handle on the database. It never runs for a refused or rolled-back write. A write made by tx.resource inside a hook runs no hook of its model. The signature and a match on Committed are in the example above.

  • Effects go here. A message to a queue sent from before_save or after_save goes out for a write that is then rolled back. Since 0.14.0 a write aborted by a serialization failure or a deadlock is run again (see Hooks can run more than once), and the transactional hooks with it, so a message sent from them would go out once per attempt. after_commit runs once, whatever the attempts.
  • It can still be lost. The process may die between the commit and the enqueue: the row stands and the message is never sent. The transactional outbox planned for 1.1.0 closes that window. Until then the consumers must be idempotent, and after_commit should do an enqueue and nothing slower, since it holds the response.
  • The commit stands whatever it returns. Err(failed) is a 500, Err(unavailable(..)) a 503 with your detail, and a panic a 500. A 40001 or 40P01 in it is a 500 like any other error: after_commit is never run again, because the write stands. conflict and unprocessable are a 500 too: a 409 or a 422 would claim that nothing was written. Each is logged once through tracing, at the error level, target ferra_http::hooks, with the word “committed” in the message. On an Err the answer is the error, never the row (on Ok(()) the answer is the write’s usual one: a create still answers 201), and can(Get) and the list filter of the response links are not called.
  • A computed field is computed after it. The response of the write computes its computed fields once after_commit has returned. If that fails the write is committed: the answer is a 500 and the row stands, and a replayed POST can create a duplicate (see Idempotent creates).
  • A 5xx after a POST invites a duplicate retry. On a non-idempotent write, log inside after_commit and return Ok(()); keep Err for the failures a client may safely hear about.
  • The request budget cuts it. With .request_budget(..), Ferra runs after_commit under a timeout of the budget that is left (never a 503 timeout after a commit). There is no call that reads the time left. When it runs out the hook’s future is dropped where it waits (at an .await), the answer is a 500 and the commit stands. A slow COMMIT can use up the whole budget: the timeout is then zero, and the hook is dropped at its first .await. Without a budget nothing bounds it.
  • The 503 detail is served as it is, whatever the caller may read: put no value in it that the caller may not read.

The pending values: {Model}Draft

For a model Model the derive writes ModelDraft, and before_save rewrites it through Saving::values(). It has one field per column you declared, Option<T> (Option<Option<T>> when the column is nullable): Some is written, None is not. A read_only field is there, because a hook is your trusted code. It has no field for what the server writes itself: the primary key, the #[field(owner)] column, the timestamp, blame and deletion columns, a computed field and a #[sea_orm(ignore)] field. A hook cannot forge them: draft.id does not compile.

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
use ferra::hooks::{FerraHooks, HookError, HookTx, Saving};
use ferra::request_context::RequestContext;

#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "accounts")]
#[ferra(auth = "bearer", hooks)]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub email: String,
    pub title: String,
    #[ferra(read_only)]
    pub status: String,
    pub slug: Option<String>,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}

impl FerraHooks for Model {
    async fn before_save(
        mut w: Saving<'_, Self>,
        _ctx: &RequestContext,
        _tx: &mut HookTx<'_, Self>,
    ) -> Result<(), HookError> {
        let is_create = matches!(w, Saving::Create { .. });
        let values = w.values();
        // Normalize: the email is stored trimmed and in lower case.
        if let Some(email) = values.email.as_mut() {
            *email = email.trim().to_lowercase();
        }
        // Set a `read_only` column: a client cannot send `status`, the hook can.
        if is_create {
            values.status = Some("draft".to_owned());
        }
        // Derive a column from another: the slug follows the title.
        if let Some(title) = values.title.as_deref() {
            values.slug = Some(Some(title.to_lowercase().replace(' ', "-")));
        }
        Ok(())
    }
}
}

The values a hook writes are trusted: Ferra validates the request body, not what a hook then puts in the draft. There is no second garde validation and no write field rule on them; the storage constraints still apply. A violated unique index is the 409 the client sees; a foreign key a write violates is the 422 reference_not_found (the 409 is a delete’s). The target of a plain BelongsTo key a hook writes is not read by Ferra: it is your responsibility, and the constraint answers the 422 for an absent one (Writing a foreign key).

Three more things to know:

  • ActiveModelBehavior runs after the draft is applied, inside the statement, and can still change any column, the owner and the owner(from) foreign key included. It is your trusted code too.
  • HookError implements From<FerraError>, so a ? on any FerraError inside a hook (a tx.resource call, for one) becomes a HookError::failed: a 500 with the generic body, never the source’s status or detail. To refuse with a 409 or a 422, build the HookError yourself.
  • A hook holds the row lock for as long as it runs, and the request budget can cut a hook only where it waits (an .await), not a thread it blocks. Write hooks as async code with async I/O, and keep them short: no synchronous I/O and no heavy computation (hand CPU-bound work to tokio::task::spawn_blocking and await it). A request that the budget drops while a hook waits for a lock may leave that wait running on the database server, notably behind PgBouncer.

Rows of other models: tx.resource

A hook reaches the rows of any other model N through tx.resource::<N>(). It has the six methods of Resource<N> (get, list, list_cursor, create, update, delete), and they run in the write’s transaction, on its connection: the side rows commit with the main row, and a failure of the hook or of the write rolls both back.

They are an ordinary operation on N for the caller of the write: N’s rules, owner scope and field rules, its authority, its parent check, and its blame (the caller’s subject). The authority of N reads the request context the hook receives. A side write that N refuses is a FerraError; the ? makes it a HookError::failed (From<FerraError>), so the write is a 500 with the generic body, and nothing is written. N need not be mounted. create takes the write shape of N, which the derive names {Model}WriteProjection (entry::ModelWriteProjection below, since the struct is called Model): the fields a POST body may carry, so no key, no owner column, no read_only field and nothing the server writes. It is not the {Model}Draft of before_save.

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod entry {
    use ferra::FerraModel;
    use sea_orm::entity::prelude::*;
    use serde::{Deserialize, Serialize};
    #[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "ledger_entries")]
    #[ferra(auth = "bearer")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub account_id: i32,
        pub note: String,
    }
    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}
    impl ActiveModelBehavior for ActiveModel {}
}
use ferra::hooks::{FerraHooks, HookError, HookTx, Saved};
use ferra::request_context::RequestContext;

#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "accounts")]

    #[sea_orm(primary_key)]

    pub name: String,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]

impl ActiveModelBehavior for ActiveModel {}

impl FerraHooks for Model {
    async fn after_save(
        w: Saved<'_, Self>,
        _ctx: &RequestContext,
        tx: &mut HookTx<'_, Self>,
    ) -> Result<(), HookError> {
        let Saved::Create(account) = w else {
            return Ok(());
        };
        // A row of another model, under the caller's rules, in this transaction.
        // If the caller may not write ledger entries, the account is not created.
        tx.resource::<entry::Model>()
            .create(entry::ModelWriteProjection {
                account_id: account.id,
                note: "opened".to_owned(),
            })
            .await?;

    }

}
  • A hook is not a write boundary. A write made through tx.resource runs no hook of N, and none of M’s own when N is M: there is no re-entry. An invariant that N keeps in its own hooks does not hold for a write made from another hook; enforce it with a database constraint.
  • The rows it returns are not read-checked. A row that a tx.resource write returns is not checked against N’s read authority (can(Get)). Do not echo it to the caller.

System grant

A model that only a grant writes. An audit log must not be rewritten through the API that serves it. The model that holds the log is marked #[ferra(system_only)]; the grant that appends to it is declared by a hooked model (#[ferra(hooks(system = T))]), and its hooks read the head of the log and append to it in the write’s transaction.

The target: #[ferra(system_only)]

A system_only model is a read-only resource as far as Ferra’s API goes:

  • No write route. Ferra registers no POST, PUT, PATCH or DELETE for it, and no restore, under the bare path or under a projection prefix. A write method on its path is a 405 whose Allow header lists the reads only (401 without a credential, as on any model that needs one).
  • No write in the document. The OpenAPI document has its list and get operations and no other, and holds no write schema (Create{Model}Input, Update{Model}Input, under a projection prefix too).
  • No write rule. A write through Resource<T> is refused like an operation without a rule: 403 with an identity, 401 without. A create, update, delete or restore rule in its #[authorize] block is FRG-135, and the block asks for list and get only.
  • Reads keep their rules. list and get follow the model’s #[authorize] block or its posture, as for any model. It needs a posture like every model (FRG-100): the #[authorize] block of the example is one, so no auth = ... key is needed beside it.
  • Mounting. A target need not be mounted for the grant to work: tx.system() reaches the table without a route. Mount it to let #[authorize]d readers list the log through the API. The hooked model is mounted as any model.
  • No hooks. #[ferra(hooks)] on a system_only model is FRG-135 too, spanned on the hooks key: the model serves no write, and the grant inserts without its hooks, so they would never run. The hooks of a grant are the hooked model’s, never the target’s.
#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "audit_entries")]
#[ferra(system_only)]
#[authorize(list = HasRole("auditor"), get = HasRole("auditor"))]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i64,
    pub action: String,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

Ferra writes the table only through the grant. SQL that does not go through Ferra is the application’s: give the database role of the API INSERT and SELECT on the table only, refuse UPDATE, DELETE and TRUNCATE with a trigger, and make the column that holds the previous hash unique, as a safety net against a fork. A sketch of the table of the example, for PostgreSQL (api_role is the role the API connects as; run the migration as another one, since an owner can drop a trigger):

CREATE TABLE audit_entries (
    id        BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    action    TEXT NOT NULL,
    prev_hash TEXT,            -- NULL for the first entry only
    hash      TEXT NOT NULL
);
-- Two entries cannot share a predecessor...
CREATE UNIQUE INDEX audit_entries_one_successor ON audit_entries (prev_hash);
-- ...and a UNIQUE index lets NULLs repeat, so the first entry needs its own guard.
CREATE UNIQUE INDEX audit_entries_one_first ON audit_entries ((true)) WHERE prev_hash IS NULL;

CREATE FUNCTION audit_entries_append_only() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    RAISE EXCEPTION 'audit_entries is append-only';
END $$;
CREATE TRIGGER audit_entries_no_rewrite BEFORE UPDATE OR DELETE ON audit_entries
    FOR EACH ROW EXECUTE FUNCTION audit_entries_append_only();
CREATE TRIGGER audit_entries_no_truncate BEFORE TRUNCATE ON audit_entries
    FOR EACH STATEMENT EXECUTE FUNCTION audit_entries_append_only();

REVOKE ALL ON audit_entries FROM PUBLIC;
GRANT SELECT, INSERT ON audit_entries TO api_role;

The grant: hooks(system = T)

A hooked model declares at most one target, shared by all its hooks. tx.system() exists only on a model that declares it: without the grant the call does not compile. It gives two calls, both in the write’s transaction, so an entry exists only for a write that committed:

  • latest().await is the head of the log: a Result<Option<T>, HookError>, the row with the highest primary key as a T (the model itself), or None for an empty table. The key is an i32 or an i64 generated by the database (a target with a key of your own, or of another type, is FRG-130).
  • insert(value).await appends a row and returns the row as written, a Result<T, HookError>. value is the write shape of T, {Model}WriteProjection (audit_entry::ModelWriteProjection below: the fields a POST body would carry, so not the key), as for tx.resource::<N>().create(..) above. Ferra hashes nothing: the hook computes the chain hash from the head.

Both fail with a HookError, the type a hook returns, so a ? inside a hook needs no conversion. The example drops the row that insert returns because the response carries nothing of the target.

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
use ferra::hooks::{FerraHooks, HookError, HookTx, Saved};
use ferra::request_context::RequestContext;

mod audit_entry {
    use ferra::FerraModel;
    use sea_orm::entity::prelude::*;
    use serde::{Deserialize, Serialize};
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "audit_entries")]
    #[ferra(system_only)]
    #[authorize(list = HasRole("auditor"), get = HasRole("auditor"))]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i64,
        pub action: String,
        pub prev_hash: Option<String>,
        pub hash: String,
    }
    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}
    impl ActiveModelBehavior for ActiveModel {}
}

#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "transfers")]
#[ferra(auth = "bearer", hooks(system = audit_entry::Model))]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub amount: i32,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}

/// Stand-in for your hash function (SHA-256 of the previous hash and the action, say).
fn sign(prev: Option<&str>, action: &str) -> String {
    format!("{}|{action}", prev.unwrap_or_default())
}

impl FerraHooks for Model {
    async fn after_save(
        w: Saved<'_, Self>,
        _ctx: &RequestContext,
        tx: &mut HookTx<'_, Self>,
    ) -> Result<(), HookError> {
        let Saved::Create(transfer) = w else {
            return Ok(());
        };
        // The head the previous entry left; `None` for the first one.
        let prev = tx.system().latest().await?.map(|head| head.hash);
        let action = format!("transfer {} created", transfer.id);
        let hash = sign(prev.as_deref(), &action);
        tx.system()
            .insert(audit_entry::ModelWriteProjection {
                action,
                prev_hash: prev,
                hash,
            })
            .await?;
        Ok(())
    }
}
}

What insert does with the target:

  • Its validation and behaviors run (the validation attributes of T’s fields, such as min_length, timestamps, ActiveModelBehavior), and so do the database’s constraints. Its authorization does not: T’s #[authorize] rules, its field rules (the read and write rules of a field, which say who may see or write it), its authority and its hooks are skipped. The caller of the write may have no right at all on T; that is the point of the grant, and why it is declared on the hooked model, narrow (one target) and logged at startup (below).
  • The owner and the blame are the caller’s. A #[field(owner)] column of T is stamped with the caller’s id, and so is the author of a #[behavior(blameable)] target. An anonymous caller has no id: the insert is refused, so a target with an owner column cannot serve a hooked model that lets an anonymous caller write, and a blameable target cannot (the compiler says so, FRG-134).
  • Nothing of the target is in the response. The hook returns (), and the target’s hooks never run for the grant’s insert.
  • A refusal is a 500. An invalid value, a storage constraint (a duplicate previous hash) or a missing subject fails the hook with HookError::failed: the whole write is rolled back and the body is the generic 500. One error! (tracing, target ferra_http::hooks) says why: the model, the target, and the failing field names with their validation codes, or the SQLSTATE and the constraint, or “no subject”, and never a value. The HookError tells nothing more (a hook cannot inspect it), but a hook can handle the Err and answer for itself, for example return Err(HookError::unprocessable("amount", ValidationCode::Max, "...")) for a 422 on a field of its own model.
  • Each call runs in a savepoint, a mark inside the write’s transaction that undoes one failed call and keeps the rest. A hook that swallows a failed insert leaves no half-written row and its write still commits. If the database cannot release or roll back the savepoint itself (a lost connection, say), the transaction is unusable: the write fails with a 500 and nothing is committed.

Serialization

Two operations that append at once must not sign the same predecessor. latest() and insert() first take a transaction-level advisory lock, pg_advisory_xact_lock(a, b) where a is the constant 0x46455252 (1178948178, the ASCII bytes of FERR) and b is the 32-bit FNV-1a hash (offset basis 2166136261, prime 16777619) of the UTF-8 bytes of the target’s schema-qualified table name, read as a signed integer (public. when the entity names no schema). The same in every binary, so a rolling deploy agrees: for public.audit_entries the call is pg_advisory_xact_lock(1178948178, 580943822). The second operation waits for the first one’s commit or rollback, then reads the head the first left. a and b are the two-integer key space, shared with your own two-integer advisory locks: do not use 0x46455252 as the first key of your own.

  • A lock or a head read that fails is logged. A lost connection, or a lock_timeout of your own that expires while another transaction holds the lock (55P03), fails the call with the generic 500 and one error! (tracing, target ferra_http::hooks) that names the target and the SQLSTATE when the database gave one, never a value.
  • The key order is the commit order only with CACHE 1. The head is the highest primary key. The sequence of a SERIAL or an identity column has CACHE 1 by default; with a larger cache the values are distinct but not ordered. Ferra assumes CACHE 1 and does not check it.
  • One lock per target, held to the end. A transaction-level lock is released at commit or rollback. A slow hook holds every other appender; there is no lock timeout, the request budget is the bound. Two hooked models that lock two targets in opposite orders can deadlock: the database aborts one (40P01) and the write is run again, up to three attempts, then answers 503 retry_exhausted (0.14.0).
  • A write runs at READ COMMITTED. The head read after the lock must see the last commit, so Ferra sets the level at BEGIN whatever default_transaction_isolation says; the hooks run at that level too (every write does since 0.16.0; see Migrating from 0.15 to 0.16).
  • Neon’s pooled endpoint. A transaction-level advisory lock works behind a pooler in transaction mode (only session-level locks do not). PgBouncer’s documentation says so, and the repository’s pooler_acceptance binary proves it through a PgBouncer in transaction mode; Neon’s own documentation does not state it.

The startup log

Foundry::build() writes one tracing info! line per system grant of a mounted model, target ferra::grants (enable that target in your subscriber’s filter), so the grants of a binary can be listed from its logs:

system grant: hooks of "transfers" may read the latest row of and insert into "public.audit_entries"

A model without a grant writes no line.

What the hook cannot put in an entry

  • Hooks do not see the stamps. Timestamps and blame are written by the statement, so a chain hash cannot include them: hash what the hook has (the action, the row’s values, the previous hash).
  • Client-supplied headers are recorded as sent. X-Forwarded-For, Host and User-Agent read from the request context are the client’s claims: record them as claims, not as facts.

Common pitfalls

Manually declaring an injected column on the struct

#[behavior(soft_delete)]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: Uuid,
    pub title: String,
    pub deleted_at: Option<ferra::DateTime>,   // ← compile error
}

The framework emits FRG-323 at proc-macro time (the complete model, bad and good, compiled: FRG-323):

error: FRG-323: field `deleted_at` conflicts with the `soft_delete` behavior's column `deleted_at`
help: remove the field (the behavior reads and writes that column itself), or name the behavior's column differently in `#[behavior(...)]`

The same diagnostic applies to created_at and updated_at under #[behavior(timestampable)], to the names you configure, and to a field whose #[sea_orm(column_name)] is one of them. Behaviors own their columns; if you need a column of that name for something else, name the behavior’s column differently.

Submitting a timestamp value in a request body

A POST /films or PUT /films/{id} body carrying created_at, updated_at or deleted_at (or the names configured) is refused with 422 unknown_field: behavior-managed columns are outside every write projection. The persisted values are the server’s own (NOW() at INSERT / UPDATE; restore clears deleted_at).

If your application needs to record a different “as-of” date (e.g., for retroactive imports), declare a separate column with a non-reserved name (recorded_at, effective_at, …) and write it normally — the framework’s behaviors own only the names listed in the closed vocabulary above.

Unknown behavior name

#[behavior(softdelete)]    // typo — missing underscore

The framework emits FRG-320 at proc-macro time (FRG-320, compiled):

error: unrecognised behavior name `softdelete`
help: did you mean `soft_delete`?
note: recognised behaviors: soft_delete, timestampable, blameable.
      See docs/user-guide/behaviors.md.

The recognised vocabulary is closed; future releases add new names additively (the #[non_exhaustive] BehaviorKind enum makes the additions non-breaking by construction).

Empty #[behavior()]

#[behavior()]    // empty

The framework emits FRG-321 (FRG-321, compiled):

error: behavior attribute requires at least one name
help: remove the attribute or supply at least one of: soft_delete, timestampable, blameable

An empty attribute is rejected because it has no effect and most likely indicates an editor template that was not filled in.

Syntax outside the grammar

#[behavior(soft_delete = true)]      // key/value — not the grammar
#[behavior("soft_delete")]            // string literal — not the grammar

Both fire FRG-322 at proc-macro time (FRG-322, compiled). The grammar is comma-separated identifiers, each with an optional (key = "name") list; a key and a value on the identifier itself, and a string literal in place of it, are not part of it.

Forward compatibility

The behaviors namespace is #[non_exhaustive] at the IR level — future releases add behaviors additively without breaking existing call sites. Future releases will likely add behaviors such as audit_log, tenanted, versioned, and other model-level concerns — the namespace is designed for additive growth and no specific shape is contracted at this release. Argument-bearing behaviors (e.g., #[behavior(versioned(strategy = "snapshot"))]) are explicitly not part of the 0.7.0 surface; the grammar widens additively when the first argument-bearing behavior lands.
