Ferra.rs — User Guide

Computed fields

A computed field is server-derived: it has no column, the client never writes it, and the application’s own code fills it before a response is serialised. An invoice’s total is subtotal + tax; a film’s comment_count is a query on another table.

This page is the page of the feature: the declaration, the two per-field hooks and the enum the derive hands them, what Ferra refuses, when the hooks run, the context they receive, what a failure answers, and how to make a replayed create safe.

Declare the field

A computed field carries #[sea_orm(ignore)] and #[ferra(computed)]:

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};

#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "invoices")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub subtotal: f64,
    pub tax: f64,
    #[sea_orm(ignore)]
    #[ferra(computed)]
    pub total: Option<f64>,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
impl ferra::compute::FerraComputed for Model {}
}
  • #[sea_orm(ignore)] is required (FRG-360): the table has no such column, no SELECT, INSERT or UPDATE names it, and Sea-ORM builds the field with Default. The field’s type must implement Default.
  • The field is read-only on the wire. A POST, PUT or PATCH body that names it is a 422 unknown_field, and the OpenAPI document marks it readOnly: true on every read schema.
  • It cannot be filtered, sorted or used as a cursor key (FRG-361), and cannot be combined with skip, write_only or a primary key (FRG-359).
  • A model with a computed field must write the impl FerraComputed (FRG-362).

Two edge cases follow from “no column”:

  • Every field computed except the key. The model is still valid. A read selects the stored columns only, here the key alone, and the hooks then fill each computed field, so the computed fields add no column to any statement.
  • A computed field in a projection’s write list is a compile error, FRG-324 (a declared action’s writes list is FRG-146). Neither can let a client write a computed field.

The two hooks, and the field they receive

A model with a computed field writes an impl FerraComputed for Model. The trait has two default-implemented hooks, and each is told which computed field it is to compute:

  • async fn compute_field(&mut self, field: ModelComputed, ctx: &RequestContext) -> Result<(), FerraComputeError> computes one field of one row. Default: nothing.
  • async fn compute_field_batch(rows: &mut [Model], field: ModelComputed, ctx: &RequestContext) -> Result<(), FerraComputeError> computes one field of a slice of rows. Default: compute_field on each row in turn, stopping at the first error. Override it to replace one query per row with one query for the slice.

ModelComputed is an enum the derive writes next to the model, with one variant per computed field, named in PascalCase after the field (total is ModelComputed::Total). The application matches on it and never chooses the type, so the field a hook is asked for is always one the model declares:

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use ferra::compute::{FerraComputeError, FerraComputed};
use ferra::request_context::RequestContext;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};

#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "invoices")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub subtotal: f64,
    pub tax: f64,
    #[sea_orm(ignore)]
    #[ferra(computed)]
    pub total: Option<f64>,
    #[sea_orm(ignore)]
    #[ferra(computed)]
    pub label: Option<String>,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}

impl FerraComputed for Model {
    async fn compute_field(
        &mut self,
        field: ModelComputed,
        _ctx: &RequestContext,
    ) -> Result<(), FerraComputeError> {
        match field {
            ModelComputed::Total => self.total = Some(self.subtotal + self.tax),
            ModelComputed::Label => self.label = Some(format!("invoice {}", self.id)),
        }
        Ok(())
    }
}
}

A model with a computed field must write the impl, empty or not: the derive writes it only for a model with no computed field. Without it the model does not compile, mounted or not (FRG-362).

Replace N queries with one

A field that needs I/O is computed for the whole slice at once. The slice is the page of a collection read, or one row on an item read, so the same code serves both:

#![allow(unused)]
fn main() {
use std::collections::HashMap;

use ferra::FerraModel;
use ferra::compute::{FerraComputeError, FerraComputed};
use ferra::request_context::RequestContext;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};

#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
    #[sea_orm(ignore)]
    #[ferra(computed)]
    pub comment_count: i64,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
// Stands for one query on a pool of your own (`WHERE film_id = ANY($1) GROUP BY film_id`).
async fn comment_counts(ids: &[i32]) -> Result<HashMap<i32, i64>, String> {
    Ok(ids.iter().map(|id| (*id, 0)).collect())
}

impl FerraComputed for Model {
    async fn compute_field_batch(
        rows: &mut [Self],
        field: ModelComputed,
        _ctx: &RequestContext,
    ) -> Result<(), FerraComputeError> {
        match field {
            ModelComputed::CommentCount => {
                let ids: Vec<i32> = rows.iter().map(|row| row.id).collect();
                let counts = comment_counts(&ids).await.map_err(FerraComputeError::new)?;
                for row in rows {
                    row.comment_count = counts.get(&row.id).copied().unwrap_or(0);
                }
            }
        }
        Ok(())
    }
}
}

Migrating a 0.14 implementation

Through 0.14 the trait had three methods, compute, compute_async and compute_async_batch, none told which field it computed. A synchronous computation is now written in the async body of compute_field, which matches on the field; compute_async_batch(rows, ctx) becomes compute_field_batch(rows, field, ctx). Migrating from 0.14 to 0.15 has the before and after, and the full list of breaks.

When the hooks run

Each computed field is computed per field, for the rows that serve it to this caller, and for no other row. Ferra calls compute_field_batch once per computed field and per read, with the rows for which both hold:

  • the field is in the read projection of the route (a prefix such as /lean/... that does not list total never computes it, and neither does a bare path whose default projection omits it);
  • the caller may read the field on that row: its read rule passes, with the row’s own owner for IsOwner.

A field whose slice is empty is not computed at all: its hook is not called, not even with an empty slice. A caller served total and refused label on the same row triggers the hook for ModelComputed::Total only. This holds for an item, /me, a page, a cursor page, and for Resource<M> and tx.resource alike: they apply the same gate to the read view they hand back, so a hand-written route computes what the generated route would serve and nothing more.

The hook is called on a clone of each served row, and only the field it was asked for is copied back. A hook that also sets another field, a stored field, the key or the owner changes nothing that is served: the owner the gate reads, the _links, the ETag and any Location are those of the row as it was fetched, before any hook ran.

A request that is refused (401, 403, 404, 422, …) computes nothing.

A write response (a create, a PUT, a PATCH, a restore, a row action) serves the same computed values a GET would, computed after the commit and after after_commit, on the row as written. It computes only when it serves a body: not for Prefer: return=minimal, not for a 201 or 204 sent without a body to a caller who may not GET the row, and not for a DELETE or a collection action. The Location, the ETag and the _links are those of the row as written, before any hook ran. Resource::create and Resource::update compute the row they return the same way.

A value is never computed for a caller who may not Get the row: whether the get rule refuses it or the authority’s can(Get) does, the hook is not called for that caller. That holds for Resource::create and Resource::update too, where the view is still returned: the field stays at its default (None where the view types it Option) and the view is meaningless, so do not echo it to a caller who may not read the row (an Option<Read> is planned for 0.17.0).

A write made by tx.resource computes inside the open transaction, as its reads do: a hook sees its own transaction’s state, which may still roll back. The after-commit rule governs only what is served to a client.

The write is already committed when a write response computes. If that compute fails, the answer is a 500 and the row stands (see When a hook fails); a client that replays the POST can create a duplicate. Idempotent creates shows how to make a replay safe.

A hook is an output path. It can read any field of the row, including a column the API never serves (skip, write_only) or a field under a stricter read rule, and what it computes is served under the computed field’s own read rule. A computed field derived from a hidden or rule-guarded field therefore needs a read rule at least as strict as the field it derives from: otherwise it hands to any reader what the source would have refused them.

The context

The ctx a hook receives is the request’s own RequestContext: the caller (ctx.subject(), ctx.has_role(..)), the typed claims, the API key identity and the request headers. A model with a computed field gets it filled, as a model with an authority or hooks does; Resource<M> hands the hook the context of the request it was extracted from, and tx.resource the context of the outer write.

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use ferra::compute::{FerraComputeError, FerraComputed};
use ferra::request_context::RequestContext;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};

#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "invoices")]
#[ferra(auth = "bearer")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub subtotal: f64,
    #[sea_orm(ignore)]
    #[ferra(computed)]
    pub viewed_by: Option<String>,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}

impl FerraComputed for Model {
    async fn compute_field(
        &mut self,
        field: ModelComputed,
        ctx: &RequestContext,
    ) -> Result<(), FerraComputeError> {
        match field {
            ModelComputed::ViewedBy => self.viewed_by = ctx.subject().map(str::to_owned),
        }
        Ok(())
    }
}
}
  • Credentials never reach it. Authorization, Proxy-Authorization, Cookie and the Foundry’s API key header are dropped when the context is built: ctx.header("authorization") answers None. The API key’s identity is there, the key is not.
  • Every other header is client-supplied. Never authorize on Host, X-Forwarded-*, Forwarded or Origin, and never build a URL or a link from them: a computed value is served in the response body, so a value derived from a header the client chose is a value the client chose.
  • Resource<M> and tx.resource apply the gate above. tx.resource reads inside the write’s transaction, so a hook of the write that reads a row of another computed model computes it there, for the caller of the write, with the outer request’s context (not a context built for that other model).

See RequestContext for the accessors.

When a hook fails

A hook that returns Err(FerraComputeError), or panics, fails the request. The answer is 500 internal with the fixed body ("internal server error"), and no part of the response is served: the rows computed before the failing one are dropped, never sent. A panic is caught, so the connection stays up.

Ferra writes one error! line for the request, not one per row, on the target ferra_http::hooks. It names the model (model) and the operation (operation: get, list, create, update, restore or action) and carries your FerraComputeError message as error, as the message of a HookError is logged: it is yours to keep free of values the logs must not hold. Ferra adds no row value of its own. A panic is logged as a computed field panicked, without its payload. The catch needs panic = "unwind": with panic = "abort" a panicking hook ends the process.

On a write the 500 does not undo anything: the row exists, the same as when after_commit fails. A client that replays the request can create a duplicate. From the first commit of the request on, every hook runs under what is left of the request budget (without a budget, nothing bounds it) and a cut answers 500, never 503 timeout, because that answer says that nothing was written. That holds for a write response, and also for a read of a hand-written route after a Resource::create or an update of the same request, and for a tx.resource write in the hook of a later write. Before any commit the budget layer cuts the request itself with 503 timeout, and the transaction rolls back.

Idempotent creates

Ferra has no generic Idempotency-Key header. A client that cannot tell whether a POST was committed (a timeout, a 500 after the commit, a lost response) replays it, and a replay can create a duplicate. The recipe below makes the replay safe for the creates that carry a request key, with the database’s own UNIQUE constraint and nothing else from Ferra. A generic header would be additive and has its own trigger; it is not tied to the transactional outbox planned for 1.1.0.

The recipe covers creates that carry a request key. An update, a delete or an action that has an unknown outcome is recovered through its own contract (If-Match for a row’s tag, for instance), not through this recipe.

The model

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};

#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "keyed_orders")]
#[ferra(auth = "bearer")]
#[behavior(soft_delete)]
#[authorize(
    get = IsOwner,
    list = IsOwner,
    create = Authenticated,
    update = IsOwner,
    delete = IsOwner
)]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    #[field(owner)]
    pub owner_id: Uuid,
    #[field(filterable)]
    pub request_key: String,
    pub item: String,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}
CREATE TABLE keyed_orders (
  id SERIAL PRIMARY KEY,
  owner_id UUID NOT NULL,
  request_key TEXT NOT NULL,
  item TEXT NOT NULL,
  deleted_at TIMESTAMPTZ NULL,
  UNIQUE (owner_id, request_key)
);

The client chooses request_key (a UUID per intended order is the usual choice) and sends the same one on every replay. Four parts of the declaration carry the guarantee:

  • request_key is NOT NULL. Postgres treats two NULL as distinct, so a row without a key would never collide with another and the constraint would guarantee nothing for it.
  • owner_id is set by the server. #[field(owner)] stamps it from the caller’s identity; a body that names it is a 422 unknown_field. The client cannot create a row in another owner’s name, nor choose which owner’s keys it collides with.
  • The owner is in the constraint. With UNIQUE (request_key) alone, a key would be global: one owner’s POST would answer 409 because another owner holds the key, an existence oracle across owners, and one owner could take another’s keys. With UNIQUE (owner_id, request_key) two owners can use the same key; each gets their own row, and neither learns that the other exists.
  • The read rules are part of the recipe. #[field(owner)] stamps the owner but does not scope reads. get = IsOwner and list = IsOwner are what keep the recovery GET to the caller’s own rows. Without them the recipe is unsafe: GET /keyed_orders?filter[request_key]=<key> returns another owner’s row, a cross-owner leak that doubles as a key-guessing oracle.

What a replay answers

A POST whose owner and key already hold a row answers 409 conflict, with the fixed detail of every conflict (it names no constraint, column or value), and nothing is written. Two concurrent POSTs with the same key give one 201 and one 409; the database decides, so there is no check-then-insert race.

A 409 is never a success. The constraint compares the owner and the key, never the body. A replay with a different body is a 409 too, and the stored row stays as the first request wrote it. A client that gets a 409 has not learned that its request was applied; it recovers the row and compares.

The recovery GET

GET /keyed_orders?filter[request_key]=<key>

returns the row to its owner, and an empty list to any other caller. A client that gets the 409 (or never saw the first answer) reads it back, checks that the item is what it meant to send, and carries on with that row’s:

  • id;
  • ETag;
  • _links.

A deleted row

  • soft_delete keeps the key. A soft-deleted row stays in the table, so its key stays taken: a replay answers 409, and the recovery GET, which leaves deleted rows out, returns nothing. The client has a 409 and nothing to recover. This is a limit of the recipe, not a bug: pick a new key for a new order, or restore the row (POST /keyed_orders/{id}/restore).
  • A hard delete frees the key. On a model without soft_delete, deleting the row removes the key with it, and a late replay creates a second row. The guarantee lasts as long as the key stays recorded. Use soft_delete for this recipe, or accept and state that window.

Not the same: client_pk

A model with #[ferra(client_pk)] lets the client choose the primary key in the create body, and a client could use it as a request key. It is not equivalent. The primary key is unique across the whole table, with no isolation per owner: a collision answers the same 409 conflict, whoever holds the row, so it tells a caller that some owner already uses the key. It also forces the client’s value into the key of the resource’s URL. Keep the recipe’s request_key column for replays.

What If-Match does not guard

If-Match guards PUT, PATCH, DELETE, restore and row actions. It guards no create (there is no row yet, so no tag to send) and no Resource<M> route of your own: the route creates or updates through Resource<M> under its own contract. A create made by a route of your own needs its own key and its own constraint.
