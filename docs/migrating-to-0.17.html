Ferra.rs — User Guide

Migrating from 0.16 to 0.17

0.17.0 (Soaking) makes a service under load answer what it can, and says so when it cannot. Each entry below is a change you may notice. This page grows with the release: read the entries, then update the application’s git dependency to v0.17.0. CHANGELOG.md lists every change.

A pool that gives no connection answers 503, not 500

Before. A request that waited for a database connection longer than the pool’s acquire_timeout answered 500 internal, the same as any database failure.

After. It answers 503 service_unavailable, with the fixed detail “the service could not handle the request in time; this operation was not applied”, and no Retry-After. The answer comes before the operation: nothing was applied and no hook ran, so the client may retry (an earlier write of a route of your own stands). A database that is down or starting gives the same 503 once the acquire_timeout elapses, because the pool retries a refused connection until then. A connection the database refuses at once (a wrong password, an unknown database) stays a 500 internal. One warn line, target ferra_db::pool, holds the resource and a fixed text. The OpenAPI document now declares the 503 (the one ServiceUnavailable response) on every operation, a read as well as a write. After a commit, if the pool gives no connection for the parents of the row just written, the answer is still a 500 with one error line, because the write stands.

Who is affected. A client, a gateway or an alert that treats 500 as “the service is broken” and 503 as “retry later”, or that matches the 500 of a saturated pool. A client generated from the OpenAPI document, which now sees a 503 on every operation, must be regenerated.

Migration. Treat 503 service_unavailable as transient: retry it with a backoff and full jitter, since no Retry-After is sent. Move any alert on a pool 500 to the 503 and to the ferra_db::pool line. Set the pool’s acquire_timeout under the request budget, so that the pool answers and not the budget’s timeout. See service_unavailable.

A failed COMMIT writes one ferra_db::commit line

A COMMIT the database fails no longer writes the generic “a database error answered 500” line (target ferra_http::error); it writes one ferra_db::commit error line with resource, outcome and db.response.status_code, and the answer is still the 500. An alert on the old line goes quiet for a failed COMMIT: move it to the new target.

Resource and TxResource create and update return Option<Read>

Before. Resource::create, Resource::update, TxResource::create and TxResource::update returned Result<Read, FerraError>: the row the call had written, whether or not the caller could read it. A route that echoed it sent a row the generated route would have kept back.

After. They return Result<Option<Read>, FerraError>. None means the row is written and the caller may not read it under the generated route’s rule: the get rule on the row, then the authority’s can(Get), mounted or not. An authority that panics or fails on the written row counts as “may not read” (one error line on ferra_http::policy; panic = "abort" defeats the catch). When it is None nothing derived from the row leaves the call: no computed field is called. The generated route answers that caller 201 or 204 with no body, no Location and no id in any header; your route should too. None comes only after a successful write: a refusal, a validation error and a row the caller cannot reach for update (the absent row’s 404) stay an Err, as before. SystemAccess::insert and SystemAccess::latest are unchanged: they return the whole row, read-checked by nothing, and it never belongs in a response.

Who is affected. Code that uses the value of one of the four calls: a route of your own, and a hook that reads what tx.resource::<N>().create(..) or .update(..) returns. A call whose value you drop (.await?;) compiles unchanged.

Migration. Replace let row = films.update(id, patch).await?; by let Some(row) = films.update(id, patch).await? else { return Ok(StatusCode::NO_CONTENT.into_response()) }; (a create answers StatusCode::CREATED there, with no Location). A handler that answers Json(films.create(v).await?) now sends null for None: answer a status with no body instead. See Custom handlers.

A handler panic answers 500 internal, not a closed connection

Before. A panic in a generated route, in a route of your own added with .route before build(), in an extractor or in a layer of the stack ended the connection: the client saw no response, and the operator’s error rate, the request metric and the request span omitted the request.

After. The panic answers 500 internal with the constant body, Cache-Control: no-store and Vary. The request is observed once, with error.type 500 and ferra.error.type internal (with the observability feature), and one error line, target ferra_http::observe, “a handler panicked”, is written. The panic’s message is client-influenced text: it is in no body, label, span field or tracing line. The process’s panic hook (stderr by default) still prints it. The answer is made outside the per-model CORS layer, so it carries no Access-Control-Allow-Origin: a browser on another origin sees a CORS failure, not the 500. A row committed before the panic stands. panic = "abort" in your profile defeats the catch: the process ends. A route merged into the router after build() is outside the stack and is not caught.

Who is affected. A client or a gateway that treated a closed connection as the signal of a handler bug, and an alert that counted such closures: the panic is now a 500 in the metrics and the span.

Migration. Alert on 500 and on the ferra_http::observe line. Do not rely on a panic to cancel a write: a panic after a commit leaves the row written. See Custom handlers and internal.

Every response writes one ferra_http::request line

Before. The only line a request wrote was the one tower_http wrote in a model’s own stack, so a 401, a 404 for an unknown route and the 503 of .request_budget(..) wrote none, and an operator who set tower_http to a quiet level silenced what there was.

After. From 0.17.0 each response writes one tracing event, target ferra_http::request, inside the request span. Its fields are http.request.method, http.route, http.response.status_code, ferra.error.type and latency_ms, and nothing else: no path, query, header, token, claim, body or cookie value. http.route is absent when no route matched, and ferra.error.type when the answer is not a Ferra problem. The level follows the status: error for 500, warn for 503, info for everything else, so a 502 or 504 your own handler answers is info (alert on error.type on the histogram or the span). The refusal events and the lines of 0.17.0’s pool and COMMIT work (ferra_http::credential, ferra_http::auth, ferra_http::rate_limit, ferra_db::pool, ferra_db::commit, ferra_http::error) are unchanged and are written beside it.

Who is affected.

  • An operator who filtered tower_http to keep the logs short: that filter no longer silences the request line, which has its own target, and the default trace layer no longer writes its tower_http line. Every request writes one, GETs included, so set ferra_http::request to the level you want (RUST_LOG=ferra_http::request=warn keeps the 503 and the 500).
  • A test or an alert that counts the error lines of a 500: the request line is one more, at error. Select by target (ferra_http::request or not) rather than by level alone.

Migration. Add ferra_http::request to the log filter, and move an alert on a tower_http access line to it. The line, its levels and the other targets are in observability.md.

The request span has one name per attribute, and api_key.prefix is gone

Before. Each model’s own stack opened a span named request with the fields method, path, credential and, for an accepted API key, api_key.prefix. A 401, a 404 for an unknown route and a hand-written route had none, and a 500 also wrote the ERROR event “response failed” from tower_http.

After. From 0.17.0 one span per request is opened by the layer build() puts outside everything, so it exists for every response, and the per-model span and its INFO line are gone. Its attributes are a closed set, in the names of OpenTelemetry’s HTTP semantic conventions:

BeforeAfter
methodhttp.request.method (_OTHER for an extension method)
pathurl.path (the path as received, percent-encoded, no query)
credentialcredential, unchanged (token, cookie or api_key); recorded only for a credential Ferra verified
api_key.prefixdropped from the span; the prefix is on the warn of a refused key (ferra_http::credential)
(none)otel.name, otel.kind, http.route, network.protocol.version, http.response.status_code, ferra.error.type, and on a 5xx error.type and otel.status_code

A write also has four child spans: ferra.authorize, ferra.hook (with hook), ferra.db.write (one per attempt, so the number of them shows the retries) and ferra.after_commit. Each carries resource and operation and no outcome, id, SQLSTATE or error text. The ERROR event “response failed” is gone: a 500 is the request line at error.

Who is affected.

  • A subscriber or a collector that masks, drops or indexes the field path: it must now name url.path, or the path is no longer masked (SEC-047). The same goes for method → http.request.method.
  • A dashboard or an alert on api_key.prefix of an accepted request: no span carries it any more. A refused key still writes its prefix on the warn.
  • A layer you pass to FerraLayer::trace_layer still runs, beside the request span and its line; the default one, which wrote the old span and the old line, is gone.

Migration. Rename path and method in the masking and indexing rules, move an alert on the old line to ferra_http::request, and read the credential kind from credential on the request span. The span and its phase spans are in observability.md.
