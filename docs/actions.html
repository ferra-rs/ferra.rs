Ferra.rs — User Guide

Declared actions

A business verb on a row, served and judged by Ferra. POST /jobs/{id}/mark_seen, POST /invoices/{id}/cancel: a model declares the action, writes the function that changes the row, and Ferra serves the route on the bare path with what a PUT gets: the rule, the lock, the preconditions, the validation of what the function returned, the write, the hooks, the retry, the ETag and the _links; the action has its own OpenAPI operation. 0.14.0.

This page covers the row action, and the collection form (collection): the same action on up to 100 rows in one request. A route that is not a row’s verb (a webhook, an aggregate, a derived list) stays a custom handler.

Declaring an action

One #[ferra(action(...))] per action, on the model, next to the derive. It is repeatable, in one or several #[ferra(...)] attributes. The handler is a function you write, named by handler = path.

use ferra::{ActionBody, FerraModel};
use ferra::hooks::{HookError, HookTx};
use ferra::request_context::RequestContext;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "jobs")]
#[ferra(auth = "bearer")]
#[ferra(action(name = "mark_seen", authorize = IsOwner, handler = mark_seen))]
#[ferra(action(
    name = "set_progress",
    authorize = IsOwner + HasRole("etl"),
    handler = set_progress,
    body = ProgressBody
))]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    #[field(owner)]
    pub owner_id: Uuid,
    pub title: String,
    pub seen: bool,
    pub progress: i32,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}

/// The handler receives the locked row and returns its new state.
async fn mark_seen(
    mut job: Model,
    _ctx: &RequestContext,
    _tx: &mut HookTx<'_, Model>,
) -> Result<Model, HookError> {
    if job.seen {
        return Err(HookError::conflict("the job is already seen"));
    }
    job.seen = true;
    Ok(job)
}

/// The body of `set_progress`, decoded and handed over as the second argument.
#[derive(Deserialize, ActionBody)]
pub struct ProgressBody {
    #[field(min = 0, max = 100)]
    pub progress: i32,
}

async fn set_progress(
    mut job: Model,
    body: ProgressBody,
    _ctx: &RequestContext,
    _tx: &mut HookTx<'_, Model>,
) -> Result<Model, HookError> {
    job.progress = body.progress;
    Ok(job)
}
fn main() {}

Mount the model as any other (.mount::<job::Model>(), Foundry); the actions need no setting of their own, but a rule that needs an identity (IsOwner, HasRole) needs .with_auth() on the Foundry, as for any write.

collectionflagOptional. Serves the action on POST /{resource}/{name}, for several rows: Collection actions.

The derive refuses a bad declaration at compile time, with the code and the line of your attribute: FRG-139 (a name outside the grammar or reserved), FRG-140 (two actions with one name), FRG-141 (an unknown or repeated key), FRG-142 (a missing name, authorize or handler), FRG-143 (collection on a composite key), FRG-144 (an action on a system_only model), FRG-145 (a body type that cannot be one) and FRG-146 (a writes entry the action cannot write). The rule’s own errors are FRG-101 to FRG-103 and FRG-110. The codes each have a section. A wrong handler path, a wrong handler signature or a body = T without the derive is rustc’s error, spanned on the path or the type you wrote. At Foundry::build(), two operations that get one operationId, or two body components with one name, are refused by FRG-153.

The rule

authorize is the action’s own rule, in the grammar of #[authorize(...)] (IsOwner, HasRole("etl"), Authenticated, Anyone, +, |; Authentication and Authorization).

  • It replaces update’s. An action does not borrow the rule of PUT, nor the posture, nor the #[authorize] block: an owner who may PUT a row may not run an action whose rule refuses them, and the reverse.
  • It is required, whatever the posture. There is no default rule and no deny-by-default shortcut: auth = "none" does not excuse the key (FRG-142). Anyone is a rule you write knowingly.
  • It is judged like every rule. A rule that needs an identity needs .with_auth() (FRG-151), IsOwner needs a #[field(owner)] (FRG-110), and a rule that reads no row (HasRole("etl") alone) is refused with a 403 before any row is read, the same bytes for a row that exists and one that does not.
  • An authority sees it. A model with #[ferra(authority)] gets can(Operation::Action(name), row) on the locked row and again on the row as the handler wrote it; its filter hides rows from the action as it does from get. End your can with _ => false and name each action you allow.

The handler

async fn(Model, &RequestContext, &mut HookTx<'_, Model>) -> Result<Model, HookError>

With a body, the decoded body is the second argument: async fn(Model, Body, &RequestContext, &mut HookTx<'_, Model>).

The handler gets the row locked, as it stands, and returns the row as it should be. Ferra compares the two, writes the columns that differ in the same statement and transaction as a PUT, and runs the model’s hooks around it (before_save sees Saving::Update, after_commit sees Committed::Updated). RequestContext is the caller; HookTx is the handle on the same transaction (tx.resource::<Other>(), tx.system(): Hooks). The handler runs while the row is locked and the request budget runs: keep it short, and leave the external effects (an e-mail, a queue, a call to another service) to after_commit.

A handler runs under the same rules as a hook:

It returnsThe answer
Ok(row)the row is judged and written (what it may change)
HookError::failed(msg), or a ? on a FerraError500 internal, the generic body; nothing written
HookError::conflict(detail)409 conflict, your detail as given
HookError::unprocessable(field, code, message)422 validation_failed, one error
HookError::unavailable(detail)503 service_unavailable, your detail, no Retry-After
a panic500 internal, the generic body

Every Err rolls the write back. The detail of a 409, a 422 or a 503 reaches the caller as you wrote it: put no value in it that the caller may not read. A failed handler is logged at error level, target ferra_http::hooks, as “action handler failed”, with the resource, the action, the message you gave and, for a database error, its SQLSTATE: never a row value. That is one error! line for a HookError::failed, and two for a ? on a FerraError, whose conversion logs “a hook propagated a FerraError; answered 500” first, with the status, the problem type and the SQLSTATE of the error. A panic is caught, answered 500, and logged (one error! line) as “action handler failed” too, whose error field is the constant text “an action handler panicked”, without the panic’s payload in Ferra’s log; the standard panic hook still prints it to stderr unless the application replaces it. panic = "abort" in the release profile defeats the catch, as for a hook.

The typed body

An action takes a value when it declares body = T. T derives ActionBody next to Deserialize: #[derive(Deserialize, ferra::ActionBody)], no #[serde(...)] attribute. The body is read by the Rust names of the fields (a model’s rename_all does not apply to it), and its list of fields is the one source of the unknown_field refusal, the validation and the OpenAPI schema. What a body admits (scalar fields, the eight validation keys) is in Ferra Forge.

The content is read once, judged before the handler runs, kept, and decoded again at each call of the handler, a retried attempt included. An action with no body reads no content: whatever a client sends is ignored.

A field that is not an Option is required by its type: a body that leaves it out is a 400 invalid_json, because the body does not deserialize, and not the 422 required of a PUT.

On a collection action the typed body is the member "body" of the request, and a key of the typed body is named body.<key> in an error (body.progress); a row action’s body is the whole request, so its keys keep their own name.

What a request is refused with

Each refusal comes before the next one, and none of them calls the handler or a hook, or changes a row. Cookie requests also face the CSRF guard, and the rate limiter answers 429, as for every write.

#ConditionAnswer
1no credential, or an invalid one, where the model reads tokens401
2the rule fails without reading a row (HasRole("etl") alone)403
3the row is absent, soft-deleted, hidden by IsOwner, by the authority’s filter or by can(Action(name))404, the bytes of an absent row (detail <resource>/<id> not found)
4the part of the rule that reads the row fails403
5the action has a body and the Content-Type is not JSON415
6If-Match or If-None-Match does not hold on the locked row, or is malformed or lists more than 32 tags412 precondition_failed

The 404 of a row comes before every precondition, If-Match: * included, so a header never tells a caller anything about a row they cannot see. An announced Content-Length over the cap is refused 413 earlier still, right after the credential check and before the row is looked up, even for an action with no body. The preconditions are the ones of every write, decided on the locked row. Then the handler runs, and its answer and the checks below follow.

What the handler may change

The row it returns is judged against the row it was given, in this order. Nothing is written when one fails.

  1. The key, the owner and the owner(from) foreign key stay. A handler that changes any of them is a bug of yours: 500 internal, the generic body, one error! that names the model, the action and the column and no value. (The foreign key is immutable since 0.16.0: delete the row and create it again to move it.)
  2. The field rules apply. A changed field the caller may not write on the bare PUT is a 403: a read_only or computed field, or a field whose write rule the caller does not meet. A field the handler leaves alone is never judged. A field the action lists in writes is the exception.
  3. The validators apply to the changed fields: a 422 that names the fields the caller may read; a 500 with the generic body when only fields the caller may not read fail, logged with their names.
  4. The parent chain. On a model with owner(from = ..), the foreign key is never written by an action: a handler that changes it is the 500 of point 1.
  5. Its own row stays untouched. A handler or a hook that updates, soft-deletes or deletes the row it was given through tx.resource is a 500 with the generic body, never a 404 (A hook cannot write its own row). Other models’ rows, written through tx.resource, are written under the caller’s rules. The exception is a row the write holds FOR SHARE, the parent of a child’s hook: the write is refused (A child’s hook cannot write the parent it holds). A parent’s action holds its row FOR UPDATE, so it may write its children, and the parent itself stays its own.
  6. can(Action(name)) on the row as written. An authority that refuses the new state is a 403.

A returned row equal to the locked one writes nothing: no UPDATE, the same ETag, the hooks still run.

writes

A read_only field is closed to every caller, and a field with a write rule is closed to the callers who fail it. An action that must set one lists it: writes = [status]. The field is then set under the action’s own rule, which has already passed by the time the handler runs, and not under the field’s.

use ferra::FerraModel;
use ferra::hooks::{HookError, HookTx};
use ferra::request_context::RequestContext;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "tickets")]
#[ferra(auth = "bearer")]
#[ferra(action(name = "close", authorize = HasRole("support"), handler = close, writes = [status]))]
#[ferra(action(name = "reprioritize", authorize = HasRole("support"), handler = reprioritize, writes = [priority]))]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
    #[ferra(read_only)]
    #[field(max_length = 8)]
    pub status: String,
    #[field(write = IsAdmin)]
    pub priority: Option<i32>,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}

async fn close(
    mut ticket: Model,
    _ctx: &RequestContext,
    _tx: &mut HookTx<'_, Model>,
) -> Result<Model, HookError> {
    ticket.status = "closed".to_owned();
    Ok(ticket)
}

async fn reprioritize(
    mut ticket: Model,
    _ctx: &RequestContext,
    _tx: &mut HookTx<'_, Model>,
) -> Result<Model, HookError> {
    ticket.priority = Some(1);
    Ok(ticket)
}
fn main() {}
  • What it opens. Only the fields it names, and only to the action that lists them. close sets status for a support agent, and reprioritize sets priority for one who is not an admin; neither opens the other’s field, and an action that lists nothing and changes status is a 403, as before.
  • To whom. To the callers the action’s rule admits, and to them alone. The field’s write rule is not asked of them in this action.
  • What it keeps. The field’s #[field(...)] rules apply to the value the handler returns: a status over eight characters is a 422 that names it, and nothing is written. The row’s other checks are unchanged (What the handler may change).
  • What it never opens. A PUT, a PATCH or a POST never reads writes: a client that sends status gets the 422 unknown_field it got before, and one that sends priority is judged by the field’s own write rule (Field rules). The key, the owner, the foreign key behind owner(from = ..), a computed field and a skip field cannot be listed: that is FRG-146, at compile time, and so is a field that anyone who may write the row can already write, or a name the model does not have.

The answer

  • 200 with the row, as GET serves it to this caller: the read projection of the bare path, the ETag of the new state, the _links. No Location.
  • 204 with the ETag under Prefer: return=minimal.
  • 204 with no body, no ETag and no Location when the caller may not GET the row as written: the write stands, and nothing of the row is told.

Retries and the request budget

When the database aborts the write with 40001 or 40P01 (at the statement or at COMMIT), Ferra runs the whole action again: the lock, the preconditions, the handler, the hooks. Three attempts, then a 503 retry_exhausted with Retry-After: 1, and the action was not applied. Details and constants: Transient conflicts are retried.

So a handler must be re-runnable:

  • No external I/O before the commit. A message, an HTTP call or a file written from the handler goes out once per attempt, and for an action that is then rolled back. Work on the database through tx, which the abort rolls back; send effects from after_commit, which runs once, for the attempt that committed.
  • Keep no state between attempts. A counter or a flag changed in the application is changed once per attempt.
  • A precondition is decided again. If another writer committed between two attempts, the new attempt locks the new row, and a stale If-Match is a 412.

Set a request budget. Without one, only the three attempts bound the work. With one, the deadline cuts a handler at its next .await before the commit starts (503 timeout, nothing written); a handler that blocks the thread without awaiting is not cut, and neither is a commit once it has started.

Sending the same request twice

Ferra does not deduplicate a request, and there is no Idempotency-Key. If-Match is the guard against running an action twice:

  • A client that sends the ETag it read as If-Match and gets no answer can send the same request again. If the first one committed a change, the row has a new tag and the replay is a 412: it ran once.
  • An action that changed nothing leaves the tag as it was, so the replay passes and the handler runs again.
  • Without If-Match, the handler runs again.

Write the handler so that running it twice on the same row is harmless, or make the client send If-Match.

_links.<name>

A served row carries _links.<name> for each action the caller may run on that row, only when self is present: the action’s rule and can(Action(name), row) both pass, judged in memory from the row in hand, with no statement. The href is the action’s bare path (/jobs/1/mark_seen), whatever projection prefix served the row. A link is a hint: following it is judged again by the route.

{
  "id": 1,
  "seen": false,
  "_links": {
    "self": { "href": "/jobs/1" },
    "collection": { "href": "/jobs" },
    "mark_seen": { "href": "/jobs/1/mark_seen" }
  }
}

Collection actions

collection in the attribute serves the action on POST /{resource}/{name} (POST /jobs/mark_all_seen): one request runs the handler on up to 100 rows of the model, in one transaction. The rule, the handler, the typed body and writes are those of a row action; the handler runs once per row, in the order of the keys. A model with a composite key cannot declare one (FRG-143).

The request is an envelope, a JSON object with the Content-Type application/json:

{ "ids": [3, 7, 12], "body": { "progress": 40 } }
  • ids is required: one to 100 distinct keys of the model’s key type, in any order. An empty list is 422 min_items, a key listed twice is 422 unique_items and a list over 100 is 422 max_items; a missing ids is 422 required; an id of the wrong JSON type or that does not parse as the key is 400 invalid_json. The message never holds an id.
  • body is the typed body, required when the action declares one (422 required) and the same for every row. An error of the typed body names its key body.<key> (body.progress). A key other than ids and body is 422 unknown_field, and so is body on an action that declares none.
  • A key repeated in the envelope (ids twice) or in the typed body is 400 invalid_json.
  • If-Match: * passes and If-Match with a tag is a 412: no tag is served for a batch. If-None-Match: * is a 412 and If-None-Match with tags passes. Prefer is ignored.

The order of refusals is the row action’s, with the envelope judged first: 401, then 413 for an announced Content-Length over the cap, 403 (a rule that reads no row), 415, 412, 413 for a body read over the cap, 400, the 422 of the envelope and of the typed body, then the rows. None of them calls the handler.

  • One 404, naming no id. If any listed row is absent, soft-deleted or hidden from the caller (IsOwner, the authority’s filter, can(Action(name))), the answer is one 404 with the status, type, title and headers of an absent row’s, and the detail <resource> not found, whatever the number of rows or which one: the rows are locked in one read, in key order, so the number of statements does not tell either.
  • All or nothing. A 403 on one row (the part of the rule that reads the row, a field the action may not write, can(Action(name)) on the row as written), a handler error, a failed validator: the whole batch is rolled back and nothing is written. The first error is the answer. The checks of What the handler may change run on every row.
  • after_commit once per row, after the commit of the batch, for each row that was committed, even if the hook of one row fails (the answer is then the first error).
  • The batch is the retried unit. On 40001 or 40P01 the whole batch runs again, the handlers and hooks of every row with it (Retries and the request budget). The rows are locked in key order, so two batches that list the same rows in opposite orders do not deadlock. On a model with owner(from = ..) the distinct parents are locked FOR SHARE first, in key order, so a batch and a child write do not either (Relations). Set a request budget: without one, a batch of 100 rows holds its locks as long as its handlers run.

The answer is 204, with no body, no ETag and no _links: a batch serves no row. A collection action never appears in _links.

On a model whose key is a String, POST /{resource}/{name} is a literal route: GET, PUT, PATCH and DELETE /{resource}/{name} answer 405, and a row whose key equals the action’s name is unreachable on those methods. Pick a name no row will have as a key.

OpenAPI

Each action is one POST operation on the bare path, in the document exactly as the router serves it: /{resource}/{id}/{name} for a row action, /{resource}/{name} for a collection action. The operationId is the name in lower camel case followed by the model (mark_seen on Job is markSeenJob); the suffix of a promoted default projection, and the version prefix, are added as for restore. A body is a component named {Pascal(operationId)}Input (SetProgressJobInput), additionalProperties: false. The responses of a row action are 200 and 204, 400, 401 where the model reads tokens, 403, 404, 409, 412, 422, 429 unless the limiter is off, 500 and 503; 413 and 415 only for an action with a body. A collection action answers 204 (no ETag) and the same errors, 413, 415 and 422 included, since its envelope is a body, the component {Pascal(operationId)}Request (AckAllJobRequest): minItems: 1, maxItems: 100, uniqueItems: true on ids, and body a $ref to the component when the action declares one. The details are in Ferra OpenAPI.

Under a projection prefix

An action is served on the bare path only. /{prefix}/{resource}/{id}/{name} (/{prefix}/{resource}/{name} for a collection action) under a projection prefix answers 404 or 405, and the handler does not run.
