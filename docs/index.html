Ferra.rs — User Guide

Introduction

Ferra is a Rust framework for building HTTP APIs from a single source of truth: a Sea-ORM entity with one derive, #[derive(FerraModel)]. From it Ferra derives the routes, the SQL queries, the OpenAPI document, the documentation page, the hypermedia links and the authorization checks, at compile time. If the struct changes, everything downstream changes with it. If the generated code would be inconsistent, the build fails.

The priorities, in order, are security, developer experience, and the experience of the AI agents that write code against Ferra. Where they pull apart, security wins: a model declares who may do what, and a route that has no rule is refused, not served.

The problem Ferra solves

Building a conventional REST API means describing the same data structure multiple times:

  • once in a migration file (the database schema),
  • once as a Rust struct (the model),
  • once in each handler (request body, response type, SQL query),
  • once in OpenAPI annotations (#[utoipa::path(...)], response schemas),
  • once in validation rules.

Every copy can drift from the others, and none of these mismatches are caught at compile time. A field renamed in the struct but not in the OpenAPI annotation is a silent documentation lie. A validation rule missing from one handler is a silent security gap.

Ferra collapses the copies into one struct:

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "bearer")] // every operation requires a valid token
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    #[field(min_length = 1, max_length = 255, filterable, sortable)]
    pub title: String,
    #[field(min = 1888, max = 2100)]
    pub year: i32,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

(The hidden lines are the imports and the Relation enum that every Sea-ORM entity carries; Getting started shows a complete file.)

What you get

Mount the model on a Foundry, give it a JWT configuration, and serve it:

use ferra::{ClaimCheck, FerraIdentity, FerraModel, Foundry, HmacAlgorithm, JwtConfig};
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod film {
    use super::*;
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "films")]
    #[ferra(auth = "bearer")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub title: String,
    }
    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}
    impl ActiveModelBehavior for ActiveModel {}
}
#[derive(Clone, Debug, Deserialize)]
struct MyClaims { sub: String }
impl FerraIdentity for MyClaims {
    fn id(&self) -> &str { &self.sub }
    fn has_role(&self, _role: &str) -> bool { false }
}
#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let conn = sea_orm::Database::connect(std::env::var("DATABASE_URL")?).await?;
    let jwt = JwtConfig::single_secret(
        "key-1",
        std::env::var("JWT_SECRET")?,
        HmacAlgorithm::Hs256,
        ClaimCheck::expect("https://auth.example.com/"),
        ClaimCheck::expect("films-api"),
    )?;
    let app = Foundry::new(conn)
        .etag_key(std::env::var("ETAG_KEY")?)?
        .with_auth::<MyClaims>(jwt)
        .mount::<film::Model>()
        // Public in development: /docs needs no token (see `with_docs_protected` in ferra-openapi.md).
        .with_docs()
        .build();
    let listener = tokio::net::TcpListener::bind("0.0.0.0:3000").await?;
    axum::serve(
        listener,
        app.into_make_service_with_connect_info::<std::net::SocketAddr>(),
    )
    .await?;
    Ok(())
}

Running it gives you all of the following, with no further code.

CRUD routes

MethodPathDescription
GET/filmsPaginated collection, ?page=1&per_page=20 (filter[...], sort and cursor for the fields that opt in)
GET/films/{id}One resource by key
POST/filmsCreate: 201 and a Location header; the server chooses the key
PUT/films/{id}Update the row the path names: 200, or 404
PATCH/films/{id}Change the fields the body names (application/merge-patch+json) and leave the others: 200, or 404
DELETE/films/{id}Delete: 204, or 404

Pagination is first-class. The collection endpoint answers a page envelope with items, total, page, per_page and, in the HAL representation, the _links for self, next, prev, first and last; Pagination has the cursor mode.

Authorization that refuses by default

Every route passes one checkpoint before the path, the query or the body is read. A model with no declared posture does not compile (FRG-100), a model that needs an identity does not mount on a chain without .with_auth() (FRG-151), and #[authorize(...)] states a rule per operation (IsOwner, HasRole(...), Authenticated, Anyone), with the owner of a row read from the token. Authentication and Authorization is the page.

Hypermedia _links in the HAL representation

By default, and with Accept: application/hal+json, every item response includes a _links block following the HAL standard, so that clients and AI agents can navigate the API without prior knowledge of its URL structure. Accept: application/json gets the same body without it (Response representations):

{
  "id":    1,
  "title": "Amélie",
  "year":  2001,
  "_links": {
    "self":       { "href": "/films/1" },
    "collection": { "href": "/films" }
  }
}

The links, like the Location header, are relative by default: resolve them against the URL you called. The request’s Host and X-Forwarded-* headers are never read, so that a client cannot make the API emit links to another origin. Configure the public origin once with .with_base_url("https://api.example.com")? for absolute links (Ferra HTTP).

An OpenAPI document that cannot drift

The OpenAPI 3.2 document is served at /docs/openapi.json and the interactive Scalar page at /docs (when the chain says .with_docs()). Both are derived from the same struct the routes are derived from, so they cannot disagree with the running code. There are no annotations to forget.

Add a field to Film and it appears in the document, the Scalar page, the request validation and the SQL insert, at the next cargo build.

Typed SQL, bound by construction

Every query a generated route runs is parameterized: a filter value is bound, a sort key is taken only from the fields the model declares sortable, a cursor is decoded before any query is built. The generated routes have no mechanism to put request data in SQL text. Your own code keeps Sea-ORM’s full SQL access on the connection it owns (sea_orm::Statement, execute_unprepared): there, the query is yours. The framework has #![forbid(unsafe_code)] on every crate.

RFC 7807 errors, typed and machine-readable

Every error response follows RFC 7807 problem details. The type field is a URI from a closed set the framework maintains as a constant, not a free-form string. SDK generators and AI agents can produce a typed branch for every possible error.

{
  "type":   "https://ferra.rs/errors/not_found",
  "title":  "Resource Not Found",
  "status": 404,
  "detail": "films/42 not found"
}

The complete error URI table is in Error Handling.

Validation on the field

#[field(min_length, max_length, min, max, pattern, email, url, required)] become garde validators, applied on POST and PUT before the query runs, and on the values a PATCH sets (a field it leaves out is not judged). A violation answers 422 with an errors array of {field, code, message}, every failing field in one response (Ferra Forge).

Behaviors

#[behavior(timestampable, soft_delete)] uses the created_at, updated_at and deleted_at columns of your table (under other names with timestampable(created = "..", updated = "..") and soft_delete(column = "..")) and adds the matching logic: both stamps are in every read response, an update refreshes updated_at in its own statement, a delete sets deleted_at (which no response carries), and a soft-deleted row is a 404, never a deleted record (Behaviors).

Security defaults, not security options

  • Rate limiting on mutation routes (POST, PUT, PATCH, DELETE), out of the box, keyed on the peer address (serve with into_make_service_with_connect_info).
  • Body size cap: requests over 1 MiB are rejected before the body is read.
  • CORS: restrictive by default. You opt in to origins, not out of open access.
  • #![forbid(unsafe_code)] on every crate in the workspace.

Extending beyond the generated surface

The generated CRUD surface is a floor, not a ceiling. Foundry::build() returns a standard axum Router: hand-written routes merge in beside the generated ones, and answer with a body of their own:

use axum::{Json, Router, routing::get};
use ferra::{FerraError, Foundry};
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod film {
    use super::*;
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, ferra::FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "films")]
    #[ferra(auth = "none")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub title: String,
    }
    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}
    impl ActiveModelBehavior for ActiveModel {}
}
async fn film_count(
    axum::extract::State(conn): axum::extract::State<DatabaseConnection>,
) -> Result<Json<u64>, FerraError> {
    let count = film::Entity::find()
        .count(&conn)
        .await
        .map_err(|err| FerraError::Internal(ferra::InternalError::new(err)))?;
    Ok(Json(count))
}

fn demo(conn: DatabaseConnection) {
let app: Router = Foundry::new(conn.clone())
    .etag_key("a-development-key-of-at-least-32-bytes")
    .expect("a key of at least 32 bytes")
    .mount::<film::Model>()
    .build()
    .merge(Router::new().route("/films/count", get(film_count)).with_state(conn));
let _ = app;
}
fn main() {}

A route of your own is not covered by Ferra’s authorization: protect it yourself, as Custom Handlers shows. It can reuse the FerraError enum and so emit the same RFC 7807 bodies: clients handle one error shape across the whole API.

What Ferra is not

Not an ORM. Database schema management (migrations, table creation) is Sea-ORM’s: sea-orm-migration or the Sea-ORM CLI, outside the framework. Ferra generates the routes and the queries; you manage the schema.

Not a general-purpose web framework. No template engines, no session handling, no WebSockets. Ferra is narrowly focused on REST, hypermedia and typed errors. When you need to go further, axum handlers compose directly alongside Ferra routes.

Not an identity provider. Ferra validates a JWT signed with a shared HMAC secret; it does not issue tokens, and in 0.9 it has no RS256/JWKS verifier or pluggable authenticator (Authentication and Authorization).

Not on crates.io. An application depends on a tag of the Git repository. The public contract of the 0.9 line is frozen, and a change of it needs a new minor version; Stability policy says what is in the contract, and Migrating from 0.8 to 0.9 what changed.
