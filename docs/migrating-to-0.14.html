Ferra.rs — User Guide

Migrating from 0.13 to 0.14

0.14.0 (Riveting) removes declarations that read as a restriction and restricted nothing, and changes some behavior of the writes. Each entry below is a break. Most stop a 0.13 application from compiling; four change what it does with no compile error (the OpenAPI names, Resource::update, an authority that ends in _ => true, and a hook that writes its own row, the last entry). Read the entries, then update the application’s git dependency to v0.14.0. CHANGELOG.md lists every change.

groups is a compile error (FRG-137)

Before. #[ferra(groups = [...])] on a field, and groups = [...] inside projection(...), compiled. Ferra parsed the key and dropped it: the field was served on every read and accepted in the default write body, whatever the list, the empty list groups = [] included. A password hash declared with #[ferra(groups = [])] was served to every caller allowed to read the model.

After. The key is refused whatever its value, on a field, inside projection(...) and on the struct, with FRG-137, spanned on the groups key. FieldMeta::groups (ferra_core::meta::FieldMeta) is removed: it was always empty. FRG-306 (skip next to a non-empty groups) is retired with it.

Migration. Replace groups with what Ferra enforces:

You wrote groups to…Write instead
keep a field out of every response and write body#[ferra(skip)]
accept a field on write and never serve it (a password)#[ferra(write_only)]
choose the fields of a shaperead = [...] and write = [...] on a projection(...), see Projections and routing
serve or accept a field only to some callers#[field(read = …)] and #[field(write = …)], see Authentication and Authorization
 
#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "users")]
#[ferra(auth = "bearer")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    #[ferra(write_only)]
    pub password_hash: String,
    #[ferra(skip)]
    pub internal_notes: String,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

Code that reads FieldMeta::groups (a loop over meta().fields) no longer compiles: delete the loop. The slice was empty for every field, so the loop never ran.

A Ferra attribute where the derive does not read it is a compile error (FRG-138)

Before. The derive declares the helper attributes ferra, field, behavior, operation and authorize, so the compiler accepted each of them on the struct and on every field, and Ferra read each in one place only. A #[field(owner)] written on the struct marked no field as the owner; an #[authorize(...)] or #[behavior(...)] written on a field declared nothing. The model compiled, and the declaration did nothing.

After. Each of these is refused with FRG-138, spanned on the attribute path:

You wroteWhere it goes instead
#[field(...)] on the structon the field it describes
#[authorize(...)] on a fieldon the struct; a rule for one field is #[field(read = …, write = …)]
#[behavior(...)] on a fieldon the struct
#[operation(...)] on a fieldnowhere: add the route yourself with .route(...), see Custom handlers

Migration. Build, and move or remove each attribute the compiler points at. A model that carried a struct-level #[field(owner)] had no owner field: check that the rows are still protected as you meant, then put #[field(owner)] on the column that holds the owner.

#[ferra(hooks)] on a system_only model is a compile error (FRG-135)

Before. A #[ferra(system_only)] model is a table that only a system grant writes (see System grant). It could declare #[ferra(hooks)] and an impl FerraHooks. It compiled, and the hooks never ran: the model serves no write, and a grant inserts into it without running its hooks.

After. The hooks key on a system_only model is refused with FRG-135, spanned on hooks, as a write rule on it already was. The hooks of a grant are those of the model that declares the grant, never the target’s.

Migration. Delete hooks and the impl FerraHooks from the system_only model. That code never ran, so nothing is lost. If it was meant to write an entry into the model, move it to the impl FerraHooks of the model whose writes it records, and call tx.system().insert(..) there:

#[ferra(system_only)]                                   // the log model: no `hooks`, no `impl FerraHooks`
#[ferra(auth = "bearer", hooks(system = log::Model))]   // the hooked model: it owns the hooks and the grant

promotes_from off a default projection, or malformed, is a compile error (FRG-316)

Before. promotes_from compiled on a projection without default = true, where it was read and dropped, and with any string as its value, "v1" or the name of a projection that does not exist included. Only the presence of the key was checked, and only next to default = true.

After. FRG-316 refuses promotes_from on a projection without default = true, spanned on the key, and a value that is neither "auto-derived" nor "named:<name>" with <name> another projection declared in the same model (never the projection itself), spanned on the value. The value is still not checked against repository history: a former named default that you removed in the same change can no longer be named; write "auto-derived".

Migration. Remove promotes_from from a projection that is not the default. Write the value of a promoted projection as "auto-derived", or as "named:" followed by the name of a projection the model declares.

use ferra::FerraModel;

OpenAPI names: some models, every list operation and every named projection change

Before. The name Ferra gives a model in the OpenAPI document, the root of its schema names and operation ids, is the singular of its resource name. It read movies as Movy, buses as Buse, gases as Gase, statuses as Statuse, viruses as Viruse, bonuses as Bonuse, cookies as Cooky and zombies as Zomby: the model Movie was published as Movy, CreateMovyInput, getMovy… The list operation id was the model name and an s (listFilms), so a model whose resource name is made with ies or es had a list id its resource name does not spell: listCategorys, listBoxs, listClasss.

After. Three changes, all in the document only. Routes, paths, tags and resource names do not change: /movies is still /movies.

  1. The eight plurals above are read as Movie, Bus, Gas, Status, Virus, Bonus, Cookie and Zombie, in any segment of a resource name (film_movies is FilmMovie, it was FilmMovy). Every other name is read as before.
  2. The list operation id is list and the plural of the model name, made the way the derive makes a resource name: a trailing y after a consonant becomes ies, a trailing s, x, z, sh or ch takes es, anything else takes s. listFilms stays, listCategorys becomes listCategories.
  3. A named projection is named after its model: {Model}{Projection}, the model being the singular of the resource name (the one #[ferra(resource = "...")] gives, else the default resource name). It was named after the Rust struct, which is Model in every Sea-ORM entity: the summary projection of Film was published as ModelSummary, CreateModelSummaryInput, UpdateModelSummaryInput, ModelSummaryCollection (and the HAL ones), and two models that named a projection alike shared one schema, the last mounted overwriting the other’s in components: a protected route could document another model’s fields. The projection’s operation ids were the default’s (getFilm twice); they now carry the projection (getFilmSummary). Schemas and operation ids of the default projection do not change.

Migration. A client generated from the document sees the renames. To spot them, list the keys of components.schemas and the operationIds of the document of the old and the new version, and compare: the generated client has the matching types and methods under the new names. Regenerate the client and rename its imports and calls. Every operation id that changes, by kind of model:

A projection named collection or hal is a compile error (FRG-317)

Before. FRG-317 refused the projection name default only. A projection named collection or hal compiled, and in 0.13 its schemas did not clash with the model’s: they were named after the Rust struct (Model, see the section above), so its read schema was ModelCollection or ModelHal, not the model’s own list envelope FilmCollection or HAL read FilmHal.

After. FRG-317 refuses collection and hal as it refuses default, spanned on the name. The message lists the three reserved names and says which schema each would overwrite.

Migration. Rename the projection (summary, compact, public), and regenerate the client if it used the projection’s schemas: the new names follow the rule of the section above (FilmSummary).

Foundry::build() panics on an OpenAPI name produced twice (FRG-153)

Before. In 0.13 the schemas of a projection were named after the Rust struct (ModelSummary, see the section above), so a projection never collided with a model’s own names. Two cases did collide in schema names. Two mounted models that each declared a projection summary both produced ModelSummary, CreateModelSummaryInput, UpdateModelSummaryInput, ModelSummaryCollection (and the HAL ones). Inside one model, a projection x-collection next to x produced ModelXCollection twice (the list envelope of x, the read schema of x-collection). The document kept the last schema registered under a name and dropped the other, so a route could document the fields of another model or projection. No data was exposed. The operationIds of a projection were also the default’s (getFilm twice).

The 0.14.0 naming, {Model}{Projection}, adds collisions that 0.13 did not have, and build() now refuses them as well: Film with a summary projection and a model FilmSummary both produce FilmSummary and getFilmSummary; a projection collection-hal produces FilmCollectionHal, the HAL form of the default list envelope; a projection details of a model Problem produces ProblemDetails, the shared error schema.

After. build() panics before the server starts, as it does for FRG-310 and FRG-312, with a message that carries the code FRG-153, the name, its two sources (a model, or a projection of a model) and, for an operationId, the two operations with their method and path, for example FRG-153: the OpenAPI component `FilmXCollection` is produced twice, by projection `x` of the model `Film` and by projection `x-collection` of the model `Film` . Its signature does not change. The check runs whether or not .with_docs() is on, and reads the operationIds of the whole document: CRUD, restore, /me and the projections’.

Migration. Rename the projection that takes the name (x-collection becomes y), or give one of two models another resource name (#[ferra(resource = "...")]), so that the names differ.

Before, in 0.13: build() returned and the document kept one ModelXCollection. In 0.14 the same model panics in build():

FerraError::Internal and FerraDbError::Db carry an InternalError

Before. FerraError::Internal held a String, and FerraDbError::Db held the sea_orm::DbErr itself, with a public From<sea_orm::DbErr>. A 500 caused by the database reached your code with its cause flattened into text.

After. Both variants hold an InternalError (ferra::InternalError): its Display is constant, the cause is in source(), and the SQLSTATE of a database cause is InternalError::sqlstate(). The response body of a 500 is the same literal as before. FerraDbError loses From<sea_orm::DbErr>: the repository converts the errors it meets, and no Sea-ORM type is in the signature any more.

Migration.

You wroteWrite instead
FerraError::Internal(err.to_string()) to answer a 500FerraError::Internal(InternalError::new(err)) (the error itself, or a text)
FerraError::Internal(text) => ... text ... to read the causeFerraError::Internal(_), and read the cause with source()
FerraDbError::Db(db_err) or db_err.into()FerraDbError::Db(InternalError::new(err)), or leave the conversion to the repository
err.source().and_then(|s| s.downcast_ref::<sea_orm::DbErr>()) on a FerraDbErrorone link further: err.source().and_then(|s| s.source()).and_then(|s| s.downcast_ref::<sea_orm::DbErr>())
 
#![allow(unused)]
fn main() {
use ferra::{FerraError, InternalError};

fn answer(err: std::io::Error) -> FerraError {
    FerraError::Internal(InternalError::new(err))
}
let _ = answer;
}

InternalError, FerraError and HookError are no longer UnwindSafe

Before. The three types were UnwindSafe and RefUnwindSafe.

After. InternalError holds a boxed dyn Error, which is neither, so InternalError, FerraError and HookError lose both auto traits.

Migration. Only code that catches a panic with one of them in the closure is affected: it no longer compiles, and AssertUnwindSafe around the closure fixes it.

#![allow(unused)]
fn main() {
use std::panic::{AssertUnwindSafe, catch_unwind};

use ferra::{FerraError, InternalError};

let err = FerraError::Internal(InternalError::new("boom"));
let caught = catch_unwind(AssertUnwindSafe(|| err.to_string()));
let _ = caught;
}

AuthorityError::Failed carries a boxed error

Before. AuthorityError::Failed held a String, and its Display repeated it.

After. It holds a Box<dyn Error + Send + Sync>: your own error stays the source() of the AuthorityError, and its Display is the constant authority failed. Ferra logs the source text verbatim, as the cause of the log line, and never sends it: keep secrets and personal data out of it. A boxed dyn Error is neither UnwindSafe nor RefUnwindSafe, so AuthorityError loses both (AssertUnwindSafe around a catch_unwind that captures one).

Migration. Add .into() to the text, or box your error.

You wroteWrite instead
AuthorityError::Failed(text) or AuthorityError::Failed("...".to_owned())AuthorityError::Failed(text.into())
AuthorityError::Failed(err.to_string())AuthorityError::Failed(Box::new(err)) (keeps the error as the source)
AuthorityError::Failed(reason) => ... reason ... to read the textAuthorityError::Failed(_), and read it with source()
 
#![allow(unused)]
fn main() {
use ferra::authority::AuthorityError;

let from_text = AuthorityError::Failed("no such team".into());
let from_error = AuthorityError::Failed(Box::new(std::io::Error::other("lookup failed")));
let _ = (from_text, from_error);
}

OpenApiError::RoundTrip carries the serde_json::Error

Before. ferra_openapi::OpenApiError::RoundTrip { stage, detail } held the text of the serde_json error in detail: String.

After. detail is the serde_json::Error itself, and OpenApiError::source() returns it. Display is unchanged. Only code that builds a RoundTrip, or reads detail as a String, is affected.

Migration. Read detail.to_string() where you read the text, and pass the error itself where you built one.

A Foundry that mounts a model requires an entity-tag key

Before. A chain that mounted a model built without any key, on every auth mode.

After. 0.14 signs an entity tag on every single-row response, and a Foundry that mounts a model requires the key that signs it before its first .mount(...). Without it, try_build() returns BuildError::EtagKeyMissing and build() panics with the same text, so the application does not start. A chain with only .route(..) mounts no model and needs none. The key is one line you add to the chain:

#![allow(unused)]
fn main() {
use ferra::Foundry;

fn configure(conn: sea_orm::DatabaseConnection) -> Result<(), Box<dyn std::error::Error>> {
    let _chain = Foundry::new(conn).etag_key(std::env::var("ETAG_KEY")?)?;
    Ok(())
}
}

Migration. Generate a secret with openssl rand -base64 32, give the same value to every replica (an environment variable or your secret store), and pass it to .etag_key(...). It is at least 32 bytes (EtagKeyError::TooShort otherwise), and it is not your JWT secret: try_build() returns BuildError::EtagKeyEqualsJwtSecret for a key equal to one of the JwtConfig secrets, and build() panics with the same text. See foundry.md.

Resource::update and TxResource::update merge a JSON object instead of replacing it

This change is silent, no compile error warns you: Resource::update and TxResource::update with a {Model}Patch now follow PATCH /{resource}/{id}, and a key your code used to drop by replacing the object stays stored. For a stored {"a": 1, "b": 2} in a JSON field:

update with0.13 stored0.14 stores
{"a": 3}{"a": 3}{"a": 3, "b": 2} (b stays)
{"a": 3, "b": null}{"a": 3, "b": null}{"a": 3} (b goes)

Before. A JSON object set on a JSON field replaced the stored document, and a null member was stored as it came. A null set on a field that cannot be null was a 400.

After. A JSON object set on a stored JSON object is merged into it (RFC 7396): a member is set, a null member removes its key if there is one, and an object member merges recursively. A value that is not an object (an array, a scalar) replaces the document, and an object set on a stored value that is not an object (an array, a scalar, JSON null) becomes the object without its null members. The bounds (max_depth, max_bytes) judge the merged document. A null set on a field that cannot be null (Some(serde_json::Value::Null) on a required JSON field) is a 422 validation_failed whose errors[].code is required; Some(None) on a nullable field still clears it. Only the values the patch sets are typed and judged: a stored value it leaves alone is neither typed, nor judged, nor named in an error.

Migration. Read each update whose patch sets a JSON field. To drop a key, send it as null. To write a whole new document, send a PUT, or write the column with your own DatabaseConnection: a patch can no longer shrink an object by sending a smaller one.

OperationMeta and ModelMeta::operations are removed

Before. ferra::meta::OperationMeta (also ferra_core::OperationMeta) and the field ModelMeta::operations listed a model’s named operations. The derive filled it with one restore entry for a soft-delete model, and the router, the links and the OpenAPI document each tested that entry.

After. Both are gone. Ferra reads one list of served operations (CRUD, then restore when the model soft-deletes and is not system_only, then the actions in declaration order) wherever it decides what a model serves. The restore route, its prefixes and its operationId do not change.

Migration. None for an application: only the derive built or read these items. Delete any code that listed meta().operations; ModelMeta::actions lists a model’s actions, and restore is served when the model soft-deletes and is not system_only.

An authority that ends in _ => true allows every action

This change is silent for a match, no compile error warns you, and it matters only once a model declares an action. Operation has a new variant, Operation::Action(name), and FerraAuthority::can receives it for each declared action. Operation is #[non_exhaustive], so your can already carries a _ arm; if that arm is _ => true, it now allows every action on the rows filter shows. The variant holds the name, so Operation is no longer a fieldless enum: an as cast of an Operation no longer compiles.

Before. can was called for get, create, update, delete and restore.

After. can is also called for Operation::Action(name). An action has its own authorize rule and never falls back to update’s, but the authority still adds its answer to it.

Migration. In each FerraAuthority::can, name the operations you allow and end the match with _ => false; add an Operation::Action("name") arm for each action you allow. Replace an as cast of an Operation with a match. See ferra-auth.md.

A hand-written model carries the action slot

Before. A hand-written FerraModel (no derive) that was mounted implemented the hidden FerraDraft with a Draft and a Hooks (see migrating to 0.13).

After. FerraDraft also has Actions, the slot of the declared actions, and Mountable requires it to be an ActionRunner (hidden). The derive writes it for every model, so a derived model changes nothing.

Migration. Add type Actions = NoActions; to the impl FerraDraft of a hand-written, mounted model, with NoActions imported from ferra::ferra_core::hooks. Hand-writing a model is outside the contract, which is the derive (see stability.md).

A before_save hook that writes its own row through tx.resource fails with 500

This change is silent, no compile error warns you: it matters to a model with #[ferra(hooks)] whose before_save writes the row it is saving.

Before. A before_save that called tx.resource::<Self>() to update, soft-delete or delete the row being written (its own row) succeeded: the hook’s write and the request’s both landed, and a hook that deleted the row made the PUT answer 404.

After. An update (PUT, PATCH, Resource::update, a declared action) is conditioned on the row it locked, by its version and its deletion column. When the hook (or an action’s handler) has updated, soft-deleted or deleted that row since, the write finds no row: the answer is 500 with the generic body, one error! names the model and the operation, nothing is written. A write through tx.resource to another model’s row, and a hook that sets a value on the draft, are unchanged.

Migration. Read each before_save that calls tx.resource::<Self>(). A value the hook computes for the row being written belongs on the draft (w.values()), which Ferra writes with the request’s own values; a change that must happen to a row other than the one being written stays a tx.resource call. See Hooks, a hook cannot write its own row.
