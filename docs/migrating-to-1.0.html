Ferra.rs — User Guide

Migrating from 0.17 to 0.18 (the 1.0 API)

The public API frozen in 0.18.0 is the API of 1.0.0: the release candidates add nothing public, and the only exceptions are those of the stability policy, a security fix among them. Each entry below is a change from 0.17 that can stop a build, refuse a startup or change an answer you rely on. Read the entries, then point the application’s git dependency at the 0.18 tag:

ferra = { git = "https://github.com/ferra-rs/ferra", tag = "v0.18.1" }

How 1.0 is distributed, crates.io or a git tag, is decided before its last release candidate; the 1.0 changelog says which line to write.

From a release before 0.17, follow the pages of the releases in between first, in order: 0.9, 0.10, 0.11, 0.12, 0.13, 0.14, 0.15, 0.16, 0.17.

What does not move. Sea-ORM stays at 2.x: your sea-orm line is unchanged. The minimum supported Rust version stays 1.94.

The changelog lists every change. The entries come in its order: the fourteen breaking changes, the last two security fixes, then the three fixes that can stop a client or a custom store. A “Before” is 0.17 code, which no longer compiles; the “After” blocks compile against 0.18.

DateTime, Date and Time report TimeError, and from_duration is gone

Before. DateTime::from_second, from_millisecond, from_microsecond, from_nanosecond and the FromStr of DateTime, Date and Time returned jiff::Error. DateTime::from_duration took a jiff duration.

fn parse(raw: &str) -> Result<DateTime, jiff::Error> { raw.parse::<DateTime>() }
let at = DateTime::from_duration(jiff::SignedDuration::from_secs(90))?;

After. They return ferra::TimeError, an opaque #[non_exhaustive] type whose Display is the fixed sentence invalid date or time value: it quotes no part of the input, and source() is None. There is no From<TimeError> for FerraError: a route of your own maps it to the error it answers. DateTime::from_duration is removed: from_nanosecond takes the nanoseconds since the Unix epoch as an i128, which a jiff::SignedDuration gives with as_nanos(). as_inner stays the one documented hatch to the time library. A bad date in a JSON body still reaches the client as the time library’s text, in the message of the invalid_json error (errors[0].message): Deserialize is unchanged.

use ferra::{DateTime, TimeError};

fn parse(raw: &str) -> Result<DateTime, TimeError> {
    raw.parse::<DateTime>()
}

fn main() -> Result<(), TimeError> {
let since_epoch = jiff::SignedDuration::from_secs(90);
let at = DateTime::from_nanosecond(since_epoch.as_nanos())?;
let _ = (parse, at);
Ok(())
}

Who is affected. Code that names jiff::Error where it parses a Ferra date, and code that calls from_duration.

Migration. Name ferra::TimeError where you named jiff::Error. Replace from_duration(d) with from_nanosecond(d.as_nanos()). See Ferra Core.

The docs verifier reads http::request::Parts

Before. with_docs_protected and with_docs_protected_at took a closure over the whole request.

.with_docs_protected(|req: &axum::extract::Request| req.headers().contains_key(AUTHORIZATION))

After. They take Fn(&http::request::Parts) -> bool + Send + Sync + 'static, a closure that reads the head of the request (method, URI, headers, extensions) and never the body, that may be shared between threads and that borrows nothing: a refusal serves nothing and leaves the body unread. DocsAuthVerifier is built from that closure, and ferra_openapi::docs_routes_protected takes the same one. Parts is the http crate’s: name it through axum, which an application declares already, as axum::http::request::Parts, or add http = "1" to your Cargo.toml.

#![allow(unused)]
fn main() {
use axum::http::{header::AUTHORIZATION, request::Parts};
use ferra::DocsAuthVerifier;

let verifier = DocsAuthVerifier::from(|parts: &Parts| parts.headers.contains_key(AUTHORIZATION));
let _ = verifier;
}

Who is affected. Every application that protects its docs routes with a closure of its own.

Migration. Write the closure over parts, and read parts.headers where it read req.headers(). A closure that read the body of the request cannot any more. See Foundry and Ferra OpenAPI.

With a request budget, the read of a written row’s parents is bounded

Before. After the commit of a write, the read of the written row’s parents (a create, an update, a patch, a restore, a row action, or a Resource<M> write, on a model with a BelongsTo) was bounded by the pool’s acquire_timeout and the server’s statement_timeout only. A slow read still answered the 2xx.

After. With a request budget (.request_budget(..), Foundry), that read has to finish by the request’s post-commit deadline: the later of the budget’s end and one second after the first work the request does once a row is committed. A read still running at that deadline answers the 500 internal with one error! line, and the row is written. Nothing is cut inside a hook’s open tx.resource transaction, without a budget, or under Prefer: return=minimal. A deadline already used up by earlier post-commit work answers the 500 for a row with a parent to read, and the 2xx for a row with none. The reads of Resource::get, list and list_cursor, and of tx.resource, stay under no deadline of their own.

Nothing in your code changes: this is an answer that changes.

Who is affected. An application that sets .request_budget(..) and mounts a model with a BelongsTo; a client that retries a create when it gets a 500.

Migration. Expect the 500 at the deadline where the late 2xx came, and make a create safe to replay before retrying it: see the idempotent create recipe.

A second with_api_keys is refused at startup

Before. A second FoundryBuilder::with_api_keys on a chain silently replaced the first store.

After. try_build returns the new BuildError::ApiKeysTwice, and build() panics with its text.

use ferra::api_key::PgApiKeyStore;
use ferra::{ApiKeyConfig, DatabaseConnection, FerraIdentity, Foundry, JwtConfig};
use serde::Deserialize;
#[derive(Clone, Deserialize)]
struct Claims { sub: String }
impl FerraIdentity for Claims {
    fn id(&self) -> &str { &self.sub }
    fn has_role(&self, _role: &str) -> bool { false }
}
fn demo(conn: DatabaseConnection, jwt: JwtConfig) -> Result<(), Box<dyn std::error::Error>> {
let keys = ApiKeyConfig::new(PgApiKeyStore::new(conn.clone()));
let builder = Foundry::new(conn)
    .etag_key(std::env::var("ETAG_KEY")?)?
    .with_auth::<Claims>(jwt)
    .with_api_keys(keys); // once: a second call is `BuildError::ApiKeysTwice`
let _ = builder;
Ok(())
}
fn main() {}

Who is affected. A chain that calls with_api_keys twice.

Migration. Call with_api_keys once, with the one ApiKeyConfig. See Foundry.

A deprecation date outside the years 0 to 9999 is refused at startup

Before. FoundryBuilder::deprecated accepted a date in a year below zero, and x-sunset read -001-01-01. (A Date above year 9999 cannot be built.)

After. deprecated refuses a year outside 0..=9999 with the new DeprecationError::YearOutOfRange.

#![allow(unused)]
fn main() {
// Year, month, day: a year from 0 to 9999.
let sunset = ferra::Date::new(2027, 1, 5);
let _ = sunset;
}

Who is affected. A chain whose deprecated or sunset date is in a year below zero.

Migration. Pass dates from year 0 on. See Foundry.

A malformed #[authorize] is FRG-023, not FRG-103

Before. An #[authorize] that does not parse (a bare #[authorize], a key with no =) was refused with FRG-103.

After. It is refused with FRG-023, the code of every attribute that does not parse. FRG-103 now only names an unknown, qualified or malformed checker. The message, its span and its help are unchanged. Nothing in your code changes: the model was refused before and is refused now.

Who is affected. A script, a test or a note that matches FRG-103 on these two mistakes.

Migration. Match FRG-023 for them. See Compile-time Diagnostics.

Two types and six variants are #[non_exhaustive]

Before. JwtSecret and HmacAlgorithm were closed, and so were the variants Saving::Create, Saving::Update, Saving::Restore, FieldMode::Key, PaginationMode::Cursor and PaginationMode::Both.

let secret = JwtSecret { kid: "key-1".into(), key: secret.into(), algorithm: HmacAlgorithm::Hs256 };
match algorithm { HmacAlgorithm::Hs256 => 256, HmacAlgorithm::Hs384 => 384, HmacAlgorithm::Hs512 => 512 }

After. All of them are #[non_exhaustive], so a later field or algorithm is not a major version. FieldMode::Key, PaginationMode::Cursor and PaginationMode::Both are built by the derive; your code only matches them.

#![allow(unused)]
fn main() {
use ferra::{HmacAlgorithm, JwtSecret};

fn bits(algorithm: HmacAlgorithm) -> u16 {
    match algorithm {
        HmacAlgorithm::Hs256 => 256,
        HmacAlgorithm::Hs384 => 384,
        HmacAlgorithm::Hs512 => 512,
        _ => 0, // a later algorithm
    }
}

let secret = JwtSecret::new("key-1", std::env::var("JWT_SECRET").unwrap_or_default(), HmacAlgorithm::Hs256);
let _ = (secret, bits);
}

Who is affected. Code that builds a JwtSecret with a struct literal, that matches HmacAlgorithm without a wildcard arm, or that matches the six variants without ...

Migration. Build a JwtSecret with JwtSecret::new(kid, key, algorithm), give a match on HmacAlgorithm a wildcard arm, and end a pattern on these variants with ... See Authentication and Authorization.

Twelve names leave the contract

Before. JsonBounds::new, FieldMeta::with_json, BehaviorKind::soft_delete, BehaviorKind::timestampable, BehaviorKind::blameable, ModelMeta::blame_columns, FieldType::ComputedUserNamed, ModelMeta::filterable_fields, ModelMeta::sortable_fields, ProjectionMeta::schema_base_name, HmacAlgorithm::min_secret_len and Date::days_since were part of the public API.

After. They are hidden, so they can change without a major version. They still compile where they are used, but a use is outside the contract.

#![allow(unused)]
fn main() {
use ferra::meta::ModelMeta;

fn filterable(meta: &ModelMeta) -> impl Iterator<Item = &'static str> + '_ {
    meta.fields.iter().filter(|field| field.filterable).map(|field| field.name)
}
let _ = filterable;
}

Who is affected. Code that calls one of them.

Migration. Let the derive build BehaviorKind and FieldMeta values, read the filterable and sortable fields from ModelMeta::fields as above, and read the minimum secret length from the min of JwtConfigError::SecretTooShort. For Date::days_since, subtract through as_inner. See the stability policy.

FerraError::ConflictWith is FerraError::ConflictDetail

Before. The variant that serves its text verbatim as the detail of a 409 was named ConflictWith.

After. It is ConflictDetail, because FerraError::Conflict(String) hides its text behind a fixed detail and this variant does not. The answer is unchanged: status 409, type https://ferra.rs/errors/conflict, title Conflict, detail as given.

#![allow(unused)]
fn main() {
use ferra::FerraError;

let refusal = FerraError::ConflictDetail("this title is taken".to_owned());
let _ = refusal;
}

Who is affected. Code that names FerraError::ConflictWith. HookError::conflict is unchanged.

Migration. Write FerraError::ConflictDetail. See Error Handling.

A sub-collection keyed on a column that is not the parent’s primary key is refused

Before. A HasMany or HasOne whose mounted child’s back BelongsTo has a to other than the parent’s primary key was served, and listed the child rows by the parent’s key, whatever to said.

After. try_build returns the new BuildError::SubCollectionKeyNotPrimary (build() panics with its text), naming the parent, the child and the column. The child’s BelongsTo points to at the parent’s primary key:

use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod client {
    use super::*;

    #[sea_orm::model]
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "clients")]
    #[ferra(auth = "none")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub name: String,
        #[sea_orm(has_many)]
        pub contexts: HasMany<super::context::Entity>,
    }

    impl ActiveModelBehavior for ActiveModel {}
}

mod context {
    use super::*;

    #[sea_orm::model]
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "contexts")]
    #[ferra(auth = "none")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub client_id: i32,
        // `to` names the parent's primary key.
        #[sea_orm(belongs_to, from = "client_id", to = "id")]
        pub client: BelongsTo<super::client::Entity>,
    }

    impl ActiveModelBehavior for ActiveModel {}
}
fn main() {}

Who is affected. A chain that mounts a parent and a child whose BelongsTo points at another column than the parent’s key.

Migration. Point to at the parent’s primary key, or do not mount both models on one Foundry: each is then served alone, with no sub-collection. See Relations.

On a dense model, model_attrs(..) mistakes are refused

A dense model is one written with #[sea_orm::model], which expands the struct into Model (the columns) and ModelEx (the columns and the relations); #[sea_orm(model_attrs(..))] puts attributes on Model alone (Relations).

Before. On a dense model whose Ferra attributes are written in model_attrs(..), three mistakes compiled that the derive refuses with the same attributes outside model_attrs: a name in the read list of a projection that is neither a field nor a BelongsTo (FRG-301), a HasMany or HasOne in it (FRG-363), and the foreign key behind owner(from = ..) in the writes of an action (FRG-146).

After. The three are refused, as a constant-evaluation error (E0080, “evaluation panicked: FRG-…”), underlined on the name at fault. A read list of names the model has compiles as before:

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[sea_orm::model]
#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films", model_attrs(ferra(auth = "none"), ferra(projection(name = "admin", read = [id]))))]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
}
impl ActiveModelBehavior for ActiveModel {}
}

Who is affected. A dense model with Ferra attributes in model_attrs(..) that made one of the three mistakes.

Migration. Correct the name in read, or remove the foreign key from writes. See Compile-time Diagnostics.

A Ferra attribute in model_ex_attrs(..) is refused (FRG-147)

Before. A Ferra attribute (#[ferra], #[authorize], #[behavior], #[operation], #[field]) written in #[sea_orm(model_ex_attrs(..))] compiled and declared nothing, so an #[authorize(delete = HasRole("admin"))] there left delete to the rule the model’s auth gives by default.

#[sea_orm(table_name = "films", model_ex_attrs(behavior(soft_delete)))]

After. It is refused with FRG-147, as a constant-evaluation error (E0080). Sea-ORM puts model_ex_attrs on ModelEx alone, and Ferra reads the rules, projections and behaviors from Model:

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[sea_orm::model]
#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "none")]
#[behavior(soft_delete)]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
}
impl ActiveModelBehavior for ActiveModel {}
}

Who is affected. A model that wrote a Ferra attribute there: its rules were not in force.

Migration. Write the attribute outside #[sea_orm(..)], or in model_attrs(..). See Compile-time Diagnostics.

An owner(from) whose BelongsTo does not point at the parent’s key is refused (FRG-148)

A security fix that refuses a model that compiled (the stability policy, exception (i)).

Before. #[field(owner(from = parent))] compiled whatever the to of the BelongsTo it follows. Ferra locked and judged the parent by its primary key: with to naming another column, the parent whose key equalled the foreign key’s value was judged and gave the row its owner, while the row pointed at another parent.

#[sea_orm(belongs_to, from = "vendor_code", to = "code")]
pub vendor: BelongsTo<super::vendor::Entity>,

After. It is refused with FRG-148, as a constant-evaluation error (E0080) on the from value. The BelongsTo of an owner(from) chain points to the parent’s primary key, as in the example of the diagnostic.

Who is affected. A model with owner(from = ..) whose BelongsTo names another column of the parent in to. A BelongsTo without owner(from) is not affected.

Migration. Point to at the parent’s primary key (and the foreign key at that key’s values), or declare the owner on the model with #[field(owner)]. See Compile-time Diagnostics.

A sea_orm key given twice on one field is refused (FRG-149)

A security fix that refuses a model that compiled (the stability policy, exception (i)).

Before. from, to or enum_name could be given twice on one field. Ferra read the first occurrence; Sea-ORM reads the last one of an attribute, and only the first #[sea_orm] of a relation field. The column Ferra checked was not always the one Sea-ORM used.

#[sea_orm(primary_key, enum_name = "Code", enum_name = "Key")]
pub id: i32,

After. It is refused with FRG-149, on the second occurrence.

Who is affected. A model that repeats one of these keys on a field, in one attribute or across two.

Migration. Keep one occurrence, the one Sea-ORM used: the last of an attribute, or, on a relation field split over two #[sea_orm], the one in the first (Sea-ORM ignored the second). See Compile-time Diagnostics.

A key whose stored record holds another prefix is refused

This is a security fix, not a breaking change, and it can stop a custom store working.

Before. verify compared only the secret hash of an API key with the record the store returned. A custom ApiKeyStore that normalized or swapped the prefix of a record (lowercased it, padded it, returned the record of another prefix) still authenticated the key.

After. verify compares the prefix of the record with the presented one, inside the constant-time check that compares the hash. A mismatch is refused with the one generic 401, before the revoked and expired checks, and without writing its last use, although the secret is right.

Who is affected. An application with an ApiKeyStore of its own that returns a record under another spelling of the prefix than the one it was asked for.

Migration. Return the record for the exact prefix you were asked for. See Authentication and Authorization.

The 401 of the protected docs routes carries WWW-Authenticate: Bearer

This is a fix, not a breaking change.

Before. The 401 of with_docs_protected and with_docs_protected_at carried no WWW-Authenticate.

After. It carries the fixed WWW-Authenticate: Bearer, as every other 401 of Ferra. The verifier declares nothing: a verifier that accepts another scheme still sends Bearer.

Who is affected. A client or a test that asserts the absence of the header on the docs 401.

Migration. Expect the header. See Foundry and Error Handling.

A path no route serves is a bare 404

This is a fix, not a breaking change.

Before. The answer to a path no route serves inherited the layers of the last model mounted: it could be a 401 under with_docs_protected or after a model under auth = "bearer", pass that model’s CORS and rate limiter, and carry the Deprecation and Sunset headers of a deprecated version.

After. It is a 404 with an empty body, whoever asks and whatever the chain mounts. The docs verifier and a model’s token check guard their own routes only. A preflight to an unknown path is a bare 404, and a token sent to it is not read.

Who is affected. A client or a test that expected a 401 on a path the API does not serve, or a header of a model’s layers there.

Migration. Expect the 404. See Error Handling.
