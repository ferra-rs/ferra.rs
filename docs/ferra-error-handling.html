Ferra.rs — User Guide

Error handling

Every Ferra-served HTTP response that is not a success carries an RFC 7807 problem-details body (Content-Type: application/problem+json). Every body’s type field is a URI from a closed set the framework maintains as a single source of truth.

This page is the reference for that closed set: the URI table, the HTTP status / title / example body for each variant, and the consumer-side branching pattern.

The closed ERROR_TYPES URI set

The framework can emit exactly seventeen type URIs on the wire. Every literal in framework source (and in any consumer crate) MUST appear in this set; a CI gate (cargo run -p xtask --bin error_types_closed) fails the build on any drift.

Three of the seventeen URIs (payload_too_large, rate_limited, unauthorized) are emitted by middleware layers, not through FerraError; a fourth, precondition_failed, is answered by the generated write routes and has no FerraError variant. retry_exhausted has one since 0.16.0, FerraError::RetryExhausted: it is a 503 wherever it is returned (before 0.16.0 it was a FerraError::Internal over a private cause). The framework’s full URI surface is the union of the two paths; both are governed by the same ERROR_TYPES slice. (unauthorized is emitted from both — the docs-protection middleware and, since 0.8.0, FerraError::Unauthorized on the per-operation authorization path.)

The unauthorized (401) and forbidden (403) URIs encode a distinction consumers should branch on rather than collapse. A 401 means the framework could not establish who the caller is: no credential was presented, or the one presented did not validate. A 403 means it established the caller’s identity successfully and the operation’s authorization rule still refused. A 403 is therefore positive evidence that the token was accepted — retrying with fresh credentials will not help, whereas on a 401 it may. Only 401 responses carry WWW-Authenticate: Bearer; a 403 is not an authentication challenge (RFC 9110 §15.5.2 vs §15.5.4).

One refusal is deliberately not a 403: when an IsOwner rule refuses a row that belongs to someone else, the answer is the not_found (404) a missing row gets, byte for byte, so the caller cannot learn that the row exists (see ferra-auth.md § Error responses).

The validation (400) and validation_failed (422) URIs are intentionally distinct. A malformed request body (JSON parse failure, type mismatch on a required field, an Id parameter that will not parse) returns 400 — the request was syntactically unprocessable. A well-formed request body whose values violate the model’s declarative #[field(...)] rules returns 422 — the request parsed cleanly but its semantics were rejected. The split follows RFC 9110 §15.5.1 (400) vs §15.5.21 (422).

Worked example bodies

not_found — 404

Returned by every read / update / delete that resolves to zero matching rows.

{
  "type": "https://ferra.rs/errors/not_found",
  "title": "Resource Not Found",
  "status": 404,
  "detail": "films/c2bb1f10-72b8-486a-9f2b-c92e4a2cdf41 not found"
}

validation — 400

Returned when an inbound JSON body or a path parameter fails the framework’s typed deserialisation, or when an Id parameter fails to parse. Declarative-rule violations on a well-formed body are the separate 422 path — see § Validation failures (422).

{
  "type": "https://ferra.rs/errors/validation",
  "title": "Validation Error",
  "status": 400,
  "detail": "query parameter `filter[title]` is repeated",
  "errors": [
    { "field": "filter[title]", "code": "duplicate_parameter", "message": "query parameter `filter[title]` is repeated" }
  ]
}

The errors member is one top-level array of {field, code, message}, the same shape as on the 422 path. code is drawn from the closed list in § Validation codes; field is the decoded query parameter, body for a malformed body, or the path parameter’s name.

A write body (POST, PUT, PATCH, and the body of an action) is decoded once from its bytes, and this 400 (invalid_json, field body) is the first refusal of that decoding: a body that is not a JSON object, a key repeated at any depth (a JSON field included; the message reads a key is repeated at line L column C, and carries no value of the body), or a value of the wrong type on a key the caller may read. A key the caller may not read is never judged here: its type is not looked at, and it is the 422 unknown_field of an unknown key. Send each key once. The refusals of a write come in one order: the row’s 404, then 415, 412, 413, this 400, the 422 unknown_field, the 403, the 422 of the bounds and the rules, and last the 400 of a required key the body does not send (missing field): typed first, it would answer a caller who sends a hidden required key with a 400 where an absent name gets the 422, and reveal that the field exists.

conflict — 409

Returned when a write would violate a unique constraint (duplicate slug, primary-key collision, etc.), or when a DELETE is refused by a foreign key (0.16.0: a parent that still has children under ON DELETE RESTRICT; nothing is deleted and the statement is not retried). The detail is fixed: the database’s message — which names the constraint and the table — goes to the server log (INFO, target ferra_http::conflict), never to the client; a foreign-key violation logs the constraint’s name only, never the key value.

{
  "type": "https://ferra.rs/errors/conflict",
  "title": "Conflict",
  "status": 409,
  "detail": "the request conflicts with an existing resource"
}

internal — 500

Returned for any database / infrastructure failure not classifiable as one of the typed variants above. detail is always the constant literal "internal server error" — no internal path fragment, no crate name, no underlying-library substring leaks (constitution §I). A stored typed JSON document that no longer decodes into its struct makes the row unreadable: a GET of it and a PATCH of it are a 500, whatever the patch sets.

{
  "type": "https://ferra.rs/errors/internal",
  "title": "Internal Server Error",
  "status": 500,
  "detail": "internal server error"
}

payload_too_large — 413

Emitted when an inbound request body exceeds the framework’s default 1 MiB cap (constitution §I — DoS protection).

{
  "type": "https://ferra.rs/errors/payload_too_large",
  "title": "Payload Too Large",
  "status": 413,
  "detail": "request body too large"
}

unsupported_media_type — 415

Returned when a POST or PUT body is not declared as JSON: the Content-Type is missing, or is neither application/json nor application/<name>+json (parameters such as charset are ignored). Nothing is read or written.

{
  "type": "https://ferra.rs/errors/unsupported_media_type",
  "title": "Unsupported Media Type",
  "status": 415,
  "detail": "the request body must be JSON: send `Content-Type: application/json`"
}

timeout — 503

Returned when the configured request budget expires before a Ferra repository commit starts. The unfinished transaction rolls back, and no Retry-After header is sent. Once a commit starts, the handler completes and returns its own response, never this 503; only a model’s after_commit hook is still bounded by the remaining budget, and when it is cut the answer is a 500 internal with the commit standing. See Request time budget.

{
  "type": "https://ferra.rs/errors/timeout",
  "title": "Request Timeout Budget Exceeded",
  "status": 503,
  "detail": "the request exceeded its time budget; no change was committed"
}

multiple_credentials — 400

Returned when a request presents more than one credential: Authorization, the API key header and the cookie count, in any combination, and any of them sent twice. Presence decides, never validity: the request is refused before any verification, whatever the credentials hold, and the body never names which ones. Send one credential per request. New in 0.12.0.

{
  "type": "https://ferra.rs/errors/multiple_credentials",
  "title": "Multiple Credentials",
  "status": 400,
  "detail": "send one credential per request"
}

identity_unavailable — 503

Returned when a credential cannot be verified because the identity source is out of reach: the key set of the identity provider (JwtConfig::key_set) could not be fetched and no fresh key is cached, or the API key store failed during a lookup. A token that the cached keys cannot verify is a 401 instead, never this. No Retry-After header is sent, and the body never says why: the cause goes to a warn trace. New in 0.12.0.

{
  "type": "https://ferra.rs/errors/identity_unavailable",
  "title": "Identity Unavailable",
  "status": 503,
  "detail": "the credential could not be verified; retry later"
}

service_unavailable — 503

Returned when a hook of yours returns HookError::unavailable(detail): something the hook depends on (a queue, a payment provider) is out of reach. The detail is yours. No Retry-After header is sent. New in 0.13.0.

After a commit the write stands. The same type answers an unavailable returned by after_commit, which runs once the row is committed: the response is a 503, and the row is written. A client must not retry a non-idempotent request blindly (RFC 9110 § 9.2.2): read the resource first, or send an idempotency key. timeout says the opposite (nothing was committed); identity_unavailable is about the credential, never about your code.

{
  "type": "https://ferra.rs/errors/service_unavailable",
  "title": "Service Unavailable",
  "status": 503,
  "detail": "the payment provider is not reachable"
}

retry_exhausted — 503

Returned when the database aborted a write’s transaction with 40001 (serialization failure) or 40P01 (deadlock) on each of its three attempts, a refused COMMIT included. The write that was given up was not applied, so the client may retry it; the response carries Retry-After: 1 (whole seconds). The detail is one fixed text that speaks for that write, not for the request, and names no SQLSTATE, table or constraint; the SQLSTATE goes to a warn trace, one line per aborted attempt. A generated route makes one write per request, so nothing of the request was written. In a route of your own, an earlier write of the same handler through Resource<M> stands: do not retry a non-idempotent request blindly (RFC 9110 § 9.2.2). The generated write routes and Resource<M> writes answer it. A Resource<M> write that was given up returns Err(FerraError::RetryExhausted) (a unit variant, 0.16.0): return it from your route to answer the 503, and never replay the write in a loop of your own, because the loop already ran and a replay under contention adds to it. A hook’s tx.resource write reaches the caller as the same variant, through the outer write; an Internal(_) arm no longer sees it. With a request budget, a deadline that leaves no room for the next attempt is the timeout instead, with no Retry-After. The attempts, the wait between them and what is rerun: Transient conflicts are retried. New in 0.14.0; the FerraError variant is new in 0.16.0.

HTTP/1.1 503 Service Unavailable
Content-Type: application/problem+json
Retry-After: 1

{
  "type": "https://ferra.rs/errors/retry_exhausted",
  "title": "Retries Exhausted",
  "status": 503,
  "detail": "this write conflicted with concurrent writes on every attempt and was not applied; retry it"
}

rate_limited — 429

Emitted by the framework’s default rate-limiter on mutation routes (POST / PUT / DELETE). The response carries a Retry-After header, in whole seconds, never below 1.

{
  "type": "https://ferra.rs/errors/rate_limited",
  "title": "Too Many Requests",
  "status": 429,
  "detail": "rate limit exceeded"
}

unauthorized — 401

Emitted by Foundry::with_docs_protected(verifier) when an unauthenticated request reaches the docs surface. New in 0.5.0.

{
  "type": "https://ferra.rs/errors/unauthorized",
  "title": "Unauthorized",
  "status": 401,
  "detail": "authentication required"
}

Every other 401 (missing, malformed, expired or badly signed token, wrong iss or aud, unknown kid) has the same bytes and the headers WWW-Authenticate: Bearer and application/problem+json, whatever the reason, so a caller cannot probe which check failed. Since 0.12.0 its detail is “valid credentials are required to access this resource” (it was “a valid Authorization: Bearer token is required to access this resource”): match on type, not on detail.

{
  "type": "https://ferra.rs/errors/unauthorized",
  "title": "Unauthorized",
  "status": 401,
  "detail": "valid credentials are required to access this resource"
}

validation_failed — 422

Returned when an inbound POST or PUT body parses cleanly but violates one or more #[field(...)] rules declared on the target model. The full worked example with multi-field aggregation lives in § Validation failures (422); the short form:

{
  "type": "https://ferra.rs/errors/validation_failed",
  "title": "Validation Failed",
  "status": 422,
  "detail": "validation failed",
  "errors": [
    { "field": "title", "code": "min_length", "message": "must be at least 1 character" }
  ]
}

The errors member on this variant is an array of {field, code, message}, field being the wire-side field name — every violation observed during the validation pass is included (no short-circuiting), so a consumer never needs to retry to discover further violations.

On a write, this 422 comes after the 400 of validation in the one order of every write: the row’s 404, 415, 412, 413, 400, then the 422 unknown_field (the unknown keys and the keys the caller may not read, in one list), the 403 of a field the caller may read and not write, the 422 of the bounds and of the #[field(...)] rules, and last the 400 of a required key the body does not send. A body with an unknown key and a wrong-typed value on a key the caller may read is therefore the 400, not this 422.

A foreign key that points at no row the caller may read is the 422 with the code reference_not_found on the key (0.16.0, see Writing a foreign key), whether Ferra’s own read of the target refused it or the database’s constraint did after that read (SQLSTATE 23503): the body is the same, and neither the body nor the log holds the key value.

A 23503 on a model with no declared BelongsTo is the 409 conflict: a constraint Ferra does not know of is a conflict of state, not a reference of the body. The create’s OpenAPI documents its 409 only as the generic conflict (a unique constraint); it does not name the foreign key, because a constraint invisible to the derive is not documented.

Validation failures (422)

A 422 response fires when the request body is well-formed — it parses as JSON and deserialises into the model’s request shape — but one or more values violate the declarative #[field(...)] rules on the target model. Validation runs before persistence on every POST (create) and PUT (update) handler, so an invalid payload never reaches the database. The wire shape is identical across create and update.

This is the 422 path. The 400 validation path above continues to denote extractor failures — a body that does not parse as JSON at all, a path parameter that will not parse as the declared type. Both paths share the application/problem+json envelope and the same errors array; only the codes differ (see § Validation codes).

The model-side declaration grammar — every supported rule, its default English message, and the compile-time FRG-2NN codes that protect typos — is documented in ferra-forge.md § Validation rules. This section pins the wire shape your consumer sees.

Worked example: multi-field violation

For a Film resource declared as:

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    #[field(min_length = 1, max_length = 255)]
    pub title: String,
    #[field(min = 0, max = 10)]
    pub rating: i32,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

a request that violates two fields simultaneously:

POST /films HTTP/1.1
Content-Type: application/json

{ "title": "", "rating": 99 }

receives:

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://ferra.rs/errors/validation_failed",
  "title": "Validation Failed",
  "status": 422,
  "detail": "validation failed",
  "errors": [
    { "field": "title",  "code": "min_length", "message": "must be at least 1 character" },
    { "field": "rating", "code": "max",        "message": "must be at most 10" }
  ]
}

Both fields appear in the same response. Ferra never short-circuits on the first failed rule, so a consumer that submits a payload with N invalid fields receives N entries in errors in a single round-trip. Within a single field, every rule that fired produces its own entry — #[field(min_length = 5, email)] on a value of "ab" produces two entries for that field, min_length and email.

Assertion contract for SDK consumers

A consumer driving validation off the wire response asserts the following invariants on a 422:

Wire fieldValueNotes
HTTP status422always equal to the body’s status integer
Content-Type headerapplication/problem+jsonidentical envelope to every other Ferra error
type"https://ferra.rs/errors/validation_failed"pinned URI; closed-namespace member (table above)
title"Validation Failed"distinct from "Validation Error" (the 400 path’s title)
status422 (integer)
detail"validation failed"constant literal — does NOT echo input back into the response (constitution §I — no reflected-XSS on the error path)
errors[{field, code, message}]one entry per rule that fired; field is the wire-side field name (the same name that appears in the request body’s JSON), code is from § Validation codes, message is human-readable English

The field of an entry is the field name of the request body. A field’s JSON name is its Rust name: a serde attribute that renames a model field does not compile (FRG-116, see ferra-forge.md § Field names on the wire).

_links is never present on a 422 body. Validation failure is terminal — there is no resource yet, no self-link to thread, no hypermedia to follow. A consumer that branches on the response’s _links.self.href should treat 422 as the absent-link case.

Update-vs-create symmetry

The validation step runs identically on POST /<resource> and PUT /<resource>/{id}. The 422 body is identical across both. A PUT is a replacement: a field omitted from its body is not “no change”. An optional field without a read or write rule becomes NULL and its per-field rules do not fire; a field with such a rule is kept; a #[field(required)] Option<T> field fails with the code required, and so does one present with an explicit null — null on the wire is a positive declaration of “set to none”, which the rule rejects.

PATCH /<resource>/{id} is the partial update (ferra-http.md): a field absent from the patch is untouched, and only the values the patch sets are judged. A null on a field that cannot be null is the 422 required, and a body that is not a JSON object, or a value of the wrong type, is the 400 invalid_json.

For a model nothing reads the row of (no rule, projection, authority or owner field does), a PUT or a PATCH sent with no precondition header does not read the row first, so its body is judged first: a wrong Content-Type is a 415, a body that is not an object a 400, an unknown key a 422, whether the row is live, absent or soft-deleted (the refusal is the same for the three, so it tells nothing about the row).

Consumer-side branching pattern

Add one branch to the existing match on the wire type field:

#![allow(unused)]
fn main() {
fn on_error(body: &serde_json::Value) {
    match body["type"].as_str() {
        Some("https://ferra.rs/errors/validation_failed") => {
            // 422 path — read body["errors"] as an array of
            // {field, code, message} and surface each entry into your
            // form's per-field error UI; branch on `code`.
        }
        Some("https://ferra.rs/errors/validation") => {
            // 400 path — same `errors` array, other codes.
        }
        // ... other arms ...
        _ => {} // not an error of Ferra's namespace
    }
}
}

Server-side, when handling a FerraError value, the 422 path reads through the new variant:

#![allow(unused)]
fn main() {
use ferra::FerraError;

fn observe(err: &FerraError) {
    match err {
        FerraError::Unprocessable(_) => {
            // 422 — declarative-rule violation
        }
        FerraError::Validation(_) => {
            // 400 — extractor failure
        }
        // FerraError is #[non_exhaustive]: keep a wildcard arm
        _ => {}
    }
}
}

FerraError::Unprocessable is the typed home for the 422 path; FerraError::error_type returns "https://ferra.rs/errors/validation_failed" on this variant.

Hook errors

A hook returns ferra::hooks::HookError; Ferra turns it into the response, so a hook never builds one. Four constructors:

ConstructorAnswer
HookError::failed(msg)500 internal; msg is logged, never sent
HookError::conflict(detail)409 conflict; your detail is served as given
HookError::unprocessable(field, code, message)422 validation_failed, one error {field, code, message}
HookError::unavailable(detail)503 service_unavailable, your detail

The detail of conflict, unprocessable and unavailable is your text, served as given: put no value in it that the caller may not read. (A conflict from a storage constraint keeps its fixed text, never the database’s message.)

#![allow(unused)]
fn main() {
use ferra::ValidationCode;
use ferra::hooks::HookError;

let _ = HookError::failed("the ledger table is locked");
let _ = HookError::conflict("the seat is already booked");
let _ = HookError::unprocessable("amount", ValidationCode::Max, "insufficient balance");
let _ = HookError::unavailable("the payment provider is not reachable");
}

A ? on a FerraError is a 500. A hook that reads another model and propagates its error with ? answers 500 internal with the generic body, whatever the source was (a 403, a 404, a 422): the other model’s status and detail describe a request the caller did not make, and could reveal its rows. Ferra logs the source’s status and type. To answer a 409 or a 422, match the error and build it with the constructors above.

#![allow(unused)]
fn main() {
use ferra::FerraError;
use ferra::hooks::HookError;

fn read_other_model(found: Result<(), FerraError>) -> Result<(), HookError> {
    found?; // a FerraError here becomes HookError::failed: 500, generic body
    Ok(())
}
let _ = read_other_model;
}

From after_commit the row is already written, so a 409 or a 422 would claim the opposite. failed answers 500, unavailable answers 503, and conflict and unprocessable answer 500 internal. Do not put in a detail a value the caller may not read.

From a computed field (FerraComputed) the hook returns a FerraComputeError, not a HookError, and there is one answer: 500 internal with the generic body, a panic caught as a failure (unless panic = "abort"). On a read, a request budget that runs out is the budget’s own 503 timeout, with no partial body. Ferra logs one error! line for the request with the model, the operation and your message, and no row value. On a write response the row is already committed and the line says so; if the request budget runs out during that compute the answer is the same 500, not 503 timeout. See When a hook fails.

Rust errors and their causes

A 500 tells the client nothing: its body is one literal. The cause is for you, and FerraError::Internal keeps it, as an InternalError, in the error’s source() chain:

  • FerraError::Internal(InternalError) displays internal server error, and its source() is the InternalError, which displays internal error. The cause (a database error, the error a hook returned) is one link further. Neither Display repeats it, so a log line that prints the error with {err} carries no database message, and the response body never does.
  • A database cause has a SQLSTATE: InternalError::sqlstate() returns the five characters (40001, 55P03…) when the database’s own answer carried one, and None otherwise. Ferra logs a database cause as its SQLSTATE and nothing else, because a Postgres message can quote the request’s values. The full chain stays reachable through source() for your own subscriber, which then owns the question of what it may print.
  • The same holds for a HookError: after a ? on a FerraError, its source() returns that error, so the Debug of a HookError can quote the Postgres error, row values included. Do not log a HookError with {:?} where row values are sensitive.
  • To answer a 500 from a route of your own, wrap the cause: InternalError::new takes a text or any error.
#![allow(unused)]
fn main() {
use std::error::Error;

use ferra::{FerraError, InternalError};

fn ledger_is_out_of_sync(cause: std::io::Error) -> FerraError {
    FerraError::Internal(InternalError::new(cause))
}

let err = ledger_is_out_of_sync(std::io::Error::other("the ledger file is locked"));
assert_eq!(err.to_string(), "internal server error");
let internal = err.source().unwrap();
assert_eq!(internal.to_string(), "internal error");
assert_eq!(internal.source().unwrap().to_string(), "the ledger file is locked");
}

Before 0.14.0 FerraError::Internal held a String and FerraDbError::Db held the sea_orm::DbErr itself; see Migrating from 0.13 to 0.14.

Consumer-side branching

The recommended consumer pattern is to compare the wire type field against the URI constants — never against the Display form of the error. The URI is the wire contract; the message text is not.

#![allow(unused)]
fn main() {
fn what_to_do(body: &serde_json::Value) -> &'static str {
    match body["type"].as_str() {
        Some("https://ferra.rs/errors/not_found") => "404: the resource is not there",
        Some("https://ferra.rs/errors/validation") => "400: extractor failure",
        Some("https://ferra.rs/errors/validation_failed") => "422: a #[field(...)] rule was violated",
        Some("https://ferra.rs/errors/conflict") => "409: a unique constraint, or a parent that still has children",
        Some("https://ferra.rs/errors/payload_too_large") => "413: split the request",
        Some("https://ferra.rs/errors/rate_limited") => "429: check Retry-After",
        Some("https://ferra.rs/errors/unauthorized") => "401: send a valid token",
        Some("https://ferra.rs/errors/forbidden") => "403: the rule refuses this caller",
        Some("https://ferra.rs/errors/invalid_cursor") => "400: restart from the first page",
        Some("https://ferra.rs/errors/unsupported_media_type") => "415: send application/json",
        Some("https://ferra.rs/errors/internal") => "500: retry with backoff",
        _ => "not an error of Ferra's namespace",
    }
}
}

Server-side, when handling a FerraError value (for example, when mapping to a custom log line or a metrics tag), use the typed FerraError::error_type method:

#![allow(unused)]
fn main() {
use ferra::FerraError;

fn log_one(err: &FerraError) {
    tracing::warn!(error_type = err.error_type(), "request failed");
}
}

FerraError::error_type returns the URI of each of the eleven variants. Two URIs, payload_too_large (413) and rate_limited (429), reach the wire through middleware layers and are never observed as FerraError values.

OpenAPI schema constraint

The OpenAPI spec the framework emits at /docs/openapi.json constrains ProblemDetails.type to the closed ERROR_TYPES set as an enum. SDK generators (orval, openapi-generator, kiota, …) produce a typed union over the eight URIs rather than a free-form string — consumers in TypeScript, Go, Python, etc. branch exhaustively on the wire type value.

For an AI coding assistant generating client code: the type field is an enum, not a free-form string. Synthesising a value outside the eight URIs above fails OpenAPI schema validation against the spec.

Observability events

Two structured tracing events fire alongside the wire surface of the error namespace and the deprecation surface. Both follow the <snake-cased crate name>::<event segment> target convention so an operator can filter them independently via tracing-subscriber’s EnvFilter (RUST_LOG=ferra_http::sunset=warn, etc.).

TargetLevelTriggerDocumented at
ferra_http::rate_limitWARNevery 429 emission from the governor middlewarethis file § “rate_limited — 429”
ferra_http::sunsetWARNonce per (version, sunset) per process when a request lands past the declared sunset datefoundry.md § “Post-sunset warn-event”

The post-sunset event carries five fields (version, sunset, days_overdue, http.method, http.target); the rate-limit event carries three (http.method, http.target, http.retry_after_seconds). Both event-schemas are contracts under ADR-0015 §“event schema is a contract” — additive widenings only, never renames. In both, http.target is the request path: the query string never reaches these events (ADR-0076).

When the observability Cargo feature is on, the framework ALSO advances a metrics::counter! named ferra.sunset.post_sunset_hits on every post-sunset hit (regardless of the once-per-process dedup that gates the warn-event). See foundry.md § “Post-sunset warn-event” for the full surface.

Adding a new URI

The framework’s URI namespace is closed by design: a new variant requires a coordinated change across three surfaces.

  1. Add the URI literal to ERROR_TYPES in crates/ferra-core/src/error.rs.
  2. Extend the OpenAPI emitter so ProblemDetails.type carries the new value in its enum constraint (the emitter reads ERROR_TYPES directly; this step is automatic once step 1 lands).
  3. Publish at least one HTML anchor on https://ferra.rs/errors/<variant> returning HTTP 200, so that AI agents and human readers reach a stable documentation page for the new variant.

The release-blocking CI gates verify (1) source-side closure (error_types_closed) and (3) network-side resolution (uri_resolution_probe, both xtask binaries). New variants without all three gates green fail the build.

The closed-namespace contract is recorded in ADR-0026. The contract is not load-bearing for consumer correctness — the URI table above is self-contained.
