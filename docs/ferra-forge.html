Ferra.rs — User Guide

ferra-forge — the #[derive(FerraModel)] derive

Reader contract. This page stands on its own. A reader with only this page plus standard Rust and Sea-ORM knowledge can produce a compiling entity on the first attempt. Cross-references to ADRs and the constitution are non-load-bearing — every correctness cue is spelled out below.

ferra-forge is the Ferra proc-macro crate. It exports one procedural derive, #[derive(FerraModel)], which binds a Rust struct to its static ferra::meta::ModelMeta description. The derive cohabits with Sea-ORM’s DeriveEntityModel on the same struct — neither replaces the other; both read the struct.

Dependencies. The examples on this page assume the dependencies of Getting started:

[dependencies]
ferra   = { git = "https://github.com/ferra-rs/ferra", tag = "v0.15.0" }
sea-orm = { version = "2.0", default-features = false, features = ["macros", "runtime-tokio-rustls", "sqlx-postgres"] }
tokio   = { version = "1", features = ["macros", "rt-multi-thread"] }
axum    = "0.8"
serde   = { version = "1", features = ["derive"] }

Canonical entity shape (sibling-derive)

The canonical entity is a plain Rust struct with six derives and three container attributes (a table, a posture, and optionally more):

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};

#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "bearer")] // the posture: `"bearer"`, `"none"`, or an `#[authorize(...)]` block
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
    pub release_year: Option<i32>,
    pub rating: f64,
}

// Sea-ORM boilerplate that `DeriveEntityModel` relies on.
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}

impl ActiveModelBehavior for ActiveModel {}
}

Key facts:

  • DeriveEntityModel is the Sea-ORM half. It owns the #[sea_orm(...)] namespace, generates the Entity, Column, PrimaryKey, Relation, and ActiveModel types, and is required on every FerraModel struct.
  • FerraModel is the Ferra half. It reads #[sea_orm(primary_key)] and #[sea_orm(table_name)], plus the #[ferra(...)] namespace, and emits a static ModelMeta that every downstream Ferra crate reads.
  • Serialize + Deserialize are required by the FerraModel supertrait bound. ferra-forge does not auto-inject them — see the next section.
  • Visibility must be at least pub(crate). Private structs trip class 8 (FRG-008) of the Troubleshooting table.

Relations

A model written with #[sea_orm::model] (Sea-ORM’s dense form) may declare its relations inline, as HasMany<..>, HasOne<..> or BelongsTo<..> fields. The macro expands the struct twice: Model keeps the scalar fields, a second struct ModelEx keeps all of them. #[derive(FerraModel)] runs on both. On Model it reads the columns as ever, so a relation field is never a column, a wire field or a projection field. On ModelEx it emits the relation metadata and nothing else.

use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod client {
    use super::*;

    #[sea_orm::model]
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "clients")]
    #[ferra(auth = "none")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub name: String,
        #[sea_orm(has_many)]
        pub contexts: HasMany<super::context::Entity>,
    }

    impl ActiveModelBehavior for ActiveModel {}
}

mod context {
    use super::*;

    #[sea_orm::model]
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "contexts")]
    #[ferra(auth = "none")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub client_id: i32,
        #[sea_orm(belongs_to, from = "client_id", to = "id")]
        pub client: BelongsTo<super::client::Entity>,
    }

    impl ActiveModelBehavior for ActiveModel {}
}
fn main() {}

A relation field is only valid in this form. On a struct that is not an expansion of #[sea_orm::model], such as a hand-written Model with an enum Relation, it is refused (FRG-125, see ferra-forge-diagnostics.md). The split form stays valid for a model without relation fields.

Explicit serde derives are required

ferra-forge does not add #[derive(Serialize, Deserialize)] for you. If you omit them, rustc fires E0277 with the span pinned to your struct’s name:

error[E0277]: the trait bound `Model: serde::Serialize` is not satisfied
  --> src/my_module.rs:7:12
   |
 7 | pub struct Model {
   |            ^^^^^ unsatisfied trait bound
   |
   = note: for local types consider adding `#[derive(serde::Serialize)]` to your `Model` type
note: required by a bound in `_assert_ferra_model_bounds`

The fix is always the same: add #[derive(Serialize, Deserialize)] to the derive list.

Why not auto-inject? A user with use serde::Serialize as S; #[derive(S)] would trip a naive name-based detector into silent double-derive and hit E0119 conflicting-impls. Delegating to the trait-bound solver is correct by construction.

Three attribute namespaces, two policies

ferra-forge reads three attribute namespaces with deliberately different handling:

NamespaceOwnerPurposeUnknown-key policy
#[sea_orm(...)]Sea-ORMPersistence shape (table name, primary key, column type)silently ignored by ferra-forge
#[ferra(...)]FerraExposure flags (read_only, write_only, skip, resource)hard compile_error!
#[field(...)]FerraDeclarative validation rules (min_length, email, …) — see § Validation rules; query markers (filterable, sortable, cursor_key, pagination.md); owner; json, json(max_depth = .., max_bytes = .., schema = ..) for a JSON document (ferra-core.md § JSON documents)hard compile_error! (FRG-213)

The asymmetry is load-bearing. Consider the worked example:

// Security-critical typo. The user MEANT `write_only`.
#[ferra(writeonly)]
pub password_hash: String,

(The complete model of this typo, bad and good, compiled, is FRG-308.)

Because #[ferra(writeonly)] is not recognised, the build fails:

error: FRG-308: `#[ferra(writeonly)]` is not a recognized attribute
         help: did you mean `write_only`?
         note: see docs/user-guide/ferra-forge-diagnostics.md § FRG-308
  --> src/models/user.rs:12:13
   |
12 |     #[ferra(writeonly)]
   |             ^^^^^^^^^

If Ferra had accepted the typo, password_hash would quietly serialise into API responses — a Broken Object Property Level Authorization (OWASP API Top 10 #3). The hard-fail rule makes this class of bug unshippable.

Conversely, an unknown-to-Ferra but Sea-ORM-permitted key such as #[sea_orm(rename_all = "camelCase")] passes through Ferra silently — it is Sea-ORM’s concern, not Ferra’s, and pre-validating it inside ferra-forge would saddle Ferra with every Sea-ORM minor-release vocabulary change.

Where each namespace goes

The derive reads each namespace in one place only. An attribute written somewhere else used to compile and do nothing, which for a security declaration is the worst outcome; from 0.14.0 it is refused with FRG-138, spanned on the attribute path.

#[ferra(...)]container keys (auth, resource, projection(...), system_only, …)field flags (read_only, write_only, skip, computed)

#[authorize(...)]the model’s rulesrefused, FRG-138: a field’s rule is #[field(read = …, write = …)]

On a relation field of the dense #[sea_orm::model] form, every Ferra attribute above is refused with FRG-122 instead.

Field names on the wire

The JSON name of a field is its Rust name (release_year) unless the model says otherwise. One declaration switches every field of the model to camelCase:

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "bearer", rename_all = "camelCase")]
#[ferra(projection(name = "summary", read = [id, film_title], write = [film_title]))]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    #[field(filterable, sortable)]
    pub film_title: String,
    #[field(filterable, sortable)]
    pub release_year: i64,
    #[field(owner)]
    pub owner_id: Uuid,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

                                  "ownerId": "0190a4a0-…", "_links": {…}}

That is the only thing to write. Do not add #[serde(rename_all = ...)]: Ferra translates the names itself, in both directions, and a serde rename does not compile (FRG-116, below).

Rules

  • Accepted values: "camelCase" and "snake_case" (the default — same as no attribute). Any other value does not compile (FRG-325). There is no per-field rename in 0.9.0.

  • The Rust names are not names of the API any more: a body key release_year is refused with 422 (unknown field), filter[release_year] and sort=release_year with 400 — the answer lists the accepted names.

  • The conversion is serde’s camelCase rule: each _ is dropped and the next character upper-cased; the first character is lower-cased.

    RustJSON
    release_yearreleaseYear
    owner_idownerId
    line_2line2
    a__baB
    _privateprivate
    r#typetype

  • Two fields must not end up with the same JSON name (line_2 and line2), and no field may be named _links on the wire — the key Ferra adds to every response object. Both are compile errors (FRG-326).

What is not renamed

  • URL paths and the resource name (/films, /summary/films/1).
  • The keys Ferra adds around your fields: items, page, per_page, total, next_cursor, _links; the query parameters page, per_page, cursor, sort, filter[...]; the members of an error body (type, title, status, detail, errors).
  • What your own code serializes. The translation is done by the routes Ferra generates. A handler of yours that returns the Model serializes it with serde: Rust names, and every field. Answer with a struct of your own in that handler.

A serde attribute that changes a field’s JSON name, presence or text would bypass the translation above, so it does not compile (FRG-116):

A #[serde(...)] attribute Ferra cannot read is refused too. To keep a field out of the API, use Ferra’s own markers: #[ferra(skip)] (never in the API), #[ferra(read_only)] (never written by a client) or #[ferra(write_only)] (never returned). #[sea_orm(rename_all = "...")] is unrelated: it names SQL columns.

#[ferra(write_only)] is structurally excluded from every read

#[ferra(write_only)] is the framework’s load-bearing primitive for fields that must be inbound-accepting but never outbound-leaking — canonically a password hash, an API-key plaintext, or any other write-side credential.

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(DeriveEntityModel, FerraModel, Serialize, Deserialize, Clone, Debug, PartialEq)]
#[sea_orm(table_name = "users")]
#[ferra(auth = "bearer")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub email: String,
    #[ferra(write_only)]
    pub password_hash: String,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

What the framework guarantees:

  • POST /users and PUT /users/{id} accept password_hash in the request body, validate it, and persist it through the standard insert / update pipeline.
  • Every read response — single-item GET /users/{id}, collection GET /users, and the create / update response envelopes — omits password_hash. There is no header, query parameter, or Accept: variant that flips the field on.
  • The same exclusion applies to every named projection: the auto-derived {Model}{Projection}ReadProjection struct emitted by ferra-forge does not have the field as a member, so the type system itself blocks any future handler from re-introducing it.

Structural-by-construction, not runtime-filter

The ferra-forge proc-macro emits one pub struct {Model}ReadProjection per model, whose field list does not contain any #[ferra(write_only)] field. Two things keep the field out of a response:

  • the generated routes serialise the model to a JSON value and keep only the keys of the route’s read projection (projection.rs), so the field is dropped at run time, before the JSON leaves the framework;
  • the resource access (Resource<M>) returns <M as FerraViews>::Read, the struct above, which has no such member: a hand-written route that answers with it cannot leak password_hash, because the field does not exist on the type the response carries.

Prior to 0.6.5 the exclusion lived only in the OpenAPI emitter and a runtime serialiser filter; the 0.6.5 promotion to a structural guarantee closes the OWASP API #3 mitigation gap.

Generated items: the views of a model

Next to the projection structs, #[derive(FerraModel)] emits what the resource access speaks (FerraViews, ADR-0058):

  • {Model}Patch: one Option<T> per field of the bare route’s write projection (write-only fields included, the key, the owner and read-only fields not). A nullable field is Option<Option<T>>: None leaves the column, Some(None) writes null. An unset entry is left out when the patch is serialized (RFC 7396).
  • impl From<{Model}> for {Model}ReadProjection, and for every named read projection: a field-by-field move. On a #[behavior(timestampable)] model the two stamps are Option<DateTime> members the projection lists, None here: the model does not carry the columns.
  • impl FerraViews for {Model}: Read, Write and Patch name the structs the bare route serves, or those of the projection promoted with default = true; Ferra puts the stamps of a row into Read.

There is no “opt-in” — FRG-305 rejects the obvious workaround

Listing a #[ferra(write_only)] field in any projection’s read = [...] is rejected at compile time with diagnostic FRG-305:

error: FRG-305: projection `admin` lists field `password_hash` in `read`, but the field is declared `#[ferra(write_only)]`
         help: remove the ident from `read = [...]`, or remove `#[ferra(write_only)]` from the field declaration
         note: the write-only declaration is enforced by construction — a write-only field cannot appear in any read projection's struct; see docs/user-guide/ferra-forge-diagnostics.md § FRG-305
  --> src/models/user.rs:16:55
   |
16 | #[ferra(projection(name = "admin", read = [id, email, password_hash]))]
   |                                                       ^^^^^^^^^^^^^

If you genuinely need the field to appear in some read surface, the resolution is to drop #[ferra(write_only)] from the field declaration entirely. The field then appears in every read by default; use #[ferra(skip)] or a per-projection read = [...] allowlist to scope the surfaces that include it. See projections-and-routing.md for the projection key set and the auto-derived URL prefix contract.

The full FRG-3NN diagnostic family for write-only-related mistakes (FRG-302 through FRG-307, FRG-314) is documented in ferra-forge-diagnostics.md.

Computed fields

A field tagged #[ferra(computed)] (with #[sea_orm(ignore)]) is server-derived: it has no column, the client never writes it, and the application’s impl FerraComputed fills it, one computed field at a time. computed-fields.md is the page of the feature: the declaration, the two per-field hooks and the ModelComputed enum the derive hands them, what Ferra refuses, when the hooks run, and what a failure answers.

Removed in 0.9.0: exposure

#[ferra(exposure = "auto_read_only" | "auto_crud" | "auto_crud_with_embeds")] is a compile error since 0.9.0 (FRG-106). The waiver let a model mount without an authorization posture, and every value — auto_read_only included — mounted all routes, writes included, with no authentication.

Declare a posture instead:

  • #[ferra(auth = "none")] for a deliberately public model;
  • #[ferra(auth = "bearer")] for a protected one, mounted with .with_auth::<YourClaims>(jwt);
  • an #[authorize(...)] block for per-operation rules. For a public, read-only surface, write list = Anyone, get = Anyone and close the writes (create = IsAdmin, update = IsAdmin, delete = IsAdmin).

Validation rules

Ferra’s third attribute namespace, #[field(...)], declares validation rules that fire at the API edge — before persistence, on every POST (create) and PUT (update) request. A payload that violates any rule is rejected with a 422 Problem+JSON body whose errors array ({field, code, message}) names every offending field; a payload that satisfies every rule flows on to persistence unchanged. Validation is opt-in: a model carrying no #[field(...)] attributes behaves identically to one written before the namespace existed.

The full 422 wire shape and consumer-side branching pattern live in Error Handling § Validation failures (422); this section pins the model-side declaration grammar.

The eight rules at a glance

A rule applied to an incompatible field type is FRG-207 / FRG-208 / FRG-209 / FRG-212 depending on the rule. A wrong-shape literal (a string where an integer is expected, an empty regex) is FRG-201 through FRG-205. Every code surfaces with a span anchored on the offending token, and multiple independent mistakes on the same struct surface in a single cargo check round-trip rather than the first-and-stop pattern.

Combined-rule example (the most common shape)

The headline call site is a single #[field(...)] carrying multiple rules separated by commas, on a struct that already derives FerraModel and Sea-ORM’s DeriveEntityModel:

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "users")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,

    #[field(min_length = 1, max_length = 255)]
    pub display_name: String,

    #[field(min = 0, max = 120)]
    pub age: i32,

    #[field(email)]
    pub contact_email: String,

    #[field(pattern = r"^[a-z0-9-]+$")]
    pub slug: String,

    #[field(url)]
    pub homepage: String,

    #[field(required)]
    pub bio: Option<String>,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

Two or more #[field(...)] attributes on the same field accumulate in source order — #[field(min_length = 1)] #[field(max_length = 255)] is identical to #[field(min_length = 1, max_length = 255)]. Two #[field(...)] attributes on two different fields are independent; each field’s rule list is evaluated in isolation against that field’s value, and every violation observed on the request is aggregated into a single 422 response (Ferra never short-circuits on the first failed rule).

Per-rule details

min_length = N and max_length = N

Fires on String and Option<String> fields. The literal N is a non-negative integer that fits in u32. On Option<String> the rule applies only when the value is Some(..) — a None is not a length violation (use required to forbid None outright).

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    #[field(min_length = 1, max_length = 255)]
    pub title: String,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

A POST /films with {"title": ""} returns 422 with an errors entry title / min_length / “must be at least 1 character” (singular — length rules pluralise only when N != 1). A 300-char title returns 422 with an entry title / max_length / “must be at most 255 characters”.

Length rules count Unicode scalar values, not grapheme clusters or UTF-8 byte length — see § Unicode counting below.

min = N and max = N

Fires on i32, i64, f64, and their Option<…> forms. The literal type must match the field’s declared numeric type: min = 1.5 on an i32 field is FRG-203. Integer literals on f64 fields are accepted (and coerce to 0.0-style values).

A POST /ratings with {"score": 99} returns 422 with an entry score / max / “must be at most 10”.

pattern = "regex"

Fires on String and Option<String> fields. The literal is a non-empty string carrying a regex-crate pattern (NOT PCRE). The regex crate has no lookaround and no backreferences — the syntactic features that drive catastrophic backtracking in PCRE-style engines are not even expressible. A raw-string literal (r"…") is the recommended shape so backslashes are not double-escaped.

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "posts")]
#[ferra(auth = "none")]

    #[sea_orm(primary_key)]

pub enum Relation {}

}

A POST /posts with {"slug": "Bad Slug!"} returns 422 with an entry slug / pattern / “does not match the required format”.

Bounded-time guarantee. Every pattern evaluation completes in time linear to the input length — O(m·n) worst-case, where m is the (compile-time-fixed) pattern size and n is the input length, per the regex crate’s upstream contract. Combined with Ferra’s default 1 MiB request-body cap, this forecloses ReDoS without a per-request timeout. You can write any regex-syntax pattern you like and submit it to user input; no pattern, regardless of shape, can cause unbounded matching time.

required

Bare flag on Option<T> fields only — no value. #[field(required)] on a non-Option field is FRG-212 (non-Option fields are required by Rust’s type system; the flag is meaningless there). On a POST request, an absent field or an explicit null both fail with "is required". A PUT request replaces the row, so it is judged as a POST is: an absent field fails with "is required", and so does an explicit null — null on the wire is a positive declaration of “set to none”, which the rule rejects. (A field omitted from a PUT body that carries no required flag is not “no change”: without a read or write rule it becomes NULL; with one it is kept.) A PATCH request leaves an absent field alone, and refuses an explicit null on it with "is required".

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;

Propagation to the OpenAPI document

Every #[field(...)] rule you declare propagates into the emitted OpenAPI 3.2 document under the canonical JSON Schema keyword for the rule. SDK generators that consume the spec (orval, openapi-generator, kiota, …) and UI tooling that drives form validation off the spec (react-jsonschema-form, JSON-Forms, …) receive the same rules the server enforces — no parallel maintenance, no spec/server drift.

#[field(...)] ruleOpenAPI keywordWhere it lands
min_length = NminLength: Nproperties.<field>
max_length = NmaxLength: Nproperties.<field>
min = Nminimum: Nproperties.<field>
max = Nmaximum: Nproperties.<field>
pattern = "<regex>"pattern: "<regex>"properties.<field>
emailformat: "email"properties.<field>
urlformat: "uri"properties.<field>
required(field name added to schema’s required: [...])<schema>.required

Per-projection coverage. Keywords appear on every projection in which the field appears: the read projection (Film), the create-input projection (CreateFilmInput), and the update-input projection (UpdateFilmInput). A field excluded from one projection (for example, a #[ferra(read_only)] field is excluded from the create-input projection because it is not writable) does NOT appear in that projection’s properties map — but its keywords continue to appear on the read projection because the rules describe the persisted state, not only the input shape.

Note on url → format: uri. JSON Schema’s vocabulary uses uri, not url — the rule name on the Rust side stays as the friendlier url, but the emitted spec uses the JSON Schema canonical name. SDK generators look up format: uri.

Combined rules merge into one property schema. A field carrying #[field(min_length = 1, max_length = 255, pattern = "^[A-Z][a-z]+$")] produces:

"title": {
  "type": "string",
  "minLength": 1,
  "maxLength": 255,
  "pattern": "^[A-Z][a-z]+$"
}

The keyword order in the JSON output is not contractual; the keyword set is.

Required behaviour. The #[field(required)] rule on an Option<T> field adds the field name to the create-input and update-input projections’ required: [...] arrays — it does NOT inject a "required": true keyword on the per-property schema (JSON Schema does not have one; required-ness is a parent-schema concern). The same array also includes every non-Option field, matching Rust’s “non-Option means required” semantics on the wire.

No-rules opt-in. A model that declares zero #[field(...)] rules emits a spec byte-identical to its 0.5.x equivalent. Validation surfaces only when you opt in.

Default messages and localisation

Every rule emits a hard-coded English message as its violation text — the literal strings shown in the table above. Length rules pluralise “character” only when N != 1: min_length = 1 produces "must be at least 1 character" (singular) while min_length = 5 produces "must be at least 5 characters" (plural). Ferra does not support per-field, per-rule message overrides or Accept-Language-driven locale negotiation; neither is scheduled.

If you need localised error text on the consumer side, branch on the code of each entry of the response’s errors array (see ferra-error-handling.md § Validation codes) and rewrite the message client-side; do not match on the message text. SDK consumers that have to rewrite the body server-side can do so in a Tower middleware layer applied after the framework’s IntoResponse runs.

Unicode counting

Length rules count characters as the underlying validation crate counts them: chars().count() on the underlying &str, which counts Unicode scalar values. The framework does not interpose a custom counting policy in 0.6.0 — there is no NFC normalisation pass, no grapheme-cluster counting, no UTF-16 code-unit counting.

The practical consequence: a 10-emoji string may not have a length of 10 by your reader’s intuition. The grinning-face emoji 😀 is one scalar value (one chars() count), but some emoji sequences (skin-tone modifiers, ZWJ-joined family emoji) are several scalar values — a single visible glyph may count as 2, 4, or more. If your length rule needs to count “what the user sees”, reach for the typed-escape path below and write a hand-rolled rule that walks unicode-segmentation graphemes.

When the eight rules are not enough — typed escape via ferra::garde

The eight-rule namespace is a closed contract surface for 0.6.0. For rule shapes the surface does not cover — a custom function predicate, a locale-aware rule, a regex syntax beyond the regex crate, a grapheme-cluster-aware length count — Ferra re-exports the underlying validation crate at ferra::garde so you can hand-roll a garde::Validate impl on your model:

#![allow(unused)]
fn main() {
use ferra::garde::{self, Validate};

// `MyModel` is a model of yours that carries no `#[field(...)]` rule.
struct MyModel;

impl Validate for MyModel {
    type Context = ();

    fn validate_into(
        &self,
        _ctx: &Self::Context,
        _parent: &mut dyn FnMut() -> garde::Path,
        report: &mut garde::error::Report,
    ) {
        // your hand-rolled checks here, appending to `report`
    }
}
}

The escape is the documented fallback — neither encouraged nor forbidden, used when the closed set is insufficient. It is not part of the v1 #[field(...)] contract surface; the rule shape and the trait surface follow the upstream garde crate’s evolution, not Ferra’s. Use it sparingly: every model that hand-rolls validation is a model the #[field(...)] diagnostics no longer protect.

Hand-rolling a Validate impl on a model that ALSO carries #[field(...)] rules is a duplicate-impl error at compile time. The two paths are exclusive: either the framework generates the impl from your declarative rules, or you write it yourself.

Primary keys

The server chooses the key of a new row, unless the model says otherwise:

  • a single i32 / i64 key: the database (SERIAL or an identity column). Do not mark it auto_increment = false.
  • a single Uuid / ferra::Id key: Ferra generates a UUID v7.
  • anything else — a composite key, a natural key (String), an integer the client assigns — needs #[ferra(client_pk)]: the create body carries every key field, and the update body never does (the path names the row).

Without client_pk, a key the server cannot generate does not compile (FRG-319). A key field in a projection’s write = [...] list does not compile either (FRG-318): the key is never written by an update.

Composite primary keys

A model can carry two or more #[sea_orm(primary_key)] markers; it then needs #[ferra(client_pk)].

A worked example with (tenant_id: Uuid, document_id: i64):

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(
    Clone, Debug, PartialEq,
    DeriveEntityModel, FerraModel,
    Serialize, Deserialize,
)]
#[sea_orm(table_name = "documents")]
#[ferra(auth = "none", client_pk)]
pub struct Model {
    #[sea_orm(primary_key, auto_increment = false)]
    pub tenant_id: Uuid,
    #[sea_orm(primary_key, auto_increment = false)]
    pub document_id: i64,
    pub title: String,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]

}

#[sea_orm(auto_increment = false)] is required on every PK field in a composite key — PostgreSQL SERIAL only synthesises a value for one column per table, so the application supplies an explicit value on every insert.

A route of your own reads a row of such a model through Resource<M>: the key is the tuple of the key fields, in declaration order.

use axum::{Json, extract::Path};
use ferra::{FerraError, Resource};
use ferra::model::FerraViews;
use ferra::FerraModel;
use sea_orm::entity::prelude::*;

    #[sea_orm(table_name = "documents")]

    pub struct Model {
        #[sea_orm(primary_key, auto_increment = false)]

}

The _links.self.href shape on a fetched row:

{
  "_links": {
    "self":       { "href": "https://api.example.com/documents/<tenant>/<doc>" },
    "collection": { "href": "https://api.example.com/documents" }
  }
}

Ferra supports any N >= 1. A three-key composite ((tenant_id, year, sequence)) emits GET /issued_documents/{tenant_id}/{year}/{sequence} with three OpenAPI parameters. The framework does not impose an upper bound; in practice 2-4 keys cover the working set (multi-tenant isolation, time-bucketed sequencing, partition keys). The N=0 case continues to fail at compile time with the existing “this model has no primary key” diagnostic — composite primary keys are a widening of the legacy single-PK rule, not a relaxation.

The body of an action: #[derive(ferra::ActionBody)]

An action that takes a value (action(.., body = ProgressBody, ..), ADR-0080) types it with a struct that derives ActionBody next to Deserialize. The derive reads the struct’s fields once and that one list is what Ferra uses to refuse a key the struct does not declare (422 unknown_field), to validate the values with Ferra’s own messages, and to describe the request body in the OpenAPI document (additionalProperties: false, the validation keywords, required). A body = T whose T lacks the derive does not compile: the error says add #[derive(ferra::ActionBody)] to T and points at body = T.

use ferra::ActionBody;
use serde::Deserialize;
#[derive(Deserialize, ActionBody)]
pub struct ProgressBody {
    #[field(min = 0, max = 100)]
    pub progress: i32,
    #[field(max_length = 200)]
    pub note: Option<String>,
}
fn main() {}

What a body admits, and no more:

  • Scalar fields: a String, i32, i64, f64, bool, a Uuid or ferra::Id, a ferra::DateTime, ferra::Date or ferra::Time, or an Option of one of them. No nested object, no JSON value, no Vec (FRG-145).
  • The eight validation keys of #[field(...)] (min_length, max_length, min, max, pattern, email, url, required), as for a model. Any other key is FRG-145.
  • A field that is not an Option is required by its type. A body that leaves it out is a 400 invalid_json, because it does not deserialize, and not the 422 required of a PUT. See Declared actions.
  • No #[serde(...)] attribute, on the struct or on a field: the wire name of a field is its Rust name (FRG-116 for a rename or a reshaping attribute, FRG-145 for the others).
  • No new dependency: the application writes Deserialize as it does for a model and names neither garde nor utoipa.

Every error class 0.2.0 emits, with the exact message shape and the fix. Numbering matches data-model.md § 4 of the Smelting spec.
