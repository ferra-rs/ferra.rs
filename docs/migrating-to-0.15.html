Ferra.rs — User Guide

Migrating from 0.14 to 0.15

0.15.0 (Alloying) describes a model without invalid states. Each entry below is a break. This page grows with the release: read the entries, then update the application’s git dependency to v0.15.0. CHANGELOG.md lists every change.

FieldMeta loses its six flags and is_id: read mode

Before. ferra_core::meta::FieldMeta carried seven independent booleans, readable, writable, skip_api, read_only, write_only, computed and is_id. Any combination compiled, including the ones that mean nothing (a field that is readable and skip_api).

After. A field has one mode: FieldMode, and four const fn methods answer the questions the flags answered. FieldMode is #[non_exhaustive]: Key { read_only }, ReadWrite, ReadOnly, WriteOnly, Computed and Hidden (#[ferra(skip)]). See FieldMeta for what each variant answers.

FieldMeta::new and FieldMeta::new_with_collection_meta take a FieldMode in place of the seven flag parameters. Both are #[doc(hidden)]: the derive is the way to build a description.

Migration. Code that reads a FieldMeta (a loop over meta().fields) changes like this:

You readRead instead
f.readablef.readable()
f.writablef.writable(), which is false on a computed field
f.is_idf.is_id()
f.read_onlyf.is_read_only(), or matches!(f.mode, FieldMode::ReadOnly)
f.computedmatches!(f.mode, FieldMode::Computed)
f.write_onlymatches!(f.mode, FieldMode::WriteOnly)
f.skip_apimatches!(f.mode, FieldMode::Hidden)

A skip field that also carried read_only had f.read_only == true; f.is_read_only() answers false for it, because the field is Hidden and never appears in a document. No output changes.

#![allow(unused)]
fn main() {
use ferra::meta::{FieldMeta, FieldMode};

fn is_served(field: &FieldMeta) -> bool {
    field.readable() && !matches!(field.mode, FieldMode::Hidden)
}
}

skip with write_only or computed, or on a primary key, is refused (FRG-359)

Before. #[ferra(skip, write_only)] compiled. The field was absent from the description, the OpenAPI document and PATCH, yet POST and PUT on the bare path still wrote it. skip with computed, and skip or computed on a primary key, compiled and did nothing useful.

After. Each of the four is a compile error, FRG-359, spanned on the skip (on the computed when there is no skip).

Migration. Remove skip to keep a field the API accepts and never returns (write_only), or remove the other attribute to keep a field the API never touches (skip). On a primary key, keep neither.

A computed field has no column: add #[sea_orm(ignore)] (FRG-360, FRG-361)

Before. A #[ferra(computed)] field was a column the framework never wrote: the table held it (NULL), SELECT read it, and filterable, sortable or cursor_key on it compiled, although the value the server computes is not what the column holds.

After. A computed field is #[sea_orm(ignore)]: Sea-ORM leaves it out of every SELECT, INSERT and UPDATE, and builds it with Default (the type must implement it). Without the attribute the model is refused with FRG-360, spanned on the computed. filterable, sortable and cursor_key on a computed field are refused with FRG-361, spanned on the key.

Migration. Three steps, in this order:

  1. Add #[sea_orm(ignore)] above each #[ferra(computed)] field, and remove filterable, sortable and cursor_key from it.
  2. Add a migration that drops the column (ALTER TABLE invoices DROP COLUMN total;). Do not edit the migration that created it.
  3. Rewrite the impl FerraComputed per field (next entry). A response still carries the computed value, and a write body that names the field is still a 422 unknown_field.
#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};

#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "invoices")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub subtotal: f64,
    #[sea_orm(ignore)] // new in 0.15: the field has no column
    #[ferra(computed)]
    pub total: Option<f64>,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
impl ferra::compute::FerraComputed for Model {}
}

A computed field needs an impl FerraComputed, even unmounted (FRG-362)

Before. A model with a #[ferra(computed)] field and no impl FerraComputed compiled as long as it was never mounted; the error came only at Foundry::mount (rustc’s E0277 on Mountable).

After. It does not compile: FRG-362, on the computed field, names the impl to write. Write impl FerraComputed for Model {} (the default hooks compute nothing) or the per-field hooks.

FerraComputed computes one field at a time: match on ModelComputed

Before. FerraComputed had three methods, compute(&mut self), compute_async(&mut self, ctx) and compute_async_batch(rows, ctx), none told which field it computed. A model with two computed fields filled both in the same body.

After. The trait has two, compute_field(&mut self, field, ctx) and compute_field_batch(rows, field, ctx), and Ferra calls compute_field_batch once for each computed field, with that field’s rows. field is a variant of ModelComputed, an enum the derive writes next to the model, one variant per computed field in PascalCase (total is ModelComputed::Total). A model with no computed field is unchanged: the derive still writes the empty impl FerraComputed.

Migration. Write the impl FerraComputed as a match on the field. A synchronous computation goes in the async body; compute_async takes the same body, and compute_async_batch takes the new field parameter.

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use ferra::compute::{FerraComputeError, FerraComputed};
use ferra::request_context::RequestContext;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};

#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "invoices")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub subtotal: f64,
    pub tax: f64,
    #[sea_orm(ignore)]
    #[ferra(computed)]
    pub total: Option<f64>,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}

// 0.14: fn compute(&mut self) { self.total = Some(self.subtotal + self.tax); }
impl FerraComputed for Model {
    async fn compute_field(
        &mut self,
        field: ModelComputed,
        _ctx: &RequestContext,
    ) -> Result<(), FerraComputeError> {
        match field {
            ModelComputed::Total => self.total = Some(self.subtotal + self.tax),
        }
        Ok(())
    }
}
}

A hand-written FerraModel that also implements FerraComputed now needs the #[doc(hidden)] trait ComputedFields as well; it is outside the derive’s guarantees, as a hand-built ModelMeta is. Computed fields is the page of the feature.

A write_only owner column is no longer in the write body

Before. On a model whose #[field(owner)] column was also #[ferra(write_only)], the bare-path write body named the owner, while the description, the OpenAPI document and PATCH left it out. POST without owner_id answered 400 invalid_json (missing field owner_id); POST with it answered 201, the value replaced by the caller’s identity; PUT with it answered 200, the value dropped. A plain owner column answered 422 unknown_field to both.

After. The owner is not in the write body, whatever its other attributes. POST without owner_id answers 201 and the owner is the identity; POST or PUT with owner_id answers 422 unknown_field.

Migration. Remove owner_id from the bodies your clients send to such a model. Nothing in the OpenAPI document changes.

PaginationMode carries the cursor key: read pagination_mode.cursor_key()

Before. ModelMeta held the mode and, beside it, cursor_key_field_name: Option<&'static str> and cursor_key_field_type: Option<FieldType>. A cursor model with None in either compiled.

After. PaginationMode is #[non_exhaustive]: Page, Cursor { key, ty } and Both { key, ty }, so a cursor mode cannot exist without its key. The two ModelMeta members are gone, and PaginationMode::cursor_key() answers Some((key, ty)) for Cursor and Both, None for Page. A page-mode model no longer reports a #[field(cursor_key)] field. The hidden constructors ModelMeta::new_with_pagination and ModelMeta::new_with_auth lose the two key parameters.

Migration.

You readRead instead
meta.cursor_key_field_namemeta.pagination_mode.cursor_key().map(|(key, _)| key)
meta.cursor_key_field_typemeta.pagination_mode.cursor_key().map(|(_, ty)| ty)
meta.pagination_mode == PaginationMode::Cursormatches!(meta.pagination_mode, PaginationMode::Cursor { .. })
 
#![allow(unused)]
fn main() {
use ferra::meta::{FieldType, PaginationMode};

fn cursor_key(mode: PaginationMode) -> Option<(&'static str, FieldType)> {
    match mode {
        PaginationMode::Cursor { key, ty } | PaginationMode::Both { key, ty } => Some((key, ty)),
        _ => None,
    }
}
}

FieldMeta::validation_rules is typed: match ValidationRule

Before. validation_rules was a &'static [&'static str]: each #[field(...)] rule encoded as a short string ("min_length=1", "min=0", "pattern=^a$", "email", "required"), which the OpenAPI emitter parsed again and silently dropped when it did not know it.

After. validation_rules is a &'static [ValidationRule]. ValidationRule is #[non_exhaustive]: MinLength(u64), MaxLength(u64), Min(Bound), Max(Bound), Pattern(&'static str), Email, Url and Required, with Bound::{Int(i64), Float(f64)}. The derive emits them from the parse that also produces the request validator, and ValidationRule::schema_keyword() gives the JSON Schema keyword the document carries. The hidden FieldMeta::new, FieldMeta::new_with_collection_meta and FieldMetaInit take the typed slice. The emitted OpenAPI document does not change.

Migration.

You read or writeUse instead
"min_length=3", "max_length=3"ValidationRule::MinLength(3), ValidationRule::MaxLength(3)
"min=0", "max=1.5"ValidationRule::Min(Bound::Int(0)), ValidationRule::Max(Bound::Float(1.5))
"pattern=^a$"ValidationRule::Pattern("^a$")
"email", "url", "required"ValidationRule::Email, ValidationRule::Url, ValidationRule::Required
rules.contains(&"required")rules.contains(&ValidationRule::Required)
parsing the string to a JSON Schema keywordrule.schema_keyword()
 
#![allow(unused)]
fn main() {
use ferra::meta::{FieldMeta, ValidationRule};

fn is_required(field: &FieldMeta) -> bool {
    field.validation_rules.contains(&ValidationRule::Required)
}
}

A write body is decoded once: send each key once

Before. A key sent twice in a POST, PUT or PATCH body was read differently by each step. On a model with hooks, POST and PUT answered 500 internal (the hooks’ draft refused the duplicate that the first decoding had taken). On a model with rename_all, or without hooks, POST, PUT and PATCH succeeded with the last value, and a repeated key inside a JSON field was stored with its last value. In a declared action’s body, an unknown key sent twice was a 422 unknown_field.

After. The body is parsed once, and a key repeated in any object, at any depth, a JSON field included, is a 400 validation, code invalid_json, field body, whose message is a key is repeated at line L column C (no value of the body). The same holds for an action’s body, known key or not: a repeated unknown key is now a 400 invalid_json instead of a 422 unknown_field.

The refusals of a write also come in one order: the row’s 404 (when something reads the row; otherwise a PUT or a PATCH with no precondition header judges the body first), then 415, 412, 413, 400, the 422 unknown_field, the 403, the 422 of the bounds and the rules, and last the 400 of a required key the body does not send, so that a hidden required key never answers differently from an absent one. The visible change is that a body with an unknown key and a wrong-typed value on a key the caller may read is now the 400, where it was the 422. The type of a key the caller may not read is never judged: it is still the 422 unknown_field of an unknown key.

Migration. Send each key once. A client that builds a body by merging objects should merge before it serializes. Nothing in the OpenAPI document changes.
