Ferra.rs — User Guide

Compile-time diagnostics — the FRG-NNN namespace

Which codes exist. The derive-shape codes (FRG-001 through FRG-023, with FRG-002, FRG-004, FRG-010, FRG-012 and FRG-015 intentionally unallocated), the validation-attribute codes (FRG-201 through FRG-215), the projection, computed and write-only codes (FRG-301 through FRG-326, with FRG-313 intentionally unallocated, and FRG-306 and FRG-330 through FRG-334 retired), the behavior codes (FRG-320 through FRG-323, and FRG-327), the collection-read codes (FRG-350 through FRG-358), the authorization codes (FRG-100 through FRG-152; #[operation(...)] is refused with FRG-335, groups with FRG-137, and an attribute where the derive does not read it with FRG-138), the FerraLayer::base_path codes (FRG-340 through FRG-342) and the dependency code FRG-400.

Every example on this page is compiled. A bad example is a rust,compile_fail block, and the guide’s guide_blocks check compiles it and requires the compiler to say the code of its section, not just to fail; a good example is a plain rust block, compiled by cargo test --doc -p ferra-doc-playground. A section whose code cannot be raised by application code (retired, reserved, or guarding a type nobody outside Ferra can write) says so instead of showing an example. Where a section names a fixture, the fixture is the byte-for-byte contract of the message (.stderr).

Reader contract. This page stands on its own. A reader with only this page plus standard Rust and Sea-ORM knowledge can identify the trigger condition for any FRG-NNN error in the table below and fix the offending source on the first attempt. Cross-references to ADRs and the constitution are non-load-bearing — every correctness cue is spelled out in the per-code section.

#[derive(FerraModel)] and the #[field(...)] attribute parser emit typed FRG-NNN codes on every diagnostic. Each code is grep-friendly, span-anchored on the offending source token, and documented below with a worked-bad → worked-good example pair plus a one-sentence fix template.

ferra-forge collects independent diagnostics rather than stopping at the first mistake — multiple independent mistakes on the same struct surface in one cargo check round-trip. If any diagnostic is reported for a model, no code is generated for that model. The emitted shape carries three logical lines (error: + help: + note:) anchored to the offending token. The note: line points to the guide section that owns the rule: ferra-forge.md for most derive-shape codes, the page of the subject for a few (pagination.md, ferra-auth.md, ferra-core.md), this page for FRG-021, FRG-022 and FRG-023. FRG-018 has no note.

How to read each entry

Every section below carries:

  • Trigger. A one-sentence description of when the error fires plus the offending #[field(...)] attribute pattern.
  • Bad. A short worked example showing the mistake. Paste it, with its hidden lines, into a sandbox crate to reproduce the diagnostic.
  • Good. A 5-15-line worked example showing the fix. Replaces the bad block one-for-one — same imports, same struct shape, only the offending attribute (or field type) changes.
  • Fix. A one- or two-sentence prescription naming what to change and where.
  • Fixture. A repo-relative link to the corresponding compile-fail fixture under crates/ferra-forge/tests/diagnostics/ (or, for the authorization codes, crates/ferra-http/tests/ui/). The fixture is the byte-shape contract — a CI-checked .stderr snapshot proves the diagnostic shape stays stable across releases.

Every example is a complete model and is compiled by the guide’s checks: a bad example (compile_fail) must fail with the code of its section, a good example must compile. What every example shares is hidden, in lines that start with # (the rendered book folds them away; on a raw page they are the first and last lines of each block):

use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
// … the example …
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}                       // the Sea-ORM boilerplate
impl ActiveModelBehavior for ActiveModel {}

Every model declares a posture (#[ferra(auth = "none" | "bearer")] or an #[authorize] block, FRG-100), so that a bad example fails for its own reason and for no other. Paste a block, with its hidden lines, into a project that declares ferra, sea-orm, serde and tokio to reproduce the error.

Every model must also declare an authorization posture (see FRG-100). The authorization entries (FRG-1NN) show it; the other entries leave it out to stay short. When you reproduce one of them, add #[ferra(auth = "none")] under #[sea_orm(table_name = …)]; otherwise FRG-100 can fire next to the code you are studying, and the “Good” block does not compile.

FRG-0NN — derive-shape diagnostics (0.14.0)

The shape of the item the derive is written on, and the values of the keys of #[ferra(...)]. They come from #[derive(FerraModel)], which refuses to generate code for a model it cannot read. Until 0.14.0 these errors had no code. Each class of ferra-forge.md § Troubleshooting now has one: class N is FRG-0NN, except class 10 (FRG-302), class 12 (FRG-304) and the classes 2, 4 and 15, which have no FRG-0NN (below). FRG-017 to FRG-023 are new codes, for errors that had no class.

FRG-002, FRG-004, FRG-010, FRG-012 and FRG-015 are intentionally unallocated, like FRG-313: class 2 (composite primary keys) has been supported since 0.6.0, class 4 is historical (retired in 0.6.0, see the note on Class 4 under FRG-215), class 10 is FRG-302, class 12 is FRG-304, and class 15 is rustc’s E0277 on the serde bound. They have no section, and no number is ever recycled.

The examples declare auth = "none" so that FRG-100 does not fire beside the code being shown, and leave out the Sea-ORM boilerplate as everywhere on this page.

FRG-001 — no primary key

Trigger. No field of the model carries #[sea_orm(primary_key)]. Reported at the struct name.

error: FRG-001: this model has no primary key
         help: annotate at least one field `#[sea_orm(primary_key)]`
         note: see docs/user-guide/ferra-forge-diagnostics.md § FRG-001

Bad.

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, FerraModel, DeriveEntityModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "none")]
pub struct Model {
    pub title: String,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

Good.

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, FerraModel, DeriveEntityModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "none")]

    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

Fix. Add #[sea_orm(primary_key)] to the id field. Several fields may carry it: a composite key is supported.

FRG-003 — unsupported field type

Trigger. A field has a type Ferra does not know how to read, write and describe. Reported at the type.

error: FRG-003: type `Vec < String >` is not supported by Ferra
         help: use one of `String`, `i32`, `i64`, `f64`, `bool`, `Uuid` (or `ferra::Id`), `ferra::DateTime`, `ferra::Date`, `ferra::Time`, `serde_json::Value` (or `Json`), or `Option<T>` of any of them; a serde type stored as JSON takes `#[field(json)]`
         note: see docs/user-guide/ferra-forge-diagnostics.md § FRG-003

Bad.

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub tags: Vec<String>,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

Good.

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    #[field(json)]
    pub tags: Tags,
}

#[derive(Clone, Debug, PartialEq, Eq, Serialize, Deserialize, FromJsonQueryResult)]
pub struct Tags(pub Vec<String>);
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

Fix. Use one of the types the help line lists. A time value takes ferra::DateTime, ferra::Date or ferra::Time (FRG-017). A serde type stored as JSON is declared as in the good example: the type derives FromJsonQueryResult, and the field takes #[field(json)] (ferra-core.md § JSON documents).

Fixture. fail_unsupported_field_type.rs (a type that is not on the list, its span on the type). The other types that point at the same token are the unit tests frg_003_* of crates/ferra-forge/src/classify.rs (a sea_orm::Value, a user-named type).

FRG-005 — not a struct with named fields

Trigger. #[derive(FerraModel)] is written on an enum, a union, a tuple struct, a unit struct, or a struct with no named field. Reported at the item name.

error: FRG-005: FerraModel must be derived on a struct with named fields (not tuple structs, unit structs, enums, or unions)
         help: change the item to `pub struct <Name> { <named fields> }`
         note: see docs/user-guide/ferra-forge-diagnostics.md § FRG-005

Bad.

#![allow(unused)]
fn main() {
use ferra::FerraModel;
#[derive(FerraModel)]
#[ferra(auth = "none")]
pub enum Model {
    Draft,
    Published,
}
}

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]

impl ActiveModelBehavior for ActiveModel {}
}

Fix. Write pub struct Name { ... } with at least one named field: a model is a Sea-ORM entity.

Fixture. frg_005_enum.rs (the span on the struct’s identifier). A tuple struct, a unit struct and a struct with no field point at the same token: they are the unit tests frg_005_* of crates/ferra-forge/src/parse.rs.

FRG-1NN — authorization diagnostics (0.8.0, 0.9.0)

Every Ferra model declares who may do what. It does so with a posture (#[ferra(auth = "bearer")] — every operation needs a valid bearer token; #[ferra(auth = "none")] — deliberately public), with an #[authorize(...)] block that gives one rule per operation, or with both (the block then decides). A rule is built from five checkers — Anyone, Authenticated, IsOwner, IsAdmin, HasRole("role") — combined with + (all must pass), | (at least one passes) and parentheses. The operations are list, get, create, update, delete, plus restore on a model with #[behavior(soft_delete)].

The codes below fire when that declaration is missing, ambiguous, or would not be enforced. FRG-100 to FRG-113 come from #[derive(FerraModel)] and point at the model; FRG-150 and FRG-151 come from the Foundry mount call, FRG-152 from a handler that reaches a model’s rows. The full authorization guide is ferra-auth.md; each entry below stands on its own.

FRG-101 — #[authorize] is empty or incomplete

Trigger. One of three forms, all of which would leave an operation without a meaningful rule:

  • the block names some operations but not all of list, get, create, update, delete — the message lists the missing ones, and the error points at the struct name;
  • the block is empty: #[authorize()];

FRG-105 — authorize on a projection (removed in 0.9.0)

Retired in 0.13.0. From 0.9.0 to 0.12.x, #[ferra(projection(..., authorize = ...))] was refused with this code: the key used to compile and enforce nothing, so a projection’s routes stayed open. Since 0.13.0 a projection’s authorize is parsed, enforced and answered with a 404 for a caller it refuses, so the key is valid and this code is never raised. The section stays as history, and the number is never recycled. The new codes are FRG-117 (a projection that widens exposure must say who may use it) and FRG-118 (IsOwner is not a projection rule). If you see FRG-105, you are reading output from a Ferra release older than 0.13.0.

Trigger. #[ferra(hooks(system = T))] declares the hooks’ one system grant, and T cannot be its target. The grant bypasses the caller’s authorization on T, so Ferra checks what it can about T before it compiles. Each case below is refused, reported at the path of T (at the second key for the last):

  • T is not marked #[ferra(system_only)]: without it, T keeps its write routes and rules, and anything could write the log around the grant.
  • T has no database-generated integer primary key: a client_pk, a Uuid or a composite key. “The latest row” is the highest key, which the database must choose in commit order.
  • T has owner(from): its parent check is the caller’s authorization on the parent, and a grant bypasses it.
  • T is the hooked model itself, whatever the spelling of the path (Model, self::Model): its hooks would append to the table they run on. A model with hooks cannot be system_only (FRG-135), so the model is never a valid target and the case is the first bullet’s: the compiler’s E0277, with the same code.

T is a valid target, so the bound passes; the derive compares the two table names and fails the constant evaluation with this code (E0080), the only guard for this case.

The first three, and the hooked model itself, are the compiler’s E0277, with the FRG-130 message, on a hidden trait that only a valid target has. The shared table is a constant-evaluation error (E0080) with the same code, underlined over the whole path of T:

FRG-153 — an OpenAPI name produced twice

Trigger. Foundry::build() finds an OpenAPI component name or operationId that the mounted models register twice, and panics: the server does not start. The document keys its schemas by name, so the second registration would overwrite the first without a word, and a client generated from the document would read a model, or a projection, through the shape of another. Both registrations can come from

  • one model: a projection x-collection, whose read schema has the name of the list envelope of a projection x (FilmXCollection), or a projection collection-hal, whose read schema has the name of the HAL form of the default list envelope (FilmCollectionHal);
  • two models: Film with a summary projection, and a model FilmSummary (FilmSummary, CreateFilmSummaryInput, getFilmSummary);
  • a projection and the shared error schema: a projection details of a model Problem produces ProblemDetails, the schema every error response references.

A projection’s schemas are {Model} then the PascalCase of its name, with the Create…Input, Update…Input, …Collection and …Hal forms. collection and hal are refused at compile time (FRG-317); this code covers every other pair of names, ProblemDetails included: Ferra registers it first, and a model or projection that produces it is the second owner.

Detection site. Foundry::build() reads the names where the document registers them, so it needs no .with_docs(). The operationIds are read in the whole document built, whatever the operation: CRUD, restore, /me, a projection’s.

The application refuses to start: Foundry::build() panics, before any route is served, with a one-line message about the first name it finds twice. The two lines below are two separate panics. The first is the FilmXCollection example above (x and x-collection of the model Film). Compile-time diagnostic wrappers

Some Ferra attributes impose a trait bound on the field’s type — for example, #[ferra(computed)] requires the field’s type to implement Default (the framework supplies a compute-time placeholder by calling T::default()). When the bound is violated, rustc’s default message would be the language-level error[E0277]: the trait bound \T: Default` is not satisfied`. That phrasing is correct but tells the user nothing about why Ferra needs the bound or how to satisfy it in the Ferra-specific context.

To close that gap, ferra-core ships a small set of wrapper traits in ferra_core::diagnostics that re-export the underlying language traits under a framework-authored name and carry a #[diagnostic::on_unimplemented] annotation. The compiler reads the annotation and renders the framework’s message / label / note triple instead of its default E0277 text. The user sees a Ferra-shaped diagnostic on the first line of compiler output.

The shipped wrappers

FerraComputedDefault, FerraSend and FerraSync wrap a language trait. FerraAuthConfigured and FerraMountableWithoutAuth wrap nothing: they are markers the derive writes for you, and the only fix for a missing one is on the model (or on the Foundry chain), never a hand-written impl. The two authorization markers are documented under FRG-150 and FRG-151. HoldsResource, the sealed trait behind FRG-152, is the same kind: a bound with a message, and nothing to implement.

The canonical diagnostic shape

The compiler renders a #[diagnostic::on_unimplemented] failure as three lines anchored on the offending type. The message is the top-line error: …; the label is the inline span annotation pointing at the offending position; the note is the bottom-line fix hint. For FerraComputedDefault:

error: `NotDefault` does not implement `Default`, but it is required for fields marked `#[ferra(computed)]`
  --> src/model.rs:LL:CC
   |
LL |     pub total: NotDefault,
   |                ^^^^^^^^^^ this type must implement `Default` for ferra-forge to supply its compute-time placeholder
   |
   = note: add `#[derive(Default)]` on `NotDefault`, or provide an explicit `impl Default for NotDefault`.

The framing — is required for fields marked \#[ferra(…)]`plus the explicitferra-forgereference in thelabel— is how a consumer (human or AI) recognises a Ferra wrapper diagnostic versus a generic rustc message. Whenever you see one of these triples, thenote:line names the fix verbatim; apply it on the offending type and re-runcargo check`.

Migration when an upgrade introduces a new wrapper-trait bound

Future Ferra releases land additional bounds (e.g. FerraAuthConfigured at 0.8.0). When an upgrade triggers a previously-passing compile to fail with a new wrapper-trait diagnostic:

  1. Recognise the framing. The message line names a Ferra attribute or generation context (required for fields marked \#[ferra(…)]`, FRG-150: … has no declared authorization posture`, …) rather than a bare language trait.
  2. Read the note: line. It names the concrete fix — a missing #[derive(...)], a missing impl, or a missing attribute on the model.
  3. Apply the fix at the named site. The diagnostic’s --> path:LINE:COL anchor points at the exact source position; the wrapper-trait substrate guarantees the fix is local to the type or the model under the cursor.

The per-code FRG-3NN sections below cite individual diagnostics; the wrapper-trait substrate is shared by every emission that imposes a typed bound on user fields (the FerraComputedDefault consumer site is documented under FRG-3NN — computed/projection codes that share the wrapper substrate).

Computed-field default-value diagnostic

A #[ferra(computed)] field is computed by the framework at serialise time. The default emission strategy substitutes T::default() for the field’s value when reading the entity off the database — so the field’s type must implement Default. The proc-macro emits a bound assertion through the FerraComputedDefault wrapper trait (see Compile-time diagnostic wrappers) so the diagnostic surfaces the framework-authored triple instead of rustc’s generic E0277 text.

FRG-316 — default = true requires promotes_from + breaking_change_version

Trigger. Three triggers, one code:

  • A projection declares default = true without both promotes_from = "..." and breaking_change_version = "..." attestations on the same declaration. Setting default = true replaces the bare-path response shape — a silent breaking change to the public API contract (consumers continue requesting /{resource}/{id} and receive a different schema). The two attestations force the change to be visible in the source. Reported at default = true.
  • A projection declares promotes_from without default = true (0.14.0). The attestation says what a promoted projection replaces; on any other projection it was read and dropped. Reported at the promotes_from key.
  • The value of promotes_from is neither "auto-derived" nor "named:<name>" with <name> another projection declared in the same model (0.14.0): "named:ghost" for a projection that does not exist, "v1" for a name written without named:, and the projection’s own name (a projection was not its own previous default). Reported at the value.

Why both are required. promotes_from names what is being replaced ("auto-derived" for the framework’s default, or "named:<other>" for a previous named-default projection). The macro checks the value against the projections the model declares, anywhere in the model, and never against repository history: a former named default that you removed in the same change can no longer be named (use "auto-derived"). breaking_change_version surfaces in the OpenAPI document as the x-ferra-promoted-in: "X.Y.Z" vendor extension on every operation under the bare resource path, so SDK consumers and downstream tooling can detect the silent break.

Nothing compares a model’s bare-path default with an earlier build: a lockfile that would record each model’s default and a hash of its schemas, and fail the build on a drift, is not planned. The two attributes above are the only protection, so a copied attestation that nobody re-read is not caught.

FRG-400 — two copies of Sea-ORM

Trigger. The application declares sea-orm in its own [dependencies], and cargo resolved that declaration and the one of ferra to different versions: the build holds two copies of the crate. Ferra’s routes read and write through ferra::sea_orm; every Sea-ORM type the application names is then a different type from the one Ferra expects. Without this code the compiler words it as “expected DatabaseConnection, found DatabaseConnection”, far from the cause. #[derive(FerraModel)] checks it, at the model, wherever the application’s sea-orm is there next to ferra, under the condition of the dependency itself:

  • sea-orm in [dependencies]: in every build;
  • sea-orm with optional = true: in the builds where one of the features that enable it is on (#[cfg(feature = "…")]: the implicit feature named like the dependency, or the features that write "dep:sea-orm" or "sea-orm/…");
  • sea-orm under [target.'cfg(…)'.dependencies]: where that cfg(…) holds;
  • sea-orm in [dev-dependencies]: under #[cfg(test)], which is the crate’s unit tests, integration tests (tests/) and benches. An example (examples/) has the dev-dependency too but nothing in the code tells it apart from the ordinary build, so there two copies show as the compiler’s own “expected DatabaseConnection, found DatabaseConnection”;
  • sea-orm under [target.<triple>.dependencies], named by a target triple and not by a cfg(…): no check, for the same reason.

Where the application’s copy is not there, the derive reaches Sea-ORM through ferra::sea_orm, and there is one copy to compare. A model with projections may add type errors of its own after FRG-400 under such a condition.

The rule: a Ferra project never holds two major versions of Sea-ORM, not even for its tests or an optional feature. The check is armed by the condition of the dependency, so a sea-orm = "1" that is only a dev-dependency, or only behind a feature (full = ["dep:sea-orm"]), is refused as soon as that condition holds (cargo test, --features full), next to a model written through the facade (use ferra::prelude::*;). Before 0.9.0 this compiled by accident; it is refused on purpose, because the model and Ferra’s routes would then speak of two different DatabaseConnections whenever the test or the feature is on. A declaration that is never active (a cfg(any()) table, an optional dependency no feature enables) is not a copy and is not refused. The remedy is the one below: give that sea-orm Ferra’s major, or remove it; cargo tree -d -i sea-orm (add --all-features for an optional one) lists the copies.

   |         Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize,
   |                                                         ^^^^^^^^^^ this model is written against another copy of `sea-orm` than the one Ferra's routes use
