Ferra.rs — User Guide

pagination — collection-read parameters

Filterable, sortable, page- and cursor-paginated collection reads derived from a single Sea-ORM entity with the FerraModel derive: declare the safelist in the type system, get parameterised SQL, a documented OpenAPI surface and HAL navigation links for free.

This page is the authoritative user-guide for the collection-read query parameters: filter[<field>], sort, page, per_page, and cursor. A reader with only this page plus standard Rust knowledge produces a working filterable / sortable / cursor-paginated endpoint on the first attempt — no ADR, no constitution, and no framework source is required.

The two related pages — ferra-http.md (the handler layer) and ferra-openapi.md (the API specification surface) — describe the broader CRUD shape and the OpenAPI emission respectively. This page focuses exclusively on the collection-read parameter surface.

Dependencies. The examples on this page assume the dependencies of Getting started:

[dependencies]
ferra   = { git = "https://github.com/ferra-rs/ferra", tag = "v0.16.0" }
sea-orm = { version = "2.0", default-features = false, features = ["macros", "runtime-tokio-rustls", "sqlx-postgres"] }
tokio   = { version = "1", features = ["macros", "rt-multi-thread"] }
axum    = "0.8"
serde   = { version = "1", features = ["derive"] }

Zero-to-filter in two lines

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    #[field(filterable)]               // ← that's the whole opt-in
    pub title: String,
    #[field(filterable)]
    pub director: String,
    pub release_year: i32,             // not filterable — no attribute
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

Mount the model and issue a filtered request:

GET /films?filter[director]=Alice

You get a parameterised WHERE director = $1 SQL statement (Alice is bound, never interpolated), a 200 response carrying only Alice’s films, and an OpenAPI filter[director] query parameter on /docs/openapi.json describing the surface to consumers.

A request naming a non-safelisted field (?filter[release_year]=1999) returns HTTP 400 with application/problem+json:

{
  "type": "https://ferra.rs/errors/validation",
  "title": "Validation Error",
  "status": 400,
  "detail": "filter field `release_year` is not filterable; allowed: director, title"
}

No database statement is issued for the rejected request — the safelist gate fires inside the extractor, before the handler runs.

Filtering

The #[field(filterable)] marker

Apply #[field(filterable)] to every field that should accept a filter[<field-name>]=<value> query parameter. The marker is the complete opt-in: a field with no marker accepts no filter. Per Constitution §I, the framework’s default posture is restrictive — a Film model that marks zero fields filterable accepts no filter[...] parameter; every request carrying ?filter[anything]=... returns 400 before any SQL is issued.

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    #[field(filterable)]
    pub title: String,
    #[field(filterable)]
    pub director: String,
    pub internal_note: String,         // not exposed as a filter
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

Multiple filter parameters compose as a single AND-joined WHERE:

GET /films?filter[director]=Alice&filter[title]=Citizen%20Kane

emits

SELECT ... FROM films
 WHERE director = $1 AND title = $2
 ORDER BY id ASC
 LIMIT $3

with $1=Alice and $2=Citizen Kane bound as typed Postgres parameters.

The parameter uses the field’s wire name: on a model that declares #[ferra(rename_all = "camelCase")], write filter[releaseYear]=… and sort=-releaseYear (see ferra-forge.md § Field names on the wire).

Allowed types

The filter wire shape carries a single string value per key, type-coerced at the extractor against the field’s underlying Rust type:

Rust typeAccepted value shapeFailure → rejection
Stringany string (incl. empty)never
i32 / i64base-10 integer literalfield … expects integer, received …
f64base-10 number literalfield … expects number, received …
bool"true" / "false"field … expects boolean, received …
uuid::Uuid / IdRFC 4122 hyphenated UUIDfield … expects uuid, received …
Option<T> (for the above)same as T; empty rejected¹same shape

¹ Empty strings on String / Option<String> are accepted as the empty string. Empty strings on every other type are a type-coercion failure per FR-007a’s closing clause.

ferra::DateTime, ferra::Date and ferra::Time fields (and their Option) are filtered like the others, and also with comparison operators (next section).

Operators and date fields

filter[<field>]=<v> is equality; it is the same as filter[<field>][eq]=<v>. On a ferra::DateTime, Date or Time field (and their Option), four comparison operators are available as well: gt, gte, lt, lte.

GET /events?filter[starts_at][gte]=2026-10-03T00:00:00Z&filter[starts_at][lt]=2026-10-04T00:00:00Z
GET /events?filter[day]=2026-10-03

Two operators on one field are two parameters, so a range is filter[f][gt]=…&filter[f][lt]=…. A comparison on any other type (filter[title][gt]=a), or an operator that does not exist (filter[f][between]=…), is 400 with the code unsupported_operator; so is empty brackets, filter[f][]=v, which is not equality (the error names the declared field, filter[f][], after the filter safelist has accepted f). A NULL matches no comparison.

The values have one spelling each, so a client does not depend on what a date library happens to accept:

TypeAcceptedRefused (400 invalid_date)
DateTimeRFC 3339 in UTC: 2026-10-03T10:00:00Z or 2026-10-03T10:00:00+00:00 (+ is %2B in a URL), with an optional fractionany other offset (+01:00), -00:00, a lowercase t or z, a space for the T, a [Europe/Paris] annotation, a date alone
Date2026-10-03a date-time, a date that does not exist
Time10:00:00 or 10:00:00.25any offset, Z, a missing seconds part

A DateTime is stored to the microsecond, and a filter value is cut to the microsecond, like the values a model writes.

Rejection shapes

The extractor produces one of two rejection shapes, both with application/problem+json content type and type: https://ferra.rs/errors/validation:

Unsafelisted filter field (?filter[release_year]=1999 on a model that does not mark release_year as filterable):

{
  "type": "https://ferra.rs/errors/validation",
  "title": "Validation Error",
  "status": 400,
  "detail": "filter field `release_year` is not filterable; allowed: director, title"
}

detail names the rejected field AND lists the allowed filterable set in stable alphabetical order. A model that marks zero fields filterable rejects every ?filter[...]= request with "no fields on this resource are filterable".

A field with a #[field(read = …)] rule (0.13.0) is in the allowed set of the callers who may read it only: a caller who may not read salary gets this same rejection for ?filter[salary]=… and for ?sort=salary, with an allowed list that leaves salary out, byte for byte what a model without the field answers. See ferra-auth.md § Field rules.

Filter value type-coercion failure (?filter[release_year]=not-a-number when release_year is i32):

{
  "type": "https://ferra.rs/errors/validation",
  "title": "Validation Error",
  "status": 400,
  "detail": "field `release_year` expects integer, received `not-a-number`"
}

detail names the field AND the expected JSON-schema type. The framework MUST NOT issue any database statement for either rejection shape — the gate runs inside the extractor.

Compile-time gates

A field marked #[field(filterable)] AND #[ferra(skip)] simultaneously fails to compile with diagnostic FRG-350 (bad and good example, compiled):

error: FRG-350: field `internal_note` cannot be both `#[ferra(skip)]` and `#[field(filterable)]`
         help: remove `#[ferra(skip)]` to expose the field, or remove the `filterable` / `sortable` marker to keep the field internal
         note: a field invisible to the API surface cannot be addressable from the API surface as a filter or sort key; see Spec 011 FR-003
  --> src/models/task.rs:18:9
   |
18 |     pub internal_note: String,
   |         ^^^^^^^^^^^^^

A field invisible to the API surface cannot be addressable from the API surface as a filter key — the contradiction is decidable from the field’s declaration alone, so it lives at compile time per Constitution §III.

OpenAPI surface

Every filterable field surfaces in the generated OpenAPI document as a query parameter on the model’s GET /{resource} operation:

parameters:
  - name: filter[director]
    in: query
    required: false
    schema:
      type: string
    description: Filter on `director` (exact-match equality predicate). See …
  - name: filter[title]
    in: query
    required: false
    schema:
      type: string
    description: Filter on `title` (exact-match equality predicate). See …

Parameters appear in stable alphabetical order by field name. Adding a new #[field(filterable)] to a model automatically widens the OpenAPI parameter set on the next emission — no parallel parameter list to maintain.

Edge cases

  • Duplicate keys: a key Ferra reads (filter[…], sort, page, per_page, cursor) that appears twice, after percent-decoding, is 400 with the code duplicate_parameter, and no statement runs. filter[title] and filter[title][eq] are one key; filter[at][gt] and filter[at][lt] are two. A key Ferra does not read (?utm=a&utm=b) is left alone. Before 0.11.0 the last value won.
  • filter[f][]=v: empty brackets are the operator [], which no field supports: 400 unsupported_operator, raised after the safelist check, naming only the declared field. Before 0.12.0 it read as equality. In Rust, CollectionQuery::with_filter("f[eq]", v) filters by equality like filter[f][eq]=v (it used to fail).
  • page=abc: a page or per_page that is not a non-negative integer is 400 with the code invalid_parameter, naming the parameter. Before 0.11.0 it fell back to the default. A valid number out of range is still clamped (page=0 is 1, per_page above 100 is 100; no Warning header since 0.12.0, the body’s per_page is the applied value).
  • Filter on a cursor-mode model: filter parameters compose with cursor pagination — the §Cursor pagination section (added at US3) describes the composition.
  • Composite-PK models: filter parameters address individual columns, not the composite key. Filtering on a composite PK column works the same as filtering on any other field.

Sorting

The #[field(sortable)] marker

Apply #[field(sortable)] to every field that should accept a sort=<field-name> (ascending) or sort=-<field-name> (descending) query parameter. The marker is the complete opt-in — a field with no marker is not addressable as a sort key. Per Constitution §I, the default posture is restrictive.

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    #[field(filterable, sortable)]
    pub title: String,
    #[field(sortable)]
    pub release_year: i32,
    pub director: String,           // not sortable
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

The parameter uses the field’s wire name: on a model that declares #[ferra(rename_all = "camelCase")], write filter[releaseYear]=… and sort=-releaseYear (see ferra-forge.md § Field names on the wire).

Direction marker

The single sort query parameter encodes both the field name and the direction via a leading-minus convention:

Wire formSQL emission
?sort=titleORDER BY title ASC
?sort=-titleORDER BY title DESC
?sort=-release_yearORDER BY release_year DESC
(omitted)ORDER BY <primary-key> ASC

The omitted-sort default is deterministic: ORDER BY <primary-key-col> ASC. Repeated identical requests return rows in identical order. Two rows whose sort-column values are equal are tiebroken by the primary-key default. Composite-PK models tiebreak on primary_key_fields[0] per the declaration-order rule pinned in ADR-0029.

Rejection shape

A request naming a non-safelisted sort field (?sort=director when director is not marked sortable) returns HTTP 400 with application/problem+json:

{
  "type": "https://ferra.rs/errors/validation",
  "title": "Validation Error",
  "status": 400,
  "detail": "sort field `director` is not sortable; allowed: release_year, title"
}

detail names the rejected field AND lists the allowed sortable set in stable alphabetical order. No fuzzy matching — a typo on the field name (?sort=titles) lands here too, not as a closest-match substitution.

Compile-time gate

A field marked #[field(sortable)] AND #[ferra(skip)] simultaneously fails to compile with the same FRG-350 diagnostic the filterable+skip case produces — the two markers share the same gate per FR-003.

OpenAPI surface

Every sortable field surfaces in the generated OpenAPI document as a single enum-constrained sort parameter on the model’s GET /{resource} operation. The enum carries both the bare-name and leading-minus form for every sortable field, alphabetised across field names:

parameters:
  - name: sort
    in: query
    required: false
    schema:
      type: string
      enum:
        - release_year
        - "-release_year"
        - title
        - "-title"
    description: Sort the collection by one of 2 fields (ascending by default; leading `-` selects descending). When omitted, results are ordered by the model's primary-key column ascending. See …

Adding a new #[field(sortable)] to a model automatically widens this enum on the next emission — no parallel enum to maintain.

Composition with filtering

Filter and sort parameters compose in a single SQL statement:

GET /films?filter[director]=Alice&sort=-release_year

emits

SELECT ... FROM films
 WHERE director = $1
 ORDER BY release_year DESC
 LIMIT $2

with $1=Alice bound as a typed parameter. The composition is WHERE <filter-predicates-AND-composed> ORDER BY <sort-col> <direction> in deterministic order.

Order is always total. Without sort, a collection is ordered by primary key. With sort, rows with equal sort values are ordered by primary key. The same request therefore returns the same rows in the same order, page after page.

Filters and sorts name the field; the SQL uses the field’s column, including one renamed with #[sea_orm(column_name = "...")].

Pagination modes

Every Ferra model carries one of three pagination postures, set via the model-level #[ferra(pagination = …)] attribute. The posture controls which query-string parameters the collection endpoint accepts:

ModeAccepted parametersDefault?When to use
page?page=, ?per_page=, ?filter[...], ?sort=yes (absent attribute)Small collections, admin UIs needing page numbers / total counts.
cursor?per_page=, ?cursor=, ?filter[...], ?sort=noDeep-pageable collections, infinite-scroll UIs, AI agents traversing data.
bothAll of the above (mutually exclusive: ?cursor and ?page cannot co-occur)noPublic APIs that need to serve both paging shapes without versioning.

page is the framework default to preserve byte-identical behaviour for collections that existed before 0.7.5. Opting into cursor or both is a single line:

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "none")]
#[ferra(pagination = "cursor")]    // ← opt-in
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    #[field(cursor_key)]            // ← exactly one field
    pub created_id: i64,
    pub title: String,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

The framework rejects mismatched parameters at the extractor boundary — no SQL is issued for the rejected request. Each rejection surfaces with https://ferra.rs/errors/validation:

  • ?cursor=… on a page-mode model → detail: "model effective pagination mode is page; cursor parameter is not accepted".
  • ?page=2 on a cursor-mode model → detail: "model effective pagination mode is cursor; page parameter is not accepted".
  • ?cursor=…&page=2 on a both-mode model → detail: "cursor and page are mutually exclusive on this collection".

Cursor pagination

Cursor pagination (also called keyset pagination) tracks the boundary of the previous page via an opaque cursor token instead of an offset. It has two qualities page pagination lacks:

  1. O(log N) on every page. The SQL emits WHERE <cursor-key> > $1 OR (<cursor-key> = $1 AND <pk> > $2) ORDER BY <cursor-key> ASC, <pk> ASC LIMIT N, which traverses the cursor-key index directly. A cursor read walks the collection in cursor-key order, ascending or, with sort=-<key>, descending; a descending walk emits WHERE <cursor-key> < $1 OR (<cursor-key> = $1 AND <pk> < $2) ORDER BY <cursor-key> DESC, <pk> DESC LIMIT N. Deep pages cost the same as the first page — no OFFSET cliff.
  2. Stable under concurrent inserts. A row inserted between two requests appears at its correct keyset position; no row disappears, no row duplicates. Page-mode ?page=2 shifts every row by one when a new row is inserted ahead of the page boundary.

Accepted cursor-key shapes

The #[field(cursor_key)] marker names the column the framework orders by. The accepted types are ferra::Id / Uuid, i64, and (0.11.0) ferra::DateTime, ferra::Date and ferra::Time; a cursor_key field of any other type fails to compile with FRG-351. A date key pages in time order, newest first with sort=-<key>; it need not be unique (the primary key breaks ties, below), and the cursor brings the key back to the microsecond the database keeps. The model’s ferra::Id key, which the server generates as a UUID v7, still sorts by creation time.

Keys need not be unique: on a model with a single-column primary key, the cursor carries the boundary row’s key and primary key, and rows with equal keys are ordered by primary key — no row is skipped or repeated between pages.

Cursor token opacity

The token is a URL-safe base64 string. Consumers MUST treat it as a single opaque value — pass it through unmodified, don’t parse it, don’t reconstruct it. The framework reserves the right to change the internal encoding in a future minor release while continuing to accept previously-issued tokens for one release window. Since 0.11.0 a token also carries the direction of the walk; a token issued by 0.10.0 is read as an ascending one, so a walk in flight when a server is upgraded goes on. The token is not signed, so a caller can build one by hand. A token of the right shape is read, and all it does is choose the row after which the page starts. It cannot widen what the caller may see: the caller’s authorization scope and the request’s filters are applied to every row returned, whatever the token says.

A malformed cursor produces HTTP 400 with the dedicated URI:

{
  "type": "https://ferra.rs/errors/invalid_cursor",
  "title": "Invalid Cursor",
  "status": 400,
  "detail": "the supplied cursor token is invalid; drop the `cursor` query parameter and restart pagination"
}

A cursor that decodes but does not fit the collection — a key of the wrong type, or a token issued before 0.9.0 — is refused the same way, before any query runs.

The framework never echoes the bad cursor bytes back to the consumer — the detail is a fixed recovery hint regardless of which decode step failed (base64 decode, JSON parse, shape mismatch, or unknown version byte). The recovery is always the same: drop the cursor parameter and restart pagination from the first page.

Cursor + filter trade-off

Cursor and filter compose in a single SQL statement:

GET /films?filter[director]=Alice&cursor=<token>&per_page=20

emits

SELECT ... FROM films
 WHERE deleted_at IS NULL       -- inherited from #[behavior(soft_delete)]
   AND (created_id > $1 OR (created_id = $2 AND id > $3))  -- cursor predicate: [key, primary key]
   AND director = $4            -- filter predicate
 ORDER BY created_id ASC, id ASC
 LIMIT $5

On a descending walk (?sort=-created_id) the two comparisons of the cursor predicate are < and the order is created_id DESC, id DESC.

The trade-off: cursor stability is per-request, not cross-request. A cursor issued on a request with ?filter[director]=Alice addresses “the next row after the boundary, filtered to Alice’s films”. If a follow-up request changes the filter to ?filter[director]=Bob, the same cursor is still meaningful — it addresses the next row after the (created_id, id) boundary — but the resulting page is filtered to Bob’s films, which may overlap, undershoot, or overshoot the originally-intended traversal. Consumers traversing a filtered cursor stream should keep the filter constant for the duration of the traversal.

Cursor + sort restriction

A cursor-paginated read walks the collection in the order of its cursor key: ascending by default, descending with a leading -. Whenever the cursor path serves the request (a cursor-mode model, or a both-mode model called with ?cursor=…) the sort parameter, if present, must name the cursor key:

RequestAnswer
?cursor=<token>200, ascending by the cursor key
?cursor=<token>&sort=created_id200, same order
?cursor=<token>&sort=-created_id200, descending, if the token was issued for a descending walk
?cursor=<ascending token>&sort=-created_id400 invalid_cursor: the token is for the other direction
?cursor=<token>&sort=title400 — title is not the cursor key

A descending walk starts without a cursor: ?sort=-created_id. The next link of a page carries sort and the request’s filter[...], so following it continues the walk. When you build the next request yourself from next_cursor (the flat representation has no links), repeat sort and the filters: a token keeps the direction it was issued for, and a request that sorts the other way is refused with the same invalid_cursor as a malformed token.

{
  "type": "https://ferra.rs/errors/validation",
  "title": "Validation Error",
  "status": 400,
  "detail": "sort field `title` does not match the cursor key `created_id`; cursor pagination requires `sort` to target the cursor key when present"
}

The request is refused rather than answered in another order than the one it asked for. The OpenAPI document of a cursor-mode model lists the cursor key and its - form as the only sort values.

Cursor + soft-delete composition

A model enrolled in #[behavior(soft_delete)] automatically excludes soft-deleted rows from every framework-generated SELECT — the same predicate composition that protects find_by_id and the page-mode find_collection applies to the cursor path by construction:

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "none")]
#[ferra(pagination = "cursor")]
#[behavior(soft_delete)]               // ← inherited filter
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    #[field(cursor_key)]
    pub created_id: i64,
    pub title: String,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

The cursor-mode SQL emits WHERE deleted_at IS NULL AND created_id > $1 automatically — soft-deleted rows are invisible to the cursor traversal. Restoring a soft-deleted row inserts it back into the cursor stream at its created_id position; subsequent cursor walks include it.

Cursor compile-time diagnostics

The cursor surface is compile-checked end-to-end. Four diagnostics surface at cargo check:

  • FRG-351 — cursor-key type not in the accepted set. Fires when #[field(cursor_key)] is applied to a String, a custom struct, or any type outside the closed list above (Id, Uuid, i64, DateTime, Date, Time). The diagnostic names the accepted shapes.

  • FRG-352 — cursor-key field is Option<T> (or a tuple with an Option<T> component). A nullable cursor key would silently drop rows whose key is NULL from the keyset traversal — the equality-vs-NULL three-valued logic puts those rows in an indeterminate state. Remove the Option<...> wrapper, or move the cursor key to a NOT-NULL sibling column.

  • FRG-353 — cursor-mode cardinality. A model declared #[ferra(pagination = "cursor")] or #[ferra(pagination = "both")] requires exactly one #[field(cursor_key)] field. Zero cursor-key fields surfaces on the pagination attribute value; more than one surfaces on every extra cursor-key field.

  • FRG-356 — a projection hides the cursor key. The cursor token carries the cursor key, and the primary key when it breaks ties. A model in cursor or both mode whose named projection lists read = [...] without one of them, or whose cursor key is #[ferra(skip)], does not compile: the diagnostic names the projection and the field. Add the field to read, or choose another cursor key. A write-only cursor key is FRG-354.

The compile gates are release-blocker tests in the framework’s trybuild UI cohort — every diagnostic ships with a pinned .stderr golden so the text never drifts unannounced.

#[ferra(write_only)] fields are not queryable

A #[ferra(write_only)] field cannot be filterable, sortable or a cursor_key (FRG-354): the rows a filter selects, or the order a sort gives, would reveal the value the API never returns — a password hash could be read back one prefix at a time. Filter, sort and page on fields the API returns.

Hypermedia links in cursor mode

A cursor-mode collection response carries a _links shape distinct from page mode — the deliberate absence of first and last is a compile-time invariant of the framework’s CursorCollectionLinks type:

{
  "items": [ ... ],
  "per_page": 20,
  "next_cursor": "<next-token>",
  "_links": {
    "self": { "href": "/films?cursor=<token>&per_page=20" },
    "next": { "href": "/films?cursor=<next-token>&per_page=20" },
    "prev": { "href": "/films?per_page=20" }
  }
}

Behaviour:

  • next_cursor is in the body in both representations: the cursor of _links.next, or null on the last page (the key is always there). The flat representation carries it without _links.
  • Every link repeats the request’s filter[...] and sort. A both-mode collection refuses cursor beside per_page, so its cursor links carry no per_page.
  • _links.self.href always present.
  • _links.next.href present if more rows exist beyond the current page (framework uses an over-fetch peek — LIMIT N + 1 — to decide). Absent on the natural last page.
  • _links.prev.href present iff the current request carried an inbound ?cursor=…; absent on the first request. At 0.7.5 the prev href points at the bare collection URL (drop the cursor to restart from the first page); a future widening will materialise an inverse-direction cursor for prev.
  • _links.first and _links.last MUST NOT appear — the framework structurally cannot emit them in cursor mode. Consumers detecting the natural last page rely on the absence of _links.next, not on _links.last.

The HAL response Content-Type is application/hal+json per ADR-0014; the flat one is application/json (ferra-http.md).
