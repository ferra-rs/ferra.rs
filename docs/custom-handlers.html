Ferra.rs — User Guide

Custom handlers

Most Ferra apps need at least one route that is not pure CRUD — a publish verb, a derived collection, an aggregation, a webhook receiver. This page is the authoritative guide to writing those handlers on top of a Ferra-served API. A reader with this page plus standard Rust knowledge produces a compiling custom handler on the first attempt — no framework source, no ADR, no constitution required.

The companion CRUD / envelope / Tower-stack / typed-extraction reference is ferra-http.md. The router-assembly facade is foundry.md.

Dependencies. The examples on this page assume the dependencies of Getting started:

[dependencies]
ferra   = { git = "https://github.com/ferra-rs/ferra", tag = "v0.15.0" }
sea-orm = { version = "2.0", default-features = false, features = ["macros", "runtime-tokio-rustls", "sqlx-postgres"] }
tokio   = { version = "1", features = ["macros", "rt-multi-thread"] }
axum    = "0.8"
serde   = { version = "1", features = ["derive"] }

When the generated routes are not enough

The five built-in handlers cover the resource-shaped endpoints — list, read, create, update, delete. They are all you need for ~80 % of the surface a typical app exposes.

You write a custom handler when the route is not one of those five operations. Common reasons:

  • Verbs on a resource. POST /films/{id}/publish, POST /invoices/{id}/cancel, POST /accounts/{id}/transfer — verbs on a resource that aren’t expressible as PUT. A verb on one row of one model is a declared action first: Ferra serves it with its own rule, the row lock, the preconditions and the write of a PUT. Write a handler of your own when the route is not a verb on one row: a collection, a webhook, an aggregate.
  • Derived collections. GET /films/popular, GET /actors/{id}/films — collections whose membership is computed, not just SELECT * WHERE ....
  • Multi-resource projections. GET /dashboard returning a join of three resources at once.
  • Webhook receivers. POST /webhooks/stripe reading a non-Ferra payload shape.
  • Cross-cutting endpoints. GET /healthz, GET /metrics.

Custom handlers are plain Axum handlers. They accept Axum extractors, return Result<_, FerraError> for RFC 7807 error continuity, and compose with the framework router by appending .route(...) or .merge(...) on the value Foundry::build() returns.

The worked example: POST /films/{id}/publish

The complete shape of a custom handler for a verb on one row — model declaration, handler signature, composition with Foundry — in one file. The route reaches the films table through Resource<Film>: it is judged by the rules of PUT /films/{id}, not by whatever the handler remembers to check. Drop this into a fresh src/main.rs whose Cargo.toml declares the canonical dependency set (ferra, tokio, serde, sea-orm as in Getting Started, and axum with its macros feature, which #[axum::debug_handler] needs) and it compiles. The route is a custom handler, not a declared action: for a verb that Ferra serves itself, with its own rule, the row lock and the preconditions, see Declared actions.

use axum::{Json, Router, routing::post};
use ferra::{
    ClaimCheck, Date, FerraError, FerraIdentity, FerraJson, FerraModel, FerraPath, Foundry,
    HmacAlgorithm, JwtConfig, Resource, ResourceHandle,
};
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};

// --- The model -----------------------------------------------------

mod film {
    use super::*;

    #[derive(
        Clone, Debug, PartialEq, Eq,
        DeriveEntityModel, FerraModel,
        Serialize, Deserialize,
    )]
    #[sea_orm(table_name = "films")]
    #[ferra(auth = "bearer")] // the posture every model declares; see ferra-auth.md
    #[authorize(              // a film belongs to the caller who created it
        list = IsOwner,
        get = IsOwner,
        create = Authenticated,
        update = IsOwner,
        delete = IsOwner
    )]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        #[sea_orm(unique)]
        pub title: String,
        pub director: String,
        pub year: Option<i32>,
        pub release_date: Option<Date>,
        pub published: bool,
        #[field(owner)]
        pub owner_id: Uuid,
    }

    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}

    impl ActiveModelBehavior for ActiveModel {}
}

pub use film::Model as Film;

// --- Who the caller is ---------------------------------------------

#[derive(Clone, Debug, Deserialize)]
struct Claims {
    sub: String,
}

impl FerraIdentity for Claims {
    fn id(&self) -> &str {
        &self.sub
    }
    fn has_role(&self, _role: &str) -> bool {
        false
    }
}

// --- The handler's request body -------------------------------------

// Plain serde struct — nothing Ferra-specific. The `FerraJson<T>`
// extractor on the handler signature accepts any `T: DeserializeOwned`.
#[derive(Deserialize)]
struct PublishRequest {
    release_date: Option<Date>,
}

// --- The handler's response body ------------------------------------

// A route of your own answers with a body of its own: the fields you
// choose, under the names you choose.
#[derive(Serialize)]
struct PublishedFilm {
    id: i32,
    title: String,
    published: bool,
    release_date: Option<Date>,
}

// --- The handler ---------------------------------------------------

// `#[axum::debug_handler]` is optional but turns the dense
// `Handler` trait-bound error into a single, targeted message
// when one of the rules below is violated. Keep it on while
// iterating; it is a no-op at runtime.
#[axum::debug_handler(state = ResourceHandle<Film>)]
async fn publish_film(
    // FromRequestParts — binds the caller (the bearer token) and gives
    //                   access to the films, under the films' rules.
    films: Resource<Film>,
    // FromRequestParts — `FerraPath` is the typed-extraction
    //                   wrapper around `axum::extract::Path<T>`.
    FerraPath(id): FerraPath<i32>,
    // FromRequest — `FerraJson` consumes the request body. Body-
    //              consuming extractors MUST be the LAST argument.
    FerraJson(body): FerraJson<PublishRequest>,
) -> Result<Json<PublishedFilm>, FerraError> {
    // Same rules as `PUT /films/{id}`: another caller's film is a 404 and
    // the row is unchanged. Only `published` and `release_date` are written.
    let patch = film::ModelPatch {
        published: Some(true),
        release_date: body.release_date.map(Some),
        ..Default::default()
    };
    let film = films.update(id, patch).await?;

    // Answer with the fields this handler exposes.
    Ok(Json(PublishedFilm {
        id: film.id,
        title: film.title,
        published: film.published,
        release_date: film.release_date,
    }))
}

// --- Composition with Foundry --------------------------------------

#[tokio::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let database_url = std::env::var("DATABASE_URL")?;
    let conn = sea_orm::Database::connect(&database_url).await?;

    let jwt = JwtConfig::single_secret(
        "key-1",
        std::env::var("JWT_SECRET")?,
        HmacAlgorithm::Hs256,
        ClaimCheck::expect("https://auth.example.com/"),
        ClaimCheck::expect("films-api"),
    )?;

    // `mount_and_handle` mounts `Film` as `.mount::<Film>()` does — the CRUD
    // routes, the JWT layer — and returns the handle that routes of your own
    // use to reach the films.
    let (foundry, films) = Foundry::new(conn)
        .etag_key(std::env::var("ETAG_KEY")?)?
        .with_auth::<Claims>(jwt)
        .mount_and_handle::<Film>();
    let api = foundry.with_docs().build();

    // The custom handler lives on a sibling sub-router whose state is the
    // handle. `ResourceHandle<M>: Clone` (reference counts only).
    let custom = Router::new()
        .route("/films/{id}/publish", post(publish_film))
        .with_state(films);

    let app = api.merge(custom);

    let listener = tokio::net::TcpListener::bind("0.0.0.0:3000").await?;
    // The rate limiter keys on the peer address: serve with connect info.
    axum::serve(listener, app.into_make_service_with_connect_info::<std::net::SocketAddr>()).await?;
    Ok(())
}

film::ModelPatch is the struct #[derive(FerraModel)] generates next to Model ({Model}Patch, one Option<T> per writable field, None leaving the column; also <Film as FerraViews>::Patch); the struct is unchanged by the PATCH route of 0.14.0, which reads the same Value it serializes to. The owner column is compared with the token’s sub rendered as a string, so a Uuid owner_id matches a sub holding that UUID (ferra-auth.md).

update does what PATCH /films/{id} does (RFC 7396): None leaves the column, and a JSON object set on a stored JSON object is merged into it instead of replacing it (a null member removes its key). A null set on a field that cannot be null (Some(serde_json::Value::Null) on a required JSON field) is the 422 required.

Resource<Film> has six methods — get, list, list_cursor, create, update, delete — each of which does what the generated route of the same name does: it runs the authorization checkpoint of the operation, scopes a list to the caller’s rows under IsOwner, stamps the owner on create, validates with the model’s #[field(...)] rules, and writes under the owner’s guard. What it hands back is the model’s read view, <Film as FerraViews>::Read: a #[ferra(write_only)] column is not a member of that type, so a route cannot send it by mistake. ferra-http.md is the reference.

Field rules reach a route of your own (0.13.0). A field with a #[field(read = …, write = …)] rule is judged for the bound caller by Resource<M> as it is by the generated routes. What get, list and list_cursor return has each field the caller may not read set to None, so a route that serializes it sends no such key (never null); an IsOwner read rule is judged row by row. A gated field of the write view, and of a patch, is an Option (Option<Option<T>> when the column is nullable): None is left alone, Some(None) is null, and a field the caller may not read or write that you set is refused like the generated route refuses it (422, then 403), the row unchanged. A filter on a field the caller may not read is refused as on the route, and a sort on it keeps the default order.

Hooks (0.13.0). Resource<M>::create and Resource<M>::update run the model’s before_save and after_save hooks, and Resource<M>::delete its before_delete and after_delete, in the write’s transaction, as the generated routes do (Hooks).

No response envelope in 0.9.0. The routes Foundry generates answer with the row filtered through its read projection, under its wire names, flat or with HAL _links as the client’s Accept chooses. That envelope is not public: a route of your own would build links that know neither the base path, nor the version prefix, nor the configured origin. Answer with a struct of your own, as above. The same goes for #[ferra(rename_all = "camelCase")]: the read view carries the model’s Rust field names, so a route that serializes it sends those, not the wire names of the generated routes.

A successful POST /films/42/publish with body {"release_date": "2026-05-10"} returns 200 OK:

{
  "id": 42,
  "title": "Rust en pratique",
  "published": true,
  "release_date": "2026-05-10"
}

Errors flow through the same FerraError taxonomy the built-in handlers use — a malformed JSON body returns 400 with type: "https://ferra.rs/errors/validation"; a film that is not yours returns 404 with type: "https://ferra.rs/errors/not_found", the same answer as a film that does not exist; no token is a 401. Clients that handle one Ferra error already handle this one.

Extractor ordering: FromRequest vs FromRequestParts

Axum has two extractor traits. The distinction looks academic until you write your first multi-extractor handler — then it becomes the load-bearing rule.

TraitReads fromExamplesPosition
FromRequestPartsrequest parts only (method, URI, headers, state)State<T>, Path<T>, Query<T>, Parts, HeaderMap, FerraPath<T>any position
FromRequestthe whole request, including the body (consumed)Json<T>, Bytes, String, Form<T>, FerraJson<T>last argument only

The rule: at most one body-consuming extractor (FromRequest) per handler, and it MUST be the last argument. Every other extractor is body-agnostic (FromRequestParts) and goes earlier.

This is a fundamental property of HTTP, not an Axum design quirk: a request body is a one-shot stream. Once you have read it, the bytes are gone.

The handler in the worked example follows the rule:

async fn publish_film(
    films: Resource<Film>,                    // FromRequestParts
    FerraPath(id): FerraPath<i32>,            // FromRequestParts
    FerraJson(body): FerraJson<PublishRequest>, // FromRequest — LAST
) -> Result<...> { ... }

(An excerpt of the handler above, which is the compiled version.)

Reorder FerraJson ahead of FerraPath and the build fails. Without #[axum::debug_handler] the compiler reports the violation through a deep trait-bound chain on Handler. With #[axum::debug_handler] the diagnostic points directly at the offending argument.

Multiple body extractors. Axum allows exactly one body-consuming extractor per handler. If you legitimately need to look at the raw bytes and a typed JSON deserialization, do both inside a single FromRequest-implementing wrapper, or read Bytes and parse it explicitly with serde_json::from_slice. There is no Json<A> + Json<B> shape.

Send + Sync + 'static: the bound-set cheat-sheet

Tokio runs handlers on a multi-threaded executor by default. Every value Axum carries through the handler must be sendable across threads and outlive the request. The compiler enforces this through Send + Sync + 'static-shaped bounds on the Handler trait — failures here look daunting at first read.

The cheat-sheet:

SymptomLikely causeFix
the trait Send is not implemented for ... inside an async fna !Send value is held across an .await (Rc<_>, RefCell<_>, MutexGuard from std::sync::Mutex)use Arc<_>, tokio::sync::Mutex, or restructure so the offending value is dropped before the .await
the trait Sync is not implemented for ... on State<T>the state type is not Sync (e.g., it owns a non-Sync cache)wrap the inner shared state in Arc<RwLock<...>> or restructure to a channel
argument requires that ... must outlive 'staticthe handler captures a non-'static reference (&str from outside the closure, a borrow from the request)own the data (String, Bytes), or extract it via an extractor
Handler<_, _> not satisfied with a long, hard-to-read chainusually one of the three above, hidden behind Handler’s blanket impladd #[axum::debug_handler] and read the first targeted error it produces

Notes on the framework’s own types:

  • ResourceHandle<M> is Clone + Send + Sync + 'static — it wraps a shared connection. Keep it in the router state and pass it through any number of handlers freely.
  • FerraJson<T> / FerraPath<T> add no bounds beyond the inner T: DeserializeOwned + Send + 'static that Axum already requires.
  • FerraError is Send + Sync + 'static and implements axum::response::IntoResponse — return Result<_, FerraError> from any handler signature.

If your handler async fn body holds a !Send value across an .await, the bound failure surfaces in the Handler impl, not in the body. Move the value into a synchronous block or drop it before the await.

Friendlier diagnostics with #[axum::debug_handler]

Axum’s Handler trait has a blanket impl that erases per-argument type information by the time the bound failure is reported. Without help, a single wrong extractor produces a multi-screen not satisfied chain.

#![allow(unused)]
fn main() {
use axum::Json;
use ferra::{FerraError, FerraPath};

#[axum::debug_handler]
async fn my_handler(FerraPath(id): FerraPath<i32>) -> Result<Json<i32>, FerraError> {
    Ok(Json(id))
}
}

The proc-macro re-checks the arguments one by one and emits a single targeted error per offending argument:

  • Json must be the last extractor
  • the trait FromRequestParts is not implemented for …
  • Send is not satisfied because …

It is purely a development aid — it adds no runtime cost and emits no code in release builds. Keep it on every custom handler while iterating; remove it only if a transitive dep needs the un-decorated handler signature for some other proc-macro to see.

It does not (and cannot) flag every misuse — extractor ordering and bound failures are visible to it; subtle data-flow bugs and panic-on-unwrap paths are not.

FerraJson<T> and FerraPath<T> — RFC 7807 error continuity

Axum’s stock Json<T> and Path<T> produce text/plain 400 bodies on rejection. A consumer that handles Ferra’s application/problem+json taxonomy elsewhere on the API gets a mixed wire format on the rejection path — two parsers, two error shapes, two test surfaces.

FerraJson<T> and FerraPath<T> are thin newtypes around the stock extractors that intercept the rejection and remap it to FerraError::Validation:

pub struct FerraJson<T>(pub T);   // wraps axum::Json<T>
pub struct FerraPath<T>(pub T);   // wraps axum::extract::Path<T>

The output on a malformed body looks like every other Ferra 400:

{
  "type":   "https://ferra.rs/errors/validation",
  "title":  "Validation Error",
  "status": 400,
  "detail": "validation failed",
  "errors": [
    { "field": "body", "code": "invalid_json",
      "message": "expected `,` or `}` at line 1 column 14" }
  ]
}

Use the wrappers in every custom handler that takes JSON or path parameters. The single-token swap from Json<T> → FerraJson<T> and Path<T> → FerraPath<T> is the only difference.

What if I genuinely want stock Axum extraction? You can — they coexist. A handler that takes axum::Json<T> produces stock 400 text/plain on rejection; one that takes FerraJson<T> produces RFC 7807. Pick per handler.

errors[*].code is drawn from the closed list in ferra-error-handling.md § Validation codes; these wrappers produce invalid_json and invalid_path_param. New codes are additive — existing consumer branches keep matching.

Composing with Foundry

Two composition patterns, in order of how often you reach for them:

1. Append routes on top of Foundry::build()

use axum::{Router, routing::post};
use ferra::Foundry;
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod film {
    use super::*;
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "films")]
    #[ferra(auth = "none")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub title: String,
        pub published: bool,
    }
    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}
    impl ActiveModelBehavior for ActiveModel {}
}
use film::Model as Film;
async fn publish_film() {}
fn demo(conn: sea_orm::DatabaseConnection) {
let (builder, films) = Foundry::new(conn).etag_key("a-development-key-of-at-least-32-bytes").expect("a key of at least 32 bytes").mount_and_handle::<Film>();
let api = builder.with_docs().build();

let custom = Router::new()
    .route("/films/{id}/publish", post(publish_film))
    .with_state(films);

let app: Router = api.merge(custom);
let _ = app;
}
fn main() {}

The framework’s Tower stack (CORS, body-limit, tracing, rate-limit on mutation routes) wraps every Ferra-mounted resource. Routes you append on the outer Router see the framework’s outer layers but not the per-resource inner layers — your custom endpoint does NOT inherit the rate-limit layer that mounts on the CRUD mutation sub-router. Add your own where needed.

2. Hand-rolled Router with no Ferra CRUD at all

use axum::{Router, routing::{get, post}};
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod film {
    use super::*;
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "films")]
    #[ferra(auth = "none")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub title: String,
        pub published: bool,
    }
    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}
    impl ActiveModelBehavior for ActiveModel {}
}
async fn publish_film() {}
fn demo() {
let app: Router = Router::new()
    .route("/healthz", get(|| async { "ok" }))
    .route("/films/{id}/publish", post(publish_film));
let _ = app;
}
fn main() {}

For apps that are only custom handlers, with no CRUD surface to derive (and so no model to reach: your own state, if the routes need one, is yours). You retain FerraJson / FerraPath / FerraError; you give up the auto-generated CRUD, the HAL _links on the responses, and the docs surface.

In both patterns, consumer-added .layer(...) calls on the final Router wrap the framework stack from the outside. Place observability and authentication layers there; place per-route policy where the policy belongs (a sub-router scoped to that route).

A route you add yourself is outside Ferra’s authorization policy: Foundry protects the routes it mounts, not yours. Protect a custom route yourself, for instance with the CurrentUser<YourClaims> extractor behind the JWT layer (see ferra-auth.md).

use std::sync::Arc;
use axum::{Router, http::StatusCode, middleware::from_fn_with_state, routing::post};
use ferra::{CurrentUser, FerraAuthLayer, FerraError, FerraIdentity, Foundry, JwtConfig};
use ferra::ferra_auth_enforcing_middleware;
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod film {
    use super::*;
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "films")]
    #[ferra(auth = "none")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub title: String,
        pub published: bool,
    }
    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}
    impl ActiveModelBehavior for ActiveModel {}
}
use film::Model as Film;
#[derive(Clone, Debug, Deserialize)]
struct YourClaims { sub: String }
impl FerraIdentity for YourClaims {
    fn id(&self) -> &str { &self.sub }
    fn has_role(&self, _role: &str) -> bool { false }
}

// `CurrentUser` rejects with 401 when the request carries no identity.
async fn publish_film(
    CurrentUser(user): CurrentUser<YourClaims>,
    /* other extractors */
) -> Result<StatusCode, FerraError> {
    // check `user` against your own rule here, return FerraError::Forbidden to refuse
    let _ = user;
    Ok(StatusCode::NO_CONTENT)
}

fn demo(conn: sea_orm::DatabaseConnection, jwt_config: JwtConfig) {
let jwt = Arc::new(jwt_config); // the same `JwtConfig` settings you give `.with_auth`
let (_api, films) = Foundry::new(conn).etag_key("a-development-key-of-at-least-32-bytes").expect("a key of at least 32 bytes").mount_and_handle::<Film>();
let custom: Router = Router::new()
    .route("/films/{id}/publish", post(publish_film))
    .with_state(films)
    .layer(from_fn_with_state(
        FerraAuthLayer::<YourClaims>::new(jwt),
        ferra_auth_enforcing_middleware::<YourClaims>,
    ));
let _ = custom;
}
fn main() {}

To unit-test such a handler, call it with CurrentUser(claims) — the tuple field is public, no token is needed. To test it behind the layer, sign a token with ferra::testing::bearer (see ferra-auth.md § Testing authenticated routes).

Raw database access, outside the contract

Ferra hands out no repository: ResourceHandle<M> and Resource<M> are the only way to a model’s rows through Ferra, and they apply the generated routes’ rules. A query they do not cover (a join, an aggregate, a report) is yours to write against your own DatabaseConnection. That connection is not Ferra’s: nothing checks the caller, scopes the owner or filters soft-deleted rows for you, and it is outside Ferra’s stability contract.

Keep both in one state and let Axum derive each part:

use axum::{Json, Router, extract::{FromRef, State}, http::StatusCode, routing::get};
use ferra::{DatabaseConnection, Foundry, ResourceHandle};
use sea_orm::{EntityTrait, PaginatorTrait};
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod film {
    use super::*;
    #[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "films")]
    #[ferra(auth = "none")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub title: String,
        pub published: bool,
    }
    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}
    impl ActiveModelBehavior for ActiveModel {}
}
use film::Model as Film;

#[derive(Clone, FromRef)]
struct AppState {
    films: ResourceHandle<Film>, // `Resource<Film>` is extracted from it
    conn: DatabaseConnection,    // yours: raw queries, no checkpoint
}

async fn count_films(State(conn): State<DatabaseConnection>) -> Result<Json<u64>, StatusCode> {
    let n = film::Entity::find()
        .count(&conn)
        .await
        .map_err(|_| StatusCode::INTERNAL_SERVER_ERROR)?;
    Ok(Json(n))
}

fn demo(conn: DatabaseConnection) {
let (builder, films) = Foundry::new(conn.clone()).etag_key("a-development-key-of-at-least-32-bytes").expect("a key of at least 32 bytes").mount_and_handle::<Film>();
let app: Router = builder.build().merge(
    Router::new()
        .route("/films/count", get(count_films))
        .with_state(AppState { films, conn }),
);
let _ = app;
}
fn main() {}

A transaction is the same: conn.begin() on your connection, outside Ferra. Ferra has no transaction-taking method on Resource<M>.
