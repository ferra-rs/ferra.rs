Ferra.rs — User Guide

Migrating from 0.15 to 0.16

0.16.0 (Brazing) serves a model’s relations under each side’s own rules. Each entry below is a change you may notice. This page grows with the release: read the entries, then update the application’s git dependency to v0.16.0. CHANGELOG.md lists every change.

New routes appear: a parent and its child

Before. A HasMany or a HasOne was a declaration Ferra did not serve. A child was reached on its own path only.

After. An application that mounts a parent and its child gets new routes; here is how to remove them. When both sides of a HasMany or HasOne are mounted on the same Foundry, it serves GET and POST {parent}/{id}/{relation} (GET /films/{id}/reviews, POST /films/{id}/reviews), with no change in your code. They allow nothing the child’s own path does not, plus the parent’s refusals (it must be readable, and updatable for a POST); they appear in the OpenAPI document, and they go through the child’s layers. Sub-collections states the rules.

Who is affected. An application that mounts a parent and its child, both derived in the dense form. The routes are extra: a client that does not call them sees no change. If you do not want them exposed, for example because a gateway lists the allowed paths or a test pins the set of routes, remove them.

Migration. There is nothing to do to keep them. To remove them, either write the parent in the split form (a model with no relation field has no sub-collection, and none of the other features of its relations), or do not mount the child. There is no per-relation opt-out yet.

A relation named like a row action or restore of its own model would take the path of that route, so build() (and try_build()) refuses it with BuildError::RelationNameCollision, naming the model and both names. Rename the relation or the action.

Every write opens at READ COMMITTED

Before. A write ran at the server’s default_transaction_isolation, except the write of a model with a system grant, which already opened at READ COMMITTED.

After. Every write Ferra opens (the generated routes, Resource<M>, and the transaction a hook borrows) runs at READ COMMITTED, whatever the server’s default says. The protocol that keeps a parent’s check valid against a concurrent child write needs it. PostgreSQL’s own default is READ COMMITTED, so an application on that default changes nothing.

Who is affected. An application whose connection defaults to REPEATABLE READ or SERIALIZABLE loses the detection of lost updates in its hooks: a hook that reads a row through tx.resource and writes it back computed from that read no longer gets 40001. Under a SERIALIZABLE default, read-write anomalies across rows are likewise no longer detected. A write of the row’s own model is not affected, because before_* hooks receive the locked row.

Migration. Compute the new value in the target row’s own hook or action, where the row is locked. HTTP clients keep If-Match; tx.resource evaluates none. See Transactions.

The owner(from) foreign key is immutable

Before. A PUT or a PATCH that named the foreign key of a model with owner(from = ..) moved the row under another parent of the same owner (a 200), and an action could return the row with another key.

After. The key is set when the row is created and never changes. A PUT or a PATCH naming it is the 422 unknown_field that any key outside the write set gets, whatever value it names, with nothing written. A PUT that leaves it out keeps the row under its parent. A row action whose handler changes it is a 500 internal, and the same refusal applies to Resource::update and tx.resource().update. The OpenAPI document no longer lists the key in the PUT and PATCH request schemas of such a model; it stays in the POST one.

Who is affected. A client that sends the whole record back on a PUT, key included (the usual read-modify-write), now gets the 422. A client generated from the OpenAPI document must be regenerated.

Migration. Stop sending the key on PUT and PATCH. To move a child, delete it and create it again; the new row has a new identity (see Relations).

A child’s hook cannot write the parent it holds

Before. A hook of a model with owner(from = ..) could update or delete, through tx.resource, the parent its write holds FOR SHARE. The UPDATE asked for FOR UPDATE on a row the transaction only shared, and deadlocked against the parent’s other children in flight (40P01, retried, then the 503 retry_exhausted).

After. The call is refused before any statement: FerraError::Internal, the write answered 500 internal, one error! that names the child’s resource, the parent’s resource, the operation and the fix, and no key value. The refusal poisons the write, so a hook that swallows it still commits nothing. A read of the parent, a sibling create and a write of a row the write does not hold are unchanged, and so is a parent’s own action writing its children.

Who is affected. A hook that keeps a counter or a status on the parent (tx.resource::<Film>().update(..) from a review’s after_save, for instance).

Migration. Write the parent from its own action, or compute the value on read. See Relations.

A PUT of an owner(from) model reads the row first

A PUT of a model with owner(from = ..) now reads the row before it judges the body, so a bad body (a wrong type, an unknown key) on an absent row is the 404, no longer the 400 or 422. Nothing to migrate unless a client relied on the body’s refusal for a row that does not exist.

An exhausted retry is FerraError::RetryExhausted

Before. A Resource<M> write that the database aborted on each of its three attempts returned a FerraError::Internal over a private cause, which answered 503 retry_exhausted wherever it was returned. The public enum had no variant for it.

After. It returns the unit variant FerraError::RetryExhausted (wire type retry_exhausted, 503, Retry-After: 1; the status, title and detail do not change). A hook’s tx.resource write that gave up reaches the caller as the same variant, through the outer write. FerraError is #[non_exhaustive], so a match with a wildcard arm still compiles.

Who is affected. A route of your own that matches FerraError::Internal(_) to tell an exhausted retry from a 500: it no longer sees it, and the request falls to your other arms.

Migration. Add an arm for FerraError::RetryExhausted and answer it as a transient 503. Never replay the write in a loop of your own: the three attempts already ran. See Transient conflicts are retried.

A #[sea_orm(ignore)] field needs #[ferra(computed)]

Before. A field with #[sea_orm(ignore)] and no #[ferra(computed)] compiled. It has no column, so Sea-ORM built it with Default on every read, and Ferra served that value as the row’s.

After. The derive refuses it: FRG-364, spanned on the ignore (the code).

Who is affected. A model that keeps an in-memory field in its Model struct without computing it.

Migration. Add #[ferra(computed)] and the impl FerraComputed for Model that fills the field (an empty impl serves its Default, as before, but says so). Or move the field out of the model, into a type of your own or a Resource<M> route.

A composite foreign key is refused

Before. A relation with from = "(studio_id, studio_region)" compiled. The foreign-key gate reads one column, so it saw none: the key was served, and a write naming an unreadable parent was accepted.

After. The derive refuses it: FRG-365, spanned on the string (the code).

Who is affected. A model with a relation keyed by several columns.

Migration. Give the relation one foreign-key column, or keep the composite key out of the model’s relations.

The relations are typed, and the back key is checked at build()

Before. Foundry did not read the relation fields of a model. A HasMany whose target had no BelongsTo back, or two, built without complaint.

After. The derive emits one typed marker per relation, Mountable carries a hidden bound that reads them, and build() (and try_build()) refuses a HasMany or HasOne whose target is mounted on the same Foundry and has none, or more than one, BelongsTo back to the model: BuildError::RelationBackKey, naming both models, the relations and the fix. A pair with a single side mounted is not checked.

Who is affected. An application that mounts both sides of a HasMany or HasOne whose target has two BelongsTo back (two keys to the same parent), or none. A model written by hand against Mountable, without the derive.

Migration. Derived models: none, unless build() refuses a pair. Then keep exactly one BelongsTo back, or mount only one of the two models. A hand-written model also implements the hidden, derive-only FerraRelations for its entity (type Relations = (); when it declares no relation); it is outside the contract and may change. See Declaring relations.

Projections that embed each other are refused at build()

Before. A projection could not embed a relation.

After. A read list may name a BelongsTo (Embedding), and build() (and try_build()) refuses a loop of embeds: BuildError::EmbedCycle, with the path as resource names (the table name unless resource = says otherwise), from the first node the walk meets again (Embedding cycle: `films.summary → studios.summary → films.summary`; remove one embed from a `read` list.).

Who is affected. An application that adds embeds to the projections of two mounted models that point at each other.

Migration. Remove one embed from a read list; the relation stays a link.

The foreign key of a BelongsTo follows the readability of its parent

Before. A row served its foreign key (film_id) to everyone who could read the row, whatever they could read of the parent. FerraViews::Read held it as a plain value.

After. A caller who may not read the parent gets no key and no film link in _links: the member is absent, never null (a key that is NULL stays null, with no link). It holds on every response that serializes the row: item, list, /me, the write responses, each projection prefix, Resource<M> and a hook’s tx.resource. “May read the parent” is the get of GET {parent item}: its rule, its authority, its owner condition and soft delete. Ferra decides it with one extra SELECT ... WHERE key IN (...) per BelongsTo per page. A parent that is not mounted on the Foundry is read by nobody, so its key and link are absent for everyone. In FerraViews::Read the key is an Option (Option<Option<T>> for a nullable key). A PUT does not need to carry a key the caller may not read: the stored value is kept. The OpenAPI read schema no longer lists the key in required, and says it is absent when the caller may not read it.

Who is affected. A client that reads the foreign key of a model whose parent some callers cannot read. A hand-written route that reads read.film_id from Resource::get, Resource::list or tx.resource(). A client generated from the OpenAPI document (the key is optional now).

Migration. Treat the key as optional on the client. In a route of yours, if let Some(id) = read.film_id, or read.film_id.flatten() for a nullable key. An app that counted the statements of a read sees one more per BelongsTo. See Links and foreign keys.

A write naming a foreign key reads its target

Before. A create, PUT or PATCH that set the key of a plain BelongsTo (no owner(from)) wrote it whatever the caller could read of the target: a row the caller could not read was accepted (201 or 200), and a row that does not exist was a 500 internal (SQLSTATE 23503).

After. The target is read under the caller’s read scope in the write’s transaction, without a lock. A target that is absent, soft-deleted, unreadable by the caller or not mounted on the Foundry is the 422 reference_not_found on the key, byte for byte the same in each case, and nothing is written. It holds through Resource<M> and a hook’s tx.resource. null and a write that does not name the key read nothing.

Who is affected. A client that wrote a key to a row it cannot read (it now gets the 422), or that handled the 500 of an absent one. A model whose BelongsTo target is not mounted on the same Foundry: its key can only be null through the API now, unless a before_save hook sets it from another value of the body. An app that counted the statements of a write sees one more per key named.

Migration. Handle the 422 reference_not_found as “that reference does not exist for you”. Mount the target model if callers must be able to point at it. See Writing a foreign key.

A create of an owner(from) model needs its parent mounted

Before. Since 0.13.0 a create of a model with owner(from = ..) accepted a key whose parent the caller cannot GET: a parent that the get rule refuses (GET {parent} answers 403), a parent that the default projection’s rule refuses (404), or a parent that is not mounted on the Foundry. The caller wrote a row (201) under a parent it cannot read.

After. The key is judged as GET {parent} judges the parent, for the caller. A parent that is refused by the get rule or by the default projection’s rule, or that is not mounted (an unmounted parent is read by nobody, whatever the value), is the one 422 reference_not_found on the key, the bytes of an absent parent, with nothing written. It holds for the route, Resource::create and a hook’s tx.resource. See Writing a foreign key.

Who is affected. An application whose owner(from) child is created by a caller that cannot GET the parent (a role that may create reviews but whose get on films is refused, say), or whose parent model is not mounted on the same Foundry as the child.

Migration. Mount the parent model, and give each caller that creates children a get on it (and a default projection that admits them). Handle the 422 reference_not_found as “that parent does not exist for you”.

A hand-written FerraModel derives its column table

Before. Ferra parsed a field’s name into its Sea-ORM column, which failed for a field such as film_1.

After. The derive emits the table from each field to its column, and no code parses a name. A FerraModel written by hand gets None from the hidden column_of_field: every request that needs a column (a write of a field, a sort, a filter) is a 500 or a refusal.

Who is affected. A model that implements FerraModel by hand. A derived model: nobody.

Migration. Derive FerraModel.

A delete a foreign key refuses is a 409

Before. A DELETE that a foreign-key constraint refused (a film that still has reviews under ON DELETE RESTRICT) was a 500 internal, and so was a write the database refused for a foreign key after Ferra’s read (the target removed in between).

After. The delete is the 409 conflict with its fixed detail: nothing is deleted, the statement is run once, and the OpenAPI document declares the 409 on the DELETE of every model that a BelongsTo targets. The write is the 422 reference_not_found on the key the constraint names, the bytes of an absent target. The log holds the constraint’s name, never a key value. ferra_db::FerraDbError gains the variant ForeignKey { constraint } (it is #[non_exhaustive]: a match on it already has a wildcard arm).

Who is affected. A client or a monitor that treated that 500 as a server fault. A generated client that now sees a 409 on a DELETE. An application that matches FerraDbError exhaustively with a wildcard that assumed a database failure.

Migration. Handle the 409 on a DELETE as “this row is still referenced”. See Deleting a parent.
