Ferra.rs — User Guide

ferra-db — the database layer

The repository layer (PgRepository, FerraRepository, FerraDbError) is internal to Ferra and outside the contract: the ferra facade does not export it, and an application does not declare ferra-db. What an application reaches from this layer is Page, CursorPage, CollectionQuery, CursorQuery, PkValue and DatabaseConnection, all exported by ferra.

To read and write a model from a route of your own, take a Resource<M> extractor (from the ResourceHandle<M> that mount_and_handle::<M>() returns): get, list, list_cursor, create, update, delete, each returning FerraError (Custom Handlers). Behaviour that used to be read on the repository (SQLSTATE 23505 becomes a 409 Conflict, a missing row a 404, an undecodable cursor a 400) is read on the HTTP side and on FerraError (ferra-http.md). For raw access, use your own DatabaseConnection, outside the contract: see Custom Handlers § Raw database access, outside the contract. Transactions are the same: begin one on your own connection with conn.begin() (below).

Dependencies. The examples on this page assume the dependencies of Getting started:

Queries and pages

CollectionQuery and CursorQuery are #[non_exhaustive]: build one with CollectionQuery::new(page, per_page) and the with_filter / with_sort methods, CursorQuery::new(per_page) and with_after / with_filter. A filter key the model does not declare #[field(filterable)] is refused, never ignored (Pagination). PkValue<M> is the Sea-ORM primary-key value type of M: a plain i32 / i64 / Uuid, or a tuple for a composite key (ferra-forge.md § Composite primary keys).

A filter key is the field name for equality, or field[op] for a comparison (gt, gte, lt, lte) on a ferra::DateTime, Date or Time field, as filter[field][op] is on the wire; a comparison on another type is refused (400 unsupported_operator). A CursorQuery walks ascending unless with_direction(SortDirection::Desc) says otherwise; a cursor issued for the other direction is refused as an invalid cursor, and Resource::list_cursor applies the same checks as the generated route.

#![allow(unused)]
fn main() {
use ferra::{CursorQuery, SortDirection};

let newest_first = CursorQuery::new(20)
    .with_direction(SortDirection::Desc)
    .with_filter("created_at[gte]", "2026-10-03T00:00:00Z");
assert_eq!(newest_first.direction, SortDirection::Desc);
}

Logging and tracing of database activity

sea_orm::Database::connect(&database_url) — the connection form used throughout this guide — accepts anything that converts Into<ConnectOptions>, including a bare &str. When you pass a bare URL, Sea-ORM builds a ConnectOptions with its own defaults, and those defaults are logging-on:

SettingDefaultWhat it emits
sqlx_loggingtrueThe SQL text of every executed statement, with its placeholders and not its bound values, is logged via the log/tracing bridge, at the level below.
sqlx_logging_levellog::LevelFilter::InfoThe level statements above are logged at (ignored if sqlx_logging is false).
record_stmt_in_spanstrueThe SQL text of the statement, with its placeholders and not its bound values, is attached to the tracing span for that query. Only under sea-orm’s non-default tracing-spans feature; without it the setting does nothing.
sqlx_slow_statements_logging_settings(LevelFilter::Off, _)Off by default; when enabled, statements slower than a threshold you set log at a separate level.

Neither setter logs a bound value (sea-orm 2.0.4, sqlx-core 0.9.0): sqlx’s statement log and the span field carry the SQL text with its placeholders, so a query binding a user’s email address or a password-reset token logs $1, not the address or the token. The text still tells a reader of your logs which tables, columns and filters your API touches, which is what the two setters cut. Bound values reach a log by one path: sea-orm’s debug-print feature, which logs every statement with its values at debug level whatever these setters say. It is off by default; never enable it outside development.

A reader of this section alone can now answer: does query text reach my logs and traces by default, and how do I change that? Yes for statement logging; for spans, only if sea-orm’s tracing-spans feature is on. To change it, build a ConnectOptions explicitly instead of passing a bare URL string, and connect with that:

use ferra::sea_orm::{ConnectOptions, Database};

async fn demo(database_url: String) -> Result<(), Box<dyn std::error::Error>> {
let mut opt = ConnectOptions::new(database_url);
opt.sqlx_logging(false)           // stop logging statements entirely, or...
   .record_stmt_in_spans(false);  // ...keep statement-shape logging but never
                                   // attach the SQL text to a span.

let conn = Database::connect(opt).await?;
let _ = conn;
Ok(())
}
fn main() {}

ConnectOptions’s setters take &mut self and return &mut Self, so they chain on an existing let mut binding as shown — they are not a consuming builder, and ConnectOptions::new(url) must be bound to a variable before you call a setter on it.

Recommended production posture. Disable sqlx_logging (or drop the level to a value your production log pipeline filters out) and disable record_stmt_in_spans to keep statement text out of your logs and spans. Never enable sea-orm’s debug-print feature outside development: it logs every statement with its values whatever these setters say. Keep both settings enabled in local development, where seeing the generated SQL is a debugging aid and the log sink is your own terminal. There is no framework-level override that does this for you today — ferra-db accepts whatever sea_orm::DatabaseConnection you construct and does not itself configure ConnectOptions — so the setting is entirely in your hands at the Database::connect(...) call site.

A connection for a permanent server

Ferra configures no ConnectOptions itself, so a server that stays up chooses its own. This recipe takes the URL from the environment, bounds the pool under the request budget, and keeps statement text out of the logs and spans (it never carries a bound value; see the debug-print bullet below):

use ferra::sea_orm::{ConnectOptions, Database, DatabaseConnection};
use std::time::Duration;

/// `budget` is the value you give `FoundryBuilder::request_budget`.
fn options(url: String, budget: Duration) -> ConnectOptions {
    let mut options = ConnectOptions::new(url);
    options
        .max_connections(20) // under the database's `max_connections`, divided by your instances
        .acquire_timeout(budget / 3) // under the budget: a full pool answers its own 503
        .idle_timeout(Duration::from_secs(300))
        .sqlx_logging(false) // no statement text in sqlx's logs
        .record_stmt_in_spans(false); // no statement text in a span (`tracing-spans` feature only)
    options
}

async fn connect(budget: Duration) -> Result<DatabaseConnection, Box<dyn std::error::Error>> {
    // From the environment or a secret store, never a literal, test fixtures included.
    let url = std::env::var("DATABASE_URL")?;
    Ok(Database::connect(options(url, budget)).await?)
}
fn main() {
    let budget = Duration::from_secs(10);
    let o = options("postgres://db.internal/app".to_owned(), budget);
    assert_eq!(o.get_max_connections(), Some(20));
    assert!(o.get_acquire_timeout().is_some_and(|t| t < budget));
    assert!(!o.get_sqlx_logging() && !o.get_record_stmt_in_spans());
    let _ = connect;
}

  • acquire_timeout under the budget. A bare URL leaves it at sqlx’s 30 s, past a 10 s budget, so a full pool would answer the budget’s 503 timeout. Under the budget, it answers 503 service_unavailable (see When no connection can be had). A third of the budget leaves room for a request that needs a connection more than once.

  • Logging off. Both setters default to true; the table above says what each one emits and cuts: the statement text in sqlx’s log lines and, under the tracing-spans feature, in a span. Neither carries a bound value. Turn them back on in local development to see the SQL. sea-orm’s debug-print feature logs every statement with its values whatever these setters say; never enable it outside development.

  • Never enable TRACE for sea_orm in production. sea-orm 2.0.4’s Postgres connect function is #[instrument(level = "trace")] with no skip, so its span records the ConnectOptions through their Debug output, and the url field has no debug skip: a subscriber that enables TRACE for sea_orm records the URL, password included. Database::connect also puts the URL in the DbErr it returns when the URL cannot be parsed. Prefer a password from a secret store over a URL that carries credentials.

  • A lock wait ends on the server, below the budget, set once per role (the role your application connects as; here app_user, 5 s under a 10 s budget):

    ALTER ROLE app_user SET lock_timeout = '5s';

    Postgres applies a role setting when the role starts a session, and only then, so it reaches every server connection a pooler opens for that role and no session already open. A SET in your own connect hook lands on one server connection: in transaction mode PgBouncer releases the server connection after each transaction (PgBouncer pool_mode) and says clients must not use any session-based features (PgBouncer server_reset_query), and Neon lists SET/RESET as unsupported on its pooled endpoint and recommends a role-level setting instead (Neon connection pooling). A lock_timeout sent as a startup parameter is refused by PgBouncer unless track_extra_parameters lists it (then PgBouncer restores it, a pooler-side setup this recipe does not rely on) or ignore_startup_parameters does (then it is ignored and never applies). Below the budget, the wait ends while the request is alive: Postgres aborts the statement and the client’s ROLLBACK ends the transaction (the SQLSTATE is in the log only; the client gets a 500 internal), and the connection goes back to the pool clean. Behind a transaction pooler says what else a pooler forbids.

  • Keep lock_timeout above deadlock_timeout (1 s by default). Otherwise a deadlock surfaces as a 55P03 500 that is never retried, instead of the 40P01 that is.

  • What a timeout answers. A lock wait cut by lock_timeout (55P03) and a statement cut by statement_timeout (57014) are a 500 internal, logged once with the SQLSTATE, never retried (only 40001 and 40P01 are), and never the 503 timeout. A COMMIT refused with either code is classed as rolled back, and is the same 500. The repository pins both answers in crates/ferra-http/tests/lock_timeout.rs; the role form itself is not run there, as it would change a role every test shares. The Lambda page sets lock_timeout the same way: Server-side timeouts.

The Page<M> shape

#![allow(unused)]
fn main() {
use ferra::Page;
use ferra::model::FerraModel;

// The four public fields of `Page<M>`; `CursorPage<M>` has `items`, `per_page` and `next_cursor`.
fn summary<M: FerraModel>(page: &Page<M>) -> String {
    format!(
        "page {} of {} per page: {} items, {} in all",
        page.page,
        page.per_page,
        page.items.len(),
        page.total
    )
}
}
  • 1-indexed page by framework convention. page = 0 is treated identically to page = 1 (the repository applies saturating_sub(1) internally to hand Sea-ORM its 0-indexed offset).
  • total: u64 fits any Postgres bigint in the non-negative half — the full-table row count observed by the count query.
  • items.len() <= per_page always. An over-scrolled request is Ok(Page { items: vec![], total, .. }), never NotFound.
  • Concurrent-insert drift. items.len() and total may disagree by ±1 under concurrent inserts — both queries run serially on the same connection (FR-015), not in parallel. Callers that need strict consistency read inside a SERIALIZABLE transaction of their own connection.
  • Serialize, not Deserialize. Page<T>: serde::Serialize whenever T: serde::Serialize. Page<T> and CursorPage<T> accept any T, a model or a view of one, which is what lets a route of your own return a page of views (Page<M> and CursorPage<M> are the same types with T = M). No Deserialize — pages are server-constructed, never parsed from client input.
  • #[non_exhaustive] — a later release may add fields. Construct via Page::new(items, total, page, per_page), not a struct literal.

Transactions

Transactions are Sea-ORM’s: begin one on your own DatabaseConnection (the type of your own sea-orm declaration, also exported as ferra::DatabaseConnection). It needs Sea-ORM’s TransactionTrait in scope. Dropping the transaction without .commit() rolls it back. A Resource<M> call runs on its own connection, not inside your transaction; inside it, write with Sea-ORM.

use ferra::DatabaseConnection;
use sea_orm::TransactionTrait; // import needed for .begin()

async fn demo(conn: DatabaseConnection) -> Result<(), Box<dyn std::error::Error>> {
let tx = conn.begin().await?;
// ... Sea-ORM statements on `&tx` ...
tx.commit().await?; // dropped without commit: rolled back
Ok(())
}
fn main() {}

Every write Ferra opens runs at READ COMMITTED, whatever the server’s default_transaction_isolation says (0.16.0). PostgreSQL’s own default changes nothing. An application whose connection defaults to REPEATABLE READ or SERIALIZABLE loses one detection: a hook that reads a second row through tx.resource().get (no lock), then writes it through tx.resource().update with a value computed from that read, no longer gets a 40001 that the retry of Transient conflicts are retried would have replayed. The update locks the row FOR UPDATE, merges the patch over the fresh row, and the stale value wins. Under a SERIALIZABLE default, read-write anomalies across rows are likewise no longer detected. A write of the row’s own model is unaffected, because before_* hooks receive the locked row. Remedy: compute the new value in the target row’s own hook or action, where the row is locked. tx.resource evaluates no If-Match; HTTP clients keep If-Match. See Migrating from 0.15 to 0.16.

A child’s write locks its parent FOR SHARE before its own row (0.16.0; see Relations). On a hot parent, a stream of children writes can keep the parent’s share lock held: PostgreSQL lets new FOR SHARE lockers pass a waiting FOR UPDATE, so a write of the parent itself may wait longer. That is latency, not a deadlock, and the request budget’s 503 timeout caps it (What Ferra executes states the wait).

A transient error that a hook swallows is not replayed. A hook that catches the error of a tx.resource call (a 40001, a 40P01) and goes on gives the write a 500 internal, with nothing committed: the retry of Transient conflicts are retried only replays an error the hook lets out.

(0.16.0.) For each operation of the generated routes, the statements Ferra sends, the locks it holds and the level it runs at. They hold for the models of that test, a studio (a root, no relation), its films and their reviews (a child through owner(from), with a soft delete and one BelongsTo). Under contention a statement that asks for a lock a transaction holds incompatibly waits for it, and the request waits with it, at that statement and nowhere else. A write waits at the parent’s FOR SHARE while the parent is held FOR UPDATE (by its own write, action or hook), then at its row’s FOR UPDATE while another write holds the row; a parent’s write waits for the shares of the child writes in flight. PostgreSQL lets new FOR SHARE lockers pass a waiting FOR UPDATE, so a stream of child writes can keep a parent’s own write waiting longer. That is latency: it ends when the holder commits or rolls back, or at the 503 timeout of the request budget when the application set one. A read takes no lock and waits for none. A collection action locks its parents, then its rows, each in key order, so two overlapping batches end without a deadlock between them. Ferra does not promise the absence of deadlocks: a deadlock the protocol cannot order away (two hooks that write each other’s siblings, a trigger of yours that writes the parent) is aborted by PostgreSQL with 40P01, replayed up to the bounded retries and answered 503 retry_exhausted when it keeps coming (Transient conflicts are retried). The locks and the order are stated in Relations.

Behind a transaction pooler

Ferra’s writes run behind a pooler in transaction mode: PgBouncer, or Neon’s pooled endpoint (the hostname with -pooler). A pooler hands a server connection to a client for one transaction only, so nothing a session keeps may matter between two transactions. Ferra keeps nothing:

  • no SET outside a transaction (what a write sets, it sets for its transaction: the isolation level of a model with a write’s READ COMMITTED level, for one), no LISTEN, no SQL-level PREPARE;
  • the advisory locks of a system grant are transaction-level (pg_advisory_xact_lock), released at commit or rollback, never session-level;
  • a write, its replay after a 40001 or a 40P01 (the whole transaction runs again) and its COMMIT each use one transaction on one server connection.

The statements Ferra prepares are protocol-level ones (sqlx’s), which a pooler can carry only if it tracks them: PgBouncer does with max_prepared_statements greater than zero (since 1.21.0; on by default at 200 since 1.24.0). sqlx also sends extra_float_digits at the start of every connection, and a PgBouncer that lists it in neither ignore_startup_parameters nor track_extra_parameters refuses the connection. Your own code is yours: a SET, a LISTEN, a session advisory lock or a WITH HOLD cursor of your own is wrong behind such a pooler, whatever Ferra does.

PgBouncer 1.26.1 or later. Earlier versions have CVE-2026-107350, a bypass of SCRAM authentication between users, fixed in 1.26.1. The repository’s compose.yml and its CI pin edoburu/pgbouncer at 1.26.1, by digest, with AUTH_TYPE=scram-sha-256; run no older one, and no looser authentication mode, in front of a database that holds data.

The repository proves the above on every run of pooler_acceptance (crates/ferra-http/tests/): CRUD, a stale If-Match on PUT, PATCH and DELETE, a forced 40001 replayed to one commit and one after_commit, a second pooled connection that reads the server’s defaults after a write, and two concurrent system appends that end with one chain head each. It needs POOLER_DATABASE_URL (podman compose up -d postgres pgbouncer, then postgres://ferra:ferra@127.0.0.1:6432/ferra_test) and fails under CI without it. #[sqlx::test] drops its database without FORCE, and PgBouncer keeps an idle server connection to it for server_idle_timeout after the client left (10 s in the repository’s test pooler, 600 s by default): the test ends those sessions itself, and a run that fails before that leaves its database undroppable (55006) until they expire.

When no connection can be had

A generated route, or a Resource<M> call, that gets no connection from your pool within its acquire_timeout answers 503 service_unavailable (0.17.0). The answer comes before the operation: nothing of it was applied, no hook ran, and the client may retry it. The detail is one fixed text; it names neither the pool, the database nor a delay (service_unavailable shows the body). It is a 503 and not a 500 because the service could not handle the request in time, whatever the cause: a saturated pool, and also a database that is down or still starting, since sqlx retries a refused connection until the acquire_timeout and the pool then reports a timeout. Say “a connection could not be had”, not “the pool is full”, when you read it. A connection the database refuses at once (a wrong password, an unknown database) stays a 500. Ferra does not retry it: only 40001 and 40P01 are retried, and a retry would add to the saturation.

  • Set acquire_timeout under the request budget. The deadline that comes first answers. With the pool’s timeout at or past the budget left, the budget’s 503 timeout wins; under it, the pool’s 503 service_unavailable wins, and that is the one an operator wants to see, because it says what is saturated. For a write made through Ferra (a generated route or a Resource<M> call), both mean nothing was written; a write on your own connection is outside this (What Ferra does not do in one request). The budget’s side of this is in Behaviors.
use ferra::sea_orm::{ConnectOptions, Database};
use std::time::Duration;

async fn demo(database_url: String) -> Result<(), Box<dyn std::error::Error>> {
let mut opt = ConnectOptions::new(database_url);
opt.acquire_timeout(Duration::from_secs(5)); // under a `.request_budget(Duration::from_secs(10))`
let conn = Database::connect(opt).await?;
let _ = conn;
Ok(())
}
fn main() {}
  • No Retry-After is sent, because no delay is known. A client or a gateway backs off with full jitter on a 503 without Retry-After and caps its attempts; a fixed delay makes every client retry in step.
  • After a commit it is a 500. A pool that gives no connection once the write is durable (the read of a written row’s parents) is a 500 internal with the write standing, never this 503 (service_unavailable).
  • API keys. An API key request whose store shares the saturated pool is a 503 identity_unavailable, not a service_unavailable: the credential could not be checked, so the handler never runs (API keys). The key store does not go through the path above, so it writes one warn line per refused request, target ferra_http::credential, reason = "store_unavailable", and no ferra_db::pool line. Under a flood of requests that is one line each. Give the key store its own small pool when its 503 must stay distinct from the rest, and, for the volume, put a de-duplicating tracing layer in your subscriber (tracing-throttle or Vector’s tracing_limit) besides the acquire_timeout and the pool size. Ferra does not de-duplicate for you.

Blameable models and the repository

The public FerraRepository write methods (insert, update, soft_delete, restore and their _in_tx forms) take no subject, so on a #[behavior(blameable)] model they return an error and write nothing: the author comes from the caller’s identity, which only the generated routes and Resource<M> hold (0.13.0).

No raw-SQL entry point

The root of the ferra crate publishes NO entry point that accepts a pre-formed SQL string: ferra::Statement, ferra::execute_unprepared and ferra::raw_sql do not resolve (compile-fail fixtures, crates/ferra/tests/ui/no_raw_sql.rs). That is not a limit on your application — ferra::sea_orm is Sea-ORM itself, and your application owns its DatabaseConnection. It is a statement about the routes Ferra generates: they never put request data in SQL text. A filter value is bound as a parameter, a sort key that is not declared #[field(sortable)] is not an identifier of the query, a cursor is decoded before any query is built (crates/ferra-db/tests/hostile_input_is_bound.rs).

Your own SQL

If you need raw SQL (a hand-written migration, an analytics query that defeats Sea-ORM’s builder), use Sea-ORM directly, on the connection you already hold. It is outside the guarantee above — the query is yours:

[dependencies]
ferra   = { git = "https://github.com/ferra-rs/ferra", tag = "v0.17.0" }
sea-orm = { version = "2.0", default-features = false, features = ["macros", "runtime-tokio-rustls", "sqlx-postgres"] }

One rule goes with that line: a Ferra project never holds two major versions of Sea-ORM, not even for its tests or an optional feature. A sea-orm = "1" in [dev-dependencies], or behind a feature such as full = ["dep:sea-orm"], next to a model written through the facade, is refused with FRG-400 as soon as the test or the feature is on. Give it the same major as Ferra, or remove it and write ferra::sea_orm::...; cargo tree -d -i sea-orm lists the copies (docs/user-guide/ferra-forge-diagnostics.md section FRG-400).

Your code reads as “I am opting out of Ferra’s SQL-injection-by-construction contract for this query”. Three entry points, in order of preference:

  • sea_orm::raw_sql! (added in Sea-ORM 2.0) — a format!-style macro that still parameterizes every interpolated value, so it carries no injection risk despite the format!-like syntax. This is Sea-ORM’s own recommended entry point for hand-written SQL as of 2.0. SomeEntity::find_by_statement(raw_sql!(DbBackend::Postgres, "SELECT * FROM films WHERE year > {}", min_year)).
  • Statement::from_sql_and_values — construct a Statement with an explicit parameter list (Vec<Value>) bound positionally ($1, $2, …). Use when you need to build the parameter list programmatically rather than at a single macro call site.
  • execute_unprepared (a ConnectionTrait method, e.g. conn.execute_unprepared("...").await?) — runs a literal SQL string with no parameter binding at all. Only ever pass a compile-time-constant string (a migration statement, a DDL command); passing anything containing interpolated request data here reintroduces the exact injection risk Ferra’s core contract exists to foreclose. Statement::from_string (construct-only, no execution) exists for cases where you need a Statement value without binding parameters — pair it with from_sql_and_values rather than execute_unprepared if the statement takes any input.

API keys

ferra::api_key holds the key store contract (ApiKeyStore, PgApiKeyStore), issue, revoke and the schema. How a key is issued, stored hashed and presented is in ferra-auth.md, section API keys.

Entity declaration: two forms

The split form — a Model struct plus a separate enum Relation { ... } naming every relation. Sea-ORM 2.0 also ships a second, terser dense form, and both are valid ways to declare a Ferra entity. This section states which to write and when, rather than leaving you to infer it from the fact that Ferra’s own shipped examples use both.

The split form

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
}

#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}   // names every relation, even when there are none

impl ActiveModelBehavior for ActiveModel {}
}

The dense form (Sea-ORM 2.0)

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[sea_orm::model]      // <- layered above the same derive list
#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
    // relations, if any, are declared inline on the struct — see below —
    // there is no separate `enum Relation` at all in this form.
}

impl ActiveModelBehavior for ActiveModel {}
}

The dense form drops the enum Relation { ... } boilerplate entirely — for a model with no relations, that is a pure line-count win. When a model does have relations, the dense form declares them inline instead of in the separate enum, and FerraModel reads such a model since 0.13.0 (see ferra-forge.md § Relations for a compiled example):

// Sea-ORM's own syntax, shown for the shape.
#[sea_orm::model]
#[derive(Clone, Debug, PartialEq, Eq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "users")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    #[sea_orm(has_one)]
    pub profile: HasOne<super::profile::Entity>,
    #[sea_orm(has_many)]
    pub posts: HasMany<super::post::Entity>,
}

Relation fields and FerraModel

Before 0.13.0 #[derive(FerraModel)] refused HasOne<...>, HasMany<...> and BelongsTo<...> as field types, so a dense-form model with a relation field had to be written in the split form. It no longer is: #[sea_orm::model] keeps the relation fields off Model (they live on a second struct, ModelEx), Ferra reads Model, and a relation field is never a column or a wire field, and never a projection field of its own, with one exception: a BelongsTo named in a projection’s read list is embedded (Embedding). The practical rule:

Your model has…Write it as…
No relation fieldsEither form. The dense form (#[sea_orm::model]) is shorter — prefer it for new models.
One or more relation fields (has_one / has_many / belongs_to)The dense form. A split-form model gets no relation feature: a model that gains relations moves to the dense form (ADR-0059).

Which shipped example uses which, and why

Every shipped example uses the dense form (ADR-0050):

  • examples/hello-ferra — its one model, Film, has no relations.
  • examples/movie-stars — its six models (Studio, Film, Review, Actor, Director, Genre) are in the dense form; Studio, Film and Review declare their relations (HasMany, BelongsTo) on it.
  • examples/lambda-neon — its one model, Film, has no relations.

The split form is not shown by an example: it stays valid, and the section above documents it, for a model without relations. A model that gains relations moves to the dense form (ADR-0059), and a new model is written in it: copy any shipped example.

Troubleshooting

error[E0277]: the trait bound <M>: sea_orm::ModelTrait is not satisfied

You forgot the DeriveEntityModel derive on the struct. A Ferra model requires BOTH FerraModel AND DeriveEntityModel on the same #[derive(...)] list. Add DeriveEntityModel back and recompile.

error[E0425]: cannot find value Statement in crate ferra

Expected — the root of ferra has no raw-SQL entry point. Use Sea-ORM’s own (sea_orm::Statement), through the sea-orm your application declares; see “Your own SQL”.

ferra::PgRepository, ferra::FerraRepository, ferra::FerraDbError, ferra::DatabaseTransaction do not resolve

Removed from the facade in 0.10.0 (the repository layer is internal). Use Resource<M> or your own DatabaseConnection (see the top of this page).
