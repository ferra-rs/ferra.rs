Ferra.rs — User Guide

Authentication & Authorization

Ferra derives authentication and authorization from your model declaration. You implement one trait, mark the model, and the framework wires the JWT pipeline and evaluates per-operation access rules before any database write.

Everything on this page lives in the ferra facade crate — there is no separate auth dependency to add.

Dependencies and URLs

The examples on this page assume the dependencies of Getting started — sea-orm declared next to ferra, at the same major version (a project that has two majors of Sea-ORM does not compile: FRG-400):

[dependencies]
ferra   = { git = "https://github.com/ferra-rs/ferra", tag = "v0.15.0" }
sea-orm = { version = "2.0", default-features = false, features = ["macros", "runtime-tokio-rustls", "sqlx-postgres"] }
tokio   = { version = "1", features = ["macros", "rt-multi-thread"] }
axum    = "0.8"
serde   = { version = "1", features = ["derive"] }

A model’s URL segment is its table name: table_name = "articles" is served at /articles. To serve a table under another name, put #[ferra(resource = "notes")] on the model. A model’s table is its own to create (a migration, or Schema::create_table_from_entity in development, as Getting started shows): Ferra never creates one.

The shape of a Ferra model

Every example below builds on the same declaration shape, so it is worth pinning once. A Ferra model is a Sea-ORM entity struct carrying a second derive:

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};

#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "articles")]
#[ferra(auth = "none")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
}

#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}

impl ActiveModelBehavior for ActiveModel {}
}

Container attributes (#[ferra(...)], #[authorize(...)]) sit next to #[sea_orm(...)]; field attributes (#[field(...)], #[ferra(...)]) sit on the field.

The type you mount is that Model struct. Sea-ORM’s DeriveEntityModel requires the struct to be named Model, so the usual layout is one module per resource and the mount site names it through the module — mount::<article::Model>(). Some codebases add pub use Model as Article; and mount article::Article; both are the same type. Every later example on this page mounts article::Model.

The resource path is derived from table_name, not from the struct name: the model above serves /articles.

Identity — the FerraIdentity trait

Your application defines its own JWT-claims struct and implements FerraIdentity. The trait has exactly two methods:

#![allow(unused)]
fn main() {
use ferra::FerraIdentity;
use serde::{Deserialize, Serialize};

#[derive(Clone, Serialize, Deserialize)]
pub struct MyClaims {
    pub sub: String,
    pub roles: Vec<String>,
    pub exp: usize,
}

impl FerraIdentity for MyClaims {
    fn id(&self) -> &str {
        &self.sub
    }
    fn has_role(&self, role: &str) -> bool {
        self.roles.iter().any(|r| r == role)
    }
}
}
  • id() is what IsOwner compares against the row’s #[field(owner)] value. The owner column is rendered to a string for the comparison, so a Uuid owner column matches a sub claim carrying that UUID’s canonical text form.
  • has_role() backs IsAdmin (which asks for the role "admin") and HasRole("...").
  • An id() that is the empty string (a token with sub: "") is refused with the generic 401, like any other failed credential, with one warn (reason = "empty_subject"); a handler never reads an empty subject as an authenticated one. Only the empty string is refused: any other sub is yours to accept. For an API key, api_key::issue refuses an empty or whitespace-only subject with ApiKeyError::EmptySubject, and a key stored with an empty subject is the same 401.

Expiry is enforced by the framework, not by your struct: exp is validated before your claims are ever deserialised, so omitting the field from MyClaims does not produce a never-expiring token. Carry it only if your own code needs to read it.

Deserialize is required — the framework deserialises the token’s claims payload directly into your type. A claims struct that cannot be built from the token (a missing non-Option field, say) is a 401, not a 400: the token is a credential, and a credential the framework cannot interpret is a failed authentication, not malformed user input.

Models that need no identity use the framework’s AnonymousIdentity by default — nothing to implement, nothing to declare.

JWT configuration

JwtConfig is rotation-aware by construction. JwtSecret.key is a secrecy::SecretString: it is elided from Debug output and zeroized on drop, so a tracing event that captures the config cannot leak key bytes.

A JwtConfig built from secrets supports the symmetric HMAC family — HmacAlgorithm::Hs256, Hs384, Hs512. This is enforced by the type: an asymmetric algorithm is not representable there, so the public surface never promises an algorithm the runtime rejects. Tokens signed with Ed25519 by an identity provider come from a key set instead.

#![allow(unused)]
fn main() {
use ferra::{ClaimCheck, HmacAlgorithm, JwtConfig};

fn demo() -> Result<JwtConfig, Box<dyn std::error::Error>> {
let jwt = JwtConfig::single_secret(
    "key-2026-05",                                 // kid — matched against the token header
    std::env::var("JWT_SECRET")?,                  // the HMAC secret, from the environment only
    HmacAlgorithm::Hs256,
    ClaimCheck::expect("https://auth.example.com/"), // `iss` the token must carry
    ClaimCheck::expect("films-api"),                 // `aud` the token must carry
)?
.with_leeway(30); // optional clock-skew tolerance, in seconds; 0 by default
Ok(jwt)
}
}

single_secret returns Result<JwtConfig, JwtConfigError>. It refuses a secret shorter than the algorithm’s output (RFC 7518 §3.2): 32 bytes for HS256, 48 for HS384, 64 for HS512 (JwtConfigError::SecretTooShort). Generate one with openssl rand -base64 32 (or 48, 64).

The JWT secret is not the entity-tag key. Foundry::etag_key takes a second secret (at least 32 bytes, the same on every replica, see foundry.md), and try_build() refuses a key equal to any HMAC secret of the JwtConfig: one secret used for both would compromise the tags and the tokens together.

There is no default for the issuer and the audience: each is either ClaimCheck::expect(value) — the token must carry that value — or ClaimCheck::Skip. Say Skip only when your identity provider cannot put a value there that identifies you. Under ClaimCheck::Skip for the audience, a token that does name an audience is still refused (RFC 7519 §4.1.3: this service names none).

For a rotation set, build the secrets with JwtSecret::new(kid, key, algorithm) and pass them, newest first, to JwtConfig::from_secrets(secrets, issuer, audience), which returns JwtConfigError::NoSecret for an empty set.

Every token must carry a kid header. A token with no kid at all is rejected exactly like one whose kid is unknown: 401. Tell whatever mints your tokens to set it — many JWT libraries omit it by default.

Wire it into the application once, naming your claims type:

use ferra::Foundry;
use ferra::{FerraIdentity, FerraModel};
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
mod article {
    use super::*;
    #[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
    #[sea_orm(table_name = "articles")]
    #[ferra(auth = "bearer")]
    pub struct Model {
        #[sea_orm(primary_key)]
        pub id: i32,
        pub title: String,
    }
    #[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
    pub enum Relation {}
    impl ActiveModelBehavior for ActiveModel {}
}
#[derive(Clone, Serialize, Deserialize)]
pub struct MyClaims {
    pub sub: String,
    pub roles: Vec<String>,
    pub exp: usize,
}
impl FerraIdentity for MyClaims {
    fn id(&self) -> &str { &self.sub }
    fn has_role(&self, role: &str) -> bool { self.roles.iter().any(|r| r == role) }
}
async fn demo(jwt: ferra::JwtConfig) -> Result<(), Box<dyn std::error::Error>> {
let conn = sea_orm::Database::connect(std::env::var("DATABASE_URL")?).await?;

let app = Foundry::new(conn)
    .etag_key(std::env::var("ETAG_KEY")?)?
    .with_auth::<MyClaims>(jwt)      // names the identity type for the whole chain
    .mount::<article::Model>()
    .build();                        // -> axum::Router

let listener = tokio::net::TcpListener::bind("0.0.0.0:3000").await?;
axum::serve(listener, app.into_make_service_with_connect_info::<std::net::SocketAddr>()).await?;
Ok(())
}
fn main() {}

with_auth must precede any mount — the builder’s typestate enforces it — and it fixes one identity type for the whole chain. It combines with .api_version("v1")? in either order; a versioned chain gets the same auth layer as an un-versioned one (see foundry.md § Versioning + deprecation).

An RS256/JWKS verifier or a session store cannot supply it. A later 0.x release may add an authenticator next to .with_auth; nothing in your code will have to change for that.

Key rotation with zero downtime

Ferra verifies tokens; it does not mint them. There is no signing API at 0.8.0 — whatever issues your tokens (your own login endpoint, an auth service) is a separate concern, and rotation is therefore a two-system dance. The secrets passed to JwtConfig::from_secrets are the set of keys this service will accept; order carries no meaning for verification.

Rotate in this order, which is safe under a rolling deploy:

  1. Add the new JwtSecret to the set on every verifier and roll the fleet. Both keys now verify; the issuer still signs with the old one.
  2. Confirm every replica is on the two-key build before continuing. Flipping the issuer while some replicas still lack the new key produces intermittent 401s for the duration of the roll.
  3. Switch the issuer to sign with the new key.
  4. Wait out the longest-lived outstanding token’s exp, plus your fleet’s clock skew. Ferra emits no per-kid success signal, so this gate is time-based — size it from the issuer’s configured token lifetime, and consider trimming on one canary replica first.
  5. Trim the old secret and roll again.

A token whose kid is absent from the active set is refused 401, and the framework emits a single structured tracing event under target ferra_http::auth named kid_unknown. That event deliberately carries no kid value, no configured- kid set, no claims and no request path — naming the failure mode without naming the credential.

Key set — tokens from an identity provider (EdDSA)

When an identity provider signs tokens with Ed25519 and publishes its public keys as a key set (a JWKS, RFC 7517), point Ferra at the set instead of sharing a secret:

#![allow(unused)]
fn main() {
use ferra::{ClaimCheck, JwtConfig, KeySetAlgorithm};
use std::time::Duration;

fn demo() -> Result<JwtConfig, ferra::JwtConfigError> {
let jwt = JwtConfig::key_set(
    "https://auth.example.com/.well-known/jwks.json", // https only
    KeySetAlgorithm::EdDsa,                           // the one accepted algorithm, named here
    ClaimCheck::expect("https://auth.example.com/"),
    ClaimCheck::expect("films-api"),
)?
.with_key_set_timeout(Duration::from_secs(2))?       // whole fetch; 3 s by default
.with_key_set_max_age(Duration::from_secs(300))?;    // cap on the cache lifetime; 10 min by default
Ok(jwt)
}
}

Everything else is the same as for a secret: pass the JwtConfig to with_auth, the claims type is yours (Deserialize plus FerraIdentity), roles come from your own claims (there is no role-claim path to configure).

What Ferra does with the key set

ValueSet by

Least time between two fetches30 sfixed
Largest key-set body64 KiBfixed
  • First use, never at startup. The set is fetched by the first request that needs a key, and by nothing else: building the configuration, building the Foundry and starting the server make no request. A request with no credential needs no key.
  • Cached. A fresh set answers a known kid with no I/O. The provider’s Cache-Control: max-age is honored, capped at the maximum above and never below 30 s; with none (or no-store, no-cache, an unparsable value) the maximum applies.
  • An unknown kid reloads at most once per 30 s. A token whose kid is not in the cached set makes one fetch when the last one is 30 s old, and is a 401 if the key is still missing; a burst of such tokens costs one fetch, not one each. A request that waits for a fetch in flight shares its outcome instead of fetching again.
  • Which keys count. Only keys of type OKP, curve Ed25519, with a kid and a 32-byte x that is a point of the curve; use and alg, when present, must be sig and EdDSA. Any other key is ignored, and two keys sharing a kid are both ignored. Only the token’s kid selects a key: jku, jwk, x5u and x5c in a token header are never read.
  • HTTPS, no redirect. The fetch is GET over HTTPS with the Mozilla roots compiled in (webpki-roots), HTTP/1.1, Accept: application/json; a redirect, a non-2xx status, a certificate that does not verify, a body over the bound or one that is not a key set is a failure. A failure logs one warn (target ferra_http::key_set, with reason and, for a status, status) that holds neither the URL, nor the body, nor a kid.

When the provider is down

  • No fresh key cached (a cold start, or the cached set has expired): 503 https://ferra.rs/errors/identity_unavailable, with no Retry-After, and the same body whatever failed. An expired set is never served.
  • Keys cached: a token the cached keys verify is accepted whatever the provider does; a token with a kid they lack is a 401, also when the reload fails.
  • A provider that answers but publishes no usable Ed25519 key (an empty set, or only keys of another type) is not “down”: the set is cached like any other and every token is a 401, not a 503, until the cache lifetime ends (with_key_set_max_age, 10 minutes by default, or the provider’s shorter max-age, never under 30 s) or the 30 s reload for an unknown kid finds a key.

On AWS Lambda the first request of a cold start pays the fetch (about one round trip to the provider). With the provider unreachable that request waits for the timeout and answers 503, inside the budget when the timeout is below it, as build() checks.

Good to know

  • A key the provider withdraws stays trusted up to the cache lifetime (the provider’s max-age, capped at with_key_set_max_age, 10 minutes by default): there is no forced refresh on rotation, only the reload for an unknown kid. Lower the maximum if that window is too long for you; a withdrawn key is not revoked sooner.
  • Rustls provider. Ferra builds its HTTPS client with its own explicit ring provider and installs no process-wide default. An application that uses rustls itself with native-tls or the aws-lc-rs provider, and relied on rustls picking its provider implicitly, finds two providers enabled once Ferra is in the tree: it must call rustls::crypto::ring::default_provider().install_default() (or the aws-lc-rs one) at startup. Applications on sea-orm’s runtime-tokio-rustls already have ring and webpki-roots and need nothing.
  • One kind of source per Foundry: a set of secrets or a key set, with one issuer and audience. Switching from one to the other is a redeploy; key rotation inside the source (several HMAC kids, or the key set’s keys) needs none.
  • The algorithm is configuration, never the token’s choice. KeySetAlgorithm::EdDsa accepts an EdDSA token and refuses none, any other algorithm, and an HS256 token signed with the public key as the secret: 401.
  • The URL is checked when the configuration is built: http:// is JwtConfigError::KeySetUrlNotHttps; no host, a user name or password, or a string that is not a URL is JwtConfigError::InvalidKeySetUrl (the error never repeats the URL). A timeout of zero is JwtConfigError::ZeroTimeout; the two setters on a configuration built from secrets are JwtConfigError::NotAKeySet.
  • The fetch runs inside the request, so its timeout must be below the request budget. With FoundryBuilder::request_budget(b) and a fetch timeout (3 s by default) that is not below b, build() panics with a message naming both values, and the two ways out: lower the timeout with with_key_set_timeout, or raise the budget. Below the budget, a key set that does not answer is a 503 identity_unavailable before the budget’s own 503 timeout can happen.
  • JwtConfig::validate, which is synchronous, answers TokenRejection::KidUnknown for a key set: verify through the Foundry layers or Resource<M>.
  • Hand-written routes. Resource<M> verifies the token the way the layer does, a key set included: a 401 for a bad token, a 503 identity_unavailable when the set cannot be fetched.

API keys — machines

A machine (an ETL job, a script) authenticates with an API key instead of a JWT. A key is ferra_<16 hex>_<64 hex>: a public prefix that finds the row and a 256-bit secret of which only the SHA-256 is stored. Keys live in a table Ferra owns, ferra_api_keys (ferra::api_key::SCHEMA_SQL is its DDL: run it with your own migration tool), behind the ApiKeyStore trait; PgApiKeyStore is the Postgres implementation.

use ferra::api_key::{PgApiKeyStore, issue};
use ferra::{ApiKeyConfig, DatabaseConnection, FerraIdentity, Foundry, JwtConfig};
use serde::Deserialize;

#[derive(Clone, Deserialize)]
struct Claims { sub: String }
impl FerraIdentity for Claims {
    fn id(&self) -> &str { &self.sub }
    fn has_role(&self, _role: &str) -> bool { false }
}

async fn demo(conn: DatabaseConnection, jwt: JwtConfig) -> Result<(), Box<dyn std::error::Error>> {
// The header defaults to `X-Api-Key`. `header` refuses `authorization` and `cookie`
// (`ApiKeyConfigError::ReservedHeader`) and a name that is not a valid header
// (`ApiKeyConfigError::InvalidHeader`).
let keys = ApiKeyConfig::new(PgApiKeyStore::new(conn.clone())).header("X-ETL-Api-Key")?;
let builder = Foundry::new(conn.clone())
    .etag_key(std::env::var("ETAG_KEY")?)?
    .with_auth::<Claims>(jwt) // keys come after `with_auth`, before the first `.mount`
    .with_api_keys(keys);

// Issue a key once, for a subject and the roles it keeps for good; the plaintext is
// shown this once, the store keeps only its hash.
let key = issue(&PgApiKeyStore::new(conn), "svc-etl", &["etl"], None).await?;
let plaintext: String = key.into_plaintext();
let _ = (builder, plaintext);
Ok(())
}
fn main() {}
  • Who the caller is. A request with a valid key is the key’s subject with exactly the roles frozen when the key was issued (ferra::ApiKeyIdentity), never your claims type. #[authorize] rules and #[field(owner)] see the subject as id().
  • A key owns rows through its subject. Issue the key with the owner’s identifier as the subject and #[field(owner)] works as for a token: IsOwner compares the subject, a row of another subject is the 404 an absent row gets, and a list is scoped to the subject’s rows. A role frozen into the key (&["admin"]) is what IsAdmin and HasRole("admin") see; roles are exact names and are never read from anywhere else.
  • In a handler: Principal<I>. ferra::Principal<I> is Token(I) for a verified JWT (your claims type) or ApiKey(ApiKeyIdentity) for a verified key; it is #[non_exhaustive], so a match needs a wildcard arm. CurrentUser<I> serves tokens only and answers 401 on a key request: a handler that must accept both extracts Principal<I>. Only the credential layer produces either: an ApiKeyIdentity or a Principal your own layer inserts as a request extension authenticates nothing.
  • Refusals. An unknown prefix, a wrong secret, a revoked key, an expired key and a malformed key are the same 401 as a bad token: same body, same headers. A malformed key (not exactly ferra_<16 hex>_<64 hex>) never reaches the database.
  • When the store fails (database down, pool timeout) on a well-formed key, the answer is 503 identity_unavailable, the same body as an unreachable key set; the failure goes to a warn trace (credential refused, reason = "store_unavailable", the key’s prefix), never to the response. The trace holds no text of the database error (no host name, no message): when the store’s error is a Sea-ORM database error, or one wrapping a DbErr as its source, that carries a SQLSTATE, the five characters are in the field db.response.status_code; any other store error logs no such field.
  • Last use (ApiKeyConfig::track_last_use(), off by default) records last_used_at without slowing the request: after a verified request whose key has no last use, or one older than a minute, the write is spawned and never awaited. At most eight such writes run at once in the process; with none free the write is skipped, because the last use is advisory. A failed write is one warn (prefix, reason = "store", and the SQLSTATE in db.response.status_code when the cause is a database error, or one wrapping a DbErr as its source, that carries one), never the key and never the text of the database error. On AWS Lambda the instance may be frozen once the response is sent: a write may be delayed or lost, so read last_used_at as “about when”, not as an audit log.
  • Revocation (ferra::api_key::revoke(&store, prefix)) takes effect at the next request: there is no key cache. The row is kept, flagged, for audit; revoke answers false for a prefix that does not exist.
  • Expiry is issue(..., Some(instant)): a key is refused from that instant, by the server’s clock, whatever store holds it.
  • Nothing readable is stored. The table holds the prefix, the SHA-256 of the secret (a fast hash is enough for 256 random bits; slow password hashes protect human passwords), the subject, the roles and the dates. issue and revoke log one info event with the prefix; nothing logs a secret.
  • Only the configured header is a credential. On a chain without with_api_keys, an X-Api-Key header is ignored. Vary names the configured header on every response.
  • One credential per request. A key next to an Authorization header, or two key headers, is a 400 multiple_credentials, whatever they hold; a key that is invalid alone is a 401 and the JWT is not tried.

Cookie — a token from a single-page app

A single-page app can keep its token in an HttpOnly cookie, out of reach of a script that an XSS flaw injected. Name the cookie and the origins allowed to use it on the JwtConfig:

#![allow(unused)]
fn main() {
use ferra::{ClaimCheck, HmacAlgorithm, JwtConfig};

fn demo() -> Result<JwtConfig, Box<dyn std::error::Error>> {
let jwt = JwtConfig::single_secret(
    "key-2026-10",
    std::env::var("JWT_SECRET")?,
    HmacAlgorithm::Hs256,
    ClaimCheck::expect("https://auth.example.com/"),
    ClaimCheck::expect("films-api"),
)?
// The cookie's name, then the origins of the app that may send it.
.with_cookie("__Host-token", ["https://app.example.com"])?;
Ok(jwt)
}
}

The cookie value is verified exactly like a bearer token: same algorithm, issuer, audience and expiry, same generic 401 when it fails, and the identity is the same Principal::Token (or CurrentUser) of your claims type. It works with a secret or a key set. A request carries one credential: the cookie next to an Authorization header or an API key, or the cookie name twice (in one Cookie field or in two), is a 400 multiple_credentials.

The cookie is the issuer’s: Ferra never sets it

Your identity provider (or login endpoint) sets the cookie; Ferra only reads it. It should set these attributes:

Set-Cookie: __Host-token=<jwt>; Path=/; Secure; HttpOnly; SameSite=Lax
  • HttpOnly: a script cannot read the token.
  • Secure: the browser sends it over HTTPS only.
  • SameSite: Lax or Strict keeps the browser from sending it on a cross-site request. Do not rely on it alone: SameSite is about sites, and the guard below is about origins.
  • Use the __Host- name prefix. A browser accepts a __Host- cookie only with Secure, Path=/ and no Domain, so a sibling subdomain cannot set or overwrite it. It is strongly recommended; with_cookie takes any RFC 6265 token as the name.

Writes are guarded against CSRF

A browser sends the cookie on every request to your API, including a request a hostile page made. So a request authenticated by the cookie whose method is not GET, HEAD or OPTIONS (a PURGE or any other method too) needs exactly one Origin header equal to an origin you listed. A missing, null, repeated, unreadable or unlisted Origin is a 403 forbidden with the fixed detail a write authenticated by a cookie must come from an allowed origin, never the Origin it received, before the handler runs and with the row unchanged. Browsers send Origin on every write.

GET, HEAD, OPTIONS with the cookie, any Origin or noneserved: reads are not guarded

  • A form sends Origin: null under Referrer-Policy: no-referrer. A page served with that policy makes a form post carry Origin: null, which is refused. Post such a form from a page whose policy lets the origin through, or use fetch from the listed app.
  • The guard is part of reading the caller. The auth layer, Resource<M> and Principal<I>/CurrentUser<I> on a .route(...) handler all apply it, so a route of your own that takes the caller is guarded. A route that never reads the caller (a webhook with its own scheme) reads no credential and is outside the guard.
  • Origins are exact. A browser omits the default port, so with_cookie refuses an explicit :443 (https) or :80 (http), like a trailing /; a request that sends https://app.example.com:443 is not https://app.example.com. The scheme and the host are compared without regard to case. List every origin of your app.

CORS with credentials, from the same list

With the cookie configured, each model’s CORS layer is built from the same origin list: a listed origin gets its exact Access-Control-Allow-Origin and Access-Control-Allow-Credentials: true; any other origin gets no Access-Control-Allow-* header at all, so a browser refuses its response. A preflight is answered without a credential. The methods are the model’s, and the headers are Content-Type, Accept, If-Match and Prefer, never a wildcard.

with_cookie refuses, at configuration, a name that is not an RFC 6265 token (JwtConfigError::InvalidCookieName), the wildcard * (WildcardOrigin), an empty list (NoOrigin) and any origin that is not https://host[:port]: null, a path, a query, a fragment, a trailing /, a user name (InvalidOrigin). Credentials with a wildcard origin is the classic hole, so it does not exist:

use ferra::{ClaimCheck, HmacAlgorithm, JwtConfig, JwtConfigError};

fn main() -> Result<(), Box<dyn std::error::Error>> {
let secret = "0123456789abcdef0123456789abcdef".to_owned();
let jwt = || {
    JwtConfig::single_secret(
        "key-1",
        secret.clone(),
        HmacAlgorithm::Hs256,
        ClaimCheck::Skip,
        ClaimCheck::Skip,
    )
};

// Refused when the configuration is built, never at the first request.

One credential per request

A request carries one credential. Ferra never picks one of two, and never falls back from one that failed to another: presence decides, not validity.

RequestAnswer
Two or more credentials: Authorization and the API key header, two Authorization headers, two key headers, whatever each holds400 multiple_credentials, before anything is verified
One credential, invalid: a bad token, a bad key401 at once; the other source is not tried

The 400 has one fixed body, send one credential per request, and names no source. A client that sends two (a proxy that adds a header, a client library that sets both) fails loudly instead of getting an identity its operator did not choose; the one rule is the same on enforcing models, on populate-only ones (an #[authorize] block that needs an identity somewhere), through Resource<M> and in Principal<I>, CurrentUser<I> on a route declared with .route(...). A model whose every rule is Anyone reads no credential, so it serves the anonymous answer, as it did before; so does a declared route that reads no caller. A CORS preflight is exempt from authentication, as before.

Logging, tracing and throttling credentials

  • Refusals are logged. Each refused credential is one warn event, target ferra_http::credential, with credential (token, api_key or cookie), api_key.prefix when the key is well formed, and a reason. The secret, the token and any cookie value are never logged.
  • Accepted requests are traced. The request span of the default trace layer carries credential and, for a key, api_key.prefix: a trace says which key acted. A custom trace_layer(...) builds its own span and does not get these fields; it also sees the request headers, so mark Authorization, Cookie and your key header sensitive in it (tower_http::sensitive_headers) before logging any header.
  • Throttle at the platform. The mutation rate limiter covers writes only and runs after the credential layer; reads are never throttled. A well-formed key that does not exist costs one indexed SELECT, and on a scaled-to-zero database it can wake the compute. Put an API Gateway or WAF throttle in front, and watch the refusal warn events for bursts.

Model auth posture — #[ferra(auth = ...)]

#![allow(unused)]
fn main() {
#[ferra(auth = "bearer")]   // every operation requires a valid bearer token
#[ferra(auth = "none")]     // deliberately, explicitly public
}

A model declaring neither auth nor #[authorize(...)] fails to compile. This is deliberate: for a framework that mounts SQL-backed CRUD, the only safe default is to refuse to build until you have made the auth surface an explicit decision. Forgetting is a compile error, not a 3am incident.

Authorization rules — #[authorize(...)]

#[authorize] is a container attribute alongside #[ferra(...)]. It attaches one rule per operation:

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "films")]
#[ferra(auth = "bearer")]
#[authorize(
    list = Authenticated,
    get = Authenticated,
    create = Authenticated,
    update = IsOwner | IsAdmin,
    delete = IsOwner | IsAdmin
)]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
    #[field(owner)]
    pub owner_id: Uuid,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

The block must cover all five operations — list, get, create, update, delete. A partial block is a compile error naming the missing operations. Ferra will not pick a posture for the ones you left out, in either direction: defaulting them to Anyone is the classic hole, and defaulting them to Authenticated would silently weaken every rule the day someone flips auth = "bearer" to "none".

A model with #[behavior(soft_delete)] also serves POST /{resource}/{id}/restore. Its rule is the optional restore key. Without it, restore requires both the update and the delete rule (update + delete): reviving a row takes the right to edit it and the right to delete it, so an owner cannot revive a row that only an admin was allowed to delete. Naming restore on a model without soft delete is a compile error (FRG-104).

The vocabulary

The checker set is closed — there is no runtime-evaluated string DSL, and that closure is the security property.

CheckerPasses when
Anyonealways; no identity needed
Authenticatedan identity was materialised from a valid token
IsOwnerthe stored row’s #[field(owner)] value equals identity.id(); on list, keeps the caller’s rows only
IsAdminidentity.has_role("admin")
HasRole("editor")identity.has_role("editor")

Combinators: + (all must pass), | (at least one), (...) for grouping. Mixed + and | must be parenthesised — Authenticated + (IsOwner | IsAdmin) compiles; the same expression without parentheses is a compile error rather than a silently assumed precedence.

Writing a redundant Authenticated alongside an identity-dependent checker is allowed and never warned about — readability beats minimalism here.

Checkers are written bare. AuthRule::IsAdmin (or any other path) is a compile error (FRG-103) that names the bare spelling; before 0.9.0 it was silently dropped, and the operation ended up with no rule. An empty #[authorize()] is refused too (FRG-101): it used to compile and check nothing. So is a HasRole whose role is empty or only whitespace — HasRole(""), HasRole(" ") (FRG-101): it names no role, and a claims type whose role list holds an empty string would satisfy it.

Ownership

A model is owner-scoped when exactly one field carries #[field(owner)]. Its type must be Id, Uuid, i32 or i64 (FRG-112): the owner is written from, and compared with, FerraIdentity::id(), so the identity’s id must be the text form of a value of that type — a UUID’s canonical text, or a decimal integer.

The server writes the owner; the client never does.

  • On create, the owner column is set to the caller’s id(), converted to the column’s type, whatever the body says. Under a projection prefix the owner field is not in the write projection, so a body that names it is refused with 422, like any other unknown field. At the bare path (POST /{resource}) the body is still the whole model: an owner named there is accepted and overwritten with the caller’s id.
  • The id must be the canonical text of a value of the column’s type: 42 for an integer column (not +42, 042 or 42), the lowercase hyphenated form for a Uuid / Id column (not the urn:uuid: form, braces, uppercase or the form without hyphens). IsOwner compares texts, so any other spelling would let one identity act as another.
  • A caller whose id() is not such a text — an IdP subject such as auth0|abc123 on a Uuid column, or a non-canonical spelling — is refused with 403: the token is valid, but that identity cannot own a row of this model.
  • On update, the owner never changes: the UPDATE leaves the column untouched, whatever the body says. Under a projection prefix the owner field is not in the write projection, so a body that names it is refused with 422.
  • A projection’s explicit write = [...] list cannot name the owner field (FRG-115).
  • The owner of a new row comes from the token, so the create rule must need an identity. A model with an owner field whose create rule lets an anonymous caller in (Anyone, or auth = "none" without a block) does not compile (FRG-114): write create = Authenticated, or a role check.

The owner field keeps its name and its text. The owner check reads the owner from the row by the field’s Rust name and compares its text with the caller’s id. No serde attribute may rename or re-serialize a model field (FRG-116, see ferra-forge.md § Field names on the wire), the owner included.

If your identity provider’s subjects are neither UUIDs nor integers, store a local Uuid per user, put it in the token as a claim that your id() returns, and use it as the owner.

IsOwner passes when the stored row’s owner equals the caller’s id(). It is valid on get, update, delete and restore, the operations that address one stored row. It is refused on create (FRG-113): a row being created has no owner yet — it will be the caller.

On list, IsOwner filters the collection in SQL: the caller sees the rows it owns (WHERE owner = <caller id>), and the page counts, links and cursors are those of the filtered collection. list = IsOwner | IsAdmin lets an administrator see every row and everyone else their own. An anonymous caller gets 401; a caller whose id is not the canonical text of a value of the owner column’s type gets 403. Filtering, sorting and pagination compose with the owner filter.

On get, update, delete and restore, the framework reads the stored row before the check and compares the stored owner, never anything the request body says. restore reads the soft-deleted row on purpose. An anonymous caller is refused with 401 before any row is read, and someone else’s row answers 404, exactly like a missing row.

A write only touches the row that was checked. update, delete and restore run in one transaction: the row is read with SELECT … FOR UPDATE, its owner and its soft-delete state are checked against what the authorization check saw, and only then is it written. A row that was deleted, soft-deleted or handed to another owner in the meantime answers 404 and nothing is written.

Read your own row. A model with a unique root owner can declare #[ferra(me)]: GET /me then answers the row whose owner is the caller’s id(), and the same 404 for any row the caller may not read. See projections-and-routing.md.

Ownership through a parent

A row that has no tenant of its own can be owned through its parent. Put #[field(owner(from = <relation>))] on the owner field, naming the BelongsTo field that reaches the parent; the parent declares #[field(owner)] of the same type (FRG-127), and so does each level above it. The owner of the row is then its parent’s owner, copied once, at create:

use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};

Create. POST /jobs {"source_id": 7, "status": "new"} reads the source 7 in the write’s transaction with SELECT … FOR SHARE, judges it under the source’s own update rule (the rules of its ModelMeta, whether or not the source is mounted on this Foundry), and gives the new job the source’s owner. The owner is never the body’s nor the token’s: a body owner_id is ignored (or refused, like any field outside the write projection). The share lock holds the source until the job is committed, so a soft delete of the source that comes meanwhile waits for the create; sibling creates do not wait for each other.

Update. The owner never changes: a body owner_id is ignored, like on any owned model. A PUT /jobs/12 that leaves source_id as it is reads no parent, so a job under a soft-deleted source stays editable. A source_id that changes moves the job: once the job is locked, the new source is read FOR SHARE and judged as on create, and its owner must be the job’s, so a job cannot leave its owner even through a parent the caller may update. Any refusal is the same 422 reference_not_found, the job unchanged. The job itself is checked first: a job the caller may not see is a 404 before the new source is looked at.

The parent’s authority. A source that has #[ferra(authority)] is also judged by it, on create and on a re-parenting update: its filter (when it serves list) is in the locking WHERE, then can(Update, source) judges the row, with the context of the request. A refusal, an Err or a panic of that authority is the same 422 below, never a 500; the job’s own can(Create) runs after the insert and answers 403 or 500. The context is the caller’s, whatever the job’s own rules say: a model with owner(from) gets at least the populate-only credential layer, so the identity is there and the API key header is dropped.

One answer for every refusal. An absent source, a soft-deleted one, one of another client and one the caller may read but not update (by its rules or its authority) are the same 422 validation_failed with one error, {"field": "source_id", "code": "reference_not_found"}: same status, body and length, no echo of the id, nothing written. A caller cannot tell a source that exists from one that does not. A foreign key that is missing or null is not this case: it stays the ordinary “missing field” or type error of the write.

What this does not do.

  • A parent whose update rule the caller cannot pass makes every child create a 422: with update = HasRole("auditor") on the parent, only an auditor creates children. Give the parent the rule that says who may attach rows to it.
  • A soft-deleted parent cascades nothing. Its children stay served under their own owner; creating under it is the 422; restoring a child does not check its parent, and restoring the parent leaves its children as they are.
  • A plain BelongsTo foreign key violated by a write Ferra cannot see (SQLSTATE 23503) is a 500 until 0.16.0; so is any write made outside Ferra (a migration, a script, a hand-written route that uses its own connection): the check lives in Ferra’s write path only.
  • Two writes that lock the same rows in opposite orders can deadlock (40P01): Postgres aborts one, which answers 500 until the retry of 0.14.0. Authority code and rules must be pure: a retry runs them again.
  • The check reads the parent by the key the body carries; a parent whose primary key is composite is not found by it and the create is refused as above.

Let the database hold the chain too. Ferra’s check does not protect rows written outside Ferra. Recommended, not required: a composite foreign key per level, so that a child cannot name a parent of another owner even there, and an index led by the owner column, which serves the owner-scoped list and its cursor:

ALTER TABLE sources ADD CONSTRAINT sources_id_owner UNIQUE (id, owner_id);
ALTER TABLE jobs ADD FOREIGN KEY (source_id, owner_id) REFERENCES sources (id, owner_id);
CREATE INDEX jobs_owner_id ON jobs (owner_id, id);

With it a write that disagrees with the chain is refused by Postgres (a 500 through Ferra, which checks first and answers 422 for every case it can see).

auth and #[authorize] on the same model

Every operation a model serves gets exactly one rule, computed when the model is mounted:

  1. the rule its #[authorize(...)] block declares (without a restore key, restore is update + delete);
  2. with no block, the rule its posture implies: auth = "bearer" gives Authenticated, auth = "none" gives Anyone.

So with a block, the block wins and auth documents intent. An operation without a rule is never served: Foundry::build() refuses to start (FRG-150).

Every request passes one checkpoint, inside the handler, that evaluates that rule. The JWT layer is defense in depth, derived from the same rules:

Rules of the served operationsLayerWho decides
every rule needs an identity (auth = "bearer" without block, or a block without Anyone)enforcing: refuses a missing or invalid token with 401the checkpoint, after the layer
some rules need an identity, some are Anyonepopulate-only: refuses an invalid token, lets a missing one throughthe checkpoint
every rule is Anyone (auth = "none" without block, or an all-Anyone block)nonethe checkpoint, which always allows

auth = "none" with #[authorize(get = IsOwner, ...)] does not disarm IsOwner: the rules decide, and the checkpoint still enforces it. But naming IsOwner in the block does not, by itself, wire the JWT layer either — the layer is only installed on a chain that also calls .with_auth::<YourClaims>(jwt) (see “What wires the auth layer” below). Mounting such a model without .with_auth() is therefore a compile error (FRG-151, see § Compile-time auth defense): without a layer nothing could ever produce an identity. The runtime checkpoint stays behind that gate: were the model mounted without a layer anyway, every operation the block marks identity-dependent (IsOwner, Authenticated, IsAdmin, HasRole) would refuse every caller — anonymous or presenting an otherwise-valid token — with 401.

Anyone inside a combinator

Anyone | IsOwner compiles, is not warned about, and always passes — | returns on its first allowing branch and Anyone always allows. It is a tautology.

It is not inert, though, and this is the subtle part: the layer derivation looks at the checker set, not at whether the rule can ever fail. IsOwner appears, so the layer is wired — and a request carrying a broken token is refused 401 on an operation whose rule can never reject anyone. If you meant “public”, write Anyone alone.

What wires the auth layer

You do not declare the token pipeline separately. Naming any identity-dependent checker (Authenticated, IsOwner, IsAdmin, HasRole) wires it, because such a checker cannot evaluate without an identity and the layer is the only thing that produces one. #[ferra(auth = "bearer")] is the equivalent shorthand for the no-#[authorize] case.

The consequence worth internalising: a model whose #[authorize] block names only Anyone gets no auth layer and serves every operation tokenless. That is a second, fully explicit way to declare a public model, and Ferra accepts it without complaint.

Projections and authorization

A projection has no rule of its own unless it declares one: its routes (/{prefix}/{resource}, /{prefix}/{resource}/{id}) are governed by the model’s rules, the #[authorize(...)] block or the auth posture. A projection that shows or accepts more than the bare path must say who may use it (0.13.0, FRG-117):

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "articles")]
#[ferra(auth = "bearer")]
#[ferra(projection(
    name = "public",
    default = true, // the bare path serves `public`: no `draft`
    promotes_from = "auto-derived",
    breaking_change_version = "0.13.0",
    read = [id, title],
))]
#[ferra(projection(
    name = "editor",
    read = [id, title, draft],
    authorize = HasRole("editor") | IsAdmin, // shows more than the bare path: says who
))]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub title: String,
    pub draft: String,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

Note what “the bare path” is: without a projection promoted with default = true, it serves every readable field of the model, so a projection that lists fewer fields hides nothing (the bare path still shows them all) and one that lists more shows nothing new. To keep a field off the bare path give it a read rule (see Field rules), or promote a narrower projection as above.

A caller the rule refuses gets a 404 (the same bytes as for a row that does not exist, or <resource> not found for a list or a create), an anonymous caller gets a 401, and nothing is read or written before the answer. The rule is added to the model’s rule of each operation, and the model’s 403 comes after the 404 (order: 401, 400, 404, 403) where the operation reads the row (an IsOwner rule, or a field rule in the write set); a model rule that reads no row keeps its 403 before any read, the same for an existing and an absent row, so it tells nothing about the row. Authenticated on a bearer model, or Anyone, restricts nothing more than the model does, and nothing checks for it.

Hooks come after these checks. A model with #[ferra(hooks)] runs zero hooks for a request refused before the statement: 401, 403, 404 (the locked-row 404 of an authority included), 413, 415, 422 (the parent check too). Three refusals come after the statement, because they need the row as written: the authority’s post-write 403, an authority error at the post-check (500), and a storage refusal (a unique 409, a foreign-key violation). before_save has run, its writes are rolled back with the statement, and after_save does not run (Hooks).

authorize = <rule> uses the same grammar as the model’s rules, except that IsOwner is refused (FRG-118): the rule is checked once per request, before any row is read. authorize = inherit declares that the model’s rules suffice. Before 0.13.0 the key was refused (FRG-105, retired): it used to be parsed and dropped.

Field rules

A field can carry its own rule: #[field(read = <rule>)] says who may read it, #[field(write = <rule>)] who may write it (0.13.0). The grammar is the model’s, and IsOwner is allowed in a read rule only (a create has no owner yet, FRG-120). A field with no read rule is readable by everyone who can read the row, and one with no write rule is writable by everyone who can write it: a field with only a write rule is not hidden from readers.

#![allow(unused)]
fn main() {
use ferra::FerraModel;
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};
#[derive(Clone, Debug, PartialEq, DeriveEntityModel, FerraModel, Serialize, Deserialize)]
#[sea_orm(table_name = "employees")]
#[ferra(auth = "bearer")]
pub struct Model {
    #[sea_orm(primary_key)]
    pub id: i32,
    pub name: String,
    #[field(read = HasRole("hr") | IsAdmin, write = HasRole("payroll"))]
    pub salary: Option<i64>,
    #[field(read = IsOwner | IsAdmin)]
    pub phone: Option<String>,
    #[field(owner)]
    pub owner_id: Uuid,
}
#[derive(Copy, Clone, Debug, EnumIter, DeriveRelation)]
pub enum Relation {}
impl ActiveModelBehavior for ActiveModel {}
}

Reads. A field the caller may not read is absent from every response: an item, a list, a create, an update, a restore. It is never null; null means the column is null and the caller may read it. An IsOwner rule is judged on each row alone, from the owner column already loaded (no query), so a list of rows of several owners shows each caller the fields of its own rows. A row whose owner is NULL has no owner. A field in two projections carries the same rule in both.

Writes. The body of a POST, a PUT or a PATCH is decoded once from its bytes, then judged key by key (a PATCH judges the keys it sets and no other), after the row is found (404) when something reads the row, in this order (on a model nothing reads the row of, a PUT or a PATCH with no precondition header judges the body first, see ferra-http):

The body, or the key sent, is…Answer
not a JSON object, a key repeated at any depth (a JSON field included), or a value of the wrong type on a key the caller may read400 invalid_json
a key unknown, outside the write projection, read_only, or a field the caller may not read422, the same unknown_field entry for each, byte for byte as for a key that does not exist
a key readable, but its write rule refuses the caller403, the fixed body, no field named
readable and writablevalidated (bounds, #[field(...)] rules: 422) and written

One body that triggers several refusals gets the first of these, in the one order of every write: the row’s 404 (when something reads the row), then 415, 412, 413, 400, 422, 403, 422 on the values, and last the 400 of a required key the body omits, and nothing is written. The 400 never looks at a key the caller may not read (its type is not judged, so a wrong type there is the 422 of an unknown key). The 422 lists the unknown and the unreadable keys together, sorted by JSON name, so the list never says which kind a key is. On a create the creator owns the row, so an IsOwner read rule never refuses the caller the field it sends.

A gated field that a body omits is left alone: a PUT keeps the column as it is, for every caller (a nullable field without a rule is still reset to NULL by a PUT that omits it, and a required one is a 422, as before), and a POST leaves it to its database default instead of writing NULL. A PATCH leaves every field it omits as it is, gated or not. Sending null sets it to NULL.

An action’s writes sets a field under that action’s rule alone: the field’s own write rule is not asked of the caller there, and a POST, a PUT and a PATCH still judge the field as above.

Filter and sort. A filter[f] or a sort=f on a field the caller may not read is refused as the same parameter on a field that is not filterable or sortable: same status, same body, and the allowed list names only the fields that caller may read. Without that, filter[salary][gt]=… would count the rows above a salary for a caller who may not read it. Through Resource::list and list_cursor the filter is refused alike, and a sort on such a field leaves the default order. A rule that cannot take effect is a compile error (FRG-119), and so is a rule on a field a write projection requires (FRG-133): make such a field Option<T>.

Programmatic authority — #[ferra(authority)]

#[authorize(...)] covers what a rule can say about the caller and the row’s owner. When access depends on something else (the team in a claim, a header, a column of the row), write the decision as code. The model opts in with #[ferra(authority)] and the application supplies two traits, which name no Sea-ORM, axum or http type:

  • FerraAuthority::can(ctx, op, row): may the caller perform op on this row? Called for get, update, delete and restore on the loaded row, and for create on the row as inserted; update is also checked on the row as written. Never called on a list.
  • FerraListAuthority::filter(ctx): the rows the caller may list, as a Condition (below). A model that serves list must implement it (FRG-126): a list with no condition would show every row. Keep it equal to what can allows for get: never more, never less (Writing can and filter).

Both are synchronous and take the RequestContext (who the caller is: subject(), claims::<C>(), header(..)), and both return Result<_, AuthorityError>; an Err or a panic refuses the request (the status is in the table under Writes), and the reason reaches the log, never a response body.

The authority adds to the declared rules, it never replaces them: the posture and #[authorize] run first, unchanged, and an authority that answers true does not override their 401, 403 or 404.

The context is filled from the credential the request carries when the Foundry has .with_auth(), also on an auth = "none" model: a valid token gives the authority its claims, an invalid one is a 401 before can or filter run. Without .with_auth() the context is anonymous (no subject, no claims) whatever the caller sent.

Writing can and filter

  • Keep filter equal to can(Get). Never more: a list would show a row that get refuses. Never less: after a write, a row can(Get) allows but filter hides still gets a self link, and following it answers 404. Ferra does not check this; test that a list and a get agree for each kind of caller.

  • Keep both pure. The same context and row give the same answer, with no write, no clock and no call out of the process. filter is called more than once per request (on the row lock, again for the links of the response), so a filter that is not pure gives answers that differ inside one request; can runs inside the write’s transaction.

  • Put no secret in an AuthorityError. The error you give AuthorityError::Failed (a text with .into(), or your own error boxed) is logged verbatim, as the cause of the log line, and never reaches a response body; but a log is where secrets leak. Keep secrets and personal data out of it. The same holds for the message of a panic.

  • panic = "abort" defeats the guard. Ferra catches a panic in can and filter and refuses the request as it does for an Err; with panic = "abort" in the release profile the process ends instead. The default panic hook writes the message to stderr, outside Ferra’s log.

  • Match Action(_) explicitly. can also receives Operation::Action(name) for each declared action, and Operation is #[non_exhaustive]: an authority that ends in _ => true allows every action on the rows its filter shows. End it with _ => false and name what you allow.

    #![allow(unused)]
fn main() {

  • Write both. Every model serves list (a rule set names all five operations, FRG-101), so FerraListAuthority is required (FRG-126) and filter runs on lists, item reads and write locks; can narrows inside it.

Conditions with Model::FIELDS

A Condition is data, built only from the typed handles of Model::FIELDS (one per scalar column), so a column name or a value type cannot be wrong at run time. Ferra turns it into SQL with bound values; there is no LIKE, no subquery, no join.

Model::FIELDS is a {Model}Fields struct (ModelFields for a Model) the derive generates next to the model: that name is reserved in the model’s module, so do not declare a type of the same name there.

  • A handle compares: eq, ne, lt, lte, gt, gte (the value is anything Into the column’s type) and is_in (any iterator of values). On an Option column the comparisons take the inner type, and NULL is reached only through is_null and is_not_null. SQL comparisons never match NULL, which can only make a condition narrower.
  • Condition::all, any and not combine, everything and nothing are the constants. An empty all is everything; an empty any, and an is_in of no value, are nothing.
  • The column types are i32, i64, f64, bool, String, Uuid, Id, DateTime, Date and Time. A computed field and a JSON field have no handle, and neither has the deletion column of a soft-delete model (nor the timestamp and blame columns a behavior owns): a condition cannot reach deleted rows.
  • Bounds: 1 000 values in one is_in, 10 000 in the whole condition, 32 levels deep. A condition over a bound is refused (AuthorityError::TooManyValues, TooDeep), never truncated.
use ferra::FerraModel;
use sea_orm::entity::prelude::*;

Lists and links

filter is joined by AND to the owner scope and the soft-delete condition, before the page is cut, so the items, total, every offset page and both directions of a cursor walk see the same rows. A condition that matches nothing is a 200 with an empty page and total: 0, never a 403 or a 404. can is never called on a list. When filter returns an Err, panics or is over a bound, the list is a 500 internal with one error! (the model and the operation, no row value, no header), never an empty page: an empty answer would look like a list with no rows.

The links of a get or a list response are decided by the declared rules, can is never called to build one. A list item carries self and collection is present only when filter answers. That is exact as long as filter never matches more than can allows for get (the rule above) and never less: a row can(Get) allows but filter hides still gets a self link, and following it answers 404. Keep filter equal to what can allows for get.

Writes

create, update and restore run the authority inside the write’s transaction. An update reads the row twice, like a Postgres USING / WITH CHECK pair: can(Update) on the row as it is (a refusal is the absent row, 404), then on the row as written, after the UPDATE and before the commit, so a caller of team 1 cannot move a row to team 2 by writing team_id = 2. create judges the row as inserted. restore judges the row before only: filter cannot name the deletion column.

The self link of a create, update or restore response also needs can(Get) on the row as returned, called once in memory after the commit. A write-only authority (can(Create) is true, can(Get) is false) gets 201 with no body and no Location, and 204 with an empty body on update and restore, whatever Prefer and Accept say: the row is written and nothing of it is sent. An Err or a panic in that call answers the same, with one error!, never a 500: the write has happened, and a client that retries would write it twice. On a model that serves list, a row can(Get) allows but filter hides gets a self that answers 404; keep filter equal to what can allows for get.

Request context

An authority and a hook read the request through a RequestContext (ferra::request_context::RequestContext, full reference in ferra-core.md):

AccessorAnswers

claims::<C>()the claims of a bearer or cookie token, as the type given to .with_auth::<C>()
api_key()the identity of the API key that authenticated the request
header(&str)the first value of a request header, case-insensitive
  • claims::<C>() is None on a mismatch. An API key request, an anonymous one, and a C other than the .with_auth type all answer None: check it, and refuse when you needed the claims.
  • Credentials are not there. Authorization, Proxy-Authorization, Cookie and the Foundry’s API key header are dropped when the context is built, in any case: header("Authorization") is None, and Debug prints the subject and the header names, never a value.
  • Every other header is the client’s. header("X-Team") returns what the caller sent. Never authorize on X-Forwarded-*, Forwarded, Host or Origin: a client can set them, unless a proxy of yours overwrites them before the request reaches Ferra. Decide from the claims, which are signed.
  • Anonymous without .with_auth(). The context then has no subject and no claims, whatever the request carried.
  • Not Copy. .clone() it where 0.12 copied it (migration note).

Compile-time auth defense

Three compile-time gates stand between a model and an unprotected route.

  1. At the model declaration — FRG-100. A model with neither #[ferra(auth = ...)] nor an #[authorize(...)] block does not compile. The error proposes, in order: auth = "bearer" with .with_auth::<YourClaims>(jwt), auth = "none" for a deliberately public model, or an #[authorize(...)] block.

  2. At the mount call site — FRG-150. Foundry::mount::<M>() requires M: FerraAuthConfigured, which #[derive(FerraModel)] implements for every model that declares a posture. It catches a hand-written FerraModel impl without one.

  3. At the mount call site — FRG-151. A model whose rules need an identity — auth = "bearer", or any rule other than Anyone, a projection’s authorize and a field’s read / write rule included — cannot be mounted on a chain without .with_auth():

    error[E0277]: FRG-151: `Film` requires an identity, but this `Foundry` chain has no `.with_auth()`

    The bad call is Foundry::new(conn).mount::<Film>().build(); the good one names the claims type (both, compiled, under FRG-151):

The 401/403 split is load-bearing and worth stating plainly: 401 means the framework could not establish who you are; 403 means it knows exactly who you are and the answer is still no. A 403 is therefore positive evidence that your token was accepted.

A present-but-invalid token is refused 401 even on an operation whose rule is Anyone — presenting a broken credential is a failed authentication attempt, which is a different event from not presenting one at all. A tokenless request to an Anyone operation is served normally.

That rule only applies to models that wired the layer at all. On a model whose every rule is Anyone (or that declares auth = "none"), there is no layer, so nothing inspects the header and a broken token is simply ignored. The behaviour of an Anyone operation therefore depends on what its sibling operations declare: add update = IsOwner to an otherwise-public model and a stale token starts 401-ing on list, which previously ignored it. Worth knowing before you tighten one operation on a live model.

403 responses do not carry WWW-Authenticate — that header is an authentication challenge, and the authentication already succeeded.

All bodies are application/problem+json (RFC 9457):

{
  "type": "https://ferra.rs/errors/forbidden",
  "title": "Forbidden",
  "status": 403,
  "detail": "forbidden"
}

None of them ever echo token bytes, decoded claims, kid values, or the row’s owner value — not in detail, not in instance, not in an extension field. Each carries a fixed, framework-authored detail string.

That last property has a client-side cost worth planning for: the six distinct 401 causes (no token, bad signature, expired, unknown kid, undeserialisable claims, iss/aud mismatch) are deliberately indistinguishable on the wire, and the WWW-Authenticate value carries no RFC 6750 error parameter. A client cannot tell “expired, refresh and retry” from “misconfigured, retrying will never work” — so cap automatic refresh-and-replay at one attempt rather than looping.

A row you may not see returns 404, not 403. When an IsOwner rule refuses a row that belongs to someone else, the answer is the 404 a missing row gets, byte for byte, so the caller cannot learn that the row exists. A 403 remains the answer for a model rule that does not depend on ownership (IsAdmin, HasRole("…")), or when the caller owns the row but fails another part of the rule (IsOwner + HasRole("editor")); a caller that the rule of the projection under a prefix refuses gets the 404 first (see Projections and authorization). A soft-deleted row is a 404 on get, update and delete; restore reads it on purpose and applies the same 404 rule.

Where auth sits in the request pipeline

Outermost first, as a request traverses it:

CORS  →  auth  →  body-size limit  →  tracing  →  route  →  rate limit (mutations)
      →  handler: #[authorize] check  →  body parse  →  validation  →  database

Two consequences worth planning around:

  • Authentication precedes body parsing and validation. An unauthenticated caller gets 401 without the framework reading their body, so probing for schema shape through validation errors requires a valid token first.
  • The per-operation #[authorize] check runs inside the handler, before the body is parsed. An unauthorised caller never receives validation detail about a resource they may not touch.

CORS answers the preflight before authentication runs. A browser sends OPTIONS with no Authorization header — the Fetch spec forbids attaching one — so the CORS layer sits outside the auth layer and answers the preflight itself; the request never reaches authentication. Without that order every browser client of a bearer-protected model would break on the preflight, before the real request was ever sent. The same order lets a listed origin read the 401, 400 and 403 of the layers inside.

The preflight is answered with headers only, and it cannot reach a CRUD handler because the routes register GET/POST/PUT/PATCH/DELETE, so any other OPTIONS falls through to 405.

Note that Ferra’s default CORS posture is restrictive (CorsLayer::new() denies all cross-origin). Reaching a browser client takes an explicit CORS configuration through FerraLayer — see foundry.md.

Testing authenticated routes

A test goes through the same JWT layer as production: it sends a real token, signed with the secret of its own test configuration. ferra::testing::bearer signs one and returns the Authorization header value — no JWT crate to add to your project:

use ferra::{ClaimCheck, Foundry, HmacAlgorithm, JwtConfig};
use ferra::{FerraIdentity, FerraModel};
use sea_orm::entity::prelude::*;
use serde::{Deserialize, Serialize};

bearer(kid, secret, algorithm, &claims) takes your own claims type (anything Serialize) and returns Result<String, ferra::testing::TokenSigningError>. The token must satisfy the configuration like any other: exp in the future (the value above is 2100-01-01), and the iss / aud the JwtConfig expects, if any. The router you exercise is the real one, JWT layer included.

There is no way to hand the framework an identity without a token. The authorization checkpoint and CurrentUser only trust an identity the layer built from a verified token: neither a test helper nor a middleware of yours can slip one in. bearer is not a bypass — a token signed with another secret is refused — so it needs no Cargo feature and cannot weaken a release build.

Two consequences to know:

  • A custom handler is tested without a token. CurrentUser is a plain tuple struct: call your handler directly with CurrentUser(claims).

    let _ = user.sub;
    Ok(StatusCode::NO_CONTENT)
}

}

  • Ferra’s checkpoint has one source of identity in 0.9.0: its JWT layer, with a shared HMAC secret (HS256, HS384, HS512). You cannot plug another authenticator — an RS256 / JWKS verifier, a session cookie — into the generated routes or into CurrentUser; JWKS is out of scope for 0.9.0. Put such a scheme in front of your own handlers with your own extractor, or exchange its credential for an HMAC token your service signs.

To craft tokens bearer does not produce (a custom header, a broken signature), sign them yourself with the JWT crate Ferra uses, declared exactly like this in [dev-dependencies]:

jsonwebtoken = { version = "11.1", default-features = false, features = ["rust_crypto"] }
